# Contract Testing

When two services talk to each other, each team usually tests its own side with [test doubles](3-application-development/3.4.3-test-doubles.md). The front-end team stubs the API, and the API team never calls the front end at all. Both suites pass, both services deploy, and production breaks, because the API renamed a field that the front end still reads. Each team's doubles described the other service the way it used to be, not the way it is now.

You could catch this with [end-to-end tests](3-application-development/3.4.7-end-to-end-testing.md) that deploy both services together, but those are slow and brittle, and they need every service deployed at compatible versions. Contract testing catches the same class of bug while testing each service on its own.

## Contracts

A **contract** is a written-down description of how two systems interact: the requests the consumer sends and the responses it expects back. Each side is tested against the contract independently:

- The **consumer** (the client) is tested against a mock provider that behaves exactly as the contract says.
- The **provider** (the service) is tested by replaying the contract's requests against the real provider and checking that its responses match.

If both sides pass, they agree on how to talk to each other, without ever being deployed together.

## Consumer-Driven Contracts

In **consumer-driven** contract testing, the consumer's tests produce the contract. Ian Robinson described the idea in [Consumer-Driven Contracts: A Service Evolution Pattern](https://martinfowler.com/articles/consumerDrivenContracts.html) (2006): a provider only needs to honor what its consumers actually use. That tells the provider team which fields and endpoints are safe to change, and which would break someone.

[Pact](https://docs.pact.io/) is the most widely used tool for this. Its documentation describes it as "a code-first tool for testing HTTP and message integrations using contract tests." [How Pact works](https://docs.pact.io/getting_started/how_pact_works):

1. The consumer's unit tests call a Pact mock server and declare the interactions they expect: "given a product with ID 10 exists, `GET /product/10` returns 200 with this JSON body."
2. Pact records those interactions in a **pact file**, which is the contract.
3. The contract is shared with the provider, usually through a **Pact Broker**.
4. The provider's build replays every interaction against the real provider and checks its responses. **Provider states** ("a product with ID 10 exists") let the provider set up the data each interaction needs.
5. Before deploying either side, the broker's `can-i-deploy` check confirms that the version you are about to release is compatible with the versions already running.

Pact supports many languages, including JavaScript, Java, Go, Python, and .NET. It also supports asynchronous messages, such as events on a queue, as well as HTTP.

## Provider-Driven and Schema-Based Contracts

Consumer-driven contracts work best when you know your consumers and can run their tests. For a public API with unknown consumers, the provider publishes the contract instead, often as an OpenAPI specification, and checks its implementation against it. Tools such as [Specmatic](https://specmatic.io/) can turn an OpenAPI document into contract tests and stubs.

## What Contract Tests Are Not

A contract test checks that two systems agree on the *shape* and *meaning* of their interactions. It doesn't check that the provider's business logic is correct. That is the job of the provider's own unit, component, and integration tests. Keep each interaction in a contract to the fields the consumer actually uses, so that the provider stays free to change everything else.

## Contracts in the Company App

The Company app has two HTTP consumers, and you're about to add the third pair:

| Consumer | Provider | Consumer test | Provider verification |
| --- | --- | --- | --- |
| web (Pact JS) | projects-service | `web/src/features/projects/api.pact.test.ts` | `projects-service/tests/integration/test_pact_provider.py` (pact-python) |
| assignments-service (PactNet) | employees-service | You write it in this exercise | A PactNet verifier test in employees-service |
| assignments-service (PactNet) | projects-service | You write it in this exercise | The same pact-python test, reading one more folder |

All three Pact libraries share one Rust core, so a pact file written by PactNet is verified by pact-python without any translation. Two simplifications keep the setup small:

- **Pact files are committed in the consumer's folder**, such as `web/pacts/`, and each provider's test reads them from there. That works because the whole app lives in one repository. Across repositories, a Pact Broker does that job; the stretch goal tries one.
- **Provider states are an endpoint.** employees-service and projects-service each have `POST /_pact/provider-states`, turned on only by `ENABLE_PROVIDER_STATES=true`. The verifier calls it before each interaction to set up data, such as "projects exist", which resets the seed rows, or "no employee with id {id} exists".

### Example: follow the web to projects-service contract

1. Open the consumer test, [`web/src/features/projects/api.pact.test.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/projects/api.pact.test.ts). Each test declares one interaction (a provider state, a request, and the response the UI needs), then runs the real `listProjects` or `getProject` against Pact's mock server. Note the matchers: `uuid()`, `like()`, and `regex()` check types and formats, not exact values, so the provider's real timestamps still match.
2. Run it from `web/`:

    ```bash
    npm run test:pact
    ```

    It rewrites [`web/pacts/web-projects-service.json`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/pacts/web-projects-service.json). Open that file: it's the contract, with every interaction the web app depends on.

3. Open the provider side, [`projects-service/tests/integration/test_pact_provider.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/tests/integration/test_pact_provider.py). It starts the real FastAPI app on a free port, against PostgreSQL from Testcontainers, with provider states turned on, and replays every interaction in `../web/pacts`. The states themselves are in [`app/routers/provider_states.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/app/routers/provider_states.py).
4. Run the verification from `projects-service/`:

    ```bash
    uv run pytest -m contract --no-cov -v
    ```

### Practice: add the missing POST interaction

The web app's New project form calls `createProject`, which sends `POST /api/projects`. SPEC's gap for 3.4.6: no contract covers it, so projects-service could change what `POST` returns and only the end-to-end tests would notice, if anyone ran them. Work on a branch, `test/web-create-project-contract`.

1. Read `createProject` in `web/src/features/projects/api.ts`, and the `ProjectInput` type in `types.ts`. Those are what the form sends.
2. In `api.pact.test.ts`, add a third test, `POST /api/projects creates a project`:
    - given `projects exist`, upon receiving `a request to create a project`;
    - the request is a `POST` to `/api/projects` with `Accept` and `Content-Type: application/json` headers, and a body that's exactly a `ProjectInput`: name `Mobile App`, a description, a `startDate`, and status `planned`. Use a name that isn't in the seed data, or the provider will answer 409;
    - the response is a 201 with a JSON body. Reuse `projectShape(...)` for the generated fields (the provider makes up the ID), but give `name`, `description`, `startDate`, and `status` the exact values you sent, because the UI shows what it gets back:

      ```typescript
      body: {
        ...projectShape(NEW_PROJECT_ID, newProject.name, newProject.status, newProject.startDate),
        name: newProject.name,
        description: newProject.description,
        startDate: newProject.startDate,
        status: newProject.status,
      },
      ```

    - in `executeTest`, call the real `createProject(newProject)` and check the result matches `newProject`.
3. Run `npm run test:pact`. Then run `git diff pacts/`: the contract now has a third interaction.
4. Run the provider verification in `projects-service/` again. It passes: projects-service already honours the new interaction.
5. Now see what the contract protects. In your new test, change the expected status to `200`, run `npm run test:pact`, and run the provider verification. The consumer test still passes, because the mock server answers whatever you told it to. The provider verification fails:

    ```text
    1.1) has status code 200
           expected 200 but was 201
    ```

    That's the bug contract testing exists for: each side passing its own tests while disagreeing with the other. Put `201` back, and run both again.

6. Update the comment at the top of the test file to list `POST /api/projects`, commit the regenerated pact file with the test, and open a pull request.

> Compare with M3's [`api.pact.test.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/web/src/features/projects/api.pact.test.ts) and [`web-projects-service.json`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/web/pacts/web-projects-service.json).

### Apply: contracts for assignments-service's calls

assignments-service calls two services, through `EmployeesClient` and `ProjectsClient`. Both only ask "does this ID exist?", reading the status code and nothing else. Record that as consumer contracts, then make both providers verify them.

#### The consumer side, in assignments-service

1. Add PactNet to the test project:

    ```bash
    dotnet add tests/AssignmentsService.Tests package PactNet --version 5.0.1
    ```

2. Create `Contracts/PactSetup.cs` with a `For(string provider)` helper that returns `Pact.V4("assignments-service", provider, config).WithHttpInteractions()`. Set `PactConfig.PactDir` to `assignments-service/pacts`. Find it by walking up from `AppContext.BaseDirectory` to the folder that contains `AssignmentsService.slnx`, so it works wherever the repository is checked out.
3. Create `Contracts/EmployeesClientPactTests.cs` with two tests. The first:
    - given `employees exist`, upon receiving `a request for an employee that exists`;
    - `GET /api/employees/{Ada's ID}` returns 200 with the body `{ id = TestData.Ada.ToString() }`. Ask only for what the client reads: it ignores the body, so pin the ID and nothing else, and leave employees-service free to change every other field;
    - in `VerifyAsync`, build the **real** client against the mock server and check its answer:

      ```csharp
      await pact.VerifyAsync(async ctx =>
      {
          var client = new EmployeesClient(new HttpClient { BaseAddress = ctx.MockServerUri });
          Assert.True(await client.ExistsAsync(TestData.Ada, TestContext.Current.CancellationToken));
      });
      ```

4. The second test: given `no employee with id {id} exists`, passing the ID as a provider-state parameter, `GET /api/employees/99999999-9999-4999-8999-999999999999` returns 404, and `ExistsAsync` returns `false`.
5. Create `Contracts/ProjectsClientPactTests.cs` the same way, with the states `projects exist` and `no project with id {id} exists`, and the Platform Modernization ID.
6. Run them:

    ```bash
    dotnet test --filter-namespace "*Contracts"
    ```

    `pacts/assignments-service-employees-service.json` and `pacts/assignments-service-projects-service.json` appear. Commit both: the providers verify these files. PactNet merges new interactions into an existing file, so if you rename or remove an interaction, delete `pacts/*.json` and run the tests again.

#### The provider side, in projects-service

7. `test_pact_provider.py` only reads `../web/pacts`. Make it read `../assignments-service/pacts` too, but only the files whose `provider.name` is `projects-service`: that folder also holds the employees contract. A small function that globs both folders and filters on the JSON does it. Pass each file to the verifier with `add_source`, and keep skipping the test when no pact files are found.
8. Run `uv run pytest -m contract --no-cov -v`. Both consumers' contracts are verified in one run.

#### The provider side, in employees-service

9. employees-service has no provider verification yet. Add `PactNet` (version 5.0.1) to its test project, and create `Contracts/AssignmentsPactVerificationTests.cs`. The Pact verifier is native code making real HTTP calls, so the app has to listen on a real port. `WebApplicationFactory` can do that:
    - pick a free port by opening a `TcpListener` on port 0 and reading the port it was given;
    - create a `ComponentTestApp` (your fixed one from 3.4.4), then `WithWebHostBuilder` to set `ENABLE_PROVIDER_STATES=true` and `PORT`;
    - call `UseKestrel()` and `StartServer()` on it;
    - build a `PactVerifier("employees-service", ...)`, then call `.WithHttpEndpoint(baseUri)`, `.WithFileSource(...)` for `assignments-service/pacts/assignments-service-employees-service.json` (walk up from `AppContext.BaseDirectory` to find it), `.WithProviderStateUrl(new Uri(baseUri, "/_pact/provider-states"))`, and `.Verify()`.
10. Run it from `employees-service/`:

    ```bash
    dotnet test --filter-namespace "*Contracts"
    ```

11. Prove it protects you. Change the route on `EmployeesController` from `api/employees` to `api/staff`. That's a breaking change for assignments-service, even if employees-service updated its own tests to match. Run the verification again. It fails on `a request for an employee that exists`, with `expected 200 but was 404`. Notice that the other interaction still passes: a missing employee and a missing route both look like 404. Put the route back.
12. Open one pull request for the consumer tests and pact files, and one per provider. Merge the consumer's first, so the providers have something to verify.

> [!TIP]
> Compare with M3's [`Contracts/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/tests/AssignmentsService.Tests/Contracts) and [`pacts/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/pacts) in assignments-service, the projects [`test_pact_provider.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/projects-service/tests/integration/test_pact_provider.py), and the employees [`AssignmentsPactVerificationTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/employees-service/tests/EmployeesService.Tests/Contracts/AssignmentsPactVerificationTests.cs).

### Stretch: a Pact Broker, can-i-deploy, and a message pact

Committed pact files work while every service lives in one repository. A Pact Broker shares contracts between repositories and records which versions have been verified against which.

1. Start the broker that the starter's `compose.yaml` keeps behind a profile, then open <http://localhost:9292>:

    ```bash
    docker compose --profile broker up -d pact-broker
    ```

2. Publish assignments-service's contracts with the Pact CLI image. On Linux, add `--add-host=host.docker.internal:host-gateway`:

    ```bash
    docker run --rm -v "$PWD/assignments-service/pacts":/pacts pactfoundation/pact-cli:1.5.0.5 \
      pact-broker publish /pacts --consumer-app-version "$(git rev-parse --short HEAD)" \
      --branch main --broker-base-url http://host.docker.internal:9292
    ```

3. Ask whether that version is safe to deploy, with `pact-broker can-i-deploy --pacticipant assignments-service --version <that version> --to-environment production --broker-base-url http://host.docker.internal:9292`. The answer is no: no provider has published a verification result yet.
4. Make the providers verify from the broker and publish their results: pact-python's [`Verifier`](https://docs.pact.io/implementation_guides/python) has `broker_source()` and publishing options, and PactNet has `WithPactBrokerSource()` with `PublishResults()`. Then record deployments with `pact-broker record-deployment`, and run `can-i-deploy` again. Chapter 6 uses this check as a release gate.
5. **Message pacts.** HTTP isn't the only contract between the services. notifications-service consumes `assignment.created`, which assignments-service publishes. Pact's [message pacts](https://docs.pact.io/getting_started/how_pact_works#non-http-testing-message-pact) test that the event's shape is what the consumer reads, with no broker involved. Try one with pact-go in notifications-service as the consumer, and PactNet's message verification in assignments-service as the provider.

Stop the broker with `docker compose --profile broker stop pact-broker`.
