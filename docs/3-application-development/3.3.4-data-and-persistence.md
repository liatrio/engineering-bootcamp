# Data and Persistence

So far your assignments vanish when the service restarts. This page gives them a home in PostgreSQL. It covers how a table is designed, how relationships work inside a service and across service boundaries, how EF Core maps C# classes to tables and generates the SQL, and why the database, not your C# code, gets the final say on what's valid.

## Tables, Keys, and Constraints

A relational database stores data in **tables**. Each table holds one kind of thing, one **row** per thing and one **column** per fact about it. Three tools turn a pile of tables into a model you can trust:

- **Primary key (PK):** a column whose value identifies exactly one row, forever. Every Company app table uses a GUID `Id` generated by the service.
- **Foreign key (FK):** a column that holds another table's primary key. It's how rows point at each other, and the database refuses to store a pointer to a row that doesn't exist.
- **Constraints:** rules the database enforces no matter which application, script, or person writes the row. `NOT NULL` (required), length limits, `UNIQUE`, and `CHECK` (an expression every row must satisfy).

An **index** makes lookups by a column fast, the way a book's index saves you reading every page. A **unique index** does that and also refuses duplicates. Index the columns you filter on: employees-service indexes `Department` because `GET /api/employees?department=` filters on it.

### Why the database gets the final say

employees-service checks for a duplicate email in C# before saving, so it can return a clear 409. It *also* has a unique index on the lower-cased email. The C# check is for a good error message in the common case. The index is the guarantee, because:

- **Races.** Two requests can both run the C# check, both see no duplicate, and both insert. Only the database sees both writes.
- **Other writers.** A migration script, a support engineer with `psql`, or a future second service all bypass your C#. Constraints still apply to them.

## Relationships

### Inside one service: foreign keys

A teacher teaches many courses: that's **one-to-many**, and it's a foreign key on the "many" side (`Course.TeacherId`). Students take many courses and courses have many students: that's **many-to-many**, which a single foreign key can't express. It needs a **join table**, `Enrollment`, with a foreign key to each side, and it can hold facts about the pairing itself, such as a grade. A composite unique index on `(StudentId, CourseId)` stops a student enrolling twice.

### Across services: IDs only

Look at an assignment through that lens: it's a join table between employees and projects, with facts about the pairing (`role`, `allocationPercent`, dates). In one database you'd give it two foreign keys. But employees and projects live in **other services' databases**, as you decided in [3.2.3](3-application-development/3.2.3-microservices-and-service-boundaries.md#owning-data-vs-referencing-it). There's nothing for a foreign key to point at.

So `Assignment` stores `EmployeeId` and `ProjectId` as plain GUIDs, and the service replaces what a foreign key would have done:

| A foreign key would... | assignments-service instead... | Where |
| --- | --- | --- |
| Refuse a row that points at a missing employee | Asks employees-service and projects-service before saving, and returns 400 for an unknown ID | [3.3.5](3-application-development/3.3.5-calling-other-services.md) |
| Block or cascade the delete of an employee who's still referenced | Hears `employee.deleted` and deletes that employee's assignments | [3.3.6](3-application-development/3.3.6-publishing-and-consuming-events.md) |
| Let you `JOIN` to show names | Returns IDs; the web app looks up names from the other APIs | Already in the web app |

What you lose is the instant, all-or-nothing guarantee. For a moment after an employee is deleted, their assignments still exist, and nothing stops a project being deleted while assignments reference it (your design's open question). That's eventual consistency, the price of separate databases.

The composite unique index still works, because both columns live in your own table: `(EmployeeId, ProjectId)` unique means an employee is on a project at most once.

## EF Core

EF Core is an **ORM** (object-relational mapper). You write plain C# classes, and it generates the tables, the SQL, and the mapping between rows and objects. Four pieces:

| Piece | What it is | employees-service |
| --- | --- | --- |
| **Entity** | A plain class, one property per column | [`Employee.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/Employee.cs) |
| **Configuration** | Keys, lengths, indexes, and constraints for one entity, in an `IEntityTypeConfiguration<T>` class | [`EmployeeConfiguration.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeConfiguration.cs) |
| **DbContext** | The object that knows every table, holds the connection, and tracks changes; one per request | [`EmployeesDbContext.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Data/EmployeesDbContext.cs) |
| **Migrations** | Generated C# files that change the schema from one version to the next | [`Migrations/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Migrations) |

### Configuration

The configuration class keeps database decisions out of the entity, next to it in the feature folder. The DbContext picks up every configuration class with one line, `modelBuilder.ApplyConfigurationsFromAssembly(...)`.

```csharp
builder.HasKey(e => e.Id);
builder.Property(e => e.Id).ValueGeneratedNever();   // the service generates GUIDs
builder.Property(e => e.Name).IsRequired().HasMaxLength(100);
builder.HasIndex(e => e.Department);                 // for ?department=
```

`IsRequired()` becomes `NOT NULL`, `HasMaxLength(100)` becomes `character varying(100)`, and `HasIndex(...).IsUnique()` becomes a unique index. Constraints EF Core has no method for go in as SQL, such as `HasCheckConstraint(...)`.

### Migrations

A migration is the difference between your model and the model as it was at the last migration. `dotnet ef migrations add <Name>` compares the two and writes three files:

- `<timestamp>_<Name>.cs`: `Up()` applies the change and `Down()` reverts it. Read it before you commit it. It's the SQL your production database will run.
- `<timestamp>_<Name>.Designer.cs`: metadata EF Core needs. Never edit it.
- `<Context>ModelSnapshot.cs`: the whole model as of this migration, used to compute the next one. This is the file two branches fight over, which is why your team has one migration owner.

The database records which migrations it has run in a table called `__EFMigrationsHistory`. The Company app's services apply pending migrations on startup in a hosted service, `DatabaseInitializer`, which keeps the app to one command. In production you'd run them as a separate, deliberate step, so several replicas starting at once don't race each other. Chapter 8 comes back to this.

### Queries

A LINQ query on a `DbSet` is translated to SQL and run in the database; only the rows you ask for come back. From `EmployeeStore`:

```csharp
var query = db.Employees.AsNoTracking();
if (!string.IsNullOrWhiteSpace(department))
{
    query = query.Where(e => e.Department == department);
}
return await query.OrderBy(e => e.Name).ThenBy(e => e.Id).ToListAsync(ct);
```

Nothing hits the database until `ToListAsync`. Building the query in steps like this adds a `WHERE` only when a filter is given. A few habits from the starter:

- **`AsNoTracking()` for reads you won't change.** Tracking costs memory and time, and a list endpoint never saves what it reads.
- **Tracked entities for updates.** `FindAsync` returns a tracked entity; the service changes its properties; `SaveChangesAsync()` writes exactly the columns that changed, in one transaction.
- **`ExecuteDeleteAsync()` for deletes.** It sends one `DELETE ... WHERE` without loading the row first, and returns how many rows it deleted, which is how the store knows whether to report a 404.
- **A stable order.** `ThenBy(e => e.Id)` breaks ties, so the same request always returns the same order.

### Turning a constraint violation into a 409

When the unique index rejects a write, `SaveChangesAsync()` throws a `DbUpdateException` wrapping Npgsql's `PostgresException` with the SQL state for a unique violation. `EmployeeStore.SaveAsync` catches exactly that case and throws the same `ConflictException` the service's own check would, so the client sees one 409 either way:

```csharp
catch (DbUpdateException ex) when (ex.InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation })
{
    throw new ConflictException("An employee with that email already exists.");
}
```

## Repository, Active Record, or Neither

You'll hear two classic patterns for where data access code lives:

| | Repository | Active Record |
| --- | --- | --- |
| Data access lives in | A separate class behind an interface (`IUserRepository`) | The entity itself (`user.Save()`, `User.Find(id)`) |
| Domain objects | Know nothing about storage | Know how to save themselves |
| Testing the rules | Pass a fake repository | Harder: the objects are tied to the database |
| Fits | Rules worth testing alone; more than one data source | Simple CRUD; frameworks built around it (Rails, Django models) |

EF Core already sits between the two: a `DbSet<T>` behaves like a repository, and the `DbContext` like a unit of work. That's why app-dev-forge has services use the `DbContext` directly, and why wrapping it in a generic `IRepository<T>` with `GetAll`, `Add`, and `Update` usually adds a layer that does nothing.

The starter takes a middle path: one thin, feature-specific store interface (`IEmployeeStore`) with methods named after what the service needs, such as `EmailInUseAsync`. It exists for the reason [3.3.3](3-application-development/3.3.3-dependency-injection-and-solid.md#why-a-store-interface) gave: component tests swap in a fake that still behaves like the database. Your `IAssignmentStore` follows the same rule. If a method wouldn't make sense to a reader who has never heard of EF Core, it's in the wrong place.

### Practice: watch the database enforce its rules

With the app running:

1. Look at the table EF Core created:

    ```bash
    docker compose exec postgres psql -U postgres -d employees -c '\d "Employees"'
    ```

    Find the generated `NormalizedEmail` column and the three indexes: the primary key, `IX_Employees_Department`, and the unique `IX_Employees_NormalizedEmail`.

    ```bash

       VALUES (gen_random_uuid(),'Ada Again','ADA@example.com','Engineer','Engineering',now(),now());"
    ```

    PostgreSQL refuses: `duplicate key value violates unique constraint "IX_Employees_NormalizedEmail"`. No C# ran, and the rule held anyway.

### Apply: store assignments in PostgreSQL

Your migration owner does steps 3 to 6; others take the store and the readiness check, then everyone reviews.

1. **Packages.** From `assignments-service/src/AssignmentsService/`, add the same versions employees-service uses:

    ```bash
    dotnet add package Microsoft.EntityFrameworkCore --version 10.0.15
    dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.0.15
    dotnet add package Npgsql.EntityFrameworkCore.PostgreSQL --version 10.0.3
    dotnet add package Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore --version 10.0.15
    ```

2. **The EF Core tool.** Install it once per machine:

    ```bash
    dotnet tool install --global dotnet-ef --version 10.0.15
    ```

    If `dotnet ef` isn't found afterwards, add `~/.dotnet/tools` to your `PATH`.

3. **Configuration.** Create `Features/Assignments/AssignmentConfiguration.cs`, modelled on `EmployeeConfiguration`:
    - the key, with `ValueGeneratedNever()`;
    - `Role` required, maximum 100;
    - a **unique** index on `new { a.EmployeeId, a.ProjectId }`, with a comment saying it's the real guarantee against duplicates;
    - an index on `ProjectId`, for `?projectId=`. You don't need one on `EmployeeId`: it's the first column of the unique index, which PostgreSQL can already use for `?employeeId=`;
    - a check constraint that keeps `AllocationPercent` between 1 and 100:

    ```csharp
    builder.ToTable(t => t.HasCheckConstraint(
        "CK_Assignments_AllocationPercent", "\"AllocationPercent\" BETWEEN 1 AND 100"));
    ```

4. **The DbContext and initializer.** Create `Infrastructure/Data/AssignmentsDbContext.cs` with one `DbSet<Assignment> Assignments` and `ApplyConfigurationsFromAssembly`, like `EmployeesDbContext`. Copy `DatabaseInitializer.cs` from employees-service and remove the seeding: assignments start empty, so it only calls `MigrateAsync`.
5. **Program.cs.** Register the DbContext with the connection string from `ConnectionStrings__Default`, and the initializer, exactly as employees-service does under its "Data access" comment. Extend the `AddHealthChecks()` line from 3.3.1 so readiness checks the database:

    ```csharp
    builder.Services.AddHealthChecks()
        .AddDbContextCheck<AssignmentsDbContext>("postgres", tags: [HealthEndpoints.ReadyTag]);
    ```

6. **The first migration.** From `src/AssignmentsService/`:

    ```bash
    ConnectionStrings__Default="Host=localhost" dotnet ef migrations add InitialCreate
    ```

    `dotnet ef` builds the app and asks it for the DbContext, which needs a connection string to construct. It only has to parse; nothing connects. (In PowerShell, set it first with `$env:ConnectionStrings__Default="Host=localhost"`.) Open the new `Migrations/..._InitialCreate.cs` and check it against your configuration: one table, the check constraint, a unique index named `IX_Assignments_EmployeeId_ProjectId`, and `IX_Assignments_ProjectId`. Commit all three files.

7. **The store.** Create `Features/Assignments/AssignmentStore.cs`, the EF Core `IAssignmentStore`, modelled on `EmployeeStore`: `AsNoTracking` and both optional filters in `ListAsync`, ordered by `StartDate` then `Id`; a tracked `FindAsync`; `PairExistsAsync` with `AnyAsync`; `ExecuteDeleteAsync` in `DeleteAsync`; and a private `SaveAsync` that turns a unique violation into the same `ConflictException` the service throws.
8. **Swap the implementation.** In `Program.cs`, replace the in-memory registration with one line, and delete `InMemoryAssignmentStore.cs` (3.4 brings a version of it back as a test fake):

    ```csharp
    builder.Services.AddScoped<IAssignmentStore, AssignmentStore>();
    ```

    The store is scoped now, because it holds a scoped `DbContext`. `AssignmentService` didn't change at all. That's the DI payoff from 3.3.3.

9. **Run it.** Rebuild with `docker compose up --build -d assignments-service`, then check the logs for the migration and the table it made:

    ```bash
    docker compose logs assignments-service | grep -i migrat
    docker compose exec postgres psql -U postgres -d assignments -c '\d "Assignments"'
    curl -s localhost:5103/readyz
    ```

    `\d` lists the unique index and the check constraint. `/readyz` now reports `"postgres":"healthy"`.

10. **Prove it persists.** Create an assignment in the UI, run `docker compose restart assignments-service`, and reload: it's still there. Then try the duplicate pair again: still a 409, now from `PairExistsAsync`. Finally, bypass the service like in the Practice and insert a duplicate pair with SQL. Which constraint refuses it?
11. **Readiness.** Run `docker compose stop postgres`, then `curl -si localhost:5103/readyz` returns 503 while `/healthz` stays 200. Start PostgreSQL again.
