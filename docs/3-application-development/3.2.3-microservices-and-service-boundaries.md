# Microservices and Service Boundaries

Splitting an application into services is easy. Splitting it in the *right places* is the hard part, and the places you choose decide how painful every later change will be. This page covers how to draw service boundaries, why each service owns its own data, how services stay consistent without sharing a database, and what microservices cost you.

## Bounded Contexts

A word can mean different things in different parts of a business. To the HR system, an *employee* has a title, a department, and an email. To assignments, an employee is just someone who can work on a project, identified by an ID. To notifications, an employee is a name in a sentence. Each of those is a **bounded context**: a part of the domain with its own model and its own language. The term comes from domain-driven design; Martin Fowler's [BoundedContext](https://martinfowler.com/bliki/BoundedContext.html) is a short introduction.

Good service boundaries usually follow bounded contexts. Inside one boundary, things change together. Across boundaries, they change independently and talk through a small, deliberate interface. The Company app has four:

| Context | Service | Its idea of an "employee" |
| --- | --- | --- |
| People | employees-service | The full record: name, email, title, department |
| Work | projects-service | None. Projects don't know who works on them. |
| Staffing | assignments-service | An `employeeId` that must exist, plus a role and an allocation |
| Activity feed | notifications-service | A name inside a message such as "Employee Ada Lovelace was created" |

A useful test for a boundary: **could a team change everything inside it, and deploy it, without coordinating with anyone else?** If two services always have to change and deploy together, they're one service in two repositories.

## Database per Service

Each Company app service owns its data, and no other service touches it. [`infra/postgres/init.sql`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/infra/postgres/init.sql) creates one database per service on a single PostgreSQL server:

```sql
-- Each service owns its database: no service reads another service's tables.
CREATE DATABASE employees;
CREATE DATABASE projects;
CREATE DATABASE assignments;
```

One server is a convenience for running on a laptop. The rule is about ownership, not hardware: in production each database could live on a different server, or a different engine, and nothing else would need to change.

### Why employees can't just JOIN projects

In a monolith with one database, "show each assignment with the employee's name and the project's name" is a single SQL query with two `JOIN`s. Here, that query is impossible, and PostgreSQL says so:

```text
employees=# SELECT name FROM projects.public.projects;
ERROR:  cross-database references are not implemented
```

That's deliberate. The pattern, called [Database per Service](https://microservices.io/patterns/data/database-per-service.html), buys real things:

- **Each service can change its schema freely.** employees-service stores a generated, lower-cased copy of the email to enforce case-insensitive uniqueness. Nobody else knows or cares. If another service queried that table, renaming the column would break it.
- **Each service can deploy alone.** A migration in one database can't break another service's queries.
- **Each service enforces its own rules.** Every write goes through the service's API, so nobody can insert an employee with a duplicate email by going around `EmployeeService`.
- **Each service can choose its storage.** notifications-service keeps its feed in memory, because losing it on restart is acceptable.

Microsoft's guide to [data sovereignty per microservice](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/architect-microservice-container-applications/data-sovereignty-per-microservice) covers the same ground for .NET teams.

The price is that you lose `JOIN`s, foreign keys, and transactions across services. The rest of this page is about living with that.

## Owning Data vs Referencing It

When one service needs another service's data, it has three choices.

| Approach | How it works | Good for | Cost |
| --- | --- | --- | --- |
| **Reference by ID** | Store only the other entity's ID. Look up details when needed. | Most relationships | A network call whenever you need the details |
| **Keep a copy, updated by events** | Store the fields you need, and update them when the owner publishes a change | Read-heavy screens; staying up when the owner is down | The copy is briefly stale, and you must handle every event |
| **Ask at the moment of the write** | Call the owner to check something before saving | Rules that must hold when you save | Your writes fail when the owner is down |

The Company app uses all three:

- **assignments-service references by ID.** An assignment stores `employeeId` and `projectId`, never names or emails.
- **assignments-service asks at write time.** Before saving, it calls `GET /api/employees/{id}` and `GET /api/projects/{id}`. A 404 becomes a 400 for its caller, and an unreachable service becomes a 503. It never saves an assignment it couldn't check.
- **notifications-service keeps a copy.** Each notification stores the text it needs, built from the event, so the feed never calls employees-service.
- **The web app does the join.** Look at [`AssignmentsPage.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/assignments/AssignmentsPage.tsx): it loads assignments, employees, and projects separately, then maps IDs to names in the browser.

> [!NOTE]
> Checking at write time doesn't make the data correct forever. An employee who exists when the assignment is saved can be deleted a minute later. The next section is about what happens then.

## Keeping Data Consistent Across Services

In a single database, a foreign key would stop you deleting an employee who still has assignments, or cascade the delete. Across two databases there is no foreign key. Instead, the services agree through an event:

1. A user deletes Grace Hopper. employees-service deletes the row and commits.
2. After the commit, employees-service publishes `employee.deleted` with `{ "id": "2222…" }` to the `company.events` exchange. It doesn't know or care who is listening.
3. RabbitMQ routes a copy to every queue bound to that event, including `assignments.employee-deleted`.
4. assignments-service consumes the event, deletes every assignment for that employee, and acknowledges the message.

Between steps 1 and 4, for a few milliseconds or for as long as assignments-service is down, the assignments database refers to an employee who no longer exists. This is **eventual consistency**: the system isn't consistent at every instant, but it becomes consistent once every event has been handled.

To make that safe, the consumer has to be built for it:

- **The queue is durable.** If assignments-service is down, events wait in RabbitMQ until it comes back. You saw this with notifications in the [3.2 exercise](3-application-development/3.2-application-architecture.md#exercise-run-the-company-app).
- **Handling is idempotent.** RabbitMQ delivers *at least once*, so the same event may arrive twice. Deleting the assignments of an employee who has none left is fine.
- **The rest of the system tolerates the gap.** The web app shows a missing employee's ID instead of a name, rather than crashing.

There is one more gap, between steps 1 and 2: if employees-service crashes after committing but before publishing, the event is lost. This is the *dual-write problem*, and 3.3 covers it and the outbox pattern that fixes it. Martin Fowler's [What do you mean by "Event-Driven"?](https://martinfowler.com/articles/201701-event-driven.html) is a good map of the different ways systems use events.

## What Microservices Cost

Every benefit above has a price. Fowler's [Microservice Trade-Offs](https://martinfowler.com/articles/microservice-trade-offs.html) sums it up: you gain strong module boundaries, independent deployment, and technology diversity, and you pay in distribution, eventual consistency, and operational complexity.

| Cost | What it looks like in the Company app |
| --- | --- |
| **Network failures** | A function call can't time out. An HTTP call to projects-service can, so assignments needs timeouts, retries, and a 503 path. The [fallacies of distributed computing](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing) list the assumptions that stop being true. |
| **Distributed debugging** | One click touches the proxy, a service, a database, the broker, and a consumer. Without trace context passed between them, you're matching timestamps across five log streams. That's why 3.5 exists. |
| **Operational overhead** | Five deployables, five pipelines, five sets of dashboards, a broker, and four languages' worth of dependency updates, instead of one of each. |
| **Consistency** | No cross-service transactions. Every rule that spans two services needs an event, a check at write time, or an accepted gap. |
| **Testing** | Each service's tests can pass while the services disagree about a request's shape. That's what contract tests in 3.4.6 catch. |

## When a Modular Monolith Is Better

A **modular monolith** is one deployable application with strong internal boundaries: vertical slices that never reach into each other's internals, and, ideally, each module owning its own tables. You get most of the design benefits of services with none of the network.

Fowler's [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) observes that almost every successful microservice system he has seen started as a monolith that grew too big and was split, while systems built as microservices from scratch often ran into serious trouble. His [MicroservicePremium](https://martinfowler.com/bliki/MicroservicePremium.html) argues that the extra cost only pays off once a system is too complex to manage as a monolith. Sam Newman, author of [*Building Microservices*](https://samnewman.io/books/building_microservices_2nd_edition/) and [*Monolith to Microservices*](https://samnewman.io/books/monolith-to-microservices/), gives similar advice: treat microservices as an option to reach for when you have a specific problem they solve, not as a default.

Reach for separate services when you have a reason, such as:

- several teams that need to deploy independently;
- parts with very different scaling or reliability needs;
- a boundary that has stayed stable long enough that you trust it.

For one small team with a young product, a modular monolith is usually the better start. Draw the boundaries inside it carefully, and splitting later becomes a deployment change rather than a rewrite.

> [!NOTE]
> The Company app is a microservice system because you are learning to run one. Its domain is small enough to be a monolith. Keep that honesty in mind when a client asks whether *they* need microservices.

### Practice: what would break if assignments read the employees database?

A teammate proposes a shortcut: instead of calling employees-service over HTTP, assignments-service could connect to the `employees` database and run `SELECT 1 FROM "Employees" WHERE "Id" = @id`. It's faster and needs no HTTP client. Work through what that would cost. Write a sentence or two for each:

1. Open `employees-service/src/EmployeesService/Features/Employees/EmployeeConfiguration.cs`. The employees team decides to rename the `Email` column, or split `Name` into first and last name. Who has to know, and how would they find out?
2. The employees team moves their database to its own server for performance. What breaks, and whose pipeline catches it?
3. Which credentials would assignments-service need, and what else could it do with them?
4. employees-service later adds soft deletes: deleted employees stay in the table with a `DeletedAt` timestamp. What does the shortcut query now get wrong?
5. How would you test assignments-service on its own? Compare with faking an `IEmployeesClient`.
6. Which of these problems would the HTTP call to `GET /api/employees/{id}` avoid, and which new problem does it bring instead?

Then answer the question from the [3.2.2 Practice](3-application-development/3.2.2-vertical-slices.md#practice-sketch-a-departments-slice-in-employees-service): why can a Departments feature *inside* employees-service use a real foreign key, when assignments can't?

### Apply: decide what assignments owns and what it references

Add the data part of your design. Work on a new branch, `docs/assignments-data`.

1. In `docs/assignments-design.md`, add a **Context** section: a short paragraph and a small text diagram showing which services assignments-service calls, which events it publishes and consumes, and which database it owns.
2. Add a bulleted summary under it: **Owns**, **Calls**, **Publishes**, and **Consumes**.
3. Add a **Data** section with a table of every field (*Field*, *Type*, *Rules*). Use the Assignments shape in `SPEC.md`. For `employeeId` and `projectId`, write down where the referenced data lives and how assignments checks it.
4. Under the table, describe the indexes: which unique index stops a duplicate assignment even if two requests race, and which index serves the `?projectId=` filter.
5. Add an **Open questions** section with at least one question your team hasn't settled. For example: projects-service publishes no events, so what should happen to assignments when a project is deleted?
6. Open a pull request, and ask your reviewer to check one thing: does any field copy data that another service owns? If so, is there a reason written down?
