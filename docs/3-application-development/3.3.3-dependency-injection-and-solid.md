# Dependency Injection and SOLID

Almost every class in a service depends on something else. A controller needs a service. A service needs storage, a clock, a way to publish events, and a client for another API. **Dependency injection (DI)** is one rule about where those come from:

> A class *declares* what it needs in its constructor. It never `new`s the thing itself. Something outside the class, the **container**, builds the dependency and hands it in.

This page covers what that rule buys you, how the .NET container works, the one decision every registration forces (how long an instance lives), and the SOLID principles that explain where the interfaces go.

## The Problem DI Solves

Here's a version of `EmployeeService` that builds its own dependencies:

```csharp
public sealed class EmployeeService
{
    private readonly EmployeesDbContext _db = new(/* connection string from where? */);
    private readonly RabbitMqEventPublisher _events = new(/* ... */);
    // CreateAsync uses _db, _events, and DateTime.UtcNow directly
}
```

Every problem with it comes from those `new`s:

- **You can't test the rules alone.** Testing "a duplicate email is a 409" needs a real PostgreSQL and a real RabbitMQ.
- **You can't change a dependency without editing the class.** Swapping RabbitMQ for another broker means editing the service that holds the employee rules.
- **Configuration leaks in.** Somebody has to know the connection string, so the rules class ends up reading configuration.
- **Nobody owns cleanup.** Who disposes the database connection, and when?

The starter's real [`EmployeeService`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeService.cs) declares its needs instead, using a C# primary constructor:

```csharp
public sealed class EmployeeService(IEmployeeStore store, IEventPublisher events) : IEmployeeService
```

It doesn't know whether `store` is EF Core or an in-memory fake, or whether `events` goes to RabbitMQ or into a list a test can inspect. Its unit tests in [`EmployeeServiceTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/Features/Employees/EmployeeServiceTests.cs) pass `InMemoryEmployeeStore` and `FakeEventPublisher`, and run in milliseconds with no infrastructure at all. Tests are the one place that *should* call `new` on concrete classes, because choosing them is the point of the test.

| Without DI | With DI |
| --- | --- |
| A class is tied to the concrete classes it constructs | A class is tied only to the interfaces it declares |
| Testing the rules drags in a database and a broker | Testing the rules means passing in fakes |
| Settings are read all over the code | Settings are read once, at registration |
| Nobody disposes anything, or everyone does | The container disposes what it created, when its lifetime ends |

## The Container in .NET

ASP.NET Core has a DI container built in, and you've used it since 3.3.1: `AddControllers()` registers controllers, and the framework resolves one from the container for every request. Making your own classes injectable takes three steps.

1. **Declare** dependencies as constructor parameters, preferably interfaces you own.
2. **Register** each implementation in `Program.cs`, choosing a lifetime:

    ```csharp
    builder.Services.AddScoped<IEmployeeStore, EmployeeStore>();
    builder.Services.AddScoped<IEmployeeService, EmployeeService>();
    builder.Services.AddSingleton<IEventPublisher, RabbitMqEventPublisher>();
    ```

3. **Ask** for the interface where you need it. `EmployeesController(IEmployeeService employees)` never sees `EmployeeService`, the `DbContext`, or RabbitMQ.

When a request arrives, the container sees that the controller needs an `IEmployeeService`, finds the registration, sees that `EmployeeService` needs an `IEmployeeStore` and an `IEventPublisher`, and builds the whole graph. **Wiring lives in one file.** Swapping an implementation is a one-line change in `Program.cs`, and no service or controller changes. You'll do exactly that in 3.3.4.

## Lifetimes

Every registration also answers: when the container is asked for this type, does it return the same object or a new one?

| Lifetime | Instances | Register with | Typical uses in the Company app |
| --- | --- | --- | --- |
| **Singleton** | One for the life of the app | `AddSingleton` | `RabbitMqConnection` (connections are expensive), `IEventPublisher`, `TimeProvider.System`, options |
| **Scoped** | One per HTTP request | `AddScoped` | The `DbContext`, and anything that uses it: stores and services |
| **Transient** | A new one every time it's asked for | `AddTransient` | Cheap, stateless helpers, such as the HTTP message handler you'll add in 3.3.5 |

Why they land where they do:

- **The `DbContext` is scoped** because it's a unit of work. It tracks every row loaded during a request so one `SaveChangesAsync()` writes them together. Two requests must not share one.
- **`EmployeeService` is scoped** because it holds a store, which holds a `DbContext`. A class can never live longer than the things it depends on.
- **`RabbitMqConnection` is a singleton** because RabbitMQ expects one connection per process. Sharing it means it must be safe to use from many requests at once, which is why it guards its channel with a lock.

> [!WARNING]
> **The captive dependency.** A singleton that takes a scoped dependency holds on to it forever: the first request's `DbContext` would serve every request after it. In Development, .NET refuses to start and says `Cannot consume scoped service ... from singleton ...`. The rule: **a class may only depend on things that live at least as long as it does.** Singletons depend on singletons; scoped classes on scoped or singleton; transients on anything.

Background work has no HTTP request, so it has no scope either. employees-service's [`DatabaseInitializer`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Data/DatabaseInitializer.cs) is a hosted service (a singleton) that needs the scoped `DbContext`, so it injects `IServiceScopeFactory` and creates a scope of its own. You'll use the same move for the event consumer in 3.3.6.

## Time Is a Dependency Too

`DateTime.UtcNow` looks harmless, but it's a hidden dependency on the system clock. A test can't say "it's 9:30 on 13 November" and then assert the exact `createdAt` a service produced. .NET's answer is `TimeProvider`: inject it, call `time.GetUtcNow()`, register `TimeProvider.System` in production, and let tests pass a `FakeTimeProvider` they can set and advance ([3.4.3](3-application-development/3.4.3-test-doubles.md) does that).

`GetUtcNow()` returns a `DateTimeOffset`. The Company app stores `DateTime` values in UTC, so the services use `time.GetUtcNow().UtcDateTime`.

## SOLID, in the Company App

SOLID is five principles for keeping object-oriented code easy to change. DI is how you apply most of them in practice. Here they are with examples from code you've already read.

| Principle | Means | In the Company app |
| --- | --- | --- |
| **S**ingle Responsibility | A class has one reason to change | `EmployeesController` changes when HTTP changes, `EmployeeService` when a rule changes, `EmployeeStore` when the database changes. A new rule never touches the controller. |
| **O**pen/Closed | Add behavior by adding code, not by editing what works | Readiness grows by registering another health check, such as `AddCheck<RabbitMqHealthCheck>("rabbitmq", ...)`. `HealthEndpoints` never changes. |
| **L**iskov Substitution | Any implementation of an interface can stand in for any other | `IEmployeeStore.AddAsync` promises a `ConflictException` for a taken email. `InMemoryEmployeeStore` keeps that promise, or tests that pass would prove nothing about production. |
| **I**nterface Segregation | Clients depend only on what they use | `IEventPublisher` has one method. The service can't reach RabbitMQ channels, queues, or connections, because it has no reason to. |
| **D**ependency Inversion | Rules depend on abstractions; details implement them | `EmployeeService` depends on `IEventPublisher`, which it owns. `RabbitMqEventPublisher` is the detail that implements it. |

Two notes keep SOLID from turning into ceremony:

- **Put interfaces where there's a seam**: I/O, time, another service, anything a test needs to replace. Entities, DTOs, and options classes don't need interfaces.
- **Pragmatism beats purity.** `GlobalExceptionHandler` is a `switch` you edit when you add an exception type, which bends Open/Closed. That's fine: one short, obvious place to change beats a plugin system nobody needs.

### Why a store interface?

app-dev-forge usually has services use the `DbContext` directly, and that's a good default. The starter adds one thin seam, `IEmployeeStore`, for one reason: the component tests in 3.4.4 run the whole HTTP stack against an in-memory fake, and a fake behind an interface you own is more honest than EF Core's in-memory provider, which ignores things a real database enforces, like a unique index. Read the comment at the top of [`IEmployeeStore.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/IEmployeeStore.cs): methods named after what the service needs, no generic `IRepository<T>`. [3.3.4](3-application-development/3.3.4-data-and-persistence.md#repository-active-record-or-neither) says more about that choice.

### Practice: inject a TimeProvider into employees-service

Close the gap SPEC lists for 3.3.3: `EmployeeService` calls `DateTime.UtcNow` directly. Work on your own branch, `refactor/employees-time-provider`, in `employees-service/`.

1. Run the unit and component tests so you know they pass first:

    ```bash
    cd employees-service
    dotnet test --filter-not-trait "Category=Integration"
    ```

2. In `src/EmployeesService/Features/Employees/EmployeeService.cs`, add a `TimeProvider time` parameter to the primary constructor, after `IEventPublisher events`.
3. Replace both uses of `DateTime.UtcNow` in that class, in `CreateAsync` and `UpdateAsync`, with `time.GetUtcNow().UtcDateTime`. Add a `<remarks>` line to the class comment saying why the clock is injected.
4. Build:

    ```bash
    dotnet build
    ```

    It fails in the test project with `error CS7036: There is no argument given that corresponds to the required parameter 'time'`. `EmployeeServiceTests` builds the service by hand, and the compiler just found every place that depended on the old constructor.

5. In `EmployeeServiceTests.cs`, pass `TimeProvider.System` as the third argument. That keeps today's behavior; 3.4.3 swaps in a fake clock.
6. Run the test command from step 1. It compiles now, but the component tests fail with `Unable to resolve service for type 'System.TimeProvider' while attempting to activate 'EmployeesService.Features.Employees.EmployeeService'`. They build the real `Program`, and nobody told the container how to make a `TimeProvider`. Register it in `Program.cs`, just above the feature registrations:

    ```csharp
    // Time: one clock for the app, injected wherever "now" matters. Tests swap in a fake.
    builder.Services.AddSingleton(TimeProvider.System);
    ```

    Run the tests again: all of them pass.

7. Rebuild the container with `docker compose up --build -d employees-service`, create an employee in the UI, and check that `createdAt` and `updatedAt` still look right.

### Apply: separate the assignment rules from storage

Your `AssignmentService` from 3.3.2 does two jobs: it holds the rules, and it holds the data. Split them, so 3.3.4 can replace the storage with PostgreSQL by changing one line.

1. **The entity.** Create `Features/Assignments/Assignment.cs`: a plain class with settable properties for every field (`Id`, `EmployeeId`, `ProjectId`, `Role`, `AllocationPercent`, `StartDate`, `EndDate`, `CreatedAt`, `UpdatedAt`) and no behavior, like `Employee.cs`. Add `public static AssignmentResponse From(Assignment a)` to `AssignmentResponse`, like `EmployeeResponse.From`.
2. **The seam.** Create `Features/Assignments/IAssignmentStore.cs`, named after what the service needs:

    ```csharp
    public interface IAssignmentStore
    {
        Task<IReadOnlyList<Assignment>> ListAsync(Guid? employeeId, Guid? projectId, CancellationToken ct);
        Task<Assignment?> FindAsync(Guid id, CancellationToken ct);
        Task<bool> PairExistsAsync(Guid employeeId, Guid projectId, Guid? exceptId, CancellationToken ct);
        Task AddAsync(Assignment assignment, CancellationToken ct);
        Task UpdateAsync(Assignment assignment, CancellationToken ct);
        Task<bool> DeleteAsync(Guid id, CancellationToken ct);
    }
    ```

    Write a doc comment on each method saying what it promises, including that `AddAsync` and `UpdateAsync` throw `ConflictException` when the employee and project pair is already taken. That promise is what every implementation must keep.

3. **A temporary store.** Create `Features/Assignments/InMemoryAssignmentStore.cs`, a dictionary-backed `IAssignmentStore`. Guard the dictionary with a `lock`, because a singleton is shared by every request at once. Store and return *copies* of each `Assignment`, so a caller changing an object it got back can't change the "stored" row without calling `UpdateAsync`, just as with a database. It lives until 3.3.4.
4. **The rules.** Rewrite `AssignmentService` to take `(IAssignmentStore store, TimeProvider time)` and keep no data of its own. Model it on `EmployeeService`:
    - `CreateAsync` checks `PairExistsAsync` and throws `ConflictException`, sets `Id`, `CreatedAt`, and `UpdatedAt` from `time`, copies the request onto a new `Assignment`, and calls `AddAsync`;
    - `UpdateAsync` finds the assignment (404 if missing), checks the pair with `exceptId: id`, applies the request, sets `UpdatedAt`, and calls `UpdateAsync`;
    - one private `Apply(request, assignment)` method copies the request's fields for both, because `PUT` replaces every writable field.
5. **The registrations.** Replace the temporary singleton line in `Program.cs`:

    ```csharp
    builder.Services.AddSingleton(TimeProvider.System);
    builder.Services.AddSingleton<IAssignmentStore, InMemoryAssignmentStore>();   // until 3.3.4
    builder.Services.AddScoped<IAssignmentService, AssignmentService>();
    ```

6. Rebuild and repeat the requests from the 3.3.2 Apply step 7. Everything behaves exactly as before. That's the point of a refactor.
7. **Break the lifetimes on purpose,** using `dotnet run --project src/AssignmentsService` (the launch profile runs in Development, where .NET checks scopes):
    - Register the store with `AddScoped` instead. Create an assignment, then list them. The list is empty: every request got a brand-new store. Explain why in one sentence.
    - Keep the store scoped and register the service with `AddSingleton`. The app refuses to start, with `Cannot consume scoped service 'AssignmentsService.Features.Assignments.IAssignmentStore' from singleton`. Which rule from the warning above did you break?
    - Put both lines back the way step 5 has them.
8. Open the pull request. In its description, list each registration and why it has that lifetime.
