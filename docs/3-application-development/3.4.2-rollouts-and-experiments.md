# Rollouts and Experiments

A flag that is simply on or off releases a feature to everyone at once. The real power of flags comes from giving different users different answers, so you can release gradually and learn as you go.

## Evaluation Context

To decide per user, the flag system needs to know who's asking. The [evaluation context](https://openfeature.dev/docs/reference/concepts/evaluation-context/) carries that information with each evaluation:

- A **targeting key**, a stable identifier for the subject of the evaluation, usually a user ID.
- **Attributes**, other facts the rules can use, such as plan, country, or email domain.

Your application builds the context from what it knows about the request, often from the authenticated user. Only include what your rules need: the context may be sent to the flag service, and, as you'll see in [OpenFeature](3-application-development/3.4.3-openfeature.md), it can end up in your telemetry.

## Targeting Rules

A targeting rule picks a variant from the context. flagd writes rules in [JsonLogic](https://flagd.dev/reference/flag-definitions/#targeting-rules). This rule gives `on` to beta users and falls back to the flag's default variant for everyone else:

```json
"targeting": {
  "if": [{ "==": [{ "var": "plan" }, "beta"] }, "on", null]
}
```

## Release Strategies

With context and rules, you can release in stages:

- **Dark launch:** deploy the code with the flag off for everyone. You can still turn it on for yourself to test it in production.
- **Internal users first:** turn it on for employees, then for beta customers. Hodgson calls this a "champagne brunch", for drinking your own champagne.
- **Percentage rollout:** turn it on for 1% of users, then 10%, 50%, and 100%, checking error rates and latency at each step. Hodgson calls a release to a random group a *canary release*.
- **Kill:** if the metrics get worse, turn the flag off. Every user is back on the old code in seconds.

A percentage rollout must be **sticky**: the same user must get the same answer on every request, or they would see the feature appear and disappear. flagd's [`fractional`](https://flagd.dev/reference/custom-operations/fractional-operation/) operation does this by hashing the flag key and the targeting key into a bucket. The same user always lands in the same bucket, so raising the percentage adds users without removing any.

## Experiments

An **experiment**, or A/B test, uses the same mechanism to answer a question. Users are split into groups that each get a different variant, and you compare a metric between the groups: does the new checkout page lead to more completed orders? To trust the answer:

- **Decide the metric and the stopping point before you start**, so you aren't tempted to stop when the numbers happen to look good.
- **Run long enough for a meaningful result**, but not so long that other changes to the system muddy it.
- **Record which variant each user got**, so you can join flag decisions to outcomes. [OpenFeature](3-application-development/3.4.3-openfeature.md) shows how flag decisions can appear in your traces.

## Exercise: Roll Out a Change to a Percentage of Users

This exercise continues from the [Flag Types exercise](3-application-development/3.4.1-flag-types.md#exercise-add-a-kill-switch-and-retire-a-release-flag), with flagd and the app running.

The change: names should be trimmed and at least two characters long. It might reject requests that work today, so you'll roll it out gradually. Requests identify their user with two headers: `X-User-Id` and `X-User-Plan`.

1. Add a `strict-names` flag to the flag file, with `on` and `off` variants and `defaultVariant` set to `"off"`, and add this rule. Beta users get `on`, and everyone else is split 10% `on`, 90% `off`:

    ```json
    "targeting": {
      "if": [
        { "==": [{ "var": "plan" }, "beta"] }, "on",
        { "fractional": [["on", 10], ["off", 90]] }
      ]
    }
    ```

2. Give OpenFeature the request's context. The SDK can hold a *transaction context* for the current request, so you set it once instead of passing it to every flag check:
    - In `app/flags.py`, before setting the provider, call `api.set_transaction_context_propagator(ContextVarsTransactionContextPropagator())`, imported from `openfeature.transaction_context`.
    - In `create_app`, add a `@app.before_request` function that calls `api.set_transaction_context(...)` with an `EvaluationContext` (from `openfeature.evaluation_context`). Use the `X-User-Id` header as the `targeting_key`, and the `X-User-Plan` header, defaulting to `"free"`, as a `plan` attribute.
3. In `create_user`, when `strict-names` is on, strip the name and raise `ValueError("name must be at least 2 characters")` if it's shorter than two characters.
4. Restart the app and check the targeting:

    ```bash
    post() { curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' \
      -H "X-User-Id: $1" -H "X-User-Plan: ${2:-free}" -d '{"name":"A"}' localhost:5001/users; }
    post alice beta
    for i in 1 2 3; do post user-1; done
    ```

    The beta user is rejected. `user-1` gets the same answer every time.
5. Count how many of 1,000 free users get the strict rule, and save their IDs:

    ```bash
    for i in $(seq 1 1000); do [ "$(post user-$i)" = 400 ] && echo user-$i; done > at-10.txt
    wc -l < at-10.txt
    ```

6. Roll out further: change the split to 50/50, save the file, and repeat step 5 into `at-50.txt`. Check that nobody in the first group lost the feature: `comm -23 <(sort at-10.txt) <(sort at-50.txt)` should print nothing.
7. Leave the 50/50 split in place. You'll finish the rollout in the next exercise, after watching it in your traces.

### Deliverables

- Your flag definition and your context code.
- The counts from steps 5 and 6, and the output of the `comm` check.
- Explain why a percentage rollout must be sticky, and what would go wrong if each request were assigned at random.
- Discuss: at each stage of this rollout, which metrics from your [Metrics exercise](3-application-development/3.3.2-metrics.md#exercise-custom-metrics-and-a-red-dashboard) would you watch before moving to the next stage, and what would make you turn the flag off?
