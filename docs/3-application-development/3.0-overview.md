# Application Development: An Overview

Most of this bootcamp is about getting software to the people who use it and keeping it running: containers, pipelines, cloud platforms, Kubernetes. All of that exists to serve one thing, the application. Before you can package, deploy, or monitor an application well, you need to know what is inside one and how it behaves.

That is what this chapter is for. Code written for a class is often a single program that one person writes, runs, and hands in. Real applications are different. They are made of several pieces, used by many people at once, changed by a team every day, and expected to keep working while that happens. In this chapter your team takes over one of those applications, the Company app, learns how it is put together, and builds a new piece of it. You keep working on the same app for the rest of the bootcamp, so later chapters on containers, delivery pipelines, the cloud, and Kubernetes all have a real application of yours to work with.

You need to be comfortable writing basic code in at least one programming language. You don't need any experience with the languages and tools used here (.NET, Python, Go, React, web APIs, databases, or message brokers). Every section explains the idea first, shows it working in code that is already written, walks you through a small change, and only then asks your team to do the same on its own service.

## What You'll Learn

- **The Basics:** the Unix shell, Vim, package installation, SSH keys, and networking.
- **Application Architecture:** foundational layers, vertical slices, service boundaries, and how services talk to each other.
- **Building a Service:** scaffolding a .NET Web API, endpoints, dependency injection, persistence, calling other services, and publishing events.
- **Code Quality:** the testing pyramid and trophy, unit, component, integration, contract, and end-to-end tests, coverage, linting, CI, code review, and pre-commit hooks.
- **Observability:** logs, metrics, and traces with OpenTelemetry, followed across several services and a message broker.
- **Feature Flags:** separating deployment from release with OpenFeature and flagd.

## How Each Section Works

Every section after The Basics teaches one topic in the same four steps:

| Step | What you do | Where |
| --- | --- | --- |
| **Theory** | Read a short explanation of the idea. | The section page |
| **Example** | See the idea working in a finished starter service. | `examples/company-app/starter/` |
| **Practice** | Close a small, deliberate gap in a starter service, following exact steps. | Your team's repository |
| **Apply** | Use the same skill on the service your team is building. | Your team's `assignments-service/` |

Practice steps are individual: every apprentice does every one. Apply work is shared: the team splits it, reviews each other's pull requests, and ends each section with a working milestone. If you fall behind, each milestone has reference code you can compare against.

## The Company App

The Company app is a small company directory: employees, projects, and who is assigned to what. It is built from several services in different languages, the way real systems grow.

![Company app architecture](img/company-app-architecture_light.svg ':size=900px :class=light-mode-img-center :alt=Company app architecture: a browser talks to an nginx frontend-proxy, which routes to the web UI and four backend services. Each backend service owns a database on one PostgreSQL server. Services exchange events through RabbitMQ. flagd and the otel-lgtm stack support every service; light mode')
![Company app architecture](img/company-app-architecture_dark.svg ':size=900px :class=dark-mode-img-center :alt=Company app architecture: a browser talks to an nginx frontend-proxy, which routes to the web UI and four backend services. Each backend service owns a database on one PostgreSQL server. Services exchange events through RabbitMQ. flagd and the otel-lgtm stack support every service; dark mode')

| Service | Language | What it does |
| --- | --- | --- |
| `web` | React + TypeScript | The UI. Its Assignments page is already built and waits for your service. |
| `employees-service` | .NET 10 | Employees. Publishes `employee.*` events. **The model for the service you build.** |
| `projects-service` | Python (FastAPI) | Projects. |
| `notifications-service` | Go | Consumes every event and shows a feed. |
| `assignments-service` | .NET 10 | **Your team builds this one.** Assigns employees to projects. |

Behind them run PostgreSQL (one database per service), RabbitMQ, flagd, and Grafana's `otel-lgtm` stack for logs, metrics, and traces. An nginx `frontend-proxy` puts everything behind one address, `http://localhost:8080`.

The starter services are complete and follow good practice, apart from one small gap per topic that a Practice step closes. The [Company app README](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app) lists the milestones, and [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md) is the contract every service follows.

## Your Team's Repository

Each cohort or team owns **one repository** for the whole chapter.

- In [3.2 Application Architecture](3-application-development/3.2-application-architecture.md#exercise-run-the-company-app), one person copies the starter into a new repository, and everyone else clones it.
- All work happens on branches named `<type>/<slug>`, such as `docs/assignments-design` or `feat/assignments-crud`, and lands through pull requests that a teammate reviews.
- Nobody pushes straight to `main`. Turn on a branch rule that requires a pull request and one approval.
- Split each section's Apply work by slice or file so two people rarely edit the same file. `Program.cs` and EF Core migrations are the usual conflict hotspots: pick one owner for each per milestone.

> [!TIP]
> Treat this repository the way you would a client's. Small pull requests, clear commit messages, and reviews that ask questions are part of what you are practicing.

## What You Need

- **Docker** with Compose v2 (`docker compose`). Docker Desktop, Rancher Desktop, and Colima all work.
- **About 8 GB of free memory** for the full stack: five services, PostgreSQL, RabbitMQ, flagd, and Grafana. Raise Docker Desktop's memory limit in its [settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/) if containers keep restarting.
- **About 10 GB of free disk** for images and build caches.
- **Git and the GitHub CLI** (`gh`), set up in [Chapter 2](2-version-control/2.0-overview.md) and [3.1.3 Installations](3-application-development/3.1.3-installations.md).
- **Language toolchains**, one of two ways:
  - install the .NET 10 SDK, Python 3.13 with `uv`, Go, and Node 24 yourself; or
  - open the repository in its [dev container](https://containers.dev/), which has all of them plus the Docker CLI. VS Code's [Dev Containers extension](https://code.visualstudio.com/docs/devcontainers/containers) and GitHub Codespaces both read it.

Running the app needs only Docker. You need the toolchains once you start changing and testing code in 3.3.
