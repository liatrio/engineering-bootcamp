# Publishing and Consuming Events

The last piece of M2 connects assignments-service to the rest of the app without anyone calling it. It **publishes** `assignment.created` so the notification feed can show new assignments, and it **consumes** `employee.deleted` so that when someone leaves, their assignments go with them. Along the way you'll meet the hardest problem in messaging, the dual write, and the habit that makes consumers safe: idempotency.

## Events and Commands

Both are messages, but they say different things:

| | Event | Command |
| --- | --- | --- |
| Says | "This happened" | "Do this" |
| Named in | The past tense: `employee.deleted` | The imperative: `delete-assignments` |
| Sender knows the receivers? | No. Zero, one, or ten services may care. | Yes. It's addressed to one handler. |
| Can the receiver refuse? | No. It already happened. | Yes. It can fail or reject it. |

The Company app uses only events. employees-service doesn't tell assignments to delete anything; it announces that an employee is gone, and assignments decides what that means for its own data. That's why employees-service needs no changes when assignments starts listening, and why notifications-service could subscribe to everything without anyone's permission. The owner announces; others react.

## The Envelope

Every event on the `company.events` exchange has the same wrapper, defined in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md#events-rabbitmq):

```json
{ "eventId": "uuid", "type": "assignment.created", "occurredAt": "2026-11-13T09:30:00Z",
  "source": "assignments-service", "data": { "...": "the assignment" } }
```

- **`eventId`** is unique per event, so a consumer can recognize a duplicate.
- **`type`** is also the routing key, so consumers bind to the events they want (`employee.deleted`) or all of them (`#`).
- **`source`** says which service published it, which helps when debugging.
- **`data`** is the payload: the whole entity for created and updated events, only `{ "id": ... }` for a delete.

In employees-service, [`EventEnvelope.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Messaging/EventEnvelope.cs) is the record, and [`RabbitMqEventPublisher`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Messaging/RabbitMqEventPublisher.cs) wraps the data, serializes it as camelCase JSON, and publishes it as a **persistent** message, which survives a broker restart. [`RabbitMqConnection`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Messaging/RabbitMqConnection.cs) uses **publisher confirms**, so a publish only returns once RabbitMQ has taken responsibility for the message.

## Publishing After Commit, and the Dual Write

Creating an employee writes to two systems: PostgreSQL and RabbitMQ. There's no transaction that spans both, so one can succeed while the other fails. This is the **dual-write problem**, and every ordering has a failure:

| Order | If the second step fails | Result |
| --- | --- | --- |
| Publish, then commit | The commit fails (a duplicate email, the database is down) | A **ghost event**: consumers react to an employee that doesn't exist |
| Commit, then publish | The publish fails (RabbitMQ is down) | A **lost event**: the employee exists, but nobody hears about it |

The Company app picks **commit, then publish**, because acting on something that never happened is worse than missing a notification. Then it's honest about the gap: if the publish fails, `RabbitMqEventPublisher` logs the error loudly and the request still succeeds, because the employee really was created. Failing the request would tell the client "it didn't work" when it did. Two more details in `EmployeeService` follow from the same reasoning:

- The publish happens only after `store.AddAsync(...)` returns, which means `SaveChangesAsync()` committed.
- It passes `CancellationToken.None`, not the request's token. A client that hangs up after the commit must not be able to cancel the event announcing a change that really happened.

### The fix you'll hear about: the transactional outbox

The standard fix is the **transactional outbox pattern**. Instead of publishing directly, the service writes the event to an `outbox` table **in the same database transaction** as the change. Either both are saved or neither is. A separate relay process then reads the outbox, publishes each event, and marks it sent. If RabbitMQ is down, the events wait in the table until it's back.

The outbox trades the lost event for a duplicate: the relay might publish an event and crash before marking it sent, so it publishes it again on restart. That's acceptable, because consumers must handle duplicates anyway (next section). The Company app names the pattern but doesn't build it, to keep the code small; libraries such as MassTransit and Wolverine provide it ready-made.

## Consuming Safely

RabbitMQ delivers **at least once**. A consumer acknowledges (acks) a message after handling it; if the consumer crashes, or its connection drops, before the ack, RabbitMQ delivers the message again. So every consumer must be ready to see the same message twice.

### Ack after the work is done

notifications-service's [`Handle`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/consumer.go) shows the order, in Go: decode the envelope, store the notification, and only then `d.Ack(false)`. A crash before the ack means redelivery, not a lost message. Acking first would be the opposite trade.

### Idempotent consumers

A handler is **idempotent** if processing a message twice has the same effect as processing it once. Some handlers are idempotent by nature: "delete every assignment for employee X" deletes nothing the second time, and that's fine. Others aren't: "add 1 to a counter" or "send an email" would happen twice. Those need to remember which `eventId`s they've already processed, usually in a table, inside the same transaction as the work.

### Messages that can never succeed

Some messages will fail every time: invalid JSON, or an envelope missing `data.id`. Retrying those forever blocks the queue. Reject them without requeueing (`BasicNack` with `requeue: false`) and log them. With a dead-letter exchange configured, RabbitMQ moves rejected messages there for someone to inspect. For failures that might be temporary, like the database being down, requeue once and give up if the redelivery fails too, so one bad moment doesn't become an endless loop.

### Durable queues

A consumer's queue must be **durable**, so it survives a broker restart, and it must be **declared by the consumer** with a stable name. Then events published while the consumer is down wait in the queue, which you saw in [3.2](3-application-development/3.2-application-architecture.md#exercise-run-the-company-app) when notifications caught up after a restart.

### Consumers in .NET

A consumer in ASP.NET Core is a **hosted service**: a `BackgroundService` whose `ExecuteAsync` runs for the life of the app. It's a singleton, but the work it does per message needs scoped services, such as the store and its `DbContext`. So, like `DatabaseInitializer`, it injects `IServiceScopeFactory` and creates one scope per message.

## Exercise

### Example: follow an event from publisher to consumer

1. In employees-service, find the three calls to `PublishAsync` in `EmployeeService.cs`. For each, note which line commits the change before it.
2. In notifications-service, read `consume` and `Handle` in `internal/consumer/consumer.go`. Find the exchange, queue, and binding declarations, the prefetch setting, the ack, and the one place it nacks without requeueing. What kind of message ends up there?
3. Open RabbitMQ's UI at `http://localhost:15672`, go to **Queues**, and open `notifications`. Create an employee, then use **Get messages** on the queue. It comes back empty, even though an event was just published. Use the queue's consumer count and message rates to explain why.

### Practice: lose an event on purpose

See the dual-write gap with your own eyes. With the app running:

1. Stop the broker, then create an employee:

    ```bash
    docker compose stop rabbitmq
    curl -si -X POST localhost:8080/api/employees -H 'Content-Type: application/json' \
      -d '{"name":"Lost Event","email":"lost@example.com","title":"Engineer","department":"Research"}' | head -1
    ```

    The answer is `201 Created`. The employee is saved.

2. Find what happened to the event:

    ```bash
    docker compose logs employees-service | grep -i "event was lost"
    ```

    There's an error: `Failed to publish employee.created ...; the event was lost`.

3. Start the broker with `docker compose start rabbitmq`, wait a few seconds, and open **Notifications**. *Lost Event* is on the Employees page but never appears in the feed, even now that RabbitMQ is back. Nothing retried it.
4. Answer in writing:
    - With a transactional outbox, what would have happened at steps 1, 2, and 3?
    - Which consumer in M2 would care most about a lost `employee.deleted`, and what would its users see?
5. Delete *Lost Event* in the UI to tidy up.

### Apply: publish assignment.created and consume employee.deleted

This finishes M2. One person takes publishing (steps 1 to 4) and another the consumer (steps 5 to 8).

1. **Package.** From `src/AssignmentsService/`:

    ```bash
    dotnet add package RabbitMQ.Client --version 7.2.2
    ```

2. **Messaging foundation.** Copy `EventEnvelope.cs`, `IEventPublisher.cs`, `RabbitMqConnection.cs`, and `RabbitMqEventPublisher.cs` from employees-service's `Infrastructure/Messaging/`, and `RabbitMqHealthCheck.cs` from `Infrastructure/Health/`. Change the namespaces, the publisher's `Source` to `"assignments-service"`, and the connection's `ClientProvidedName`. Register them in `Program.cs` as employees-service does, and add the RabbitMQ check to readiness:

    ```csharp
    builder.Services.AddSingleton<RabbitMqConnection>();
    builder.Services.AddSingleton<IEventPublisher, RabbitMqEventPublisher>();
    // ...and on AddHealthChecks(), after the postgres check:
        .AddCheck<RabbitMqHealthCheck>("rabbitmq", tags: [HealthEndpoints.ReadyTag]);
    ```

3. **Publish after commit.** Add `IEventPublisher events` to `AssignmentService`'s constructor and a `public const string CreatedEvent = "assignment.created";`. In `CreateAsync`, after `store.AddAsync(...)`, publish the response:

    ```csharp
    var response = AssignmentResponse.From(assignment);
    // The row is committed. Publishing ignores the request's cancellation
    // token so a client hanging up now can't suppress the event.
    await events.PublishAsync(CreatedEvent, response, CancellationToken.None);
    return response;
    ```

4. Rebuild with `docker compose up --build -d assignments-service`. `curl -s localhost:5103/readyz` now lists `"rabbitmq":"healthy"`. Create an assignment in the UI, then open **Notifications**: *Employee 1111... was assigned to project aaaa... as Tech Lead*. notifications-service binds `#`, so it picked up your new event type without anyone changing it.
5. **A channel for consuming.** The copied `RabbitMqConnection` has one channel, for publishing. A consumer needs its own: RabbitMQ expects one channel per concurrent activity, and publishing and consuming must never share one. Add a `CreateChannelAsync(CancellationToken ct)` method that opens a new channel on the shared connection, declares the exchange on it, and returns it to the caller, who owns it. Use M2's [`RabbitMqConnection.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M2-assignments-mvp/assignments-service/src/AssignmentsService/Infrastructure/Messaging/RabbitMqConnection.cs) as your reference: connection handling is fiddly, and getting it subtly wrong is easy.
6. **Delete by employee.** Add `Task<int> DeleteForEmployeeAsync(Guid employeeId, CancellationToken ct)` to `IAssignmentStore`, implemented in `AssignmentStore` with one `ExecuteDeleteAsync`. Add `Task<int> RemoveForEmployeeAsync(Guid employeeId, CancellationToken ct)` to `IAssignmentService`, which calls it. Deleting zero rows is a normal result, not an error.
7. **The consumer.** Create `Features/Assignments/EmployeeDeletedConsumer.cs`, a `BackgroundService` that takes `RabbitMqConnection`, `IServiceScopeFactory`, and a logger. It lives in the feature folder because what it does, removing assignments, is assignment logic. It must:
    - in `ExecuteAsync`, keep trying to start every 5 seconds until it succeeds, because RabbitMQ may still be booting;
    - declare a **durable** queue named `assignments.employee-deleted`, bind it to `company.events` with the routing key `employee.deleted`, set a prefetch of 10, and start an `AsyncEventingBasicConsumer` with `autoAck: false`;
    - for each message, deserialize the envelope with web (camelCase) JSON settings, and read `data.id`;
    - nack without requeue a message it can't read or that has no `data.id`, with an error log;
    - otherwise create a scope, resolve `IAssignmentService`, call `RemoveForEmployeeAsync`, log how many it removed, and **then** ack;
    - if that fails, nack with `requeue: !delivery.Redelivered`, so it gets one more try;
    - dispose its channel in `StopAsync`.

    Register it with `builder.Services.AddHostedService<EmployeeDeletedConsumer>();`.

8. **Watch it work.** Rebuild, then:
    - In RabbitMQ's UI, under **Queues**, open `assignments.employee-deleted`. It has one consumer, and its binding is `employee.deleted` on `company.events`.
    - Create a new employee, assign them to a project, then delete the employee on the **Employees** page. Reload **Assignments**: their assignment is gone. `docker compose logs assignments-service` shows *Employee ... was deleted; removed 1 assignments*.
    - Assign another employee, then run `docker compose stop assignments-service`, delete that employee in the UI, and run `docker compose start assignments-service`. The assignment still disappears within a few seconds: the durable queue held the event while the service was down.
    - Use RabbitMQ's UI to publish the same `employee.deleted` message twice to `company.events` (**Exchanges → company.events → Publish message**, routing key `employee.deleted`, payload `{"type":"employee.deleted","data":{"id":"<some employee id>"}}`). Both are handled, and the second removes 0 assignments. That's idempotency.
9. **Finish M2.** Refresh `assignments-service/openapi.yaml`. Write `assignments-service/README.md`: how to run it, its environment variables, its endpoints, its events, and its layout. Add a **Commands** table to `AGENTS.md` with the commands you used most: rebuilding one service, reading its logs, adding a migration, refreshing `openapi.yaml`. Then open the pull request.
