# Service Communication

Services are only useful together. This page covers the two ways the Company app's services talk, synchronous HTTP requests and asynchronous messages, then follows one click through every layer and service it touches. It ends with the contracts that keep services in agreement: Problem Details for errors and OpenAPI for APIs.

## Synchronous Requests

In a **synchronous** call, the caller sends a request and waits for the answer before it continues. In the Company app that means REST over HTTP: the web app calls every API this way, and assignments-service will call employees-service and projects-service this way.

Synchronous calls are simple to reason about, because you get an answer, or an error, right away. Their cost is **coupling in time**: the caller can only succeed while the callee is up and fast. Their failure modes are the ones you'll design for in 3.3:

- **Slow responses.** Without a timeout, a slow dependency holds the caller's threads and connections until it slows down too.
- **Failures that spread.** If assignments waits on projects, and projects is down, assignments' writes fail as well. A chain of synchronous calls is only as available as its weakest link.
- **Retries that make things worse.** Retrying a struggling service right away adds load at the worst time. Retries need backoff and a limit, and a circuit breaker stops calling a service that is clearly down.

## Asynchronous Messaging

In **asynchronous** messaging, the sender publishes a message to a broker and moves on. Consumers process it in their own time. The Company app uses RabbitMQ with one **topic exchange**, `company.events`:

- **The routing key is the event type**, such as `employee.created`.
- **Each consumer has its own durable queue**, bound to the exchange with a pattern. notifications-service binds `#` (every event); assignments-service will bind `employee.deleted`.
- **A queue delivers each message to one consumer; a topic exchange copies each message to every bound queue.** So one event can reach any number of services, each processing it independently.
- **Delivery is at least once.** A consumer acknowledges a message after handling it; if it crashes first, RabbitMQ delivers it again.

RabbitMQ's [AMQP concepts](https://www.rabbitmq.com/tutorials/amqp-concepts) guide explains exchanges, queues, and bindings in more depth.

The big win is **decoupling**. employees-service doesn't know notifications-service exists. A new consumer can start listening tomorrow without anyone changing employees-service. And as you saw in the [3.2 exercise](3-application-development/3.2-application-architecture.md#exercise-run-the-company-app), a consumer can be down for a while and catch up when it returns. The cost is that the sender gets no answer: it can't know whether, when, or how a consumer handled the event.

## Choosing Between Them

| Question | Synchronous (HTTP) | Asynchronous (events) |
| --- | --- | --- |
| Does the caller need the answer to continue? | Yes: "does this employee exist?" before saving | No: "an employee was created", for whoever cares |
| Who knows about whom? | The caller knows the callee's address and API | The publisher knows only the exchange and the event shape |
| What happens if the other side is down? | The caller's request fails, or it returns a 503 | The message waits in the queue |
| Consistency | Immediate: you have the answer now | Eventual: consumers catch up |
| Debugging | One request, one response | A chain of handlers, possibly much later |

A rule of thumb: **ask with a request, announce with an event.** When you need something from another service to finish your work, call it. When something happened that others might care about, publish it.

### In the browser

1. **The form**, [`web/src/features/employees/EmployeeForm.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/employees/EmployeeForm.tsx), owns the fields. Its zod schema mirrors the server's rules, so most mistakes are caught before any request. On submit it calls a mutation hook. It doesn't know the URL, the HTTP verb, or the payload format.
2. **The feature's API module**, [`web/src/features/employees/api.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/employees/api.ts), has one line per endpoint. `createEmployee` sends a `POST` through `api()`. On success, the hook invalidates the cached employee list, so the table refetches.
3. **The API client**, [`web/src/lib/api.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib/api.ts), is the only code in the frontend that calls `fetch`. It sends the request to a relative path, `/api/employees`, on the same origin. It turns any non-2xx response into an `ApiError`, and a network failure into an `ApiError` with status 0.

### Through the proxy

1. **The proxy**, [`infra/proxy/nginx.conf`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/infra/proxy/nginx.conf), matches `location /api/employees` and passes the request to `employees-service:8080` with the path unchanged. Every service serves its full path, so the same request also works directly on port 5101.

### In employees-service

1. **The controller**, `EmployeesController.Create`, is reached by attribute routing. Before it runs, `[ApiController]` binds the JSON body to `EmployeeRequest` and checks its data annotations. An invalid body gets a 400 here, and the action never runs.
2. **The service**, `EmployeeService.CreateAsync`, applies the business rules. It checks that no other employee has the email (ignoring case), generates the ID and timestamps, and trims the fields.

    ```csharp
    await EnsureEmailIsFreeAsync(request.Email, exceptId: null, ct);
    var now = DateTime.UtcNow;
    var employee = new Employee { Id = Guid.NewGuid(), CreatedAt = now, UpdatedAt = now };
    Apply(request, employee);
    await store.AddAsync(employee, ct);
    ```

3. **The store**, `EmployeeStore.AddAsync`, adds the entity and calls `SaveChangesAsync`. EF Core turns that into a parameterized `INSERT` in one transaction. If a second request with the same email slipped past the service's check, the unique index from `EmployeeConfiguration` rejects it, and the store turns that error into the same 409.
4. **The database** enforces the constraints that must hold no matter which code path wrote the row: the primary key, the lengths, and the unique index on the lower-cased email.
5. **The publisher**: once the row is committed, the service publishes `employee.created`. [`RabbitMqEventPublisher`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Messaging/RabbitMqEventPublisher.cs) wraps the employee in the event envelope and sends a persistent JSON message to `company.events` with the routing key `employee.created`. If publishing fails, it logs the error loudly instead of failing the request, because the employee really was created. You'll meet that trade-off again in 3.3.
6. **The response** unwinds: the controller returns `CreatedAtAction(...)`, which becomes a `201 Created` with a `Location: /api/employees/{id}` header and the new employee as JSON.

The user now has their answer. Everything below happens afterwards.

### In notifications-service

1. **The consumer**, `Handle` in [`notifications-service/internal/consumer/consumer.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/consumer.go), receives the message from its `notifications` queue. It continues the publisher's trace from the message headers, decodes the envelope, and turns it into text with `events.Message`. It stores the notification and only then acknowledges the message, so a crash before that point means RabbitMQ delivers it again.
2. **The feed**: the web app's Notifications page polls `GET /api/notifications` every five seconds, and the new line appears.

### Why the layers earn their keep

Each hop is a boundary where one concern stops and the next begins. So **every failure has an obvious home**:

| Failure | Who detects it | What the user sees |
| --- | --- | --- |
| Invalid email format | The zod schema; the server's data annotations if it gets past | A message under the Email field |
| Email already used | `EmployeeService`, or the unique index in a race | 409, shown as a form error |
| employees-service is down | The proxy | 502, shown as an error message |
| The network drops | `api()` in the browser | An `ApiError` with status 0 |
| RabbitMQ is down | `RabbitMqEventPublisher` | Nothing: the employee is saved, the event is lost, and an error is logged |

The layer that owns a rule is the layer that reports its failure. When you're on call, that table is your map.

## Contracts Between Services

Services built by different teams, in different languages, stay compatible through explicit contracts.

### Problem Details: the error contract

Every Company app service returns errors as **Problem Details**, defined by [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) and sent as `application/problem+json`. Here is employees-service rejecting a duplicate email:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Conflict",
  "status": 409,
  "detail": "An employee with email 'ADA@example.com' already exists.",
  "traceId": "00-23395a29340aab5793304301ead940db-83fca5c2cd5a4a3f-03"
}
```

A validation failure adds an `errors` map of field names to messages. Because every service uses this shape, including the Python and Go ones, the web app handles errors once, in `api()`, and the type URIs tell a client what kind of failure happened. ASP.NET Core produces it with `AddProblemDetails()` and its exception handling, described in [Handle errors in ASP.NET Core APIs](https://learn.microsoft.com/en-us/aspnet/core/web-api/handle-errors). projects-service builds the same fields by hand in `app/errors.py`.

### OpenAPI: the API contract

An **OpenAPI** document describes every endpoint, parameter, request body, response, and error of an HTTP API in YAML or JSON. The [OpenAPI Specification](https://spec.openapis.org/oas/latest.html) is the standard. Each Company app service commits its document as `openapi.yaml` in the service root:

- employees-service generates its document with ASP.NET Core's built-in OpenAPI support and serves it at `/openapi/v1.json`. The committed file is a saved copy.
- projects-service gets its document from FastAPI, served at `/openapi.json`.
- notifications-service has a hand-written file, because Go's standard library doesn't generate one.

A committed OpenAPI file is useful long before anyone reads it. Reviewers see API changes in the diff, client code can be generated from it, and in Chapter 9 Backstage reads these files to build a service catalog. Writing one *before* the code, as a design sketch, forces you to decide the endpoints, status codes, and shapes while they're still cheap to change. That's what your team does next.

> [!NOTE]
> An OpenAPI document says what a provider *offers*. It doesn't say which parts each consumer *relies on*. Contract tests (3.4.6) close that gap.

### Events are contracts too

Every event shares one envelope: `eventId`, `type`, `occurredAt`, `source`, and `data`. The event types and their `data` are listed in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md). Changing an event's shape can break consumers that the publisher has never heard of, so treat it with the same care as an API change. notifications-service shows one defensive habit: an unknown event type still produces a notification instead of an error, so a new publisher shows up without a code change.

### Apply: finish the Assignments design (M1)

This completes milestone M1: everything your team needs to start building in 3.3, written down. Work on a branch, `docs/assignments-communication`, and split the steps between teammates.

1. **Rules.** Add a **Rules** section to `AGENTS.md`, written as instructions. Start with these, then add at least three of your own: one for any row of your foundation table that has no rule yet.

    ```markdown
    - Controllers never catch exceptions and never build error responses.
    - Validation of the request shape is data annotations on the DTO.
    - Only `Program.cs` and options classes read configuration.
    - A service never touches another service's database; call its API.
    - Publish events only after `SaveChanges` succeeds, through `IEventPublisher`.
    ```

2. **Endpoints and rules.** In `docs/assignments-design.md`, add an **Endpoints** table (*Method and path*, *Success*, *Errors*) and a numbered **Rules** list. Both IDs must exist (400 if not), no duplicates (409), and a dependency that can't be reached means 503. The service never saves an assignment it couldn't check.
3. **Calling other services.** Add a section that answers:
    - Which endpoints does assignments call, and what does it do with a 200, a 404, a timeout, and a 5xx?
    - Where do the base URLs come from? (`EMPLOYEES_URL` and `PROJECTS_URL`.)
    - Should `/readyz` fail when employees-service is down? Think about what happens to every caller of assignments if it does.
4. **Events.** Add a table with the columns *Direction*, *Type*, *`data`*, and *What we do*: publish `assignment.created`, and consume `employee.deleted` from the durable queue `assignments.employee-deleted`. Say when you acknowledge the message, and why handling it twice is safe.
5. **OpenAPI sketch.** Create `assignments-service/openapi.yaml`. Start from a copy of `employees-service/openapi.yaml` and change it to match your design: the five endpoints, the `employeeId` and `projectId` query filters, `AssignmentRequest` and `Assignment` schemas, and Problem Details responses for 400, 404, 409, and 503. Paste it into the [Swagger Editor](https://editor.swagger.io/) to check that it parses and renders the way you expect.
6. **Check it.** Read `AGENTS.md` and the design doc as if you joined the team tomorrow, and answer without opening any code: where does a 404 come from? Where does a new table's mapping go? What happens when projects-service is down and someone creates an assignment? If the files answer all three, open the pull request, and have every teammate review it.
