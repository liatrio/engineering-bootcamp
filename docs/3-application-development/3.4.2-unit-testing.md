# Unit Testing

Unit testing is the process of verifying that specific units of code are working as expected. Unit tests are typically concise
in nature, and they make assertions against a very specific part of the codebase - usually a single function.

The process for writing a unit test might look something like this:

1. Identify a function / method as the system under test (SUT).
2. Invoke the function / method with predefined arguments.
3. Observe the return value(s) of the function / method, and assert that they match the expected return value(s).

Unit testing is most effective against smaller functions that are scoped to a singular task. Functions that do multiple
tasks are typically more complex, and their input / output will usually reflect that.

Unit tests should be able to execute in isolation without requiring any other dependencies to be present. Functions that are
more complicated to test might also need to include mocks or stubs in order to fake some behavior, which will allow these
tests to run in complete isolation. For example, a function that makes an HTTP request to a server during its execution should
not do so when running the associated tests for this function. Instead, the code that performs the HTTP request should be
replaced with a mock to simulate this.

This allows unit tests to run quickly and consistently across all environments. Developers running unit tests on their own
machines should see the same test results as a CI server.

Fast and consistent feedback is extremely important when dealing with unit tests because a slow or flaky test suite will
discourage developers from running tests and contributing more tests to the codebase.

## Anatomy of a Unit Test

Most unit tests follow the same three steps, often called **Arrange, Act, Assert**:

1. **Arrange:** build the system under test and its inputs. Give it fresh test doubles for anything slow or unpredictable.
2. **Act:** call the one method you're testing.
3. **Assert:** check the result, or the one side effect that matters.

A blank line between the three steps makes a test easy to scan. Name each test after the behavior it checks, such as `Create_with_an_email_already_in_use_throws_conflict`, so a failing test explains itself without anyone opening the file. One behavior per test keeps the failures precise: when a test fails, you know which rule broke.

### Practice: add the project status rule to projects-service, test-first

SPEC lists a gap for 3.4.2: projects can change status in any direction. The rule you'll add is that a project moves `planned` → `active` → `completed`, one step at a time and never backwards. Keeping the current status is always allowed, so a `PUT` can change other fields. An invalid move raises `ConflictError`, which the API already turns into a 409. Work on a branch, `feat/projects-status-rule`, in `projects-service/`.

The seed data gives you one project in each status: Customer Portal is `planned`, Platform Modernization is `active`, and Data Warehouse is `completed`.

1. **Write the test list** in a comment or on paper before any code: skipping from planned to completed; each backwards move; each allowed move; staying put. You'll turn one item at a time into a test.
2. **Red.** Add the first test to the end of `tests/unit/test_project_service.py`:

    ```python
    CUSTOMER_PORTAL_ID = uuid.UUID("bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb")  # planned


    def test_update_cannot_skip_from_planned_to_completed():
        service, repository = make_service()

        with pytest.raises(ConflictError, match="status"):
            service.update_project(CUSTOMER_PORTAL_ID, write(status="completed"))

        assert repository.projects[CUSTOMER_PORTAL_ID].status == "planned"
    ```

    Run it, and check it fails for the reason you expect:

    ```bash
    uv run pytest tests/unit/test_project_service.py --no-cov -q
    ```

    The output ends with `Failed: DID NOT RAISE ConflictError`. Good: the test works, and the rule is missing.

3. **Green.** In `app/services/project_service.py`, make `update_project` raise `ConflictError` with a message that mentions "status" for this one case, before it changes any field. The simplest code is a single `if`. Run the tests: all green.
4. **Red again.** Turn the backwards moves into one parametrized test, `test_update_rejects_invalid_status_moves`, with the cases (Platform, `planned`), (Data Warehouse, `active`), and (Data Warehouse, `planned`). Use [`@pytest.mark.parametrize`](https://docs.pytest.org/en/stable/how-to/parametrize.html). Run it: the three new cases fail.
5. **Green.** A pile of `if` statements doesn't scale. Replace it with a table that says where each status may go, and check against it:

    ```python
    ALLOWED_TRANSITIONS: dict[ProjectStatus, set[ProjectStatus]] = {
        ProjectStatus.PLANNED: {ProjectStatus.PLANNED, ProjectStatus.ACTIVE},
        ProjectStatus.ACTIVE: {ProjectStatus.ACTIVE, ProjectStatus.COMPLETED},
        ProjectStatus.COMPLETED: {ProjectStatus.COMPLETED},
    }
    ```

    In `update_project`, look up `ProjectStatus(project.status)` and raise if `data.status` isn't in its set. Import `ProjectStatus` from `app.schemas`.

6. **Guard the allowed moves.** Add `test_update_allows_forward_status_moves`, parametrized over the five allowed moves. It passes the first time you run it. A test you've never seen fail may not test anything, so break the table on purpose (remove `ProjectStatus.ACTIVE` from the planned set), watch the test fail, and put it back.
7. **Run the whole unit suite.** `test_update_can_keep_its_own_name` now fails with a `ConflictError`. It moves Platform Modernization back to `planned`, because `write()` defaults to that status. The rule is right and the old test data is wrong: pass `status="active"`.
8. **Find the test that passes for the wrong reason.** `test_update_maps_database_duplicate_to_conflict` still passes, but read it: it also moves Platform back to `planned`, so the new status check raises `ConflictError` before the fake repository's duplicate is ever reached. Pass `status="active"`, then delete the line `repository.fail_next_write_with_duplicate = True` and check that the test fails. Put the line back.
9. **Refactor.** Add a comment above the table saying what the rule is and why staying put is allowed. Update the 409 description on the `PUT` route in `app/routers/projects.py` to mention the status rule, then regenerate the committed OpenAPI file with `uv run python scripts/export_openapi.py`. `test_committed_openapi_matches_the_code` fails until you do.
10. **Run the integration tests** (Docker needed):

    ```bash
    uv run pytest -m integration --no-cov
    ```

    `test_put_replaces_every_writable_field` fails with `assert 409 == 200`, because it also moves Platform back to `planned`. Change its body and assertion to `completed`. Then add `test_put_moving_status_backwards_is_409`, which checks that a backwards move returns a 409 Problem Details body and leaves the status unchanged. That test proves the HTTP mapping, which the unit tests can't.

11. Run `uv run pytest` and `uv run ruff check --fix`, then open a pull request.

### Apply: test-drive the assignment rules

assignments-service is missing two rules from SPEC, on purpose:

- **Allocation:** the assignments of one employee that overlap in time add up to 100% at most. A request that would go over is a conflict (409).
- **End date:** when `endDate` is set, it comes after `startDate`. Otherwise the request is invalid (400), with the error on the `endDate` field.

Add both test-first. First, give assignments-service a test project.

1. **Create the test project** from employees-service's, so both services test the same way:

    ```bash
    cd assignments-service
    mkdir -p tests/AssignmentsService.Tests
    cp ../employees-service/tests/EmployeesService.Tests/EmployeesService.Tests.csproj \
      tests/AssignmentsService.Tests/AssignmentsService.Tests.csproj
    ```

    In the copy, point the `ProjectReference` at `..\..\src\AssignmentsService\AssignmentsService.csproj`. Then add it to the solution with `dotnet sln AssignmentsService.slnx add tests/AssignmentsService.Tests/AssignmentsService.Tests.csproj`. Until the project has a test, `dotnet test` exits with code 8, which means "zero tests ran".

2. **Add the test helpers** under `tests/AssignmentsService.Tests/`:
    - `TestData.cs`: the seed IDs from SPEC that the tests share: Ada and Grace from employees-service, and the three projects.
    - `Fakes/InMemoryAssignmentStore.cs`: an `IAssignmentStore` backed by a dictionary. Model it on employees-service's [`InMemoryEmployeeStore`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/Fakes/InMemoryEmployeeStore.cs): a lock, copies in and out, `ConflictException` when the employee and project pair is taken, and results ordered by `StartDate`.
    - `Fakes/FakeEventPublisher.cs`: copy employees-service's, and change the namespace.
    - Two stubs, `StubEmployeesClient` and `StubProjectsClient`, whose `ExistsAsync` always returns `true`. The next page replaces them with proper fakes.
    - `Features/Assignments/ServiceTestContext.cs`: an abstract base class that creates all of the above and `new AssignmentService(Store, Employees, Projects, Events, TimeProvider.System)`, plus a `Request(...)` helper with defaults for every field. xUnit creates a new test class instance for every test, so each test gets fresh fakes.

3. **Write the test list.** Put it in a comment at the top of `Features/Assignments/AssignmentRulesTests.cs`:
    - 60% and then 40% on two overlapping assignments is fine, but 60% and then 41% is a conflict;
    - assignments that don't overlap don't count against each other;
    - date ranges are inclusive, so sharing one day is an overlap;
    - a missing `endDate` means open-ended, which overlaps everything after the start;
    - other employees' allocations don't count;
    - updating an assignment doesn't count its own old allocation;
    - an `endDate` before, or on, the `startDate` is invalid, and one day after is fine;
    - the `endDate` rule applies to updates too.
4. **Red.** Write the over-100% test first:

    ```csharp
    [Fact]
    public async Task Overlapping_assignments_over_100_percent_are_a_conflict()
    {
        await Service.CreateAsync(Request(projectId: TestData.Platform, allocation: 60), Ct);

        await Assert.ThrowsAsync<ConflictException>(
            () => Service.CreateAsync(Request(projectId: TestData.Portal, allocation: 41), Ct));
    }
    ```

    Run `dotnet test --filter-class "*AssignmentRulesTests"`. It fails with `Assert.Throws() Failure: No exception was thrown`.

5. **Green.** In `AssignmentService`, add a private `EnsureAllocationFitsAsync(request, exceptId, ct)` and call it from `CreateAsync` after the duplicate check. It lists the employee's assignments with `store.ListAsync(request.EmployeeId, projectId: null, ct)`, sums the allocations of those that overlap the requested dates, adds the new one, and throws `ConflictException` if the total is over 100. Two inclusive ranges overlap when each starts on or before the other ends:

    ```csharp
    private static bool Overlaps(DateOnly startA, DateOnly? endA, DateOnly startB, DateOnly? endB) =>
        startA <= (endB ?? DateOnly.MaxValue) && startB <= (endA ?? DateOnly.MaxValue);
    ```

6. **Repeat** for every item on the list, one test at a time. Some tests pass the moment you write them, such as "exactly 100% is fine". Keep them: they pin the boundary. Break the code briefly (change `> 100` to `>= 100`) to see them fail. The update test drives the `exceptId` parameter: `UpdateAsync` passes the assignment's own ID, so its old allocation is left out of the sum.
7. **The end-date rule.** Its first test asserts that `CreateAsync` throws `RequestValidationException` and that `ex.Errors.Keys` is exactly `["endDate"]`. Make it pass with an `EnsureEndDateAfterStartDate(request)` check that runs first in both `CreateAsync` and `UpdateAsync`. It needs no I/O, so a bad request fails before any call to another service.
8. **Refactor.** Update the class comment on `AssignmentService` to list every rule it enforces, and add a one-line comment on each new method saying why it exists. Run the whole suite with `dotnet test` after each change.
9. **Try it through the API.** Rebuild with `docker compose up --build -d assignments-service`. Create an assignment for an employee with 60% allocation and no `endDate`, then a second one on another project at 50%. The second returns 409, with your message saying the employee would be over 100%. A request with `"endDate"` before `"startDate"` returns 400 with `errors.endDate`.
10. Open a pull request. In its description, paste the list from step 3 and tick each item.
