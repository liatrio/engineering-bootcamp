# Feature Flags

A feature flag is, in the words of [OpenFeature](https://openfeature.dev/docs/reference/intro/), "an if/else statement that can be controlled at runtime". The code for both branches ships to production, and a setting outside the code decides which one runs, for everyone or for particular users.

## Deploy Is Not Release

Without flags, deploying code and releasing a feature are the same event: the moment new code reaches production, every user gets it. Flags separate the two:

- **Deploy** puts new code into production. With the flag off, nobody sees a difference.
- **Release** turns the feature on, for a few users first, then for everyone, when the team or the business is ready.

That separation is what makes small, frequent changes safe. Teams practicing [trunk-based development](https://dora.dev/capabilities/trunk-based-development/) merge unfinished work into the main branch every day and deploy it switched off. A risky change can go to internal users first, then a small percentage of customers, while the team watches its metrics. And if something goes wrong, turning a flag off takes seconds, while rolling back a deployment can take much longer.

## How a Flag Is Evaluated

Every flag check in your code names a flag and supplies a default:

```python
if client.get_boolean_value("sorted-users", False):
    users = sorted(users, key=lambda u: u["name"])
```

| Part | What it is |
| --- | --- |
| Flag key | The flag's name, here `sorted-users` |
| Default value | What your code uses when the flag can't be evaluated, here `False` |
| Variants | The values a flag can return, such as `on: true` and `off: false`, or several strings for an experiment |
| Evaluation context | Facts about the current request, such as a user ID or plan, that rules can use |
| Targeting rules | Logic that picks a variant from the context, such as "beta users get `on`" or "10% of users get `on`" |

A **flag management system** stores the flags and their rules, and evaluates them when your code asks. In this section you'll use [flagd](https://flagd.dev/), a small open-source flag service that reads flags from a JSON file, through [OpenFeature](3-application-development/3.4.3-openfeature.md), a vendor-neutral API for feature flags.

## The Cost of Flags

Flags aren't free. Every flag adds a branch to your code, and every combination of flags is a configuration you might have to test. Flags that outlive their purpose pile up as dead code that nobody dares delete. Pete Hodgson's [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) article, the standard reference on the topic, recounts how Knight Capital Group lost $460 million partly through mismanaged flags. [Flag Types](3-application-development/3.4.1-flag-types.md) covers how to keep that cost down.

## Exercise: Ship a Feature Behind a Flag

The exercises in this section build on each other, using the same [layered Flask app](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/layered-architecture/example2) as the testing and observability exercises. Work in your copy from the [Observability exercises](3-application-development/3.3-observability.md#exercise-set-up-the-stack) if you have it, or copy `examples/layered-architecture/example2` into a new directory and create a virtual environment.

The new feature: `GET /users` should return users sorted by name. You'll deploy it switched off, then release it.

1. In the app's directory, create `flags/flags.flagd.json` with one flag, switched off:

    ```json
    {
      "$schema": "https://flagd.dev/schema/v0/flags.json",
      "flags": {
        "sorted-users": {
          "state": "ENABLED",
          "variants": { "on": true, "off": false },
          "defaultVariant": "off"
        }
      }
    }
    ```

2. Start flagd, serving that file on port 8013. flagd watches the file, so changes take effect without a restart:

    ```bash
    docker run --rm -d --name flagd -p 8013:8013 -v "$(pwd)/flags:/flags" \
      ghcr.io/open-feature/flagd:latest start --uri file:/flags/flags.flagd.json
    ```

3. Install the OpenFeature SDK and its flagd provider, then create `app/flags.py` to connect them. The provider talks to flagd on `localhost:8013` by default:

    ```bash
    pip install openfeature-sdk openfeature-provider-flagd
    ```

    ```python
    from openfeature import api
    from openfeature.contrib.provider.flagd import FlagdProvider

    api.set_provider(FlagdProvider())
    client = api.get_client()
    ```

4. In `app/services/user_service.py`, import `client` from `..flags` and wrap the new behavior in `get_users` with the flag check shown in [How a Flag Is Evaluated](#how-a-flag-is-evaluated).
5. Start the app with `flask --app app run --port 5001 --no-reload`, or under `opentelemetry-instrument` as in the Observability exercises. Then add a user whose name sorts first:

    ```bash
    curl -X POST -H 'Content-Type: application/json' -d '{"name":"Aaron"}' localhost:5001/users
    curl localhost:5001/users
    ```

    Aaron is last. The new code is deployed, but the feature isn't released.

6. Release it: change `defaultVariant` to `"on"` and save the file. Request the users again within a few seconds. Aaron is first, and you didn't restart or redeploy anything.

Keep flagd and the flag running for the next exercise. When you're finished with the whole section, stop flagd with `docker stop flagd`.

- Explain the difference between deploying and releasing, using what you did in this exercise.
