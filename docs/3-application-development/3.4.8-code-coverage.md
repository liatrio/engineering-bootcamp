# Code Coverage

Code coverage measures which parts of your code ran while the tests ran. A coverage tool instruments the code, runs the suite, and reports, per file, which lines and branches were executed and which weren't. It's the cheapest way to find code that no test touches at all.

## What Coverage Measures

- **Line coverage:** the share of executable lines that ran at least once.
- **Branch coverage:** the share of decision outcomes that ran. `if (x) { ... }` has two outcomes, true and false. A test that only ever passes `x = true` covers every line and half the branches.
- **Method coverage:** the share of methods called at least once. Coarse, but a 0% method is a loud signal.

Every language in the Company app has a tool for this:

| Service | Tool | How it runs |
| --- | --- | --- |
| projects (Python) | [coverage.py](https://coverage.readthedocs.io/) through [pytest-cov](https://pytest-cov.readthedocs.io/) | `uv run pytest`, configured in `pyproject.toml` |
| employees, assignments (.NET) | [coverlet](https://github.com/coverlet-coverage/coverlet) (`coverlet.MTP`) | `dotnet test --coverlet` |
| notifications (Go) | Built into the toolchain | `go test -cover ./...` |
| web (TypeScript) | Vitest's coverage providers | `npx vitest run --coverage` |

### What coverage doesn't tell you

Coverage says a line *ran*, not that anything *checked* it. A test that calls a method and asserts nothing covers every line in it. That makes coverage useful in one direction only:

- **Low coverage is a reliable signal.** Code that never runs in a test is untested, full stop.
- **High coverage is not proof of good tests.** It's possible to reach 100% with tests that would pass whatever the code returned.

## Why 100% Isn't the Goal

Chasing the last few percent costs more than it returns:

- **Diminishing returns.** The final lines are usually the hardest to reach: startup code, defensive branches for "can't happen" cases, framework glue. Testing them takes elaborate setup and catches little.
- **It distorts the tests.** When a number becomes the target, people write tests to move the number: tests of getters, tests without assertions, tests coupled to implementation details. Those tests break on every refactor and protect nothing.
- **Not all code carries the same risk.** An untested business rule is dangerous. An untested log line is not. A single percentage hides the difference.

Use coverage as a **floor and a flashlight** instead:

- A **gate** (a threshold the build must meet, such as 80% of lines) stops coverage sliding as the code grows. Teams often ratchet it: raise it when real coverage settles above it, never lower it to get a change through.
- The **report** shows you where to look. Read the uncovered lines and ask "would a bug here hurt?" Test those first.

## Exercise

### Example: the coverage gate in projects-service

Open [`projects-service/pyproject.toml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/pyproject.toml) and find the two settings that make coverage part of every test run:

- `addopts = "--cov=app --cov-report=term-missing"` under `[tool.pytest.ini_options]` measures the `app` package on every `uv run pytest` and prints the lines each file is missing.
- `fail_under = 80` under `[tool.coverage.report]` fails the run if total line coverage is below 80%.

Run the full suite (it needs Docker, for Testcontainers) and read the table it prints:

```bash
cd projects-service
uv run pytest
```

The last lines say `Required test coverage of 80.0% reached. Total coverage: 93...%`. Now run only the unit tests, the way you would while writing code:

```bash
uv run pytest tests/unit --cov-fail-under=0
```

Total coverage drops, because the routers and the repository only run in the integration tests. A gate measures one suite: here it's the whole suite, which is why CI runs everything.

For .NET, the starter's test projects run on [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro) (see `"runner"` in `global.json`). That platform uses `coverlet.MTP`, which adds `--coverlet-*` options to `dotnet test`. The older `coverlet.collector` and `--collect:"XPlat Code Coverage"` belong to VSTest and don't apply here. employees-service has no coverage tool yet; in the Apply step you add one to `assignments-service`.

### Practice: cover the untested branch in projects-service

The projects-service suite passes its 80% gate, yet one error branch in the service layer never runs.

1. Branch: `git switch -c test/projects-coverage-gap`.
2. Run `uv run pytest` and find the row for `app/services/project_service.py`. Its **Missing** column lists one line.
3. Open the file at that line. It's the `raise` in `update_project` that fires when you rename a project to a name another project already has. Creating a duplicate is tested; renaming into one isn't.
4. In `tests/unit/test_project_service.py`, add a test that updates the Platform Modernization project (`PLATFORM_ID`) with the name of another seeded project in a different case, such as `"DATA warehouse"`, and expects a `ConflictError` matching `"already exists"`. Use the existing `make_service()` and `write()` helpers, and keep `status="active"` so the status rule from 3.4.2 doesn't fire first.
5. In `tests/integration/test_projects_api.py`, add the same case through HTTP: `PUT /api/projects/{PLATFORM_ID}` with the name `"customer portal"` returns a 409 Problem Details. The file's `assert_problem` helper checks the shape.
6. Run `uv run pytest` again. `project_service.py` shows 100% and an empty **Missing** column.
7. Look at what's still missing elsewhere in the report. Pick one line you would *not* write a test for, and write down why.
8. Commit, push, and open a pull request.

### Apply: a coverage gate for assignments-service

Your M3 suite tests the rules, the endpoints, the store, and the contracts. This step measures how much of the service that actually reaches, then closes the riskiest gaps.

1. **Add coverlet.** From `assignments-service/tests/AssignmentsService.Tests/`:

    ```bash
    dotnet add package coverlet.MTP --version 10.1.0
    ```

    Add `TestResults/` to `assignments-service/.gitignore`: reports are build output, not source.

2. **Measure.** From `assignments-service/`, with Docker running:

    ```bash
    dotnet test --coverlet --coverlet-output-format cobertura \
      --coverlet-include "[AssignmentsService]*" \
      --coverlet-exclude-by-file "**/Migrations/*.cs"
    ```

    `--coverlet-include` measures only the service, not the test project or third-party code. Migrations are excluded because EF Core generates them. The report lands in `TestResults/coverage.cobertura.<id>.xml`.

3. **Read the report.** The XML is hard to read, so turn it into HTML with [ReportGenerator](https://reportgenerator.io/):

    ```bash
    dotnet tool install --global dotnet-reportgenerator-globaltool
    reportgenerator -reports:"TestResults/coverage.cobertura.*.xml" \
      -targetdir:TestResults/report -reporttypes:"Html;TextSummary"
    ```

    Open `TestResults/report/index.html`, or read `Summary.txt`. The reference M3 code measures about **60%** of lines. The features are well covered; the 0% rows are infrastructure: the `employee.deleted` consumer, the RabbitMQ publisher and connection, the auth-forwarding handler, and parts of the HTTP client setup.

4. **Decide what to test.** As a team, sort the uncovered classes into "a bug here would hurt" and "a bug here would be obvious or harmless". The consumer that deletes an employee's assignments, and the publisher that sends `assignment.created`, belong in the first group: today only a manual run or the E2E test exercises them.
5. **Close the gaps.** Split the work:
    - **Typed clients (unit).** Test `EmployeesClient` and `ProjectsClient` with a stub `HttpMessageHandler` that returns a canned response: 200 means the ID exists, 404 means it doesn't, any other status or a connection failure throws `DependencyUnavailableException`. Add a case for the auth token: forwarded when `AUTH_TOKEN` is set, absent when it isn't.
    - **RabbitMQ (integration).** Add `Testcontainers.RabbitMq` (version 4.16.0, like the PostgreSQL package) and a fixture that starts one broker per test class. Test that a published event arrives as a persistent JSON envelope with the event type as its routing key, that an `employee.deleted` message removes that employee's assignments, and that the readiness check is healthy when the broker is up. Mark the class `[Trait("Category", "Integration")]` like your database tests.
6. **Add the gate.** Rerun the step 2 command with these two options on the end:

    ```bash
    --coverlet-threshold 80 --coverlet-threshold-type line
    ```

    The reference M4 code reaches about 90%. Then raise the threshold to 95 and run it again to see what a failing gate looks like.

    > [!IMPORTANT]
    > A missed threshold shows up only as `error: 1` in the summary and exit code 14, with every test passing. The message `Coverage thresholds not met` is only in the diagnostic log (`--diagnostic`). If `dotnet test` fails with no failed tests, check the coverage gate first. Put the threshold back to 80.

7. **Write it down.** Add the gate command to the **Commands** table in `AGENTS.md`, and add a **Quality gates** section to `docs/assignments-test-plan.md` saying what the gate measures, what it excludes, and that it exists to stop coverage sliding, not to reach 100%.
8. Open the pull request. CI runs this gate from 3.4.10 onwards.

> [!TIP]
> Compare with M4's [`AssignmentsService.Tests.csproj`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/assignments-service/tests/AssignmentsService.Tests/AssignmentsService.Tests.csproj), [`Infrastructure/DependencyClientTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/assignments-service/tests/AssignmentsService.Tests/Infrastructure/DependencyClientTests.cs), [`Infrastructure/RabbitMqTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/assignments-service/tests/AssignmentsService.Tests/Infrastructure/RabbitMqTests.cs), and the *Quality gates* section of [`docs/assignments-test-plan.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/docs/assignments-test-plan.md).
