# Building a Service

In 3.2 your team designed `assignments-service`. In this section you build it. By the end, the Assignments page in the web app lists, creates, and deletes real assignments, the service checks with employees-service and projects-service that every ID exists, and it takes part in the app's events.

You won't invent the patterns. `employees-service` already shows every one of them in .NET, and your job is to understand each pattern well enough to reproduce it, adapt it, and explain why it's there.

## What M2 Is

Milestone **M2** is a working `assignments-service` that meets the Assignments contract in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md):

| Request | Result |
| --- | --- |
| `GET /api/assignments?employeeId=&projectId=` | 200; both filters optional |
| `GET /api/assignments/{id}` | 200, or 404 |
| `POST /api/assignments` | 201 with `Location`. 400 for an invalid body or an unknown `employeeId` or `projectId`. 409 if that employee is already on that project. 503 if employees-service or projects-service can't answer. |
| `PUT /api/assignments/{id}` | 200; the same checks as `POST`, plus 404 |
| `DELETE /api/assignments/{id}` | 204, or 404 |
| `GET /healthz`, `GET /readyz` | Alive; ready when PostgreSQL and RabbitMQ are reachable |

It also publishes `assignment.created` after each insert, and removes an employee's assignments when it hears `employee.deleted`.

M2 has **no tests and no telemetry yet**. Those come in 3.4 and 3.5, when the service is already there to test and instrument.

> [!NOTE]
> The reference for the end of this section is [`milestones/M2-assignments-mvp/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M2-assignments-mvp). Each page tells you which of its files that page builds. Compare after you've written your own version, not before: the point is to practice the decisions.

Each page adds one layer, and the service runs at the end of every page. You never spend a week on code that can't be called.

Every page follows the loop from the [chapter overview](3-application-development/3.0-overview.md#how-each-section-works): read the theory, see it in the starter, close a small gap in a starter service on your own (Practice), then build the same thing into `assignments-service` with your team (Apply).

## Splitting the Work

Practice steps are individual: every apprentice does every one, in their own branch, and the team merges one of them. Apply work is shared. The pages build on each other, so the team moves through them together, but inside a page the work splits cleanly by slice:

| Page | One way to split the Apply work |
| --- | --- |
| 3.3.1 | One person scaffolds and opens the pull request; everyone else reviews it and gets it running locally |
| 3.3.2 | DTOs and validation / the controller and status codes / the error foundation and OpenAPI |
| 3.3.3 | The entity and store / the service refactor / the registrations |
| 3.3.4 | Entity configuration and migration (the migration owner) / the EF Core store / readiness check |
| 3.3.5 | The two clients / resilience and error mapping / the service checks |
| 3.3.6 | Publishing / the consumer |

Two files cause most merge conflicts in a .NET service:

- **`Program.cs`.** Every new capability adds a registration, so every slice wants to edit it. Name one **Program.cs owner** per page. Others add their line in a small pull request, rebase on `main` just before merging, and keep the registrations grouped under the same comments employees-service uses.
- **EF Core migrations.** Each migration also rewrites `Migrations/<Context>ModelSnapshot.cs`. Two branches that both add a migration conflict in that file, and a hand-merged snapshot is a broken snapshot. Name one **migration owner** per milestone. If a conflict happens anyway, delete your branch's migration, rebase, and generate it again.

> [!TIP]
> Merge often. Small pull requests that each leave the service running are easier to review and much easier to rebase than one large "assignments" pull request at the end.

## Keep employees-service Open

Put `employees-service` next to your editor for the whole section. Your team's `AGENTS.md` already says "New .NET code copies `employees-service`", and that's what you'll do: copy a file, change the names, then read every line and make sure you can say why it's there. Copying without reading is how teams end up with code nobody can change.

The same goes for coding agents. An agent that has your `AGENTS.md` and the employees-service folder will produce code that looks right. You still have to judge whether it is, and this section gives you the knowledge to do that.

## Exercise: Plan the M2 Work

Do this as a team, before anyone writes code.

1. Read the M2 table above and the Assignments design in your `docs/assignments-design.md`. Note anything in your design that the SPEC contract now settles differently, and fix the design in a small pull request.
2. Create one GitHub issue per page (3.3.1 to 3.3.6), each with a checklist of its Apply slices from the table above. Create one more issue for the Practice steps, with a checkbox per apprentice per Practice.
3. Decide, and write in each issue:
    - who owns `Program.cs` for that page;
    - who owns EF Core migrations for the whole milestone;
    - the branch name for each slice, following your `<type>/<slug>` convention, for example `feat/assignments-scaffold` or `feat/assignments-crud`.
4. Agree on one rule for `main`: after every merge, `docker compose up --build -d` still starts the whole app. Add it to the **Rules** section of `AGENTS.md`.
5. Make sure every teammate has a .NET toolchain before 3.3.1: either the [dev container](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/.devcontainer/devcontainer.json) or the .NET 10 SDK installed locally. [3.3.1](3-application-development/3.3.1-scaffolding-a-web-api.md#install-the-net-sdk) has the steps.

## Deliverables

- Seven GitHub issues for M2: one per page and one for Practice, with owners and branch names.
- A named Program.cs owner per page and one migration owner for the milestone, written down where the team will see them.
- The "app still starts after every merge" rule in your `AGENTS.md`.
- Discuss with your team: which parts of the Assignments contract depend on another service being up, and which don't? Keep the answer; 3.3.5 asks it again.
