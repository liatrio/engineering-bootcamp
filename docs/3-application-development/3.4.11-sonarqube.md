# SonarQube

[SonarQube](https://www.sonarsource.com/products/sonarqube/) is a static analysis platform. It reads your source code, without running it, and reports bugs, security vulnerabilities, security hotspots (code a person should review for security), code smells (maintainability problems), and duplication. It also imports the coverage reports your test runs produce and shows them next to the code. It supports C#, Python, Go, TypeScript, and many more languages, so one dashboard can cover the whole Company app.

![SonarQube image](img/sonarqube_dark.svg ':size=400px :class=dark-mode-img-center :alt= SonarQube image; dark mode')

## How It Fits With What You Have

You already have linters and analyzers from [3.4.9](3-application-development/3.4.9-code-styling.md) and a coverage gate from [3.4.8](3-application-development/3.4.8-code-coverage.md). SonarQube adds three things they don't:

- **Deeper rules,** including security rules that trace data through several methods, such as user input that reaches a SQL string.
- **History.** It keeps every analysis, so you can see whether quality is improving or sliding, per project and per pull request.
- **A quality gate on new code.** Sonar's default gate, *Sonar way*, judges only the code changed since a baseline: new code must have no new issues above a severity, enough coverage (80% by default), and little duplication. Old code doesn't block you, but nothing new adds to the pile. This is the "clean as you code" approach.

## Editions

- **SonarQube Server** is self-hosted. The free **Community Build** runs in Docker and is enough to learn with.
- **SonarQube Cloud** (formerly SonarCloud) is the hosted service. It signs in with GitHub, decorates pull requests with its results, and is free for public repositories. Check the current plans for private ones.

Both use the same rules and the same scanners.

## How Analysis Works

A **scanner** runs on your machine or the CI runner, analyzes the code, and uploads the results to the server, which applies the quality gate. For most languages that's the generic [SonarScanner CLI](https://docs.sonarsource.com/sonarqube-server/latest/analyzing-source-code/scanners/sonarscanner/), configured by a `sonar-project.properties` file or `-D` options. C# is different: the [SonarScanner for .NET](https://docs.sonarsource.com/sonarqube-cloud/advanced-setup/ci-based-analysis/sonarscanner-for-dotnet/) wraps your build in three steps, because it needs the compiler's view of the code:

1. `dotnet sonarscanner begin` with the project key and settings.
2. `dotnet build`, which the scanner observes.
3. `dotnet sonarscanner end`, which analyzes and uploads.

SonarQube never runs your tests. Coverage comes from a report your test run already wrote, and if the scanner can't find it, every line counts as uncovered and the coverage shows 0%.

### Practice: scan projects-service on a local SonarQube

1. Start SonarQube. It runs Elasticsearch inside and needs about 2 GB of memory, so stop the Company app first with `docker compose down`:

    ```bash
    docker run -d --name sonarqube -p 9000:9000 sonarqube:community
    ```

2. Open [http://localhost:9000](http://localhost:9000) once `docker logs sonarqube` says `SonarQube is operational`. Sign in as `admin` / `admin` and choose a new password.
3. Create a project **manually**, with the display name and key `projects-service`. Choose **Locally** as the analysis method, generate a token, and keep it for the next step.

    ![SonarQube create project](img/sonarqube-create-project.png ':class=img-shadow-center :alt= SonarQube create project')

    ![SonarQube name project](img/sonarqube-name-project.png ':class=img-shadow-center :alt= SonarQube name project')

4. Scan with the SonarScanner CLI image. From `projects-service/`:

    ```bash
    docker run --rm -v "$PWD":/usr/src \
      -e SONAR_HOST_URL=http://host.docker.internal:9000 -e SONAR_TOKEN=<your token> \
      sonarsource/sonar-scanner-cli \
      -Dsonar.projectKey=projects-service -Dsonar.sources=app -Dsonar.tests=tests \
      -Dsonar.python.version=3.13
    ```

    On Linux, add `--add-host=host.docker.internal:host-gateway` after `--rm`.

5. Open the project in SonarQube and look at:
    - the **quality gate** result, and the conditions it checked;
    - **Issues**: pick one and read the rule's explanation. Would ruff or a reviewer have caught it?
    - **Security Hotspots**: what is it asking a person to review, and is it safe?
    - **Coverage**: 0%. Explain why in one sentence.
6. Stop it with `docker rm -f sonarqube`.

### Apply: SonarQube Cloud for assignments-service, with coverage

Do this with the person who owns the CI workflow from 3.4.10.

1. **Create the project.** Sign in to [SonarQube Cloud](https://sonarcloud.io) with GitHub, import your team's GitHub organization or account, and create a project for the team repository. Note the **project key** and **organization key** it shows.
2. **Switch to CI-based analysis.** In the project's **Administration → Analysis Method**, turn off **Automatic Analysis**. Only an analysis run from CI can import your coverage report, and a CI analysis fails while Automatic Analysis is on.
3. **Add the token.** Generate a token under **My Account → Security**, and save it as a repository secret named `SONAR_TOKEN` (**Settings → Secrets and variables → Actions**).
4. **Write `sonar-project.properties`** at the repository root: `sonar.projectKey`, `sonar.organization`, `sonar.host.url=https://sonarcloud.io`, a `sonar.projectName`, `sonar.exclusions=**/Migrations/**,**/bin/**,**/obj/**`, and `sonar.cs.opencover.reportsPaths`. Add a header comment saying the CI step reads it, since the .NET scanner doesn't read the file itself.
5. **Produce an OpenCover report.** Sonar reads OpenCover for C#. In the `assignments` job's coverage step, ask coverlet for both formats: `--coverlet-output-format opencover --coverlet-output-format cobertura`.

    > [!IMPORTANT]
    > coverlet adds an ID to each report's file name, such as `coverage.opencover.131126193755869.xml`. A path of `TestResults/*.opencover.xml` matches nothing, and Sonar shows 0% without an error. Use `TestResults/coverage.opencover.*.xml`.

6. **Add the analysis step** to the end of the `assignments` job, after the tests:
    - give the checkout `fetch-depth: 0`, because Sonar uses history to work out what counts as new code;
    - run it only `if: env.SONAR_TOKEN != ''`, with the secret in the step's `env`, so forks and teammates without the secret still get a green build;
    - install the scanner with `dotnet tool install --global dotnet-sonarscanner`, pinned to a version;
    - run `dotnet sonarscanner begin` with `/k:`, `/o:`, `/d:sonar.host.url=`, `/d:sonar.token=`, the exclusions, and `/d:sonar.cs.opencover.reportsPaths=`, reading the values from `../sonar-project.properties`;
    - run `dotnet build --no-incremental`, then `dotnet sonarscanner end /d:sonar.token="$SONAR_TOKEN"`.
7. **Run it.** Open a pull request. When the job finishes, SonarQube Cloud comments on the pull request with the quality gate result. Open the project and check that its coverage matches coverlet's, about 90% on the reference code. If it shows 0%, the scanner didn't find the report: search the step's log for `opencover`.
8. **Triage.** As a team, go through the issues on the overall code. Fix the real ones in small pull requests. For each one you disagree with, mark it as *Accept* or *False positive* in SonarQube Cloud with a comment saying why.

> [!TIP]
> Compare with M4's [`sonar-project.properties`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/sonar-project.properties) and the **SonarQube analysis** step in its [`ci.yml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/.github/workflows/ci.yml).
