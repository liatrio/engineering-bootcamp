# Logging

A log is a timestamped record of something that happened: a request arrived, a user was created, a payment failed. Logs are the oldest and most familiar signal, and the one with the most detail about a single event. They are also the easiest to get wrong: too little, and you can't diagnose a problem; too much, and the one line that matters is buried in noise, or a password ends up in your log storage.

## Structured Logging

Traditional logs are free-form text:

```text
2026-11-05 14:02:11 WARNING Rejected user create from 10.0.0.7: name required
```

That is easy for a person to read, but hard for a machine to search: to find every rejection for one reason, you have to write a regular expression and hope the wording never changes. **Structured logs** record each event as a message plus named fields, usually as JSON:

```json
{"time": "2026-11-05T14:02:11Z", "level": "WARN", "message": "user rejected",
 "reason": "name_required", "trace_id": "0018e076ca831ac13d6cc6a59bb5bf7e"}
```

Now you can filter by `reason`, count by `level`, and jump straight to the request's trace through `trace_id`. Keep the message short and constant ("user rejected"), and put the variable parts in fields.

## Log Levels

Levels let you separate routine events from problems, and turn the volume up or down without changing code:

| Level | Use it for |
| --- | --- |
| `DEBUG` | Detail that's only useful while developing or diagnosing a specific problem. Usually off in production. |
| `INFO` | Normal, significant events: a user was created, a job finished. |
| `WARNING` | Something unexpected that the application handled, such as a rejected request or a retried call. |
| `ERROR` | An operation failed and needs attention. |
| `CRITICAL` | The application can't continue. |

If you log something at `ERROR`, someone should eventually need to act on it. A level that cries wolf trains people to ignore it.

## Good Logging Practices

- **Write logs to standard output** and let the platform collect them. [The Twelve-Factor App](https://12factor.net/logs) puts it this way: "each running process writes its event stream, unbuffered, to `stdout`." Containers, Kubernetes, and log agents all expect this.
- **Correlate logs with traces.** Include the trace ID in every log line written during a request, so you can move from a log to the full request and back. OpenTelemetry does this for you.
- **Never log secrets or sensitive data.** The [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) lists data that should usually not be recorded directly in logs, including passwords, access tokens, session IDs, database connection strings, encryption keys, payment card data, and sensitive personal data. Logs are copied, shipped, and retained far more widely than databases.
- **Log events, not every line of code.** Log what happened and the context needed to understand it, once, at the place where it's handled. An exception logged at every layer it passes through appears five times and helps no one.
- **Use metrics for counting.** If you mostly want to know *how many* times something happened, a [metric](3-application-development/3.3.2-metrics.md) is far cheaper than searching millions of log lines.

## Exercise: Structured Logs

This exercise continues from the [Observability exercise](3-application-development/3.3-observability.md#exercise-set-up-the-stack), with the stack and the instrumented app running.

1. So far the only logs are Flask's request logs. Add application logs to `app/services/user_service.py`: create a logger with `logging.getLogger(__name__)`, then:
    - log `user created` at `INFO` when a user is created, with the new user's ID as a field;
    - log `user rejected` at `WARNING` when validation fails, with the reason as a field.

    In Python, fields go in the `extra` argument: `logger.warning("user rejected", extra={"reason": "name_required"})`. OpenTelemetry exports each `extra` key as a log attribute.
2. Restart the app and generate traffic. You'll see your warnings in Loki, but not the `INFO` lines. Python's root logger only passes `WARNING` and above by default. Fix it by setting your application's logger level in `create_app` in `app/__init__.py`: `logging.getLogger("app").setLevel(logging.INFO)`.
3. In Grafana Explore, query Loki for your application logs only, for example `{service_name="user-api"} |= "user rejected"`. Expand a log line and find the `reason`, `trace_id`, and `span_id` attributes. You didn't add those IDs yourself: the OpenTelemetry logging instrumentation attaches the current trace context to every record.
4. Copy a `trace_id` from a rejected request, then search for that trace ID in Tempo. Confirm it's the request that produced the log.
