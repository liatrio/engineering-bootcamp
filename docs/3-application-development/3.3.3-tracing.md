# Tracing

Logs tell you what happened, and metrics tell you how often. Neither tells you where the time went in one specific request, or which of ten services a failure started in. A **trace** does: it records the whole journey of one request as it passes through functions, services, databases, and queues.

## Traces and Spans

A trace is made of **spans**. Each span is one timed operation, such as handling an HTTP request, running a database query, or calling another service. A span records:

- a name, plus start and end times;
- the trace ID it belongs to, its own span ID, and its parent span's ID;
- **attributes**: key-value details such as `http.route` or `user.id`;
- a **status** (unset, OK, or error), plus **events**, such as an exception being raised.

The parent links turn the spans into a tree. Visualization tools draw the tree as a **waterfall**: one bar per span, positioned by time, so slow and failing operations stand out immediately.

```text
POST /users                                      [=================] 12 ms
  create_user                                      [=============]   10 ms
    users.add                                        [==========]     8 ms
```

See [Traces](https://opentelemetry.io/docs/concepts/signals/traces/) in the OpenTelemetry docs for the full model.

## Context Propagation

Within one process, the current span is held in a *context*, and any span you start becomes its child automatically. Across processes, the context travels with the request. For HTTP, the [W3C Trace Context](https://www.w3.org/TR/trace-context/) standard defines a `traceparent` header that carries the trace ID and parent span ID, so the receiving service continues the same trace. This is **distributed tracing**: one trace spanning every service the request touched. OpenTelemetry's HTTP instrumentation sends and reads the header for you. See [Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/).

## Automatic and Manual Spans

Instrumentation libraries create spans automatically for the frameworks you use: incoming HTTP requests, outgoing HTTP calls, database drivers, and message queues. That gives you the skeleton of every trace without writing any code.

Add **manual spans** for the operations that matter to *your* application, such as validation, business rules, or expensive computations, and add attributes that help you search: an order ID, a feature flag, a customer tier. Keep spans meaningful. A span per significant operation helps; a span per line of code is noise.

## Exercise: Manual Spans

This exercise continues from the [Metrics exercise](3-application-development/3.3.2-metrics.md#exercise-custom-metrics-and-a-red-dashboard).

1. Open a `POST /users` trace in Tempo. It has a single span from the Flask instrumentation. You can't tell how long validation took, or whether the data layer was even called.
2. Using the [OpenTelemetry tracing API](https://opentelemetry.io/docs/languages/python/instrumentation/#creating-spans), get a tracer with `trace.get_tracer(__name__)`, then add:
    - a `create_user` span around the body of `create_user` in `app/services/user_service.py`, with a `user.id` attribute once the user exists;
    - a `users.add` span around `add` in `app/data/in_memory_repo.py`.

    Use `with tracer.start_as_current_span("name") as span:` so each new span becomes a child of the current one.
3. Restart the app, send traffic, and open a new `POST /users` trace. Check that your spans are nested under the request span, as in the waterfall above.
4. Open a trace for a rejected request. The `ValueError` is raised inside your span. Look at the span's status and events: OpenTelemetry records the exception and marks the span as an error automatically when an exception leaves a `start_as_current_span` block.
5. Simulate a slow dependency: in `add`, sleep for a random 0–300 ms (`time.sleep(random.uniform(0, 0.3))`). Rerun the traffic loop and use the trace search to find the slowest `POST /users` requests. Confirm the waterfall points straight at `users.add`. Then check your p95 panel from the Metrics exercise.
6. Remove the sleep when you're done.

### Deliverables

- Your tracing code.
- Screenshots of a nested trace waterfall, and of a failed request's span with its exception event.
- Discuss: your p95 panel showed requests got slower. How did the traces help you find out *why*, in a way the metric couldn't?
