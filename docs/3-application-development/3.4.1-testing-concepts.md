# Testing Concepts

Before learning how to write each kind of test, it helps to have a map: what kinds of tests exist, what each one is good at, and how much of each a project should have. This section introduces the vocabulary used in the rest of the chapter and two popular models for balancing a test suite: the **testing pyramid** and the **testing trophy**.

## Types of Tests

Tests are usually grouped by how much of the system they exercise.

| Type | What it checks | Speed | Example |
| --- | --- | --- | --- |
| Static | Code is well-formed and type-correct, without running it | Instant | A linter or type checker flags an undefined variable |
| [Unit](3-application-development/3.4.2-unit-testing.md) | A single function, method, or class in isolation | Milliseconds | `Add(2, 3)` returns `5` |
| [Component](3-application-development/3.4.4-component-testing.md) | One service or module through its public interface, with external dependencies replaced by test doubles | Milliseconds | `POST /users` with no name returns `400` |
| [Integration](3-application-development/3.4.5-integration-testing.md) | Your code against a real dependency, such as a database or another service | Milliseconds to seconds | A repository saves a user to a real database and reads it back |
| [Contract](3-application-development/3.4.6-contract-testing.md) | Two services agree on the requests and responses between them, each tested on its own | Milliseconds to seconds | The product API still returns every field the front end reads |
| [End-to-end](3-application-development/3.4.7-end-to-end-testing.md) | The whole application, the way a user drives it | Seconds to minutes | A browser test signs up, logs in, and places an order |

Contract tests sit slightly apart from this scale: they cover the boundary between two services rather than more or less of either one. For the other types, the further down the table, the more of the system a test covers. That brings more confidence that the system really works, but the test is also slower, harder to debug when it fails, and more likely to break for reasons unrelated to the change you made.

The boundaries are blurry. The most common disagreement is over what counts as a "unit". Some teams mean a single class with every collaborator replaced by a [test double](3-application-development/3.4.3-test-doubles.md) (a *solitary* unit test). Others let a unit use its real collaborators as long as the test stays fast and in-process (a *sociable* unit test). Neither is wrong, but a team should agree on which it means.

## The Testing Pyramid

<div class="grid2"><div class="col">

The testing pyramid comes from Mike Cohn's 2009 book *Succeeding with Agile*, and Martin Fowler's [Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html) article popularized it. It recommends:

- **Many unit tests** at the base. They are fast and cheap, and they pinpoint exactly what broke.
- **Fewer integration tests** in the middle. They check that the pieces fit together.
- **Very few end-to-end tests** at the top. They are slow and brittle, so keep them for the most important user journeys.

</div><div class="col">

![testing pyramid](img/testing-pyramid_light.svg ':size=500px :class=light-mode-img-center :alt= testing pyramid with unit tests at the wide base, integration in the middle, and end-to-end at the narrow top; light mode')
![testing pyramid](img/testing-pyramid_dark.svg ':size=500px :class=dark-mode-img-center :alt= testing pyramid with unit tests at the wide base, integration in the middle, and end-to-end at the narrow top; dark mode')

</div></div>

The shape follows from cost. A test higher up the pyramid takes longer to write, longer to run, and longer to diagnose. A suite built mostly from fast tests can run on every change, which keeps feedback quick.

The anti-pattern is the **ice-cream cone**: a suite that is mostly manual or UI-driven tests with few unit tests underneath. Fowler notes that tests run through the UI tend to be "brittle, expensive to write, and time consuming to run", so teams with an ice-cream cone run their tests rarely and find bugs late.

For a longer, hands-on treatment, read Ham Vocke's [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html).

## The Testing Trophy

<div class="grid2"><div class="col">

Kent C. Dodds proposed the [testing trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) in 2018, building on Guillermo Rauch's advice: "Write tests. Not too many. Mostly integration." From bottom to top it has four layers:

- **Static**: linters, formatters, and type checkers catch typos and type errors as you write the code.
- **Unit**: tests for individual functions and modules.
- **Integration**: tests that several units work together. This is the widest part of the trophy.
- **End-to-end**: a small number of tests that drive the whole application.

</div><div class="col">

![testing trophy](img/testing-trophy_light.svg ':size=450px :class=light-mode-img-center :alt= testing trophy with static analysis as the base, a narrow unit stem, a wide integration bowl, and a small end-to-end cap; light mode')
![testing trophy](img/testing-trophy_dark.svg ':size=450px :class=dark-mode-img-center :alt= testing trophy with static analysis as the base, a narrow unit stem, a wide integration bowl, and a small end-to-end cap; dark mode')

</div></div>

Dodds frames testing as a return on investment, where the return is confidence and the investment is time. Integration tests are weighted most heavily because they exercise code the way it is actually used, without the cost of full end-to-end tests. Unit tests that replace every collaborator with a mock can all pass while the pieces fail to fit together.

The trophy is common in front-end and JavaScript projects. Spotify's [testing honeycomb](https://engineering.atspotify.com/2018/01/testing-of-microservices) makes a similar argument for microservices, recommending a focus on integration tests with few tests of implementation details.

## Pyramid or Trophy?

The two models look like they disagree, but in [On the Diverse And Fantastical Shapes of Testing](https://martinfowler.com/articles/2021-test-shapes.html), Martin Fowler argues that most of the disagreement is about vocabulary. A fast, sociable test that the trophy calls an "integration test" is often what a pyramid advocate calls a "unit test". Both models agree on the things that matter:

- **Most tests should be fast** enough to run on every change, locally and in CI.
- **End-to-end tests should be few** and reserved for critical paths.
- **Tests should fail only when behavior breaks**, not whenever the internal structure changes.
- **Static analysis is cheap**, so use it. The [Code Styling](3-application-development/3.4.9-code-styling.md) and [Git Hooks](3-application-development/3.4.13-pre-commit.md) sections cover the tooling.

Rather than aiming for a fixed ratio of test types, ask what gives your team the most confidence for the least time. When someone talks about "unit" or "integration" tests, ask what they mean by the words.

## Further Testing Techniques

The tests in this chapter check behavior with examples that you write by hand. These techniques go further, each answering a different question. You won't need them for the bootcamp exercises, but they are worth knowing about.

### Fuzz Testing

Fuzzing feeds a program large numbers of random or mutated inputs, looking for crashes, hangs, and security holes that hand-picked examples miss.

- [Go Fuzzing](https://go.dev/doc/security/fuzz/), with a hands-on [tutorial](https://go.dev/doc/tutorial/fuzz). Fuzzing is built into `go test`.
- [OSS-Fuzz](https://google.github.io/oss-fuzz/): Google's continuous fuzzing service for open-source projects.

### Property-Based Testing

Instead of writing individual examples, you describe a property that should hold for every input ("reversing a list twice gives back the original list"), and the framework generates hundreds of inputs to try to break it. When it finds a failure, it shrinks the input to the smallest case that still fails.

- [What is Property-Based Testing?](https://hypothesis.works/articles/what-is-property-based-testing/) from the Hypothesis project.
- [Hypothesis](https://hypothesis.readthedocs.io/) for Python, and [fast-check](https://fast-check.dev/) for JavaScript and TypeScript.

### Formal Verification

Formal methods prove that a design or program is correct for *all* possible inputs and interleavings, rather than sampling some of them. They are used where bugs are very costly, such as in distributed systems, concurrency, and security.

- [Learn TLA+](https://learntla.com/), a practical introduction to the [TLA+](https://lamport.azurewebsites.net/tla/tla.html) specification language.
- [Dafny](https://dafny.org/), a programming language with built-in verification.
- [How Amazon Web Services Uses Formal Methods](https://www.amazon.science/publications/how-amazon-web-services-uses-formal-methods) (Newcombe et al., *Communications of the ACM*, 2015).

### Mutation Testing

Mutation testing checks the quality of the tests themselves. It makes small changes (mutants) to your code, such as flipping a `<` to `<=`, and checks that some test fails. A mutant that survives points to a gap in your tests that [code coverage](3-application-development/3.4.8-code-coverage.md) can't show.

- [Stryker](https://stryker-mutator.io/) for JavaScript, C#, and Scala, and [PIT](https://pitest.org/) for Java.

### Performance and Load Testing

Performance tests measure how fast the system responds, and load tests measure how it behaves under realistic or extreme traffic.

- [Grafana k6](https://grafana.com/docs/k6/latest/), which scripts load tests in JavaScript.
- [Locust](https://locust.io/), which scripts load tests in Python.

### Chaos Engineering

Chaos engineering deliberately injects failures, such as killed instances, network latency, or unavailable dependencies, into running systems to build confidence that they withstand real-world turbulence.

- [Principles of Chaos Engineering](https://principlesofchaos.org/).
- Netflix's [Chaos Monkey](https://netflix.github.io/chaosmonkey/), which randomly terminates instances in production.

### Snapshot and Approval Testing

Snapshot and approval tests capture a piece of output, such as rendered UI, a JSON response, or a report, approve it once, and fail whenever the output changes. They make large outputs easy to test, but each change needs a careful review rather than an automatic re-approval.

- [Jest snapshot testing](https://jestjs.io/docs/snapshot-testing).
- [ApprovalTests](https://approvaltests.com/), available for many languages.

## Exercise

The starter ships with tests in four languages, and every kind from the table above is in there somewhere. The rest of 3.4 builds on these suites, so start by finding your way around them.

### Example: tour the starter's test suites

Each service keeps its tests next to its code, and each one lets you run the fast tests without Docker.

| Service | Tests | Fast tests (no Docker) | Everything |
| --- | --- | --- | --- |
| [employees-service](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests) | xUnit v3: `EmployeeServiceTests` (unit), `EmployeesApiTests` (component), `EmployeesDatabaseTests` (integration) | `dotnet test --filter-not-trait "Category=Integration"` | `dotnet test` |
| [projects-service](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/tests) | pytest: `tests/unit/`, `tests/integration/`, and the Pact provider check `test_pact_provider.py` | `uv run pytest tests/unit --no-cov` | `uv run pytest` |
| [notifications-service](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal) | `go test`: a `_test.go` file beside each package, plus `consumer/integration_test.go` behind a build tag | `go test -race ./...` | `go test -tags integration ./internal/consumer/` |
| [web](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web) | Vitest with MSW (`*.test.tsx`), Pact JS (`api.pact.test.ts`), Playwright (`e2e/`) | `npm run test:unit` and `npm run test:pact` | `npm run test:e2e`, with the app running |

1. From each service folder, run the fast tests. Note roughly how long each suite takes. (`--no-cov` turns off projects-service's 80% coverage gate, which only the full suite can meet. [Code Coverage](3-application-development/3.4.8-code-coverage.md) explains it.)
2. Run the Docker suites for employees-service and projects-service. Testcontainers pulls and starts PostgreSQL, so the first run takes a while. Compare the times with step 1.
3. Open one file of each kind and read the comment at the top. Every test file in the starter says what kind of test it is and what it replaces with a double.
4. Look at how each project keeps the slow tests separate: an xUnit trait (`[Trait("Category", "Integration")]`), pytest markers (`integration`, `contract`), a Go build tag (`//go:build integration`), and separate Vitest projects. You'll use these switches in CI and in Git hooks later in 3.4.

> [!NOTE]
> .NET 10 runs xUnit v3 on Microsoft.Testing.Platform (see `global.json`), so filters are options like `--filter-not-trait` and `--filter-class`. The older `--filter "Category!=Integration"` syntax from VSTest doesn't work here.

> [!IMPORTANT]
> Testcontainers needs a Docker it can reach. The [dev container](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/.devcontainer/devcontainer.json) already sets `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`, so tests inside it reach containers through your host. projects-service's [`tests/conftest.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/tests/conftest.py) points Testcontainers at `/var/run/docker.sock`, which Docker Desktop on macOS needs. If you don't have the .NET SDK, the [employees-service README](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/README.md) shows how to run `dotnet test` in the SDK image.

### Practice: classify a set of tests

For each test below, write down:

- its type from the table at the top of this page, and a one-line reason;
- whether it is solitary or sociable;
- where it sits on the testing pyramid, and where on the testing trophy.

| # | Service | File | Test |
| --- | --- | --- | --- |
| 1 | employees | `EmployeeServiceTests.cs` | `Create_with_an_email_already_in_use_throws_conflict_and_publishes_nothing` |
| 2 | employees | `EmployeesApiTests.cs` | `Create_with_an_invalid_body_returns_400_with_field_errors` |
| 3 | employees | `EmployeesDatabaseTests.cs` | `Startup_applies_every_migration` |
| 4 | projects | `tests/unit/test_project_service.py` | `test_create_maps_database_duplicate_to_conflict` |
| 5 | projects | `tests/unit/test_openapi.py` | `test_committed_openapi_matches_the_code` |
| 6 | projects | `tests/integration/test_projects_api.py` | `test_create_duplicate_name_is_409_regardless_of_case` |
| 7 | projects | `tests/integration/test_pact_provider.py` | `test_projects_service_honours_consumer_contracts` |
| 8 | notifications | `internal/store/store_test.go` | `TestOldestIsEvictedWhenFull` |
| 9 | notifications | `internal/httpapi/httpapi_test.go` | `TestListNotificationsNewestFirst` |
| 10 | notifications | `internal/consumer/integration_test.go` | `TestConsumesFromRealRabbitMQ` |
| 11 | web | `src/features/employees/EmployeesPage.test.tsx` | `creates an employee and returns to the list` |
| 12 | web | `src/features/projects/api.pact.test.ts` | `GET /api/projects returns the list of projects` |
| 13 | web | `e2e/employees.spec.ts` | `create an employee and see it in the list` |

Some of these don't fit neatly in one box. That's expected:

- Compare 4 and 6. Both check a duplicate project name. What does each one prove that the other can't?
- Number 5 doesn't check behavior at all. Which layer of the trophy is it closest to?
- Pick one test you'd classify differently under the pyramid than under the trophy, and explain why in a sentence or two. Number 11 or number 2 is a good place to start.

Compare your answers with a teammate's and settle the disagreements.

### Apply: write the assignments test plan

Before you write any tests for `assignments-service`, decide which tests it needs and at which level. Write the plan as `docs/assignments-test-plan.md` in your team repository. Pair or mob on it: the whole team works from this plan for the rest of 3.4.

1. Open your `docs/assignments-design.md` from 3.2 and the assignments behavior table in `assignments-service/README.md`. List every rule the service enforces, including the two that 3.4.2 adds: an employee's overlapping allocations add up to 100% at most (409), and `endDate`, when set, comes after `startDate` (400).
2. Add a **Levels** table with one row per kind of test: unit, component, integration, contract (consumer), contract (provider), and end to end. For each, name the planned file, what it runs against, what it proves, and roughly how fast it is.
3. Add a **rules** table: one row per rule from step 1, and a column per level. Tick the level or levels that will test each rule. Most rules belong at one fast level, plus one slower level only where a real dependency matters, such as the database's unique index on the employee and project pair.
4. List the **fakes** you'll need, and what each must do to behave like the real thing.
5. Add **how to run** the tests, using the commands from the Example, and a **known gaps** section for anything you've decided not to test yet, with the reason.
6. Open a pull request and get a review from someone who didn't write it.

When you're done, compare your plan with the milestone's [`docs/assignments-test-plan.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/docs/assignments-test-plan.md). It doesn't need to match, but if the milestone tests a rule at a level you didn't, decide whether your plan should change. Milestone [M3-tested](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested) contains every test the rest of 3.4.1 to 3.4.7 builds.
