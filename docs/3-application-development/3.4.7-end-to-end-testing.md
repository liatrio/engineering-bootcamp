# End-to-End Testing

End-to-end (E2E) tests exercise the whole application the way a user does: through the browser, the mobile app, or the public API, against a fully deployed system with its real database and services. They sit at the top of both the [testing pyramid and the testing trophy](3-application-development/3.4.1-testing-concepts.md). Where a [unit test](3-application-development/3.4.2-unit-testing.md) checks one function and an [integration test](3-application-development/3.4.5-integration-testing.md) checks that a few parts work together, an end-to-end test checks that a complete user journey works.

That makes end-to-end tests the most realistic tests you can write, and also the slowest, the most expensive to maintain, and the hardest to debug when they fail. A failure could come from any part of the system, or from the environment itself. Keep the suite small and focused on the journeys that matter most, such as signing up, logging in, or checking out, and push everything else down to faster tests.

You may also hear these called *functional*, *UI*, or *acceptance* tests. The terms overlap, and teams use them differently.

## How to do end-to-end testing

End-to-end tests are written from a user’s perspective: you check that the system behaves the way you (and the user) expect. Since they depend so heavily on the application's use cases, how you write them varies widely. A few practices help keep them reliable:

- Test a few critical journeys end to end, rather than every edge case.
- Select elements by role, label, or test ID rather than by CSS layout, so tests survive cosmetic changes.
- Wait for the page to reach the state you expect rather than sleeping for a fixed time. Fixed sleeps are the most common cause of flaky tests.
- Give each test its own data, so tests don't depend on each other or on the order they run in.

## Tools

[Selenium](https://www.selenium.dev/) has automated browsers since 2004 and is still widely used. It drives each browser through the W3C WebDriver protocol, has bindings for most languages, and has a large ecosystem, including Selenium Grid for running tests across many machines and browsers.

[Playwright](https://playwright.dev/), from Microsoft, is newer and is what the Company app uses. It installs its own browser builds, waits automatically for elements to be ready before acting on them, and encourages locators that match what a user sees, such as `getByRole('button', { name: 'Create project' })` and `getByLabel('Name')`. Its trace viewer records every step of a failed test, with screenshots and network calls, which takes much of the pain out of debugging. Both tools are good choices; the practices above matter more than the tool.

## Exercise

End-to-end tests need the whole app running. Start it from the root of your team repository:

```bash
docker compose up --build -d
```

### Example: the starter's employee journey

1. Open [`web/e2e/employees.spec.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/e2e/employees.spec.ts). One test, one journey: open the Employees page, fill in the form, and check the new employee appears in the list. Note how it finds elements (by role and by label), and why it builds a unique name and email for every run.
2. Open [`web/playwright.config.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/playwright.config.ts). The tests run against `BASE_URL`, which defaults to the proxy at `http://localhost:8080`, and they keep a trace when a test fails.
3. Install the browser once, then run the suite from `web/`:

    ```bash
    npx playwright install chromium
    npm run test:e2e
    ```

4. Run it again with `npx playwright test --ui` and step through the journey. Then make it fail: change the expected email in the last assertion, run `npm run test:e2e`, and open the trace with `npx playwright show-trace` and the path it prints. Put the assertion back.

### Practice: add a create-a-project journey

SPEC's gap for 3.4.7: Playwright covers creating an employee, but not creating a project. Work on a branch, `test/e2e-create-project`.

1. Create the project once by hand in the UI, at <http://localhost:8080/projects>, and note the labels on each field and the text on each button.
2. Create `web/e2e/projects.spec.ts` with one test, `create a project and see it in the list`:
    - project names are unique and the database outlives the test, so build the name from `Date.now()`;
    - open `/projects`, click the `New project` link, fill in `Name`, `Description`, and `Start date`;
    - check that `Status` starts as `planned`, because the status rule from 3.4.2 means a new project starts at the beginning;
    - click `Create project`, then assert that the URL is back on `/projects` and that a row containing the name shows `planned`.
3. **Clean up after yourself.** Re-running the suite shouldn't fill the database with test projects. Add a `test.afterEach` that uses Playwright's `request` fixture to find the project by name through `GET /api/projects` and delete it with `DELETE /api/projects/{id}`. It runs even when the test fails:

    ```typescript
    test.afterEach(async ({ request }) => {
      if (!projectName) return;
      const projects: { id: string; name: string }[] = await (await request.get('/api/projects')).json();
      const created = projects.find((p) => p.name === projectName);
      if (created) await request.delete(`/api/projects/${created.id}`);
      projectName = undefined;
    });
    ```

4. Run `npm run test:e2e` twice. Both runs pass, and no test projects are left in the list.
5. Run `npm run lint` and `npm run typecheck` (the E2E code is type-checked too), then open a pull request.

> [!TIP]
> Compare with M3's [`projects.spec.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/web/e2e/projects.spec.ts).

### Apply: an end-to-end journey for the Assignments page

The web app's Assignments page was built in the starter, and has shown an error since day one, because assignments-service didn't exist. Now it does, and this journey proves the whole path works: the browser, the proxy, assignments-service, its calls to employees-service and projects-service, and PostgreSQL.

1. Rebuild everything so the stack runs your latest assignments-service: `docker compose up --build -d`.
2. Create `web/e2e/assignments.spec.ts` with one test, `assign an employee to a project and see it in the list`.
3. **Check the precondition first.** `GET /api/assignments` must return 200. If it doesn't, fail with a message that says assignments-service isn't running behind the proxy, rather than a confusing timeout on a missing button.
4. **Arrange through the API, act through the UI.** Assigning the same employee to the same project twice is a 409, and allocations from earlier runs would add up past 100%. So create a fresh employee for each run with `request.post('/api/employees', ...)`, and keep their ID. Only the journey under test goes through the browser.
5. **The journey:** open `/assignments`, click `New assignment`, pick your employee by name in `Employee`, pick Customer Portal in `Project`, fill in `Role`, `Allocation (%)`, and `Start date`, and click `Create assignment`.
6. **Assert what a user sees:** back on `/assignments`, a row with the employee's name shows the project name and the allocation. The list shows names, not IDs, because the page looks them up from employees-service and projects-service. Use `exact: true` when you match the `Customer Portal` cell, because the row's Delete button also mentions the project.
7. **Clean up** in `afterEach`: delete the employee's assignments through `/api/assignments?employeeId=`, then the employee.
8. Run the whole suite twice. Then stop assignments-service with `docker compose stop assignments-service`, run it once more, and read the failure message from step 3. Start it again.
9. Open a pull request. Add a row for this journey to `docs/assignments-test-plan.md` if it isn't there.

> [!TIP]
> Compare with M3's [`assignments.spec.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/web/e2e/assignments.spec.ts). Milestone [M3-tested](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested) is the whole of 3.4.1 to 3.4.7: overlay it on the starter to see every test from this part of the chapter working together.
