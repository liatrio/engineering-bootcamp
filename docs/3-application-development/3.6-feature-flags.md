# Feature Flags

A feature flag is, in the words of [OpenFeature](https://openfeature.dev/docs/reference/intro/), "an if/else statement that can be controlled at runtime". The code for both branches ships to production, and a setting outside the code decides which one runs, for everyone or for particular users.

At the end of 3.5 your team's `assignments-service` is tested and observable. In this section you'll change what it does without redeploying it, and use its traces to see which flags shaped each request. The section ends at milestone **M6**.

## Deploy Is Not Release

Without flags, deploying code and releasing a feature are the same event: the moment new code reaches production, every user gets it. Flags separate the two:

- **Deploy** puts new code into production. With the flag off, nobody sees a difference.
- **Release** turns the feature on, for a few users first, then for everyone, when the team or the business is ready.

That separation is what makes small, frequent changes safe. Teams practicing [trunk-based development](https://dora.dev/capabilities/trunk-based-development/) merge unfinished work into the main branch every day and deploy it switched off. A risky change can go to internal users first, then a small percentage of customers, while the team watches its metrics. And if something goes wrong, turning a flag off takes seconds, while rolling back a deployment can take much longer.

## How a Flag Is Evaluated

Every flag check in your code names a flag and supplies a default. In assignments-service at M6, publishing `assignment.created` looks like this:

```csharp
if (await flags.GetBooleanValueAsync("assignment-notifications", false))
{
    await events.PublishAsync(CreatedEvent, response, CancellationToken.None);
}
```

| Part | What it is |
| --- | --- |
| Flag key | The flag's name, here `assignment-notifications` |
| Default value | What your code uses when the flag can't be evaluated, here `false` |
| Variants | The values a flag can return, such as `on: true` and `off: false`, or several strings for an experiment |
| Evaluation context | Facts about the current request, such as a user ID or plan, that rules can use |
| Targeting rules | Logic that picks a variant from the context, such as "beta users get `on`" or "25% of users get `on`" |

A **flag management system** stores the flags and their rules, and evaluates them when your code asks. The Company app uses [flagd](https://flagd.dev/), a small open-source flag service, through [OpenFeature](3-application-development/3.6.3-openfeature.md), a vendor-neutral API for feature flags with SDKs for .NET, Python, Go, and many more.

## Flags in the Company App

flagd already runs in [`compose.yaml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/compose.yaml). It reads every flag from one file, [`infra/flagd/flags.flagd.json`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/infra/flagd/flags.flagd.json), mounted read-only into the container, and watches it, so a saved change takes effect within seconds, with no restart. Services reach it at `flagd:8013`, from the `FLAGD_HOST` and `FLAGD_PORT` variables.

A flag in that file looks like this:

```json
"project-description-required": {
  "state": "ENABLED",
  "variants": { "on": true, "off": false },
  "defaultVariant": "off"
}
```

By the end of M6, the file holds five flags:

| Flag | Service | What it controls | Default variant |
| --- | --- | --- | --- |
| `project-description-required` | projects-service | Creating a project needs a description | `off` |
| `employee-events` | employees-service | Whether employee changes are published | `on` |
| `assignment-notifications` | assignments-service | Whether `assignment.created` is published | `off` |
| `assignments-writes` | assignments-service | Whether assignments can be created, changed, or deleted | `on` |
| `allocation-check` | assignments-service | Whether the 100% allocation rule applies to this caller | `off`, rolled out to a percentage |

## The Cost of Flags

Flags aren't free. Every flag adds a branch to your code, and every combination of flags is a configuration you might have to test. Flags that outlive their purpose pile up as dead code that nobody dares delete. Pete Hodgson's [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) article, the standard reference on the topic, recounts how Knight Capital Group lost $460 million partly through mismanaged flags. [Flag Types](3-application-development/3.6.1-flag-types.md) covers how to keep that cost down.

## Exercise

### Example: release a rule without a deploy

projects-service already reads one flag. Read [`app/flags.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/app/flags.py) and find where `project_description_required()` is called in `app/services/project_service.py`.

1. Answer from the code:
    - What does the service do if flagd is down when a project is created?
    - The rest of the app depends on a small `FeatureFlags` protocol, not on OpenFeature directly. What does that buy the tests? (Look at `FakeFlags` in `tests/fakes.py`.)
2. Ask flagd directly what every flag evaluates to. Its evaluation API also speaks plain JSON over HTTP:

    ```bash
    curl -s -X POST localhost:8013/flagd.evaluation.v1.Service/ResolveAll \
      -H 'Content-Type: application/json' -d '{}'
    ```

3. Create a project with no description. It's accepted:

    ```bash
    curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8080/api/projects \
      -H 'Content-Type: application/json' -d '{"name":"No Description","startDate":"2026-04-01","status":"planned"}'
    ```

4. Release the rule: in `infra/flagd/flags.flagd.json`, change `project-description-required`'s `defaultVariant` to `"on"` and save. Watch flagd notice with `docker compose logs flagd --since 1m`, then create another project with no description and a new name. It's rejected with a 400, and `errors.description` says why. You didn't restart or redeploy anything.
5. Set the flag back to `"off"`.

### Practice: an employee-events flag in employees-service

Close the 3.6 gap in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md#deliberate-gaps-for-each-sections-practice-step): employees-service publishes every change with no way to stop it. Add an ops flag, `employee-events`, that turns publishing off without stopping the service. On by default.

1. **Packages.** From `employees-service/src/EmployeesService/`:

    ```bash
    dotnet add package OpenFeature --version 2.14.1
    dotnet add package OpenFeature.Hosting --version 2.14.1
    dotnet add package OpenFeature.Providers.Flagd --version 0.8.0
    ```

2. **The flag constant.** Create `Features/Employees/EmployeeFlags.cs`: a static class with `public const string Events = "employee-events";` and `public const bool EventsDefault = true;`, and a comment saying why the default is `true`.
3. **Register OpenFeature** in `Program.cs`, next to the observability registrations:

    ```csharp
    builder.Services.AddOpenFeature(features => features
        .AddFlagdProvider(flagd =>
        {
            flagd.Host = builder.Configuration["FLAGD_HOST"] ?? "flagd";
            flagd.Port = int.Parse(builder.Configuration["FLAGD_PORT"] ?? "8013", CultureInfo.InvariantCulture);
        }));
    ```

    > [!IMPORTANT]
    > Set the host and port explicitly, as above. Registered through dependency injection, this flagd provider ignores `FLAGD_HOST` and `FLAGD_PORT` and connects to `localhost:8013`, which inside a container is nothing. Every evaluation would then quietly return the code default. You'll see exactly what that looks like in [OpenFeature](3-application-development/3.6.3-openfeature.md#apply-flags-in-traces-and-in-tests).

4. **The check.** Add `IFeatureClient flags` to `EmployeeService`'s constructor. In the private `PublishAsync` helper, publish only when `flags.GetBooleanValueAsync(EmployeeFlags.Events, EmployeeFlags.EventsDefault, cancellationToken: CancellationToken.None)` returns `true`. All three events go through that helper, so one check covers them.
5. **Tests.** The unit tests construct `EmployeeService` themselves and now need an `IFeatureClient`. For now, pass `Api.Instance.GetClient()`: with no provider set, OpenFeature returns the code default for every flag, so the existing tests behave as before. You'll replace this with proper flag tests in [3.6.3](3-application-development/3.6.3-openfeature.md). Run `dotnet test`.
6. **The flag.** Add `employee-events` to `infra/flagd/flags.flagd.json`, with `on` and `off` variants and `defaultVariant` `"on"`.
7. **Try it.** Rebuild with `docker compose up --build -d employees-service`. Create an employee and check **Notifications**: it's there. Switch `employee-events` to `"off"`, create another, and check again: the employee is saved, but nobody heard about it. Switch it back on.

### Apply: assignment.created behind a release flag

Your team's `assignments-service` publishes `assignment.created` as soon as an assignment is saved. Pretend that feature is new and not ready for everyone: put it behind a **release flag**, `assignment-notifications`, that starts off.

1. Add the same three packages to assignments-service, and register OpenFeature in `Program.cs` the same way, host and port included.
2. Create `Features/Assignments/AssignmentFlags.cs` with `Notifications = "assignment-notifications"` and `NotificationsDefault = false`. Write a comment explaining why a release flag's default is off.
3. Add `IFeatureClient flags` to `AssignmentService`. In `CreateAsync`, publish only when the flag is on. The insert itself must not depend on the flag.
4. Fix the tests that construct `AssignmentService`, as in Practice step 5. Then ask yourselves: with no provider set, the default is `false`, so which existing test now fails, and why is that correct?
5. Add `assignment-notifications` to the flag file with `defaultVariant` `"off"`. Rebuild, create an assignment, and confirm it does **not** appear in **Notifications**.
6. Release it: switch the flag to `"on"`, create another assignment, and watch it appear in the feed.
7. Add a row to the **Planned features** table in your `AGENTS.md` for removing `assignment-notifications`, with an owner and a date. You'll see why in [Flag Types](3-application-development/3.6.1-flag-types.md#removing-flags).
