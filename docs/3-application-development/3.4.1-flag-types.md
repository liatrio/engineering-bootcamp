# Flag Types

Not all flags are alike. A flag that hides a half-built feature for a week needs different handling from one that disables an expensive feature during an outage, or one that gives paying customers extra features for years.

## Four Categories

Pete Hodgson's [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) article sorts flags into four categories, along two dimensions: **longevity** (how long the flag lives) and **dynamism** (how often its decision changes, from per deployment to per request).

| Category | Used for | Lifetime | Decision changes |
| --- | --- | --- | --- |
| **Release** | Shipping unfinished or untested code switched off, so the main branch can always deploy | Days or weeks, until the feature is released | Rarely; usually the same for every user |
| **Experiment** | A/B and multivariate tests that compare how groups of users behave | Hours or weeks, long enough for a meaningful result | Per user: each user stays in their group |
| **Ops** | Controlling operational behavior, such as switching off a new feature with unknown performance cost, or a long-lived **kill switch** that sheds non-essential work under heavy load | Mostly short; kill switches can last years | Quickly, by operators during an incident |
| **Permission** | Giving some users features others don't have: premium features, or early access for internal and beta users | Can be years | Per user, on every request |

The category tells you how to manage the flag. A release flag should have a removal date. An ops flag must be easy for an on-call engineer to change quickly. A permission flag is really part of your product and deserves the same care as the rest of your business logic.

## Safe Defaults

Every flag check in your code supplies a default value, and that value runs whenever the flag can't be evaluated: the flag service is down, the flag was deleted, or the flag has a typo in its name. Choose the default deliberately, as the behavior you'd want if the flag system failed:

- For a **release flag**, the default is usually the old behavior, so a failure never exposes an unfinished feature.
- For a **kill switch**, the default is usually "feature available", so a failure in the flag system doesn't cause an outage of its own.

Many flag clients, including flagd's, keep the last values they received, so a short outage of the flag service often goes unnoticed. The default matters most when an application starts while the flag service is unavailable, which you'll test in the exercise.

## Removing Flags

Flags that have done their job become **flag debt**: branches that always go the same way, extra test cases, and confusion about which code is live. Hodgson recommends treating flags as inventory with a carrying cost, and keeping that inventory low. Teams do it in several ways:

- **Add a removal task to the backlog when you create a release flag**, so removal is planned work, not a favor.
- **Record an owner and an expiry date** with each flag.
- **Limit the number of flags** a service may have at once, so adding one means removing another.

Remove a flag in two steps. First, deploy code that no longer checks the flag, keeping the behavior you released. Then delete the flag from the flag system. In the opposite order, the running code would fall back to its default the moment the flag disappeared.

## Exercise: Add a Kill Switch and Retire a Release Flag

This exercise continues from the [Feature Flags exercise](3-application-development/3.4-feature-flags.md#exercise-ship-a-feature-behind-a-flag), with flagd and the app running.

1. Add a second flag to `flags/flags.flagd.json`, an ops flag that can pause sign-ups. Give both flags `metadata` recording their type and owner, and give the release flag an expiry date:

    ```json
    "user-signups": {
      "state": "ENABLED",
      "variants": { "on": true, "off": false },
      "defaultVariant": "on",
      "metadata": { "type": "ops", "owner": "user-api team" }
    }
    ```

    flagd doesn't act on metadata: it's there for the people managing the flags.
2. In `app/presentation/routes.py`, check the flag at the start of `add_user`. When it's off, return `{"error": "sign-ups are paused"}` with status `503 Service Unavailable`. Pick a default value for the check, following [Safe Defaults](#safe-defaults).
3. Restart the app. Switch `user-signups` to `"off"`, then try to create a user and list users. Sign-ups are paused, but the rest of the service still works. Switch it back on.
4. Test what happens when flagd fails:
    - Stop flagd with `docker stop flagd`, then send a few requests. What do the flags return now?
    - Restart the app while flagd is still stopped, and send the same requests. What changed, and why?
    - Start flagd again, with the same `docker run` command as before, and send the requests once more.
5. The sorted-users feature is released, so retire its flag. First, remove the flag check from `get_users`, keeping the sorting, and restart the app. Then delete `sorted-users` from the flag file. Confirm users are still sorted.

### Deliverables

- Your kill switch code and your flag file.
- What did the flags return in each part of step 4? Explain the difference between the first and second parts.
- Classify each of these as release, experiment, ops, or permission, and say how long you'd expect it to live: a new checkout page tested against the old one; a switch that disables PDF generation under heavy load; a dashboard only enterprise customers can see; a payment integration that isn't finished yet.
- Discuss: why remove the code before the flag, and not the other way around?
