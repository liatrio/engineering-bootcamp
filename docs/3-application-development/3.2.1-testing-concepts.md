# Testing Concepts

Before learning how to write each kind of test, it helps to have a map: what kinds of tests exist, what each one is good at, and how much of each a project should have. This section introduces the vocabulary used in the rest of the chapter and two popular models for balancing a test suite: the **testing pyramid** and the **testing trophy**.

## Types of Tests

Tests are usually grouped by how much of the system they exercise.

| Type | What it checks | Speed | Example |
| --- | --- | --- | --- |
| Static | Code is well-formed and type-correct, without running it | Instant | A linter or type checker flags an undefined variable |
| Unit | A single function, method, or class in isolation | Milliseconds | `Add(2, 3)` returns `5` |
| Integration | Several units, or a unit and a real dependency, working together | Milliseconds to seconds | A repository saves a user to a real (or in-memory) database and reads it back |
| End-to-end | The whole application, the way a user drives it | Seconds to minutes | A browser test signs up, logs in, and places an order |

The further down the table, the more of the system a test covers. That brings more confidence that the system really works, but the test is also slower, harder to debug when it fails, and more likely to break for reasons unrelated to the change you made.

The boundaries are blurry. The most common disagreement is over what counts as a "unit". Some teams mean a single class with every collaborator replaced by a [test double](3-application-development/3.2.6-test-doubles.md) (a *solitary* unit test). Others let a unit use its real collaborators as long as the test stays fast and in-process (a *sociable* unit test). Neither is wrong, but a team should agree on which it means.

## The Testing Pyramid

<div class="grid2"><div class="col">

The testing pyramid comes from Mike Cohn's 2009 book *Succeeding with Agile*, and Martin Fowler's [Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html) article popularized it. It recommends:

- **Many unit tests** at the base. They are fast and cheap, and they pinpoint exactly what broke.
- **Fewer integration tests** in the middle. They check that the pieces fit together.
- **Very few end-to-end tests** at the top. They are slow and brittle, so keep them for the most important user journeys.

</div><div class="col">

![testing pyramid](img/testing-pyramid_light.svg ':size=500px :class=light-mode-img-center :alt= testing pyramid with unit tests at the wide base, integration in the middle, and end-to-end at the narrow top; light mode')
![testing pyramid](img/testing-pyramid_dark.svg ':size=500px :class=dark-mode-img-center :alt= testing pyramid with unit tests at the wide base, integration in the middle, and end-to-end at the narrow top; dark mode')

</div></div>

The shape follows from cost. A test higher up the pyramid takes longer to write, longer to run, and longer to diagnose. A suite built mostly from fast tests can run on every change, which keeps feedback quick.

The anti-pattern is the **ice-cream cone**: a suite that is mostly manual or UI-driven tests with few unit tests underneath. Fowler notes that tests run through the UI tend to be "brittle, expensive to write, and time consuming to run", so teams with an ice-cream cone run their tests rarely and find bugs late.

For a longer, hands-on treatment, read Ham Vocke's [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html).

## The Testing Trophy

<div class="grid2"><div class="col">

Kent C. Dodds proposed the [testing trophy](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications) in 2018, building on Guillermo Rauch's advice: "Write tests. Not too many. Mostly integration." From bottom to top it has four layers:

- **Static**: linters, formatters, and type checkers catch typos and type errors as you write the code.
- **Unit**: tests for individual functions and modules.
- **Integration**: tests that several units work together. This is the widest part of the trophy.
- **End-to-end**: a small number of tests that drive the whole application.

</div><div class="col">

![testing trophy](img/testing-trophy_light.svg ':size=450px :class=light-mode-img-center :alt= testing trophy with static analysis as the base, a narrow unit stem, a wide integration bowl, and a small end-to-end cap; light mode')
![testing trophy](img/testing-trophy_dark.svg ':size=450px :class=dark-mode-img-center :alt= testing trophy with static analysis as the base, a narrow unit stem, a wide integration bowl, and a small end-to-end cap; dark mode')

</div></div>

Dodds frames testing as a return on investment, where the return is confidence and the investment is time. Integration tests are weighted most heavily because they exercise code the way it is actually used, without the cost of full end-to-end tests. Unit tests that replace every collaborator with a mock can all pass while the pieces fail to fit together.

The trophy is common in front-end and JavaScript projects. Spotify's [testing honeycomb](https://engineering.atspotify.com/2018/01/testing-of-microservices) makes a similar argument for microservices, recommending a focus on integration tests with few tests of implementation details.

## Pyramid or Trophy?

The two models look like they disagree, but in [On the Diverse And Fantastical Shapes of Testing](https://martinfowler.com/articles/2021-test-shapes.html), Martin Fowler argues that most of the disagreement is about vocabulary. A fast, sociable test that the trophy calls an "integration test" is often what a pyramid advocate calls a "unit test". Both models agree on the things that matter:

- **Most tests should be fast** enough to run on every change, locally and in CI.
- **End-to-end tests should be few** and reserved for critical paths.
- **Tests should fail only when behavior breaks**, not whenever the internal structure changes.
- **Static analysis is cheap**, so use it. The [Code Styling](3-application-development/3.2.4-code-styling.md) and [Git Hooks](3-application-development/3.2.10-pre-commit.md) sections cover the tooling.

Rather than aiming for a fixed ratio of test types, ask what gives your team the most confidence for the least time. When someone talks about "unit" or "integration" tests, ask what they mean by the words.

## Exercise

Classify the tests in two example projects from this repository.

1. Read [`examples/layered-architecture/example2/tests/test_routes.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/layered-architecture/example2/tests/test_routes.py) and the application code it calls under `app/`.
2. Read [`examples/data-patterns/repository/repository_test.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/data-patterns/repository/repository_test.go). Look at `TestInMemoryUserRepository`, `TestSQLiteUserRepository`, and `TestUserService`.
3. For each test, write down:
    - which type from the table above it is, and why;
    - whether it is solitary or sociable;
    - where it sits on the testing pyramid and on the testing trophy.
4. Pick one test you would classify differently under the pyramid than under the trophy, and explain the difference in a sentence or two.

### Deliverables

- Your classification of each test, with a one-line reason.
- Discuss with your team: if you were adding a feature to the repository example, which kind of test would you write first, and why?
