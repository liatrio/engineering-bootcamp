# OpenTelemetry

Every exercise in this section has used [OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/) (often shortened to OTel) to produce logs, metrics, and traces. It is "a Cloud Native Computing Foundation (CNCF) project that is the result of a merger between two prior projects, OpenTracing and OpenCensus", and it has become the industry standard for producing telemetry.

OpenTelemetry standardizes how telemetry is *produced and transported*. It is "**not** an observability backend itself": storing, querying, and visualizing the data is left to tools such as Prometheus, Loki, Tempo, Jaeger, Grafana, or commercial vendors. Because every backend accepts the same format, you instrument your code once and can change backends without touching it.

## The Pieces

| Piece | What it does |
| --- | --- |
| **API** | The interfaces your code calls to create spans, record metrics, and emit logs. It is safe to call from libraries: without an SDK configured, the calls do nothing. |
| **SDK** | The implementation that processes telemetry, applies sampling, batches it, and hands it to exporters. Configured once, by the application. |
| **Instrumentation libraries** | Ready-made instrumentation for popular frameworks and clients (Flask, requests, database drivers, and many more). **Zero-code instrumentation**, such as `opentelemetry-instrument`, installs and configures them without code changes. |
| **Exporters** | Send telemetry out of the process, to the console, a backend, or a collector. |
| **OTLP** | The OpenTelemetry Protocol, the standard wire format for all three signals, over gRPC (port 4317) or HTTP (port 4318). |
| **Collector** | A standalone service that receives, processes, and exports telemetry. |

## The Collector

Applications can export directly to a backend, but most production setups send telemetry to an [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/) first. A collector [pipeline](https://opentelemetry.io/docs/collector/configuration/) has three stages:

- **Receivers** accept data, for example OTLP from your applications, or scraped Prometheus metrics.
- **Processors** transform it: batch it, add or remove attributes, drop noisy data, redact sensitive fields, or sample traces.
- **Exporters** send it to one or more backends.

This keeps applications simple. They only speak OTLP to a nearby collector, while decisions about routing, retries, filtering, and which vendor to use live in one place that operators can change without redeploying any applications. The `grafana/otel-lgtm` container you've been using runs a collector in front of Loki, Tempo, and Prometheus.

## Semantic Conventions

If one service names its attribute `http_status` and another `statusCode`, you can't query across them. OpenTelemetry's [semantic conventions](https://opentelemetry.io/docs/concepts/semantic-conventions/) define standard names for common operations and attributes, such as `http.request.method`, `http.response.status_code`, `db.system`, and `service.name`. Instrumentation libraries follow them, and your own attributes should follow them wherever a convention exists. Conventions do evolve, which is why the zero-code Flask instrumentation you used still emits some older names, such as `http_server_duration_milliseconds`.

## Resources

A **resource** describes the entity producing telemetry: the service name and version, the deployment environment, the host, container, or Kubernetes pod. Resource attributes are attached to every span, metric, and log the process emits, which is what lets you filter "errors in version 1.4.2 in production". `OTEL_SERVICE_NAME` sets `service.name`, and `OTEL_RESOURCE_ATTRIBUTES` sets the others.

## Sampling

A busy service can produce millions of traces an hour, and storing them all is expensive. [Sampling](https://opentelemetry.io/docs/concepts/sampling/) keeps a representative subset:

- **Head sampling** decides when a trace starts, for example keeping a fixed 10% of traces. It's simple and cheap, but it decides before anyone knows whether the request will be slow or fail.
- **Tail sampling** decides after the trace is complete, by "considering all or most of the spans within the trace". That lets you keep every error and every slow request, plus a sample of the rest. It runs in a collector, because it needs to see whole traces.

Sampling applies to traces. Metrics are aggregated in the SDK before export, so they still count every request: you can sample traces aggressively while keeping accurate rates and percentiles.

## Configuring OpenTelemetry

Most SDK settings can be configured with [environment variables](https://opentelemetry.io/docs/languages/sdk-configuration/general/), which keeps configuration out of your code and works the same way across languages. You've already used `OTEL_SERVICE_NAME`, `OTEL_EXPORTER_OTLP_ENDPOINT`, and `OTEL_METRIC_EXPORT_INTERVAL`. See the [Python zero-code configuration](https://opentelemetry.io/docs/zero-code/python/configuration/) for the full list.

## Exercise: Resources and Sampling

This exercise continues from the [Tracing exercise](3-application-development/3.3.3-tracing.md#exercise-manual-spans).

1. Restart the app with two resource attributes, a version and an environment, by adding this to the environment variables you've been using:

    ```bash
    export OTEL_RESOURCE_ATTRIBUTES=service.version=0.1.0,deployment.environment.name=dev
    ```

    Send some traffic, open a trace in Tempo, and find the attributes in the span's resource section. Then find them on a metric in Prometheus and on a log in Loki, where the dots become underscores, as in `service_version`.
2. Turn on head sampling, keeping a quarter of traces:

    ```bash
    export OTEL_TRACES_SAMPLER=traceidratio
    export OTEL_TRACES_SAMPLER_ARG=0.25
    ```

    Restart the app, then send exactly 100 requests: `for i in $(seq 1 100); do curl -s localhost:5001/users > /dev/null; done`.
3. Compare the two signals. How many traces does Tempo show for those 100 requests? (Allow a few seconds for Tempo to index them.) How many requests does `http_server_duration_milliseconds_count` count? Explain the difference.
4. Unset the two sampler variables when you're done, so later work keeps every trace.

### Deliverables

- Screenshots showing your resource attributes on a trace, a metric, and a log.
- Your trace and request counts from step 3, and your explanation.
- Discuss: with head sampling at 25%, what fraction of *failed* requests would you keep traces for? How would tail sampling in a collector change that?
- Discuss: why might a team send telemetry through a collector instead of straight to a vendor?
