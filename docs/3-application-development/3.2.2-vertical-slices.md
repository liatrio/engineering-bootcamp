# Vertical Slices

The [previous page](3-application-development/3.2.1-foundational-layers.md) covered the horizontal layers every feature uses. This page is about what sits on top of them. A **vertical slice** is one feature, cut top to bottom through every layer: its endpoint, its rules, its data, and, in the UI, its screens. The foundation runs horizontally under everything; a feature runs vertically through it.

> [!NOTE]
> A **vertical slice** is everything one feature needs, kept together in one folder, using the foundation for everything that isn't specific to that feature.

## Two Ways to Organize the Same Files

Here is a .NET API with three features, laid out two ways. Same files, same classes, different folders.

<div class="grid2"><div class="col">

**By layer** (what most templates give you)

```text
Controllers/
  EmployeesController.cs
  ProjectsController.cs
  AssignmentsController.cs
Services/
  EmployeeService.cs  ...
Models/
  Employee.cs  ...
Data/CompanyDbContext.cs
```

</div><div class="col">

**By feature** (what the starter uses)

```text
Features/
  Employees/
    Employee.cs  EmployeeService.cs
    EmployeesController.cs  ...
  Projects/      ... same files
  Assignments/   ... same files
Infrastructure/
  Data/  Errors/  Messaging/  ...
Program.cs
```

</div></div>

The layer layout groups files by *what kind of thing they are*. The feature layout groups them by *what they are for*. Both compile. The difference shows up when you do real work:

| Task | By layer | By feature |
| --- | --- | --- |
| Add a feature | Touch four folders, add one file to each | Create one folder, plus a mirrored test folder |
| Understand how a feature works | Open four folders and stitch them together in your head | Open one folder |
| Delete a feature | Hunt through every folder for its pieces | Delete the folder |
| Two people build two features | Both edit `Controllers/` and `Services/`, and their changes conflict | Each works in their own folder |
| Ask an agent to add a feature | "Put the controller in Controllers, the service in Services, the…" | "Add `Features/Departments/` like `Features/Employees/`" |

Notice what doesn't move: `Infrastructure/` and `Program.cs`. The foundation stays horizontal because it really is shared. Only feature code gets sliced. Jimmy Bogard's [Vertical Slice Architecture](https://www.jimmybogard.com/vertical-slice-architecture/) is a good longer read on the idea.

## A Slice Touches Every Layer and Owns None

For each layer, a slice writes only the small piece that is specific to it. Here is what the Employees slice in employees-service contributes:

| Layer | What the Employees slice wrote |
| --- | --- |
| Routing | `[Route("api/employees")]` on one controller |
| Auth | Nothing. The middleware protects `/api/*` already. |
| Validation | Data annotations on `EmployeeRequest` |
| Error handling | `throw new NotFoundException(...)` and `throw new ConflictException(...)` |
| Data access | One entity, one `IEntityTypeConfiguration`, a thin store, and one `DbSet` |
| Observability | One business counter, `company.employees.created`, and spans around publishing on create and update |
| Testing | Three test files in the mirrored folder, using the shared test apps |
| Conventions | Its folder name and file names, which follow the template |

Two things stand out. **The cells are small.** A feature's whole contribution to error handling is a `throw`, and its contribution to auth is usually nothing. And **every slice has the same shape.** Once you've seen one, you know what the next will look like, and so does anyone (or anything) you ask to build it.

## The Employees Slice, End to End

Open [`employees-service/src/EmployeesService/Features/Employees/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees) in your team repository. Every file is about employees.

| File | Job | What it does *not* contain |
| --- | --- | --- |
| `Employee.cs` | The EF Core entity: properties only | Rules or validation |
| `EmployeeConfiguration.cs` | Keys, lengths, and the unique index on the lower-cased email | A connection string or a table-creation script |
| `EmployeeDtos.cs` | `EmployeeRequest` (with data annotations) and `EmployeeResponse` | Any `if` checks for required fields |
| `IEmployeeStore.cs`, `EmployeeStore.cs` | The persistence seam and its EF Core implementation | Business rules |
| `EmployeeService.cs` | The rules: unique email, IDs and timestamps set by the service, events published after saving | HTTP types or SQL |
| `EmployeesController.cs` | HTTP in, HTTP out: five thin actions | `try/catch` or hand-built status codes |
| `EmployeeSeed.cs` | The fixed seed rows from `SPEC.md` | Anything used by real requests |
| `ProviderStatesController.cs` | Test support for contract tests (3.4.6), off unless enabled | Anything reachable in production |

Wiring the slice into the foundation takes two lines in `Program.cs` and one property on the `DbContext`:

```csharp
builder.Services.AddScoped<IEmployeeStore, EmployeeStore>();      // Program.cs
builder.Services.AddScoped<IEmployeeService, EmployeeService>();  // Program.cs
public DbSet<Employee> Employees => Set<Employee>();              // EmployeesDbContext.cs
```

The tests live in the mirrored folder, [`tests/EmployeesService.Tests/Features/Employees/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/Features/Employees): a service test with fakes, an API test through the whole HTTP stack, and a database test against a real PostgreSQL. Each leans on a shared test app from the foundation instead of setting anything up itself.

The rule worth noticing is the unique email. It is checked twice, on purpose. `EmployeeService` checks first, so the common case gets a clear 409 message. The unique index in `EmployeeConfiguration` is the real guarantee: if two requests pass the check at the same moment, the database rejects the second, and `EmployeeStore` turns that error into the same 409.

## The UI Slice

The React slice has the same character. [`web/src/features/employees/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/employees) owns its screens and its API calls, and leans on `api()`, the router, and the shared form components:

| File | Job |
| --- | --- |
| `api.ts` | One function per endpoint using `api()`, plus TanStack Query hooks |
| `types.ts` | The request and response shapes |
| `EmployeesPage.tsx`, `EmployeeForm.tsx` | The screens. The form's zod schema mirrors the server's rules. |
| `routes.tsx` | The routes this feature exports |
| `EmployeesPage.test.tsx` | A component test using `renderWithProviders()` |

Registering it is one spread in `src/app/router.tsx`: `...employeeRoutes`. When the API returns a 409 for a duplicate email, `api()` throws an `ApiError`, TanStack Query hands it to the form, and the message appears. The feature never inspected a status code.

Now look at [`web/src/features/assignments/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/features/assignments). It is a complete slice with the same files, already wired into the router, waiting for a backend. Your team builds the other half.

## What About projects-service?

projects-service lays out `app/` by layer: `routers/`, `services/`, `repositories/`. That's a reasonable choice for a service with **one** feature, where "the feature" and "the service" are the same thing. The trouble starts when a second feature arrives and every folder gains a file. The rule of thumb: a small service with one feature can go either way; a service that will grow features should slice by feature from the start. Your `assignments-service` follows employees-service.

## The Second Slice Is Cheaper Than the First

The payoff of a foundation plus slices is that each feature costs less than the last. In employees-service, a new feature such as Departments needs:

| | Files written | Foundation touched | New patterns |
| --- | --- | --- | --- |
| API: `Features/Departments/` | About seven, plus test files | Two `AddScoped` lines, one `DbSet`, one migration | None |
| UI: `features/departments/` | About five, plus a test | One spread in the router | None |

The first slice took a while because it was also proving the foundation. The tenth is routine.

> [!NOTE]
> This is also why slices matter for AI-assisted work. A prompt such as *"Add a Departments feature. Follow `Features/Employees/` and the rules in `AGENTS.md`"* is enough when the codebase contains one clear example of every decision. The folder is the prompt.

## Rules That Keep Slices Clean

Feature folders are easy to start and easy to erode. Four rules keep them honest.

1. **A slice never reaches into another slice's internals.** If two features need the same thing, that thing is either foundation or a deliberately exported piece of one feature. Importing another feature's private helper couples the two in ways nobody can see.
2. **A slice never re-implements the foundation.** The moment a controller grows a `try/catch` that returns a status code, the app has two error formats. The moment a component calls `fetch` directly, there's a request that skips `api()`. If the foundation can't do something, extend the foundation.
3. **The foundation never knows about a specific feature.** A `DbSet<Employee>` and a `...employeeRoutes` spread are registration, and that's fine. An `if (path.StartsWith("/api/employees"))` inside the exception handler isn't.
4. **Promote to shared on the second use, not the first.** Write the concrete thing in the slice. When a second slice needs it, move it to the foundation, now that you have two examples to shape it around.

## Exercise

### Example: read the Employees slice

Open `employees-service/src/EmployeesService/Features/Employees/` and `web/src/features/employees/` in your team repository, and answer:

1. Follow a duplicate email from `EmployeeService.CreateAsync` to the HTTP response. Which files does it pass through, and which of them lives outside the slice?
2. `EmployeeService` publishes an event after every change. Which interface does it depend on, and where is the real implementation registered?
3. Find every place outside `Features/Employees/` that mentions `Employee`. Is each one registration, or something that breaks rule 3?

### Practice: sketch a Departments slice in employees-service

The business wants departments to be managed records instead of free text: each has a unique name and an optional description, and a department with employees can't be deleted. Sketch the slice **without writing code**.

1. List every file you would add under `Features/Departments/`, with a one-line job for each. Use the Employees slice as your template.
2. List the endpoints, with the success status and the error statuses for each, following the CRUD rules in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md).
3. Decide where the rule *"a department with employees can't be deleted"* lives, and which exception it throws.
4. List the lines you'd change outside the slice folder. Is any of them in `Infrastructure/`?
5. Today `Employee.Department` is a string. Would you change it to a `DepartmentId` with a foreign key? Both features live in the same service and the same database, so what does that make possible that wouldn't be possible across two services? Keep your answer; [3.2.3](3-application-development/3.2.3-microservices-and-service-boundaries.md) comes back to it.

### Apply: plan the Assignments slices

Plan your service's slices so that every later section fills in a plan instead of inventing one. Work on a new branch, `docs/assignments-slices`.

1. Append a **Feature folder template** section to your team's `AGENTS.md`. It has two tables, one for a .NET API feature and one for a web feature, each listing the files every slice contains and what goes in them. Add a sentence on where tests go and what wiring a new slice needs.
2. Append a **Planned features** table to `AGENTS.md` with the columns *Feature*, *Service*, *What it is*, and *Endpoints*. Fill in Employees and Projects from `SPEC.md`, then fill in the Assignments row yourself:
    - What are the endpoints? Assignments need full CRUD, and listing must filter by `employeeId` and by `projectId`.
    - What business rule makes this feature different, and which exception does it throw? (Can the same employee be assigned to the same project twice?)
    - Which two things must the service check exist before it saves anything?
3. Create `docs/assignments-design.md` with a **Slices** section: a table of every file in `assignments-service/src/AssignmentsService/Features/Assignments/` and its job. Include one file the Employees slice doesn't have: a background consumer for the `employee.deleted` event.
4. Check it: without looking at any code, list the API files, test files, and web files for Assignments by name. If the template lets you do that in under a minute, your slices are planned.
5. Open a pull request. Ask the reviewer to try step 4 from your files alone.
