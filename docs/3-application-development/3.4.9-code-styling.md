# Code Styling and Linting

> “Formatting issues are the most contentious but the least consequential. People can adapt to different formatting styles but it's better if they don't have to, and less time is devoted to the topic if everyone adheres to the same style.”
>
> _- [Effective Go](https://go.dev/doc/effective_go#formatting)_

Code written in several styles is slower to read and noisier to review. One developer writes `snake_case`, another `camelCase`; one sorts imports, another doesn't. Every difference is something a reader has to notice and discard. Teams solve this by agreeing on one style per language and letting tools enforce it, so nobody spends review time on it.

## Formatters and Linters

The two kinds of tool do different jobs, and most projects use both:

- A **formatter** rewrites code into one canonical layout: indentation, line breaks, spacing, quote style. It has no opinions about correctness and changes nothing about behavior. You run it and accept the result.
- A **linter** (or **analyzer**) reads code and reports likely problems: unused variables, a mutable default argument, a missing `await`, a logging call that allocates on every request. Some findings can be fixed automatically; others need a person to decide.

Prettier's documentation explains [the split](https://prettier.io/docs/comparison) well: use formatters for formatting and linters for catching bugs.

A linter's **rule set** is a choice. Each rule is a trade between catching real problems and generating noise. Start with a recommended set, add rules that catch bugs you've actually had, and turn off a rule only with a comment saying why.

## The Tools in the Company App

| Service | Formatter | Linter | Check command |
| --- | --- | --- | --- |
| projects (Python) | [Ruff](https://docs.astral.sh/ruff/) (`ruff format`) | Ruff (`ruff check`) | `uv run ruff check .` |
| web (TypeScript) | [Prettier](https://prettier.io/) | [ESLint](https://eslint.org/) with typescript-eslint | `npm run lint` |
| notifications (Go) | `gofmt` | `go vet` | `gofmt -l .` and `go vet ./...` |
| employees, assignments (.NET) | `dotnet format` | The .NET analyzers, built into the SDK | `dotnet format --verify-no-changes` and `dotnet build` |

### Go: one style, no settings

`gofmt` has no configuration. Every Go project in the world is formatted the same way, which is the point. `gofmt -l .` lists files that aren't formatted, `gofmt -d .` shows the difference, and `gofmt -w .` rewrites them. `go vet` is the linter: it finds code that compiles but is probably wrong, such as a `Printf` whose arguments don't match its format string.

### .NET: analyzers and .editorconfig

The .NET SDK ships with [code analyzers](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/overview) that run during every build. Three settings control them:

- **`AnalysisLevel`** picks the rule set. `latest-recommended` turns on the rules Microsoft recommends for most code, as warnings.
- **`EnforceCodeStyleInBuild`** makes the build report code-style rules (the `IDE` rules, such as unused usings) as well as quality rules (the `CA` rules).
- **`TreatWarningsAsErrors`** fails the build on any warning.

An **`.editorconfig`** file holds the style itself: indentation, `var` preferences, braces, namespace style, and the severity of individual rules. Editors read it as you type, the build reads it, and `dotnet format` applies it. A **`Directory.Build.props`** file next to the solution applies MSBuild settings to every project under it, so the source and test projects share one configuration.

### Practice: enable bugbear in projects-service

[flake8-bugbear](https://docs.astral.sh/ruff/rules/#flake8-bugbear-b) (`B`) is a set of rules for code that is probably a bug. projects-service doesn't run it yet, and one finding is waiting.

1. Branch: `git switch -c chore/projects-ruff-bugbear`.
2. See what the rules would find before you turn them on:

    ```bash
    cd projects-service
    uv run ruff check --select B .
    ```

    One finding: **B006**, "Do not use mutable data structures for argument defaults", in `app/services/seed.py`. `reset_to_seed` has `remove_ids: list[uuid.UUID] = []`.

3. Understand the bug before you fix it. Python evaluates a default value **once**, when the function is defined, and every call that omits the argument shares that one list. If any call ever appended to `remove_ids`, the next call's "empty" default would already contain IDs. The code doesn't append today, which is exactly why nobody noticed.
4. Fix it. Ruff suggests `= None` plus an `if remove_ids is None` check, but its own note calls that fix unsafe, and it would break the type hint. The function only needs to ask "is this ID in the collection?", so change the parameter to `remove_ids: Collection[uuid.UUID] = ()`, with `from collections.abc import Collection`. A tuple can't be mutated, and `Collection` accepts the lists the provider-state router passes. Add a line to the docstring saying why the default is a tuple.
5. Turn the rule on: in `pyproject.toml`, change `select` to `["E", "F", "I", "B"]` and update the comment above it.
6. Check: `uv run ruff check .` prints `All checks passed!`, and `uv run pytest` still passes. The provider-state tests exercise `reset_to_seed`.
7. Update the sentence about ruff's rule set in `projects-service/README.md`, then commit and open a pull request.

> [!TIP]
> Compare with M4's [`seed.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/projects-service/app/services/seed.py) and [`pyproject.toml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/projects-service/pyproject.toml).

### Apply: analyzers, .editorconfig, and dotnet format for assignments-service

1. **Shared settings.** Create `assignments-service/Directory.Build.props`:

    ```xml
    <Project>
      <PropertyGroup>
        <AnalysisLevel>latest-recommended</AnalysisLevel>
        <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
        <TreatWarningsAsErrors Condition="'$(CI)' == 'true'">true</TreatWarningsAsErrors>
        <GenerateDocumentationFile>true</GenerateDocumentationFile>
        <NoWarn>$(NoWarn);CS1591</NoWarn>
      </PropertyGroup>
    </Project>
    ```

    Warnings fail the build only in CI (GitHub Actions sets `CI=true`), so you can experiment locally before tidying up. The compiler reports unused usings (`IDE0005`) only when it's also generating XML documentation, hence `GenerateDocumentationFile`. `CS1591` would then demand a comment on every public member, so it's turned off. Remove the `TreatWarningsAsErrors` lines your two `.csproj` files copied from employees-service: this file owns that setting now. Add a comment to each setting saying why it's there.

2. **Style.** Create `assignments-service/.editorconfig` with `root = true`, then agree as a team on the rules. At minimum:
    - spaces, a final newline, and no trailing whitespace for every file; 4-space indents for `.cs` and 2 for project and YAML files;
    - `System` usings first and outside the namespace; file-scoped namespaces, as a `warning`;
    - braces always (`csharp_prefer_braces = true:warning`);
    - `dotnet_diagnostic.IDE0005.severity = warning`, so unused usings fail CI;
    - a `[tests/**.cs]` section that turns off `CA1707`, because test names use underscores;
    - a `[**/Migrations/*.cs]` section with `generated_code = true`, so EF Core's output isn't held to your rules.

3. **See what they find.** From `assignments-service/`:

    ```bash
    dotnet build --no-incremental
    CI=true dotnet build --no-incremental
    ```

    The first build passes with warnings; the second fails on them. On the reference M3 code you'd see nearly twenty: `IDE0005` (unused usings), `CS1573` (a documented method with an undocumented parameter), `CA1861` (a constant array allocated on every call), and, mostly, `CA1848` and `CA1873` on every `logger.LogInformation(...)` call.

4. **Fix them.**
    - **Run `dotnet format`.** It applies the code fixes for everything that has one: whitespace, unused usings, the missing `<param>` tag, the constant array. Read the diff before you commit it. On the reference code, only the logging findings are left afterwards.
    - **`CA1848` and `CA1873`** ask for [compile-time logging](https://learn.microsoft.com/dotnet/core/extensions/logger-message-generator): a `partial` method with a `[LoggerMessage]` attribute, which the compiler turns into logging code that does no work when the level is off. In each class that logs, make the class `partial`, add a nested `private static partial class Log` with one method per message, and call `Log.Published(logger, type, envelope.EventId)` instead. Keep each message template exactly as it was: dashboards and alerts search for that text.
    - If you decide a rule is wrong for your code, set its severity in `.editorconfig` with a comment saying why. Don't suppress it in place.

5. **Check.** All three must pass:

    ```bash
    dotnet format --verify-no-changes
    CI=true dotnet build --no-incremental
    dotnet test
    ```

6. Add the formatting command to the **Commands** table in `AGENTS.md`, and a rule: "fix analyzer warnings rather than suppressing them; a suppression needs a comment saying why." Open the pull request. CI runs both checks from 3.4.10 onwards.
