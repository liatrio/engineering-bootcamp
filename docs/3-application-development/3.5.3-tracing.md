# Tracing

Logs tell you what happened, and metrics tell you how often. Neither tells you where the time went in one specific request, or which of five services a failure started in. A **trace** does: it records the whole journey of one request as it passes through functions, services, databases, and queues.

## Traces and Spans

A trace is made of **spans**. Each span is one timed operation, such as handling an HTTP request, running a database query, or publishing a message. A span records:

- a name, plus start and end times;
- the trace ID it belongs to, its own span ID, and its parent span's ID;
- a **kind**: `server` (handling a request), `client` (making one), `producer` and `consumer` (sending and processing a message), or `internal` (work inside the process);
- **attributes**: key-value details such as `http.route` or `employee.id`;
- a **status** (unset, OK, or error), plus **events**, such as an exception being raised.

The parent links turn the spans into a tree. Visualization tools draw the tree as a **waterfall**: one bar per span, positioned by time, so slow and failing operations stand out immediately. Here is a real trace from the Company app, an employee created in the browser:

```text
web                    POST                          [==================] 130 ms
employees-service        POST api/employees            [================] 124 ms
employees-service          postgresql                   [=]
employees-service          publish employee.created         [=========]
employees-service            publish employee.created (producer)     |
notifications-service          process company.events (consumer)     |
```

See [Traces](https://opentelemetry.io/docs/concepts/signals/traces/) in the OpenTelemetry docs for the full model.

## Context Propagation

Within one process, the current span is held in a *context*, and any span you start becomes its child automatically. Across processes, the context travels with the request. For HTTP, the [W3C Trace Context](https://www.w3.org/TR/trace-context/) standard defines a `traceparent` header that carries the trace ID, the parent span ID, and a *sampled* flag, so the receiving service continues the same trace. This is **distributed tracing**: one trace spanning every service the request touched. See [Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/).

HTTP instrumentation sends and reads the header for you. Messages are different: the context has to travel *inside* the message, in its headers, and both ends have to agree on how. In the Company app:

- **The browser** starts the trace. Its fetch instrumentation adds `traceparent` to every `/api/*` call.
- **The frontend-proxy** (nginx) has no instrumentation. It passes the header through untouched, so the trace continues, but the proxy itself never appears in it.
- **.NET services** read and write `traceparent` through ASP.NET Core and `HttpClient` instrumentation. When publishing, the RabbitMQ.Client 7 library starts a `producer` span and writes `traceparent` into the message headers itself.
- **notifications-service** reads it back by hand. There's no OpenTelemetry instrumentation for Go's `amqp091-go`, so [`carrier.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/carrier.go) adapts AMQP headers to OpenTelemetry's `TextMapCarrier` interface, and [`consumer.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/consumer.go) extracts the context and starts a `consumer` span whose parent is the publisher's span. The one surprise, documented in the carrier: RabbitMQ.Client writes header values as bytes, not strings.

If any hop drops the context, the trace breaks in two, and you lose the connection between cause and effect.

## Automatic and Manual Spans

Instrumentation libraries create spans automatically for the frameworks you use: incoming HTTP requests, outgoing HTTP calls, database drivers, and message clients. That gives you the skeleton of every trace without writing any code.

Add **manual spans** for the operations that matter to *your* application, such as validation, business rules, or a group of calls that belong together, and add attributes that help you search: an employee ID, a feature flag, a validation result. Keep spans meaningful. A span per significant operation helps; a span per line of code is noise.

In .NET, OpenTelemetry's spans are .NET's own `Activity` objects, so a manual span looks like this:

```csharp
using (var activity = ServiceTelemetry.ActivitySource.StartActivity("publish " + CreatedEvent))
{
    activity?.SetTag("employee.id", employee.Id);
    await PublishAsync(CreatedEvent, response);
}
```

`StartActivity` returns `null` when nobody is listening, or when the trace isn't sampled, which is why every call after it uses `?.`. When an operation fails in a way your code handles, mark the span yourself with `activity?.SetStatus(ActivityStatusCode.Error, "...")`. Otherwise the trace shows it as a success.

## Exercise

### Example: one click, five services

1. In the app at <http://localhost:8080>, create an employee. In Grafana **Explore**, choose **Tempo** and run:

    ```traceql
    {resource.service.name="web" && span.http.request.method="POST"}
    ```

    Open the trace and click **Expand all**. Then answer:
    - What is each span's **Kind**, and how does the kind relate to where the span sits in the tree?
    - There are two spans named `publish employee.created`. Which library created each one (**Library Name**), and what does each tell you that the other doesn't?
    - The notifications-service span is a child of the employees-service producer span. Click it and find `messaging.message.id`. Then find the same attribute on the producer span. What does that tell you?
    - How long after the producer span started did notifications-service start processing? What would make that gap grow?

2. Read `EmployeeService.CreateAsync` in [`EmployeeService.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeService.cs) next to the trace. Which spans in the waterfall came from that method's code, and which from libraries it called?

3. Find an `employee.deleted` trace. If you've finished the [Observability Apply step](3-application-development/3.5-observability.md#apply-wire-opentelemetry-into-assignments-service), it has *two* consumers:

    ```traceql
    {span.messaging.rabbitmq.destination.routing_key="employee.deleted" && kind=consumer}
    ```

    Which services consumed the message, and which consumer span came from a library and which from hand-written code? How can you tell?

### Practice: a span around publishing on delete

In the Observability Practice step you found the gap: `CreateAsync` and `UpdateAsync` in employees-service wrap their publish in a manual span with an `employee.id` attribute, and `DeleteAsync` doesn't.

1. Open a `DELETE api/employees/{id:guid}` trace in Tempo. The RabbitMQ.Client producer span is there, directly under the server span. Note what you *can't* find: which employee was deleted, and how long publishing took in total, including serialization and waiting for RabbitMQ to confirm.
2. In `DeleteAsync`, wrap the `PublishAsync` call the same way the other two methods do: a span named `"publish " + DeletedEvent`, with `employee.id` set to the deleted ID.
3. Run the employees-service tests, rebuild with `docker compose up --build -d employees-service`, delete an employee in the UI, and find the new span:

    ```traceql
    {resource.service.name="employees-service" && name="publish employee.deleted" && kind=internal}
    ```

    Check that the producer span and both consumer spans are now children of your span.
4. Now search by what you added: create an employee, delete it, and run `{span.employee.id="<its id>"}`. You get both traces, its whole life. Before your change, which of the two would have been missing?

### Apply: a validate span in assignments-service

Creating or updating an assignment calls employees-service and projects-service to check that both IDs exist. Each call already has its own `client` span. A manual span around both groups them, shows how long validation takes in total, and records what it decided.

1. In `AssignmentService`, wrap the body of the method that checks the employee and project exist in a span named `validate employee and project`:
    - set `employee.id` and `project.id` attributes at the start;
    - set a `validation.result` attribute at the end: `ok`, or the names of the fields that failed;
    - when either check fails, set the span's status to error before throwing, so failed validations are easy to find.
2. Rebuild, then create one valid assignment and one with an employee ID that doesn't exist. Find them both:

    ```traceql
    {resource.service.name="assignments-service" && name="validate employee and project"}
    ```

    - In the failed one, which spans are marked as errors? The server span returns 400: is it marked, and why not? (Look back at step 4 of the [Observability Example](3-application-development/3.5-observability.md#example-explore-what-the-starters-send).)
    - Write the TraceQL query that finds only failed validations.
3. **Find a slow dependency.** Freeze projects-service for a few seconds while you create an assignment in the UI:

    ```bash
    docker compose pause projects-service; sleep 5; docker compose unpause projects-service
    ```

    Create the assignment during those five seconds. Then find it:

    ```traceql
    {resource.service.name="assignments-service" && span.http.route="api/assignments" && duration > 2s}
    ```

    - How long did the request take, and how much of that was inside your validate span?
    - How many `GET` client spans to projects-service are there, and how long did each take? Match them to the timeout and retry settings from [3.3.5](3-application-development/3.3.5-calling-other-services.md).
    - Look at the projects-service server spans under the client spans that timed out. projects-service handled those requests after it was unpaused, even though assignments-service had already given up on them. What does that cost, and when could it be dangerous?
4. **Follow an event out.** Assignments publishes `assignment.created` after the insert. Find its producer span in the trace from step 2 and confirm notifications-service's consumer span sits under it.
