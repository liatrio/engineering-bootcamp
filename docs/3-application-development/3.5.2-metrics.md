# Metrics

A metric is a number measured over time: requests per second, error count, response time, queue length. Where a log describes one event in detail, a metric summarizes thousands of events into a few numbers. That makes metrics cheap to store and fast to query, which is why they power dashboards and alerts.

## Kinds of Metrics

Most metrics systems, including [Prometheus](https://prometheus.io/docs/concepts/metric_types/) and [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/metrics/), offer the same basic kinds:

| Kind | What it records | Example |
| --- | --- | --- |
| Counter | A total that only goes up | Requests served, employees created, errors |
| Gauge | A value that goes up and down, measured at a point in time | Memory in use, queue length, temperature |
| Histogram | The distribution of many measurements, in buckets | Request duration, response size |

OpenTelemetry also has an **UpDownCounter**, for totals that can decrease, such as active connections, and *asynchronous* counters, UpDownCounters, and gauges, which read a value on demand rather than having your code record every change.

You usually look at a counter's **rate** (how fast it grows) rather than its raw value, and at a histogram's **percentiles**. An average hides your slowest requests, but the 95th or 99th percentile (p95, p99) shows what your unhappiest users experience.

## Attributes and Cardinality

Metrics carry **attributes** (Prometheus calls them labels), such as the HTTP method, route, or status code, so you can break a metric down: errors *by route*, latency *by status code*. Every distinct combination of attribute values is stored as a separate time series. The [Prometheus naming guide](https://prometheus.io/docs/practices/naming/) warns:

> Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values.

An `employee.id` attribute on a counter creates one time series per employee, which can overwhelm your metrics backend. Put unbounded values in logs and traces instead, where each event is stored individually anyway. That's why employees-service's counter has a `department` attribute (a handful of values) and no employee ID.

## Naming

Consistent names make metrics discoverable. OpenTelemetry's [metric naming guidelines](https://opentelemetry.io/docs/specs/semconv/general/metrics/) say:

- **Use an existing semantic convention name** when one fits, such as `http.server.request.duration`.
- **Build names from dot-separated namespaces**, from general to specific. Prefix your own metrics with a namespace of your own, so they can't clash with a convention added later. The Company app uses `company.`, as in `company.employees.created`.
- **Record the unit on the instrument, not in the name.** Units follow [UCUM](https://ucum.org/ucum): `s` for seconds, `By` for bytes, and a word in curly braces, such as `{employee}` or `{request}`, for a count of things.
- **Don't add a `_total` suffix.** The instrument type already marks a counter, and the suffix is misleading in backends that store changes rather than running totals.

Prometheus, which stores the metrics in this stack, has its own [naming conventions](https://prometheus.io/docs/practices/naming/): underscores instead of dots, the unit in the name, and `_total` on counters. When it receives OpenTelemetry metrics, it [translates the names](https://opentelemetry.io/docs/specs/otel/compatibility/prometheus_and_openmetrics/#metric-metadata-1). Dots become underscores, the unit is appended as a word (a curly-brace unit is dropped), and counters gain `_total`. Your code uses the OpenTelemetry name. Your PromQL queries use the Prometheus one.

## One Measurement, Two Names

Semantic conventions evolve, and not every instrumentation library moves at the same speed. The Company app shows this in its request-duration histograms:

| Service | Instrument | Unit | In Prometheus | Status label | Route label |
| --- | --- | --- | --- | --- | --- |
| employees-service (.NET) | `http.server.request.duration` | `s` | `http_server_request_duration_seconds` | `http_response_status_code` | `http_route`, such as `api/employees/{id:guid}` |
| notifications-service (Go) | `http.server.request.duration` | `s` | `http_server_request_duration_seconds` | `http_response_status_code` | `http_route` |
| projects-service (Python) | `http.server.duration` | `ms` | `http_server_duration_milliseconds` | `http_status_code` | `http_target`, such as `/api/projects/{project_id}` |

.NET and Go follow the current, stable HTTP conventions. The Python FastAPI instrumentation in this version still emits the older ones by default. A dashboard that covers every service has to query both, and you have to remember that one is in seconds and the other in milliseconds.

> [!NOTE]
> The OpenTelemetry Python instrumentations can switch to the stable names with `OTEL_SEMCONV_STABILITY_OPT_IN=http`. The Company app leaves the default on purpose: you'll meet this mismatch in real systems, and it's better to recognize it here first.

    sum by (department) (increase(company_employees_created_total[5m]))
    sum by (job, http_response_status_code) (rate(http_server_request_duration_seconds_count[1m]))

### Practice: count projects created

projects-service has no business metric (the gap you found on the [Observability page](3-application-development/3.5-observability.md#practice-find-the-gaps)). Add `company.projects.created`, counted only when a project is really saved, with the project's status as an attribute.

projects-service uses zero-code instrumentation, but your code can still record metrics. `opentelemetry-instrument` installs the global `MeterProvider` before the app is imported, so a meter from `metrics.get_meter(...)` exports through the same pipeline. Without it, in plain `pytest` for example, the API hands back a no-op meter, and counting costs nothing.

1. Create `projects-service/app/telemetry.py` with a small `ProjectMetrics` class. It takes an optional `Meter` (so a test can pass its own), falls back to `metrics.get_meter("projects-service")`, and creates the counter once:

    ```python
    self._created = meter.create_counter(
        "company.projects.created", unit="{project}", description="Projects created through the API"
    )

    def project_created(self, status: str) -> None:
        self._created.add(1, {"project.status": status})
    ```

2. Give `ProjectService.__init__` an optional `metrics: ProjectMetrics | None = None` parameter, defaulting to a new `ProjectMetrics()`. In `create_project`, call `self._metrics.project_created(...)` **after** `self._repository.add(project)` returns, so a create that fails (a duplicate name, say) is never counted.
3. Instruments are meant to live as long as the process. Create one `ProjectMetrics()` in `create_app` in `app/main.py`, store it on `app.state.metrics`, and pass it to `ProjectService` in the router's dependency function.
4. Test it without a collector. In `tests/unit/test_metrics.py`, build a private `MeterProvider` with an `InMemoryMetricReader` (both from `opentelemetry.sdk.metrics`), pass `ProjectMetrics(provider.get_meter("test"))` into the service with the fakes from `tests/fakes.py`, and write two tests:
    - creating three projects, two `planned` and one `active`, gives counts `{"planned": 2, "active": 1}`;
    - creating a duplicate of a seed project raises `ConflictError` and records nothing.

    Run `uv run pytest -m "not integration"` from `projects-service/`.
5. Rebuild with `docker compose up --build -d projects-service`, create a few projects in the UI, and find your counter in Prometheus. What is it called there, and what's its label called? Explain each difference from the names in your code.

### Apply: count assignments, and a RED dashboard

1. **The counter.** In assignments-service's `AssignmentService`, add `company.assignments.created`, unit `{assignment}`, created once as a `static readonly` field from `ServiceTelemetry.Meter`, the way employees-service does it. Increment it right after `store.AddAsync(...)`. Before you add any attributes, discuss as a team: which attributes would be useful, and which would explode the number of series? Write the decision in a comment next to the counter.
2. Check that `TelemetryExtensions` registers `ServiceTelemetry.Name` with `AddMeter`. Rebuild, create a few assignments, and query `company_assignments_created_total`.
3. **The dashboard.** k6 doesn't create assignments, so give assignments-service some traffic of its own while you build. Run this alongside k6; it lists assignments and, every few seconds, asks for one that doesn't exist:

    ```bash
    while true; do
      curl -s -o /dev/null localhost:8080/api/assignments
      curl -s -o /dev/null localhost:8080/api/assignments/00000000-0000-4000-8000-000000000000
      sleep 0.5
    done
    ```

4. Build a Grafana dashboard (**Dashboards → New → New dashboard**) with one row of RED panels per service, starting with assignments-service:
    - **Rate:** requests per second, by status code.
    - **Errors:** the fraction of requests that end in a 5xx.
    - **Duration:** p95 request duration.

    Add projects-service's row with its own metric names, and make both Duration panels show the same unit. Then add a panel for assignments created per minute.
5. **Break something.** Stop projects-service for a minute and create assignments in the UI. Which panels move, in which rows? Start it again, then save the dashboard and export it as JSON (**Export → Export as JSON**). Commit it to your repository as `docs/dashboards/red.json`.
