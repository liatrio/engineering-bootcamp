# Application Architecture

This section is about the shape of an application: what the moving pieces are, what each one is responsible for, and how they talk to each other. By the end of it your team will have the Company app running from its own repository and a written design for the service you are about to build.

## Why App Development Matters for Platform Engineers

You build the pipelines that ship applications, the clusters that host them, and the dashboards that watch them. For many platform engineers, the application itself is the one box in that picture they can't see into. This chapter is the case for opening it.

### Every platform decision is an app decision in disguise

Most infrastructure questions are really questions about how the application behaves.

| Question you get asked | What actually answers it |
| --- | --- |
| "Can we scale this to 10 replicas?" | Is the app **stateless**? Where does session or cached data live? |
| "Why does the pod fail its readiness probe?" | What does **startup** do: migrations, cache warming, connecting to a broker? |
| "The database is out of connections. Add more?" | How big is each replica's **connection pool**, and how many replicas share the database? |
| "How do we inject this secret?" | How does the app **read configuration**: environment variables, files, a vault client? |
| "Why is it returning 500s under load?" | Where is the **bottleneck**: a slow query, a blocking call, a dependency timing out? |
| "Can we deploy with zero downtime?" | Are **schema migrations** compatible with the version still running? |

None of the right-hand column needs you to enjoy writing UI code. It needs you to know what the app is doing when your platform runs it.

### You can't triage what you can't picture

At 3 a.m. the alert says "elevated 5xx rate". Without a mental model of the app, all you can do is restart pods, scale up, and page the developers. With one, you check the logs for *where* the request failed. Was it validation in the controller, a rule in the service, or the data access layer running out of connections? Then you fix the cause. Anyone who has traced one request through a controller, a service, and a database once can take the second path. You will do exactly that in [3.2.4 Service Communication](3-application-development/3.2.4-service-communication.md).

### Your customers are developers

A platform's users build applications on it. Templates and golden paths only get adopted if they fit how applications are really built. A service template that ignores database migrations gets forked and abandoned the first time a team needs one. A review comment such as "this endpoint has business logic in the controller" earns more trust than a perfectly tuned autoscaler.

### "But AI writes the code now"

It does, and that makes the fundamentals more valuable, not less. AI makes producing code cheap. It does not make *judging* code cheap. Someone still has to notice that the generated service opens a database connection per request, or keeps state in memory that vanishes on the next restart. Platform work is also turning into application work: Kubernetes operators, Backstage plugins, internal CLIs, and Terraform providers are all programs with inputs, state, errors, and a lifecycle.

> [!NOTE]
> The goal is narrower than becoming a full-stack developer. You should be able to **read** an unfamiliar codebase and find its routing, rules, and data access, **talk** about dependency injection, statelessness, and migrations with confidence, and **predict** how an app will behave on your platform before it gets there.

## Monolith or Microservices

There are two broad ways to package an application's features.

| | Monolith | Microservices |
| --- | --- | --- |
| Deployed as | One unit | Many small units, each deployed on its own |
| Data | Usually one database | Each service owns its data |
| A feature calls another feature | In-process function call | Network call (HTTP) or a message |
| Strengths | Simple to build, test, debug, and deploy | Teams and services change and scale independently; each can use a different stack |
| Costs | Grows tangled without discipline; one deploy for everything | Network failures, distributed debugging, more to operate, harder consistency |

Neither is "the modern one". Most successful microservice systems started as a monolith that got too big, and a well-structured *modular* monolith gives you many of the benefits with none of the network. [3.2.3 Microservices and Service Boundaries](3-application-development/3.2.3-microservices-and-service-boundaries.md) covers when each fits.

The Company app is built as microservices on purpose. You are platform engineers: the rest of the bootcamp containerizes, deploys, observes, and scales this app, and a multi-service, multi-language system is what you'll meet at clients.

## The Company App's End State

This is the system your team will have at the end of the chapter. Solid boxes are in the starter today. Dashed ones are what your team adds.

![Company app architecture](img/company-app-architecture_light.svg ':size=900px :class=light-mode-img-center :alt=Company app architecture: a browser talks to an nginx frontend-proxy, which routes to the web UI and four backend services. ![Company app architecture](img/company-app-architecture_dark.svg ':size=900px :class=dark-mode-img-center :alt=Company app architecture: a browser talks to an nginx frontend-proxy, which routes to the web UI and four backend services. Employees, projects, and assignments each own a database on one PostgreSQL server. Employees publishes events to RabbitMQ and notifications consumes them; assignments calls employees and projects over HTTP, publishes assignment.created, and consumes employee.deleted. flagd and otel-lgtm support every service; dark mode')

| Piece | Responsibility |
| --- | --- |
| `frontend-proxy` (nginx) | The only thing the browser talks to. Routes `/` to `web` and `/api/<name>` to that service, so there is one origin and no CORS. |
| `web` (React) | Renders the UI in the browser and calls the APIs through the proxy. |
| `employees-service` (.NET) | Owns employees. Publishes `employee.created`, `employee.updated`, and `employee.deleted`. |
| `projects-service` (Python) | Owns projects. Reads one feature flag from flagd. |
| `assignments-service` (.NET) | Owns assignments. Checks with employees and projects that IDs exist, publishes `assignment.created`, and removes assignments when it hears `employee.deleted`. |
| `notifications-service` (Go) | Listens to every event and keeps the latest 100 in memory as a feed. |
| PostgreSQL | One server with a separate database per service. No service reads another's database. |
| RabbitMQ | Carries events on the `company.events` topic exchange. |
| flagd | Serves feature flags (3.6). |
| `otel-lgtm` | Grafana with Loki, Tempo, and Prometheus-compatible storage. Every service sends logs, metrics, and traces to it (3.5). |

## Exercise: Run the Company App

Set up your team's repository and get the whole app running on every teammate's machine. Read the [hardware and tooling list](3-application-development/3.0-overview.md#what-you-need) first.

### 1. Create the team repository (one person)

1. Pick a name with your team, such as `<cohort>-company-app`, and the GitHub organization it lives in.
2. Copy the starter into a new repository and push it:

    ```bash
    git clone --depth 1 https://github.com/liatrio/engineering-bootcamp.git
    mkdir company-app
    cp -R engineering-bootcamp/examples/company-app/starter/. company-app/
    cd company-app
    git init -b main
    git add .
    git commit -m "chore: import the company app starter"
    gh repo create <org>/<repo-name> --private --source . --push
    ```

3. Add your teammates as collaborators, then add a branch rule for `main` (**Settings → Rules → Rulesets**) that requires a pull request with one approval before merging.

> [!IMPORTANT]
> Copy the *contents* of `starter/` (note the `/.`), not the folder itself. The repository root must contain `compose.yaml` and the service folders, because every later section and milestone assumes that layout.

### 2. Clone and start the app (everyone)

1. Clone the team repository and start everything:

    ```bash
    gh repo clone <org>/<repo-name>
    cd <repo-name>
    docker compose up --build -d
    ```

    The first build takes several minutes, because it builds four services and pulls the infrastructure images. Later starts take seconds. How Compose works is the subject of [4.5.1 Docker Compose](4-virtual-machines-containers/4.5.1-docker-compose.md); for now it is just how you run the app.

2. Check that everything is up:

    ```bash
    docker compose ps
    curl http://localhost:8080/api/employees
    ```

    `docker compose ps` lists nine running containers. The `curl` returns three seeded employees: Ada Lovelace, Grace Hopper, and Alan Turing.

> [!TIP]
> If a service keeps restarting, run `docker compose logs <service>`. The usual causes are Docker running out of memory or another program already using port 8080, 3001, 5433, 5672, or 15672.

### 3. Click through the app

1. Open `http://localhost:8080`. Look at the **Employees** and **Projects** pages.
2. On **Employees**, choose **New employee**, fill in the form, and choose **Create employee**.
3. Open **Notifications**. Within about five seconds, a line appears: *Employee &lt;name&gt; was created*. The web app never told notifications-service anything. Employees published an event, and notifications heard it.
4. Open **Assignments**. It says the service isn't running yet. That is the service your team builds.

### 4. Look behind the UI

1. Open RabbitMQ's management UI at `http://localhost:15672` (user `guest`, password `guest`).
    - Under **Exchanges**, open `company.events`. Its type is `topic`.
    - Under **Queues**, open `notifications`. Its binding key is `#`, which matches every event.
    - Create another employee and watch the queue's message rate move.
2. Open Grafana at `http://localhost:3001`. Go to **Explore**, choose the **Tempo** data source, and search for recent traces from `employees-service`. Open the trace for your `POST`. You'll learn to read it in [3.5 Observability](3-application-development/3.5-observability.md); for now, notice which services appear in it.

### 5. Answer these questions

Try each one, then write a sentence or two about what you saw and why.

1. Run `curl -i http://localhost:8080/api/assignments`. Which status code comes back, and which component sent it?
2. The browser only ever talks to port 8080. Call projects-service directly instead: `curl http://localhost:5102/api/projects`. Why is it useful that the same path works both ways?
3. Run `docker compose exec postgres psql -U postgres -l`. Which databases exist, and which one is empty?
4. Stop the notifications service with `docker compose stop notifications-service`. Create an employee, wait a few seconds, then run `docker compose start notifications-service` and reload **Notifications**. Did the new event arrive? What happened to the older notifications, and why?
5. Stop employees-service with `docker compose stop employees-service`. Which pages still work? Start it again afterwards.

> [!TIP]
> Stop everything with `docker compose down`. Add `-v` to also delete the database volume and start fresh next time.

## Deliverables
