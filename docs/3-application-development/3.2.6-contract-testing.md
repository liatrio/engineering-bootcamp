# Contract Testing

When two services talk to each other, each team usually tests its own side with [test doubles](3-application-development/3.2.3-test-doubles.md). The front-end team stubs the API, and the API team never calls the front end at all. Both suites pass, both services deploy, and production breaks, because the API renamed a field that the front end still reads. Each team's doubles described the other service the way it used to be, not the way it is now.

You could catch this with [end-to-end tests](3-application-development/3.2.7-end-to-end-testing.md) that deploy both services together, but those are slow and brittle, and they need every service deployed at compatible versions. Contract testing catches the same class of bug while testing each service on its own.

## Contracts

A **contract** is a written-down description of how two systems interact: the requests the consumer sends and the responses it expects back. Each side is tested against the contract independently:

- The **consumer** (the client) is tested against a mock provider that behaves exactly as the contract says.
- The **provider** (the service) is tested by replaying the contract's requests against the real provider and checking that its responses match.

If both sides pass, they agree on how to talk to each other, without ever being deployed together.

## Consumer-Driven Contracts

In **consumer-driven** contract testing, the consumer's tests produce the contract. Ian Robinson described the idea in [Consumer-Driven Contracts: A Service Evolution Pattern](https://martinfowler.com/articles/consumerDrivenContracts.html) (2006): a provider only needs to honor what its consumers actually use. That tells the provider team which fields and endpoints are safe to change, and which would break someone.

[Pact](https://docs.pact.io/) is the most widely used tool for this. Its documentation describes it as "a code-first tool for testing HTTP and message integrations using contract tests." [How Pact works](https://docs.pact.io/getting_started/how_pact_works):

1. The consumer's unit tests call a Pact mock server and declare the interactions they expect: "given a product with ID 10 exists, `GET /product/10` returns 200 with this JSON body."
2. Pact records those interactions in a **pact file**, which is the contract.
3. The contract is shared with the provider, usually through a **Pact Broker**.
4. The provider's build replays every interaction against the real provider and checks its responses. **Provider states** ("a product with ID 10 exists") let the provider set up the data each interaction needs.
5. Before deploying either side, the broker's `can-i-deploy` check confirms that the version you are about to release is compatible with the versions already running.

Pact supports many languages, including JavaScript, Java, Go, Python, and .NET. It also supports asynchronous messages, such as events on a queue, as well as HTTP.

## Provider-Driven and Schema-Based Contracts

Consumer-driven contracts work best when you know your consumers and can run their tests. For a public API with unknown consumers, the provider publishes the contract instead, often as an OpenAPI specification, and checks its implementation against it. Tools such as [Specmatic](https://specmatic.io/) can turn an OpenAPI document into contract tests and stubs.

## What Contract Tests Are Not

A contract test checks that two systems agree on the *shape* and *meaning* of their interactions. It doesn't check that the provider's business logic is correct. That is the job of the provider's own unit, component, and integration tests. Keep each interaction in a contract to the fields the consumer actually uses, so that the provider stays free to change everything else.

## Exercise

Pact's official [JavaScript workshop](https://github.com/pact-foundation/pact-workshop-js) walks through consumer-driven contract testing between a React front end and a product API. Each step lives on its own git branch (`step1`, `step2`, and so on), and the README explains what changes in each one.

1. Install the prerequisites listed in the workshop's README: Node.js with npm, plus Docker with Docker Compose, which the local Pact Broker in step 11 needs.
2. Clone the workshop and work through steps 1 to 11, checking out each branch in turn and running the tests as the README describes. Along the way you will:
    - see a consumer's stubbed unit tests pass while the real integration fails (steps 1 and 2);
    - write a consumer Pact test that generates a contract (step 3);
    - verify the contract against the real provider, which exposes the consumer's wrong assumption about an endpoint, and fix the consumer (steps 4 and 5);
    - add contract tests for missing data (`404`) and implement them on the provider with provider states (steps 6 and 7);
    - add authorization (`401`), and use a request filter to verify it (steps 8 to 10);
    - publish contracts to a Pact Broker running in Docker (step 11).
3. Steps 12 and 13 (broker webhooks, and the hosted PactFlow broker, which needs an account) are optional.

### Deliverables

- Your completed workshop through step 11.
- Explain the bug in step 2: why did the consumer's unit tests pass even though the integration was broken?
- Discuss: when would you choose contract tests over end-to-end tests, and what can contract tests not tell you?
- Discuss: in a system you know, which service-to-service interactions would benefit most from contract tests?
