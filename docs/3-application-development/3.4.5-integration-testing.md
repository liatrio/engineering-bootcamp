# Integration Testing

Unit and component tests replace a component's dependencies with [test doubles](3-application-development/3.4.3-test-doubles.md). That keeps them fast, but a double only behaves the way you programmed it to. It can't tell you that your SQL has a typo, that the database rejects a duplicate key, or that the payment API returns dates in a different format than you assumed. Integration tests close that gap by running your code against the **real** dependency.

## Narrow and Broad Integration Tests

"Integration test" is used for two quite different things. Martin Fowler's [Integration Test](https://martinfowler.com/bliki/IntegrationTest.html) article separates them:

- **Narrow integration tests** exercise only the part of your code that talks to one external system, such as a repository and its database, or an HTTP client and the API it calls. They run against a real instance of that one dependency, or a close stand-in, and nothing else.
- **Broad integration tests** need live versions of every service and exercise code paths across all of them. They need a full test environment, and they behave much like [end-to-end tests](3-application-development/3.4.7-end-to-end-testing.md).

This section is about narrow integration tests. They catch the bugs that doubles hide, while staying fast enough to run on every change.

## Writing Good Integration Tests

- **Test the boundary, not the business logic.** An integration test for a repository checks that data is saved, queried, and constrained correctly. Validation rules and other business logic belong in faster unit and component tests.
- **Use the same technology as production.** An in-memory or embedded database is convenient, but SQLite and PostgreSQL differ in SQL syntax, types, and locking, so a test against one can pass while production on the other fails. [Testcontainers](https://testcontainers.com/) starts real databases, message brokers, and other services in throwaway Docker containers from your test code, in most popular languages.
- **Start every test from a known state.** Create a fresh schema or database per test run, wrap each test in a transaction that you roll back, or give each test its own data, such as unique email addresses.
- **Keep the suite fast.** Start containers once per test run rather than once per test, and keep the number of integration tests proportionate to the number of boundaries you have.
- **Keep fakes honest.** If unit tests use an in-memory fake of a dependency, run the same tests against both the fake and the real thing. Fowler calls tests that check a double still behaves like the real service [contract tests](https://martinfowler.com/bliki/ContractTest.html), a theme the [next section](3-application-development/3.4.6-contract-testing.md) takes further.

## Exercise

The [repository pattern example](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/data-patterns/repository) from [Data Layer Patterns](3-application-development/3.3.2-data-layer-patterns.md) has two implementations of the same `UserRepository` interface: an in-memory fake and a SQLite repository. Its tests already run one shared suite, `testUserRepository`, against both. You don't need to have read Data Layer Patterns yet. This exercise only needs the interface in `service.go`.

1. Copy `examples/data-patterns/repository` into a new directory and run `go test ./...`. All tests should pass. (The SQLite driver uses cgo, so you need a C compiler, such as Xcode Command Line Tools on macOS.)
2. Read `impl_sqlite.go` and note the constraints the database enforces. Add a shared test that creating two users with the same email fails, and run it against both implementations.
3. The test passes against SQLite and fails against the in-memory fake. Decide which implementation is wrong, and fix it so both implementations behave the same.
4. Look for other places the implementations could disagree, and add a shared test for each:
    - Updating a user to an email that another user already has.
    - The order `FindAll` returns users in. Run the test several times (`go test -count=10 ./...`). Then decide whether callers should be able to rely on an order. If they should, make both implementations guarantee it. If they shouldn't, make the test order-independent.
5. **Stretch (requires Docker):** add a PostgreSQL implementation and run the same shared suite against it using [Testcontainers for Go](https://golang.testcontainers.org/modules/postgres/). Start the database with `postgres.Run` and connect with the URL from `ConnectionString`. Two things will differ from SQLite: PostgreSQL uses `$1`-style placeholders instead of `?`, and its drivers don't support `LastInsertId`, so read the new ID back with `INSERT ... RETURNING id`.

### Deliverables

- Your shared test suite, with every implementation passing it.
- Explain which bug the SQLite tests found that the in-memory tests could not, and why.
- Discuss: when is a fast in-memory fake good enough, and when do you need a test against the real database? What would you lose if the project only had integration tests?
