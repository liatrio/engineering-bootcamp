# Integration Testing

Unit and component tests replace a component's dependencies with [test doubles](3-application-development/3.4.3-test-doubles.md). That keeps them fast, but a double only behaves the way you programmed it to. It can't tell you that your SQL has a typo, that the database rejects a duplicate key, or that the payment API returns dates in a different format than you assumed. Integration tests close that gap by running your code against the **real** dependency.

## Narrow and Broad Integration Tests

"Integration test" is used for two quite different things. Martin Fowler's [Integration Test](https://martinfowler.com/bliki/IntegrationTest.html) article separates them:

- **Narrow integration tests** exercise only the part of your code that talks to one external system, such as a repository and its database, or an HTTP client and the API it calls. They run against a real instance of that one dependency, or a close stand-in, and nothing else.
- **Broad integration tests** need live versions of every service and exercise code paths across all of them. They need a full test environment, and they behave much like [end-to-end tests](3-application-development/3.4.7-end-to-end-testing.md).

This section is about narrow integration tests. They catch the bugs that doubles hide, while staying fast enough to run on every change.

## Writing Good Integration Tests

- **Test the boundary, not the business logic.** An integration test for a repository checks that data is saved, queried, and constrained correctly. Validation rules and other business logic belong in faster unit and component tests.
- **Use the same technology as production.** An in-memory or embedded database is convenient, but SQLite and PostgreSQL differ in SQL syntax, types, and locking, so a test against one can pass while production on the other fails. [Testcontainers](https://testcontainers.com/) starts real databases, message brokers, and other services in throwaway Docker containers from your test code, in most popular languages.
- **Start every test from a known state.** Create a fresh schema or database per test run, wrap each test in a transaction that you roll back, or give each test its own data, such as unique email addresses.
- **Keep the suite fast.** Start containers once per test run rather than once per test, and keep the number of integration tests proportionate to the number of boundaries you have.
- **Keep fakes honest.** If unit tests use an in-memory fake of a dependency, run the same tests against both the fake and the real thing. Fowler calls tests that check a double still behaves like the real service [contract tests](https://martinfowler.com/bliki/ContractTest.html), a theme the [next section](3-application-development/3.4.6-contract-testing.md) takes further.

## Exercise

All three backend starters have narrow integration tests that use Testcontainers: employees-service and projects-service against PostgreSQL 17, and notifications-service against RabbitMQ. You need Docker running for every step on this page.

> [!IMPORTANT]
> Testcontainers starts containers through your Docker socket, then connects to them. Inside the dev container, `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` is already set, so the tests reach those containers through your host. On macOS with Docker Desktop, the cleanup container (Ryuk) may fail to mount the socket. projects-service sets `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` in its `tests/conftest.py` for that reason, and you can export the same variable for the .NET and Go tests.

### Example: the Testcontainers tests in the starter

1. Open [`PostgresTestApp.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/PostgresTestApp.cs). It's a `WebApplicationFactory` like the component tests use, but it starts a real `postgres:17-alpine` container in `InitializeAsync`, points the connection string at it, and lets the app's own startup apply the migrations. Only RabbitMQ is faked. Why does it use the same PostgreSQL version as `compose.yaml`?
2. Open [`EmployeesDatabaseTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/Features/Employees/EmployeesDatabaseTests.cs). It's an `IClassFixture<PostgresTestApp>`, so the class shares one container: starting one per test would take seconds each. Find the `[Trait]` that lets you skip these tests, and the round-trip assertion that `createdAt` survives PostgreSQL to the millisecond.

    Then find the two unique-email tests. `EmployeeService` checks for a duplicate email before it saves, but that check can't stop two requests that arrive at the same moment: both look, both see no match, and both save. The real guarantee is the unique index on a lower-cased copy of the email, in [`EmployeeConfiguration.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeConfiguration.cs). One test goes straight to the `DbContext` and proves the index exists. The other proves the API answers 409. The API test would pass even without the index, because the service's check answers first. What does each test prove that the other can't?
3. Run only the integration tests, and time them against the fast suite:

    ```bash
    cd employees-service
    dotnet test --filter-trait "Category=Integration"
    ```

4. Skim projects-service's [`tests/integration/conftest.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/tests/integration/conftest.py), which starts PostgreSQL once per session and resets the seed rows before each test, and notifications-service's [`internal/consumer/integration_test.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/integration_test.go). Three languages, the same idea.

### Practice: prove a bad message can't break the consumer

notifications-service reads every event from RabbitMQ. When a message isn't valid JSON, `Handle` in [`consumer.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/consumer/consumer.go) logs it and calls `Nack` without requeue, so RabbitMQ throws the message away instead of redelivering it forever. The unit test `TestHandleNacksMalformedJSONWithoutRequeue` proves that `Handle` calls `Nack`, but it uses a fake acknowledger, so it can't show what the real broker does next. SPEC's gap for 3.4.5 is that no test proves, against a real RabbitMQ, that a bad message leaves the queue and the consumer keeps processing other events.

This step is in Go. You don't need to know Go well: the existing integration test is your template, and the shape is the same as the .NET and Python tests you just read. Work on a branch, `test/notifications-malformed-messages`.

1. Run the existing integration test:

    ```bash
    cd notifications-service
    go test -tags integration ./internal/consumer/
    ```

    The first line of `integration_test.go`, `//go:build integration`, keeps these tests out of a plain `go test ./...`. It does the same job as the `[Trait]` in .NET and the `integration` marker in pytest.

2. Read `TestConsumesFromRealRabbitMQ`, then move its setup into a helper that a second test can reuse: `startConsumer(t *testing.T) (string, *store.Store)` starts RabbitMQ, runs the consumer, waits until it's ready, and returns the broker URL and the store. Register the container's cleanup with `t.Cleanup`, and pass `t.Context()` to the consumer so it stops when the test ends. A small `publish` helper that sends one message keeps both tests short.
3. Add `TestDropsMalformedMessagesAndKeepsConsuming`:
    - publish `{not json` with the routing key `employee.created`, then a valid `assignment.created` event (copy the envelope's shape from the Events section of [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md));
    - wait until a notification of type `assignment.created` is stored. RabbitMQ delivers in order, so by then the bad message has been handled too;
    - assert that the store holds exactly one notification;
    - assert that the queue is empty: `ch.QueueDeclarePassive(Queue, true, false, false, false, nil)` returns the queue, and its `Messages` field counts the messages still waiting.
4. Run the integration tests. Both pass in about 15 seconds, most of it spent starting RabbitMQ.
5. Make sure your test catches something the unit tests can't. In `consumer.go`, change `BindingKey` from `"#"` to `"employee.*"`, so the queue only receives employee events. Run `go test ./internal/consumer/`: every unit test still passes. Run the integration tests: `TestConsumesFromRealRabbitMQ` still passes, and your new test fails after 30 seconds with `timed out waiting for assignment notification stored`. Put `"#"` back.
6. Discuss with a teammate: which mistakes can only show up against a real broker, and which would the unit tests catch faster?
7. Run `go vet -tags integration ./...` and `go test -tags integration ./...`, then open a pull request for notifications-service's owners to review.

> [!TIP]
> Compare with M3's [`integration_test.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/notifications-service/internal/consumer/integration_test.go).

### Apply: integration-test the assignments store

Your component tests use an in-memory store, which you wrote to behave like the `assignments` table. Now prove the real table behaves the way the fake does.

1. **The app.** Create `tests/AssignmentsService.Tests/PostgresTestApp.cs`, modeled on employees-service's:
    - start `postgres:17-alpine` with Testcontainers in `InitializeAsync`, then touch `Services` so the migrations run before the first test;
    - set the connection string from the container, and the other required settings to unused values;
    - remove the `EmployeeDeletedConsumer` hosted service, and replace both clients and the publisher with fakes. Expose the fake clients so tests can add IDs.
2. **The tests.** Create `Features/Assignments/AssignmentsDatabaseTests.cs` with `[Trait("Category", "Integration")]` and `IClassFixture<PostgresTestApp>`:
    - startup leaves no pending migrations;
    - an assignment can be created, read, updated, and deleted through the API, and an `endDate` comes back exactly as sent, which proves `DateOnly` maps to a `date` column;
    - straight to the `DbContext`, two rows for the same employee and project throw a `DbUpdateException` whose inner `PostgresException` is a unique violation, like employees-service's `The_database_rejects_an_email_that_differs_only_in_case`;
    - `RemoveForEmployeeAsync` deletes every assignment of one employee, and only theirs.
3. **Keep tests independent.** The tests share one database, so each test creates its own employee ID with `Guid.NewGuid()` and adds it to the fake employees client. No test depends on rows another test created, so the order doesn't matter.
4. Run `dotnet test --filter-trait "Category=Integration"`, then the whole suite, and open a pull request.
5. Update `docs/assignments-test-plan.md` if your integration tests ended up covering something different from what you planned.

> [!TIP]
> Compare with M3's [`PostgresTestApp.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/tests/AssignmentsService.Tests/PostgresTestApp.cs) and [`AssignmentsDatabaseTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/tests/AssignmentsService.Tests/Features/Assignments/AssignmentsDatabaseTests.cs).
