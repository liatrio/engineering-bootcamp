# Integration Testing

Unit and component tests replace a component's dependencies with [test doubles](3-application-development/3.4.3-test-doubles.md). That keeps them fast, but a double only behaves the way you programmed it to. It can't tell you that your SQL has a typo, that the database rejects a duplicate key, or that the payment API returns dates in a different format than you assumed. Integration tests close that gap by running your code against the **real** dependency.

## Narrow and Broad Integration Tests

"Integration test" is used for two quite different things. Martin Fowler's [Integration Test](https://martinfowler.com/bliki/IntegrationTest.html) article separates them:

- **Narrow integration tests** exercise only the part of your code that talks to one external system, such as a repository and its database, or an HTTP client and the API it calls. They run against a real instance of that one dependency, or a close stand-in, and nothing else.
- **Broad integration tests** need live versions of every service and exercise code paths across all of them. They need a full test environment, and they behave much like [end-to-end tests](3-application-development/3.4.7-end-to-end-testing.md).

This section is about narrow integration tests. They catch the bugs that doubles hide, while staying fast enough to run on every change.

## Writing Good Integration Tests

- **Test the boundary, not the business logic.** An integration test for a repository checks that data is saved, queried, and constrained correctly. Validation rules and other business logic belong in faster unit and component tests.
- **Use the same technology as production.** An in-memory or embedded database is convenient, but SQLite and PostgreSQL differ in SQL syntax, types, and locking, so a test against one can pass while production on the other fails. [Testcontainers](https://testcontainers.com/) starts real databases, message brokers, and other services in throwaway Docker containers from your test code, in most popular languages.
- **Start every test from a known state.** Create a fresh schema or database per test run, wrap each test in a transaction that you roll back, or give each test its own data, such as unique email addresses.
- **Keep the suite fast.** Start containers once per test run rather than once per test, and keep the number of integration tests proportionate to the number of boundaries you have.
- **Keep fakes honest.** If unit tests use an in-memory fake of a dependency, run the same tests against both the fake and the real thing. Fowler calls tests that check a double still behaves like the real service [contract tests](https://martinfowler.com/bliki/ContractTest.html), a theme the [next section](3-application-development/3.4.6-contract-testing.md) takes further.

## Exercise

All three backend starters have narrow integration tests that use Testcontainers: employees-service and projects-service against PostgreSQL 17, and notifications-service against RabbitMQ. You need Docker running for every step on this page.

> [!IMPORTANT]
> Testcontainers starts containers through your Docker socket, then connects to them. Inside the dev container, `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` is already set, so the tests reach those containers through your host. On macOS with Docker Desktop, the cleanup container (Ryuk) may fail to mount the socket. projects-service sets `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock` in its `tests/conftest.py` for that reason, and you can export the same variable for the .NET and Go tests.

### Practice: prove the database enforces unique emails

employees-service promises that no two employees share an email, ignoring case. `EmployeeService` checks that before it saves, but that check can't stop two requests that arrive at the same moment: both look, both see no match, and both save. The real guarantee is the unique index on a lower-cased copy of the email, in [`EmployeeConfiguration.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeConfiguration.cs). SPEC's gap for 3.4.5 is that no test proves the index exists. Work on a branch, `test/employees-unique-email`.

1. Add a test to `EmployeesDatabaseTests` that goes straight to the `DbContext`, past the service's check, and saves two employees whose emails differ only in case:

    ```csharp
    await using var scope = app.Services.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<EmployeesDbContext>();
    db.Employees.AddRange(Row("Hedy@example.com"), Row("hedy@EXAMPLE.com"));

    var ex = await Assert.ThrowsAsync<DbUpdateException>(() => db.SaveChangesAsync(Ct));

    Assert.Equal(PostgresErrorCodes.UniqueViolation, Assert.IsType<PostgresException>(ex.InnerException).SqlState);
    ```

    `Row(email)` is a private helper that returns a new `Employee` with a new ID. `PostgresErrorCodes` and `PostgresException` come from `using Npgsql;`. Name the test `The_database_rejects_an_email_that_differs_only_in_case`.

2. Run the integration tests. The new test passes.
3. Make sure it can fail: change the second email to `hedy.lamarr@example.com` and run it again. It fails with `Assert.Throws() Failure: No exception was thrown`, so the test really depends on the index. Put the email back.
4. Add an API-level test, `The_api_returns_409_for_a_duplicate_email_in_another_case`: `POST` `Mary@example.com`, then `mary@example.com`, and assert 201 and then 409. The shared database outlives each test, so use emails no other test uses.
5. Discuss with a teammate: test 4 would pass even without the index, because the service's check answers first. So what does each test prove that the other can't?
6. Run `dotnet test` and open a pull request.

> [!TIP]
> Compare with M3's [`EmployeesDatabaseTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/employees-service/tests/EmployeesService.Tests/Features/Employees/EmployeesDatabaseTests.cs).

### Apply: integration-test the assignments store

Your component tests use an in-memory store, which you wrote to behave like the `assignments` table. Now prove the real table behaves the way the fake does.

1. **The app.** Create `tests/AssignmentsService.Tests/PostgresTestApp.cs`, modeled on employees-service's:
    - start `postgres:17-alpine` with Testcontainers in `InitializeAsync`, then touch `Services` so the migrations run before the first test;
    - set the connection string from the container, and the other required settings to unused values;
    - remove the `EmployeeDeletedConsumer` hosted service, and replace both clients and the publisher with fakes. Expose the fake clients so tests can add IDs.
2. **The tests.** Create `Features/Assignments/AssignmentsDatabaseTests.cs` with `[Trait("Category", "Integration")]` and `IClassFixture<PostgresTestApp>`:
    - startup leaves no pending migrations;
    - an assignment can be created, read, updated, and deleted through the API, and an `endDate` comes back exactly as sent, which proves `DateOnly` maps to a `date` column;
    - straight to the `DbContext`, two rows for the same employee and project throw a `DbUpdateException` whose inner `PostgresException` is a unique violation, as in the Practice step;
    - `RemoveForEmployeeAsync` deletes every assignment of one employee, and only theirs.
3. **Keep tests independent.** The tests share one database, so each test creates its own employee ID with `Guid.NewGuid()` and adds it to the fake employees client. No test depends on rows another test created, so the order doesn't matter.
4. Run `dotnet test --filter-trait "Category=Integration"`, then the whole suite, and open a pull request.
5. Update `docs/assignments-test-plan.md` if your integration tests ended up covering something different from what you planned.

> [!TIP]
> Compare with M3's [`PostgresTestApp.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/tests/AssignmentsService.Tests/PostgresTestApp.cs) and [`AssignmentsDatabaseTests.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M3-tested/assignments-service/tests/AssignmentsService.Tests/Features/Assignments/AssignmentsDatabaseTests.cs).
