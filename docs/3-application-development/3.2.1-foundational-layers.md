# Foundational Layers

Some parts of an application are needed by *every* feature: routing, auth, validation, error handling, data access, observability and configuration, testing, and conventions. This page is about building each of those once, before the first feature, and how the Company app's starter services do it.

## Two Ways to Start an App

Imagine two teams building the same company directory.

**Team A starts with a feature.** They build Employees end to end: a controller, a service, a table, a form. It works. Then they build Projects by copying Employees and renaming things. Projects needs a 404, so someone writes a `try/catch` in the controller. Assignments needs a 409 for "already assigned", so someone else returns `StatusCode(409, "dupe")`. By the fifth feature there are three ways to return an error, two ways to validate input, and a database context built by hand in one service because its author didn't know about the shared one. Every feature is a little slower than the last, and every bug fix has to be made in several places.

**Team B starts with the foundation.** Before Employees exists, they decide: URLs look like `/api/employees`. Every error is a Problem Details response produced by one handler. Input is validated by one mechanism. There is one database context, and services get it injected. They write those rules down in a file at the root of the repository. *Then* they build Employees, and it is small, because the hard parts are done. Projects is smaller still. A new teammate can build the sixth feature without asking where a 404 comes from.

> [!NOTE]
> A **foundational layer** is a capability that every feature needs and no feature should implement. You build it once, in one place, and features *use* it rather than *re-create* it.

## What Every Feature Needs

You can't know every feature an app will have. You can know what every feature will need, because the list barely changes between applications.

| Layer | The question it answers once |
| --- | --- |
| **Routing** | How does a URL reach code, and what do URLs look like? Deciding `/api/employees/{id}` once means nobody ships `/getEmployee?id=4`. |
| **Authentication and authorization** | Who is calling, and may they? If everything is protected unless it opts out, a forgotten setting fails safe. |
| **Input validation** | Bad input is rejected *before* feature code runs, in the same error shape every time. Features declare rules; the foundation enforces them. |
| **Error handling** | One handler decides how "not found" becomes a 404 and how an unexpected exception becomes a 500 with no stack trace. Features just throw. |
| **Data access** | One configured connection and one pattern for reads and writes. Nobody builds their own database context or their own `fetch` wrapper. |
| **Observability and configuration** | Logs and traces with request context, health endpoints for the platform, and settings read from one place that change per environment. |
| **Testing** | One harness that boots the app with test doubles, and a rule for what every feature must cover. |
| **Conventions** | Where files go, what they are called, and which patterns are in and out. Not code, but what makes the code predictable. |

## The Foundation in employees-service

In an ASP.NET Core service, [`Program.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Program.cs) is the foundation's table of contents. Everything above `builder.Build()` registers a capability; everything below it puts that capability in the request pipeline. Open it now and notice that it mentions the Employees feature in only two lines.

| Layer | Where it lives in employees-service |
| --- | --- |
| Routing | `AddControllers()` and `MapControllers()`; `[Route("api/employees")]` on the controller; `AddOpenApi()` serves `/openapi/v1.json` |
| Auth | [`Infrastructure/Auth/BearerTokenMiddleware.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Auth/BearerTokenMiddleware.cs): checks `/api/*` only when `AUTH_TOKEN` is set |
| Validation | `[ApiController]` plus data annotations on the request DTO |
| Error handling | [`Infrastructure/Errors/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Errors): two exception types and one `GlobalExceptionHandler` |
| Data access | [`Infrastructure/Data/EmployeesDbContext.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Data/EmployeesDbContext.cs), registered with `AddDbContext`; migrations applied on startup |
| Observability and config | [`Infrastructure/Configuration/ServiceOptions.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Configuration/ServiceOptions.cs), [`Infrastructure/Health/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Health), [`Infrastructure/Telemetry/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Telemetry) |
| Testing | [`tests/EmployeesService.Tests/ComponentTestApp.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/tests/EmployeesService.Tests/ComponentTestApp.cs): boots the real app with fakes |
| Conventions | `Features/<Name>/` for feature code, `Infrastructure/` for the foundation |

Four of these layers are worth seeing up close, because they are the ones Team A kept reinventing.

### Error handling: features throw, the foundation responds

The foundation defines a small vocabulary of exceptions that mean something in HTTP terms, in [`DomainExceptions.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Errors/DomainExceptions.cs): `NotFoundException` and `ConflictException`. One handler, [`GlobalExceptionHandler.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Errors/GlobalExceptionHandler.cs), translates them:

```csharp
var status = exception switch
{
    NotFoundException => StatusCodes.Status404NotFound,
    ConflictException => StatusCodes.Status409Conflict,
    _ => StatusCodes.Status500InternalServerError,
};
```

It logs only the unexpected 500s, and it never sends an unexpected exception's message to the client, because that message can leak table names or connection details. Now a service anywhere in the app writes one line, and the controller has no `try/catch`:

```csharp
var employee = await store.FindAsync(id, ct) ?? throw new NotFoundException(nameof(Employee), id);
```

Adding a new kind of failure, such as a 503 when a dependency is down, is one line in the `switch`, and every feature gets it.

### Validation: features declare rules, the foundation enforces them

With `[ApiController]` on a controller, a request whose body fails validation never reaches the action method. The framework returns a 400 with field errors, in the same Problem Details shape the error handler uses. [`EmployeeDtos.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeeDtos.cs) only declares the rules:

```csharp
[Required, EmailAddress, StringLength(254, MinimumLength = 3)]
public string Email { get; init; } = "";
```

`Program.cs` adds one more detail: a metadata provider that makes the `errors` keys use the JSON names (`email`, not `Email`), so the web form can show each message next to the right field.

### Data access: one context, injected everywhere

There is exactly one `DbContext`. It lives in the foundation, but it learns each feature's tables from configuration classes that live *with* the feature, through `ApplyConfigurationsFromAssembly`. Adding a table never means editing a big central file. Because it is registered with `AddDbContext`, it is scoped to one HTTP request, and nobody outside `Program.cs` reads a connection string.

employees-service adds one small seam on top: [`IEmployeeStore`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/IEmployeeStore.cs), a thin interface with methods named after what the service needs. It exists so the component tests in 3.4.4 can run the whole HTTP stack against an in-memory fake instead of PostgreSQL. Read its comment for why that fake beats EF Core's in-memory provider.

### Configuration: typed, validated at startup

Every setting comes from an environment variable, bound to [`ServiceOptions`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Configuration/ServiceOptions.cs) with the options pattern:

```csharp
builder.Services.AddOptions<ServiceOptions>()
    .Bind(builder.Configuration)
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

`ValidateOnStart` means a missing `RABBITMQ_URL` stops the service at startup with a clear message, instead of failing on the first request an hour later. The same image runs on a laptop, in CI, and in production, with only the environment changing. That is the [twelve-factor](https://12factor.net/config) rule, and the platform chapters rely on it.

## The Foundation in web

The React app has the same layers. They live in [`src/app/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/app) (composition) and [`src/lib/`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib) (capabilities every feature uses).

| Layer | Where it lives in web |
| --- | --- |
| Routing | [`src/app/router.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/app/router.tsx): one route table; each feature exports its routes, and adding one is a single spread |
| Validation | react-hook-form with a zod schema per form; [`src/lib/ui/serverErrors.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib/ui/serverErrors.ts) copies a 400's field errors onto the same inputs |
| Error handling | [`src/lib/api.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib/api.ts) turns any non-2xx into an `ApiError`; [`RouteError.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/app/RouteError.tsx) catches what renders wrong |
| Data access | `api()` for every request, and TanStack Query for caching, loading states, and refetching ([`providers.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/app/providers.tsx) sets the retry rules once) |
| Observability | [`src/lib/telemetry.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib/telemetry.ts): browser traces sent through the proxy |
| Testing | [`src/test/renderWithProviders.tsx`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/test/renderWithProviders.tsx) wires the router and query client for every component test |
| Conventions | `src/features/<name>/` per feature; `src/lib/` for shared code |

Read across the two tables and you'll notice that **the foundation on one side shapes the foundation on the other**. Every service fails with Problem Details, so `ApiError` can rely on that shape. The API returns field-level errors with JSON names, so the form can show them next to the right input. Designing both sides together is what makes several services feel like one application.

## Same Layers, Different Languages

The Company app's other services solve the same problems in their own languages. The concern stays the same; only the mechanism changes.

| Layer | employees-service (.NET) | projects-service (Python) | notifications-service (Go) |
| --- | --- | --- | --- |
| Routing | Controllers with attribute routes | `APIRouter(prefix="/api/projects")` in [`app/routers/projects.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/app/routers/projects.py) | `http.ServeMux` patterns such as `"GET /api/notifications"` |
| Auth | Middleware in the pipeline | A FastAPI dependency, `Depends(require_token)`, on the router | A `requireToken` wrapper around the handler |
| Validation | Data annotations | Pydantic models in `app/schemas.py` | None needed: it accepts no request bodies |
| Error handling | `IExceptionHandler` | `register_exception_handlers()` in [`app/errors.py`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/projects-service/app/errors.py), with the same type URIs as ASP.NET Core | A `writeProblem` helper |
| Data access | `DbContext` + `IEmployeeStore` | A SQLAlchemy session per request + a `ProjectRepository` protocol | An in-memory store (the feed is allowed to vanish on restart) |
| Config | Options pattern | pydantic-settings in `app/config.py` | `config.Load()` |
| Observability | OpenTelemetry SDK configured in code | Zero-code `opentelemetry-instrument` in the Dockerfile | SDK in code, plus a hand-written carrier to read trace headers from RabbitMQ |
| Testing | xUnit + `WebApplicationFactory` | pytest + fakes in `tests/fakes.py` | `go test` with table tests |

projects-service teaches one thing employees-service doesn't: **dependency injection doesn't need a container**. FastAPI builds a `ProjectService` per request from small functions such as `get_project_service`, declared with `Depends`. The idea, "a feature asks for what it needs instead of building it", is the same. You'll go deeper in 3.3.

## Choosing Libraries and Writing It Down

Every layer involves a choice: a library, a built-in, or a hand-written helper. The choices matter less than making them *once* and *on purpose*. Four tests help:

- **Is it the boring default?** Prefer what the framework ships or what most of the ecosystem uses. Boring means documented, searchable, and already familiar to the next person, or the next model.
- **Does it remove code from features?** A validation library that still needs an `if` in every controller hasn't earned its place.
- **Can it be swapped behind a seam?** If features depend on your wrapper, such as `api()`, `IEventPublisher`, or `IEmployeeStore`, replacing the library later touches one file, not fifty.
- **Would you want two of them?** If the honest answer is "no, there should be exactly one", it belongs in the foundation.

Some things aren't foundation on day one but become it: a shared form component once two screens need it, or a cache once two features hit the same slow query. Leave them in the first feature and promote them when the second one asks. [3.2.2 Vertical Slices](3-application-development/3.2.2-vertical-slices.md#rules-that-keep-slices-clean) makes this a rule.

Then write the decisions down, in the repository, next to the code. A conventions file at the root that says *where things go, what they are called, and which patterns are in and out* is the cheapest layer to build and the one with the highest return.

> [!NOTE]
> Coding agents read the repository before they write to it. Claude Code, Cursor, GitHub Copilot, and others look for a file such as [`AGENTS.md`](https://agents.md/) at the root and treat it as standing instructions. A codebase with a clear foundation and a written conventions file gives an agent what it gives a new hire: one right way to do each thing, and an example to copy. Ask an agent to "add a feature like Employees" in Team B's codebase and you get a controller that throws `NotFoundException`. Ask the same in Team A's, and it copies whichever of the three error styles it saw first.

### Apply: decide the foundation for assignments-service

Your service is .NET, and employees-service is its model. Decide, layer by layer, what it copies, what it extends, and what it adds. Write the result where both humans and agents will read it.

1. On a new branch (`docs/agents-md`), create `AGENTS.md` at the root of your team repository with three sections:
    - **A one-paragraph description** of the app and what your team is adding.
    - **Layout:** a table of the top-level folders, what each is, and its stack.
    - **Foundation decisions:** a table with the columns *Layer*, *.NET services* (employees and assignments), *Web*, and *Why*. Add a **Messaging** row, because two of your services publish events.
2. Fill in the *Why* column with one sentence per row. For example, the error-handling row might say *"features throw and never map status codes, so every error has the same shape for the UI"*. If a row stumps you, write `?` and come back after 3.3.
3. Decide these three for assignments, and record each one in the right row:
    - Which `Infrastructure/` folders can it copy from employees-service unchanged? (Look at `Auth`, `Configuration`, `Data`, `Errors`, `Health`, `Messaging`, and `Telemetry`.)
    - What must `GlobalExceptionHandler` learn? Assignments must answer **503** when employees-service or projects-service is unreachable, and **400 with `errors.employeeId`** when an employee doesn't exist.
    - Which settings does `ServiceOptions` gain? Check the configuration table in [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md).
4. Open a pull request and ask a teammate to review it with one question in mind: *could I build a feature from this file without asking anyone?*
