# Logging

A log is a timestamped record of something that happened: a request arrived, an employee was created, a message couldn't be read. Logs are the oldest and most familiar signal, and the one with the most detail about a single event. They are also the easiest to get wrong: too little, and you can't diagnose a problem; too much, and the one line that matters is buried in noise, or a password ends up in your log storage.

## Structured Logging

Traditional logs are free-form text:

```text
2026-11-05 14:02:11 ERROR Failed to publish employee.deleted 8b5cf86d; the event was lost
```

That is easy for a person to read, but hard for a machine to search: to find every lost event of one type, you have to write a regular expression and hope the wording never changes. **Structured logs** record each event as a message plus named fields, usually as JSON:

```json
{"time": "2026-11-05T14:02:11Z", "level": "ERROR", "message": "event lost",
 "event_type": "employee.deleted", "trace_id": "8e08810122a82dcdd0105155af69ec4b"}
```

Now you can filter by `event_type`, count by `level`, and jump straight to the request's trace through `trace_id`. Keep the message short and constant, and put the variable parts in fields.

.NET builds this into its logging API. The first argument is a **message template**, not a finished string, and each `{Placeholder}` becomes a field:

```csharp
logger.LogInformation("Published {EventType} {EventId}", type, envelope.EventId);
```

The formatted message reads naturally, and `EventType` and `EventId` are kept as separate fields. Writing `logger.LogInformation($"Published {type}")` instead throws the structure away: the interpolated string is a different message every time.

## Log Levels

Levels let you separate routine events from problems, and turn the volume up or down without changing code. The names differ slightly between languages (.NET says `Warning` and `Critical`, Python `WARNING` and `CRITICAL`, Go's `slog` `WARN`), but the meaning is the same:

| Level | Use it for |
| --- | --- |
| Debug | Detail that's only useful while developing or diagnosing a specific problem. Usually off in production. |
| Information | Normal, significant events: an employee was created, an event was published. |
| Warning | Something unexpected that the application handled, such as a dependency that didn't answer, or a retried call. |
| Error | An operation failed and needs attention. |
| Critical | The application can't continue. |

If you log something at Error, someone should eventually need to act on it. A level that cries wolf trains people to ignore it.

Levels are configured, not hard-coded. In .NET, the `Logging:LogLevel` section of `appsettings.json` sets a minimum level per category. employees-service's [`appsettings.json`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/appsettings.json) keeps its own code at `Information` but raises ASP.NET Core and EF Core's SQL logging to `Warning`, because traces already record every request and query.

## Good Logging Practices

- **Write logs to standard output** and let the platform collect them. [The Twelve-Factor App](https://12factor.net/logs) puts it this way: "each running process writes its event stream, unbuffered, to `stdout`." Containers, Kubernetes, and log agents all expect this. That's where `docker compose logs` reads them from.
- **Correlate logs with traces.** Include the trace ID in every log line written during a request, so you can move from a log to the full request and back. OpenTelemetry does this for you.
- **Never log secrets or sensitive data.** The [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) lists data that should usually not be recorded directly in logs, including passwords, access tokens, session IDs, database connection strings, encryption keys, payment card data, and sensitive personal data. Logs are copied, shipped, and retained far more widely than databases.
- **Log events, not every line of code.** Log what happened and the context needed to understand it, once, at the place where it's handled. An exception logged at every layer it passes through appears five times and helps no one.
- **Use metrics for counting.** If you mostly want to know *how many* times something happened, a [metric](3-application-development/3.5.2-metrics.md) is far cheaper than searching millions of log lines.

## Logs in the Company App

Every starter service writes JSON to standard output, with the trace ID in each line, and also sends the same records to Loki over OTLP:

| Service | How |
| --- | --- |
| employees-service | `AddJsonConsole(options => options.IncludeScopes = true)` in [`TelemetryExtensions.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Telemetry/TelemetryExtensions.cs). The `TraceId` and `SpanId` arrive in a *scope*, so `IncludeScopes` is what puts them in the line. `WithLogging(...)` sends the same records over OTLP. |
| projects-service | Python's standard `logging`, formatted as JSON. The zero-code logging instrumentation adds `trace_id` and `span_id` to every record and exports it. |
| notifications-service | Go's `log/slog` with a JSON handler, wrapped in a small handler in [`telemetry.go`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/notifications-service/internal/telemetry/telemetry.go) that copies `trace_id` and `span_id` from the context. |

Errors that reach a client carry the trace ID too: every Problem Details response has a `traceId` field. When someone reports "I got a 503", that field takes you straight to the logs and the trace.

## Exercise

### Example: three languages, one log format

With the app running and k6 load going (`docker compose --profile load up -d load`):

1. Look at the raw lines on standard output:

    ```bash
    docker compose logs employees-service | grep Published | tail -1
    docker compose logs projects-service | tail -1
    docker compose logs notifications-service | tail -1
    ```

    - Where is the trace ID in each service's line? Which one has the most fields, and where do they come from?
    - In the employees-service line, find `{OriginalFormat}`. What is it, and why is it useful to keep alongside the formatted message?

2. In Grafana **Explore**, choose **Loki** and run `{service_name="projects-service"}`. Expand a line.
    - Which logger wrote most of these lines? Is it application code or the web server?
    - Which attributes did OpenTelemetry add that aren't in the JSON on standard output?

3. Find every Error-level line in the whole app:

    ```logql
    {service_name=~".+"} | severity_text=~"Error|ERROR"
    ```

    If the app has started at least once with a fresh database, you'll find one from EF Core in employees-service: `Failed executing DbCommand ... FROM "__EFMigrationsHistory"`. Read [3.3.4](3-application-development/3.3.4-data-and-persistence.md) again if you need to: what was EF Core doing, and did anything actually fail? Should someone be woken up for it?

### Practice: follow one deletion through three services

When an employee is deleted, employees-service publishes `employee.deleted`, and both notifications-service and assignments-service react. Each writes its own log line in its own language. One trace ID ties them together.

1. In Loki, find a deletion:

    ```logql
    {service_name="employees-service"} |= "Published employee.deleted"
    ```

    Expand the newest line and copy its `trace_id`.

2. Query every service's logs for that trace ID:

    ```logql
    {service_name=~".+"} | trace_id="<the trace id>"
    ```

    You should see three lines, from three services: *Published employee.deleted ...*, *notification stored*, and *Employee ... was deleted; removed 0 assignments*. If assignments-service's line is missing, you haven't done the [Apply step on the Observability page](3-application-development/3.5-observability.md#apply-wire-opentelemetry-into-assignments-service) yet.

3. Answer:
    - The message crossed RabbitMQ between the first line and the other two. What carried the trace ID across, and which service had to write code by hand to read it? (Look for `HeaderCarrier` in notifications-service.)
    - Which of the three lines would you change, and how? Consider the message, the fields, and the level.
    - From one of the lines, open the trace: paste the trace ID into a Tempo query. How does the waterfall match the three log lines?

### Apply: logs worth reading in assignments-service

The `AddTelemetry` you copied in the [Observability Apply step](3-application-development/3.5-observability.md#apply-wire-opentelemetry-into-assignments-service) already writes JSON with trace IDs and exports to Loki. Now make sure what assignments-service logs is worth that plumbing.

1. **Check the correlation.** Run `{service_name="assignments-service"}` in Loki. Expand a line written during a request and find `trace_id`. Then run `docker compose logs assignments-service | tail -3` and find the same trace ID in the `Scopes` of the JSON.

2. **Follow an error report.** Stop projects-service and create an assignment through the proxy:

    ```bash
    docker compose stop projects-service
    curl -s -X POST localhost:8080/api/assignments -H 'Content-Type: application/json' \
      -d '{"employeeId":"33333333-3333-4333-8333-333333333333","projectId":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","role":"Advisor","allocationPercent":10,"startDate":"2026-01-05"}'
    docker compose start projects-service
    ```

    The 503 response has a `traceId` like `00-0f4a9b82...-46773c43...-03`. That's a W3C `traceparent`: the second part is the trace ID. Use it to find every log line for that request in Loki.
    - How many lines are there, and which component wrote each one? (The retry lines come from the resilience handler you added in [3.3.5](3-application-development/3.3.5-calling-other-services.md).)
    - At which level is the "dependency unavailable" line? Do you agree with it, given what the service did for the client?

3. **Review every log statement.** List every place assignments-service logs, with its level and message. For each one, decide:
    - Is the message a constant template with `{Placeholders}`, not an interpolated string?
    - Does the level match the table in [Log Levels](#log-levels)? Would anyone act on each Error?
    - Could any field ever contain something from the [OWASP list](#good-logging-practices)? Pay attention to anything logged from a request body or a message.
    - Is anything important missing? Think about what you'd want to know if a consumer silently stopped removing assignments.

    Fix what you find in a pull request, and explain each change in its description.

4. **Turn the volume down.** Check that assignments-service's `appsettings.json` raises `Microsoft.AspNetCore` and `Microsoft.EntityFrameworkCore.Database.Command` to `Warning`, as employees-service does. Then rebuild, and compare how many lines per request assignments-service writes with how many spans its traces have.

> [!TIP]
> M5's assignments-service logs through `[LoggerMessage]` source-generated methods, for example at the bottom of [`EmployeeDeletedConsumer.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M5-observable/assignments-service/src/AssignmentsService/Features/Assignments/EmployeeDeletedConsumer.cs). They're the same message templates, checked at compile time and cheaper at run time.
