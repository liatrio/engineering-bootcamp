# Flag Types

Not all flags are alike. A flag that hides a half-built feature for a week needs different handling from one that disables an expensive feature during an outage, or one that gives paying customers extra features for years.

## Four Categories

Pete Hodgson's [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) article sorts flags into four categories, along two dimensions: **longevity** (how long the flag lives) and **dynamism** (how often its decision changes, from per deployment to per request).

| Category | Used for | Lifetime | Decision changes |
| --- | --- | --- | --- |
| **Release** | Shipping unfinished or untested code switched off, so the main branch can always deploy | Days or weeks, until the feature is released | Rarely; usually the same for every user |
| **Experiment** | A/B and multivariate tests that compare how groups of users behave | Hours or weeks, long enough for a meaningful result | Per user: each user stays in their group |
| **Ops** | Controlling operational behavior, such as switching off a new feature with unknown performance cost, or a long-lived **kill switch** that sheds non-essential work under heavy load | Mostly short; kill switches can last years | Quickly, by operators during an incident |
| **Permission** | Giving some users features others don't have: premium features, or early access for internal and beta users | Can be years | Per user, on every request |

The category tells you how to manage the flag. A release flag should have a removal date. An ops flag must be easy for an on-call engineer to change quickly. A permission flag is really part of your product and deserves the same care as the rest of your business logic.

## Safe Defaults

Every flag check in your code supplies a default value, and that value runs whenever the flag can't be evaluated: the flag service is down, the flag was deleted, the flag has a typo in its name, or the service is pointed at the wrong flag service. Choose the default deliberately, as the behavior you'd want if the flag system failed:

- For a **release flag**, the default is usually the old behavior, so a failure never exposes an unfinished feature. That's why `assignment-notifications` defaults to `false`.
- For a **kill switch**, the default is usually "feature available", so a failure in the flag system doesn't cause an outage of its own. That's why `employee-events` defaults to `true`.

Some flag providers keep the last values they received, so a short outage of the flag service goes unnoticed. Don't count on it. The .NET flagd provider, used the way the Company app uses it (RPC, no cache), asks flagd on every evaluation, and the moment flagd can't be reached, every evaluation returns the code default. You'll see that in the exercise. When flagd comes back, the provider reconnects on its own within a few seconds.

Write the default next to the flag key, as a named constant, with a comment that says why. Then a reviewer can check the choice, and nobody has to guess what `false` meant.

## Removing Flags

Flags that have done their job become **flag debt**: branches that always go the same way, extra test cases, and confusion about which code is live. Hodgson recommends treating flags as inventory with a carrying cost, and keeping that inventory low. Teams do it in several ways:

- **Add a removal task to the backlog when you create a release flag**, so removal is planned work, not a favor.
- **Record an owner and an expiry date** with each flag.
- **Limit the number of flags** a service may have at once, so adding one means removing another.

Remove a flag in two steps. First, deploy code that no longer checks the flag, keeping the behavior you released. Then delete the flag from the flag system. In the opposite order, the running code would fall back to its default the moment the flag disappeared, and for a release flag that default is the *old* behavior.

flagd lets you record ownership in the flag file itself. Each flag can carry a `metadata` object that flagd returns with every evaluation but doesn't act on:

```json
"assignment-notifications": {
  "state": "ENABLED",
  "variants": { "on": true, "off": false },
  "defaultVariant": "off",
  "metadata": { "type": "release", "owner": "assignments team", "expires": "2026-12-31" }
}
```

## Exercise

### Example: classify the Company app's flags

1. Look at the flags table on the [Feature Flags page](3-application-development/3.6-feature-flags.md#flags-in-the-company-app). For each flag, decide its category, how long you'd expect it to live, and who should be allowed to change it in production.
2. For each flag, find its code default (or decide what it should be, for those you haven't built yet) and check it against [Safe Defaults](#safe-defaults). Is there one where you'd argue for the other default?
3. Add `metadata` with `type` and `owner` to `project-description-required`, `employee-events`, and `assignment-notifications` in `infra/flagd/flags.flagd.json`, and an `expires` date to the release flags. Then ask flagd for one of them and find your metadata in the answer:

    ```bash
    curl -s -X POST localhost:8013/flagd.evaluation.v1.Service/ResolveBoolean \
      -H 'Content-Type: application/json' -d '{"flagKey":"employee-events","context":{}}'
    ```

### Practice: what employee-events does when flagd fails

Test the kill switch you added to employees-service in the [Feature Flags Practice step](3-application-development/3.6-feature-flags.md#practice-an-employee-events-flag-in-employees-service). Stop the k6 load first, so the notification feed only shows your own changes.

1. **flagd stops.** Run `docker compose stop flagd`, then create an employee. Is it published? Check **Notifications**. Which value did the flag check return, and where did it come from?
2. **The switch can't be used.** Now imagine RabbitMQ is misbehaving and you need publishing off *right now*. Switch `employee-events` to `"off"` in the flag file and create another employee. What happens, and what does that tell you about depending on the flag system during an incident?
3. **flagd comes back.** Run `docker compose start flagd`, wait five seconds, and create a third employee. Is the `"off"` value honored now? Switch the flag back to `"on"`.
4. **The wrong default.** Change `EventsDefault` to `false`, rebuild employees-service, and repeat step 1. Explain why this is worse, even though the code still "works". Then change it back.
5. Write your results from steps 1 to 4 in a short table: flagd state, flag value in the file, what the service did, and why.

### Apply: an assignments-writes kill switch

Add an ops flag to assignments-service, `assignments-writes`. When it's off, `POST`, `PUT`, and `DELETE` return **503 Service Unavailable** with a Problem Details body that says why, while `GET` keeps working. That lets an operator freeze changes during a data migration or an incident without taking the service down.

1. Add `Writes = "assignments-writes"` to `AssignmentFlags`, with a default chosen by [Safe Defaults](#safe-defaults). Write the reason in a comment.
2. Add an exception for "deliberately switched off" next to the other domain exceptions, such as `FeatureSwitchedOffException`, and map it to 503 in the global exception handler. Why is 503 better here than 403 or 409?
3. In `AssignmentService`, check the flag at the start of `CreateAsync`, `UpdateAsync`, and `DeleteAsync`, before any validation or calls to other services. Leave `RemoveForEmployeeAsync` alone: discuss with your team why the `employee.deleted` consumer should keep working when writes are switched off.
4. Add the flag to the flag file, `on` by default, with `metadata`. Rebuild, then:

    ```bash
    curl -s -X POST localhost:8080/api/assignments -H 'Content-Type: application/json' \
      -d '{"employeeId":"33333333-3333-4333-8333-333333333333","projectId":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","role":"Advisor","allocationPercent":10,"startDate":"2026-01-05"}'
    ```

    With the flag on, you get a 201 (or a 409 if you've already made that assignment). Switch it off and send it again: a 503 with your message. Then check that `GET /api/assignments` still answers 200, and look at what the Assignments page in the UI shows when you try to create one. Is it clear enough for a user?
5. Delete an employee who has an assignment while `assignments-writes` is off. Is the assignment removed? Should it be?
6. Switch the flag back on, and update your tests so they compile and pass. You'll write proper tests for each flag in [OpenFeature](3-application-development/3.6.3-openfeature.md).

> Compare with `EnsureWritesEnabledAsync` in M6's [`AssignmentService.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M6-flagged/assignments-service/src/AssignmentsService/Features/Assignments/AssignmentService.cs) and the exception mapping in its [`GlobalExceptionHandler.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M6-flagged/assignments-service/src/AssignmentsService/Infrastructure/Errors/GlobalExceptionHandler.cs).
