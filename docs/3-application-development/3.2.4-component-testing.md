# Component Testing

A component test checks one component of a system, such as a service, a module, or a front-end widget, through its public interface, with everything outside the component replaced by [test doubles](3-application-development/3.2.3-test-doubles.md). Martin Fowler's [definition](https://martinfowler.com/bliki/ComponentTest.html) is a test that "limits the scope of the exercised software to a portion of the system under test."

Component tests sit between unit and integration tests:

- A **unit test** checks a single function or class.
- A **component test** checks many units working together inside one component, driven the way a real caller would drive it, but with no real external dependencies.
- An **integration test** checks a component against a real dependency, such as a database or another service.

For a web service, a component test sends real HTTP requests to the service running in the test process, and stubs out the databases, queues, and other services it talks to. Because it never leaves the process, it stays fast and deterministic, yet it exercises the routing, validation, business logic, and serialization together. Those are often where bugs hide: in how the units fit together rather than in any single one.

## What Makes a Good Component Test

- **Drive the public interface.** Call the component the way its clients do, such as an HTTP endpoint, a CLI command, or a module's exported functions, rather than reaching into internal classes. Then the tests survive refactoring.
- **Replace only what is outside the component.** Use in-memory fakes or stubs for databases and remote services, but let the component's own layers run for real.
- **Assert on observable behavior**, such as the response status and body, or the data handed to a dependency, rather than on which internal methods were called.
- **Isolate every test.** Each test should start from a known state. Shared state between tests makes the results depend on the order the tests run in.

Toby Clemson's [Testing Strategies in a Microservice Architecture](https://martinfowler.com/articles/microservice-testing/) shows where component tests fit alongside the other test types in a service-based system.

## Exercise

The [layered Flask application](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/layered-architecture/example2) from the [Layers](3-application-development/3.3-layers.md) section has a presentation layer (routes), a service layer (validation), and a data layer (an in-memory repository). Its existing tests in `tests/test_routes.py` already drive the app through Flask's test client. In this exercise you will extend them into a proper component test suite.

1. Copy `examples/layered-architecture/example2` into a new directory and run the existing tests with `uv run --with flask --with pytest pytest`. Both should pass.
2. Read Flask's [testing guide](https://flask.palletsprojects.com/en/stable/testing/), then add tests in `tests/test_component.py` for these behaviors:
    - `GET /users` returns the two seed users, Alice and Bob.
    - `POST /users` with a missing name, an empty name, or a non-string name returns `400` with an error message.
    - A user created with `POST /users` appears in the next `GET /users`.
3. Run the whole suite. One of your new tests will probably fail when it runs after `test_routes.py`, even though it passes on its own (`pytest tests/test_component.py`). Work out why.
4. Fix the isolation problem with a [pytest fixture](https://docs.pytest.org/en/stable/how-to/fixtures.html) that gives every test a fresh app and fresh data. Keep the change outside the routes and the service layer.
5. Run the suite several times, and in a different order (for example `pytest tests/test_component.py tests/test_routes.py`), to confirm the results no longer depend on order.

### Deliverables

- Your component test suite and fixture.
- Explain what was causing the order-dependent failure, and how your fixture prevents it.
- Discuss: these tests use the in-memory repository rather than a real database. What kinds of bugs could they miss? Which kind of test from the next section would catch them?
