# OpenFeature

Every feature flag vendor ships its own SDK, and code written against one vendor's SDK has to be rewritten to move to another. [OpenFeature](https://openfeature.dev/docs/reference/intro/) solves this the way [OpenTelemetry](3-application-development/3.5.4-opentelemetry.md) does for telemetry: it defines one vendor-neutral API for evaluating flags, with SDKs for many languages, and leaves the flag management to whichever system you plug in. It is a [CNCF incubating project](https://www.cncf.io/projects/openfeature/).

## The Pieces

| Piece | What it does | In the Company app |
| --- | --- | --- |
| **API and client** | What your code calls: `GetBooleanValueAsync(...)` in .NET, `get_boolean_value(...)` in Python, and so on. The same in every application, whatever system stores the flags. | `IFeatureClient`, injected into `EmployeeService` and `AssignmentService`; `api.get_client("projects-service")` |
| **[Provider](https://openfeature.dev/docs/reference/concepts/provider/)** | The adapter between the API and a flag management system, such as flagd, a commercial vendor, or an in-memory provider for tests. Switching systems means switching providers, not rewriting flag checks. | The flagd provider in every service; `InMemoryProvider` in .NET tests |
| **[Evaluation context](https://openfeature.dev/docs/reference/concepts/evaluation-context/)** | Facts about the request, set globally, per client, per request, or per call, and merged before each evaluation. | The `allocation-check` targeting key |
| **[Hooks](https://openfeature.dev/docs/reference/concepts/hooks/)** | Code that runs before and after every evaluation, for cross-cutting concerns such as logging, validation, or telemetry. | `TraceEnricherHook` |

Each evaluation can also return its **details**, not just the value: the variant, an error code if it failed, and a **reason**. Reasons include `STATIC` (no targeting rules), `TARGETING_MATCH` (a rule chose the variant), `DEFAULT` (a rule ran but fell back to the default variant), `DISABLED`, `CACHED`, and `ERROR`. In .NET, call `GetBooleanDetailsAsync(...)` instead of `GetBooleanValueAsync(...)` to see them.

## flagd

[flagd](https://flagd.dev/) is OpenFeature's own flag service. It reads flag definitions from files, HTTP endpoints, or Kubernetes resources, and evaluates them. A flagd provider can use it in two ways:

- **RPC** (the default): the application asks flagd for each evaluation over the network, with gRPC. Some providers cache flags without targeting rules and let flagd tell them when they change; the .NET provider's cache is off by default, so every evaluation is a call.
- **In-process**: flagd sends the flag definitions to the application, and the provider evaluates them locally, with no network call per evaluation. Set `FLAGD_RESOLVER=in-process` (or the provider's equivalent option) to use it.

## Flags in Telemetry

When a request misbehaves, you need to know which flags it saw. OpenTelemetry's [semantic conventions for feature flags](https://opentelemetry.io/docs/specs/semconv/feature-flags/) define a `feature_flag.evaluation` event. OpenFeature's .NET SDK ships a hook, `TraceEnricherHook`, that adds that event to the current span after every evaluation, so each trace records the flag decisions made during its request. In the Company app, each event carries:

| Attribute | Example |
| --- | --- |
| `feature_flag.key` | `allocation-check` |
| `feature_flag.result.variant` and `feature_flag.result.value` | `off`, `False` |
| `feature_flag.result.reason` | `targeting_match` (the hook writes reasons in lower case) |
| `feature_flag.provider.name` | `flagd Provider` |
| `error.type` and `error.message` | Only when evaluation failed, such as `providernotready` and the connection error |

That last row is the one that saves you. A flag check that fails doesn't throw: it quietly returns the code default, and the service carries on. Without telemetry, a misconfigured provider looks exactly like a flag that's switched off.

## Testing Flagged Code

A flag doubles the paths through the code it guards, and a test suite that only ever sees one variant leaves the other untested. Test both, and test the default too. Your tests shouldn't depend on a running flag service, or on whatever the shared flag file says today, so give them an **in-memory provider** that returns exactly the variants each test needs.

Providers are registered with OpenFeature's API, which is shared state. If one test's flags can leak into the next, results depend on the order the tests run in. Either reset the provider after each test, or, as the Company app's .NET tests do, give each test its own provider: a separate OpenFeature *domain* in unit tests, and a separate provider per test app in component tests.

projects-service takes a third route: its code depends on a small `FeatureFlags` protocol instead of OpenFeature, and its tests pass a hand-written fake. That's simpler, but it skips the OpenFeature evaluation path entirely, so hooks and providers are never exercised in tests.

### Practice: flags in employees-service's traces and tests

1. **The hook.** In employees-service's `Program.cs`, add `.AddHook(_ => new TraceEnricherHook())` (from `OpenFeature.Hooks`) to the `AddOpenFeature` registration. Rebuild, create an employee, and find the event:

    ```traceql
    {resource.service.name="employees-service" && event:name = "feature_flag.evaluation"}
    ```

    Open the trace and find the event on the `publish employee.created` span you saw in [Tracing](3-application-development/3.5.3-tracing.md). Which flag, variant, and reason does it record?
2. Look at the spans *outside* the main tree in the same trace: `POST` client spans to `flagd:8013/.../ResolveBoolean`. What are they, how long do they take, and why does Grafana show them without a parent? (Hint: their parent is a span from the gRPC client library, which nothing is configured to export.)
3. **A test for the off switch.** Replace the `Api.Instance.GetClient()` from the [Feature Flags Practice step](3-application-development/3.6-feature-flags.md#practice-an-employee-events-flag-in-employees-service) with a client backed by an `InMemoryProvider` (from `OpenFeature.Providers.Memory`), registered under a domain of its own so parallel tests don't share it:

    ```csharp
    var flags = new Dictionary<string, Flag>
    {
        [EmployeeFlags.Events] = new Flag<bool>(new() { ["on"] = true, ["off"] = false }, defaultVariant: "off"),
    };
    var domain = Guid.NewGuid().ToString();
    await Api.Instance.SetProviderAsync(domain, new InMemoryProvider(flags));
    var client = Api.Instance.GetClient(domain);
    ```

    Write a test that creates an employee with `employee-events` off and asserts the employee is saved and nothing is published. Keep the existing tests running with the flag on.
4. Component tests start the whole app, with the flagd provider. Make them independent of flagd too: in the test app's `ConfigureServices`, find the `FeatureProvider` registration that `AddOpenFeature` added, remove it, and register an `InMemoryProvider` under the same service key. Stop flagd and run `dotnet test`. Every test should pass.

### Apply: flags in traces, and in tests

1. **The hook.** Add `TraceEnricherHook` to assignments-service's `AddOpenFeature` registration and rebuild. Create an assignment in the UI and open its trace. You should see up to three `feature_flag.evaluation` events on the server span.
    - Why does `assignment-notifications` have the reason `static` and `allocation-check` the reason `targeting_match`?
    - If the assignment was rejected for an unknown employee, which events are missing, and what does that tell you about where each flag is checked?
    - The browser sent no `X-User-Id`. Which targeting key did `allocation-check` use?
2. **Watch the rollout.** With `allocation-check` still at 50/50 from [Rollouts and Experiments](3-application-development/3.6.2-rollouts-and-experiments.md#apply-roll-out-the-allocation-rule), rerun the `check` loop for 100 users. Then count the evaluations by variant:

    ```traceql
    {event.feature_flag.key = "allocation-check" && event.feature_flag.result.variant = "on"}
    ```

    Raise **Limit** under **Search Options** to 200 so every trace is listed, then run it again with `"off"`. Do the counts match your loop's? Write a query that finds requests where the rule was on *and* the response was a 409.
3. **See a misconfiguration.** Now find out what the [IMPORTANT note on the Feature Flags page](3-application-development/3.6-feature-flags.md#practice-an-employee-events-flag-in-employees-service) was protecting you from. In `Program.cs`, comment out the two lines that set `flagd.Host` and `flagd.Port`, rebuild assignments-service, and create an assignment.
    - Does the request succeed? Does anything in the UI or the response look wrong?
    - Open the trace. What do the flag events say now? Read `error.message`: which host did the provider try to reach?
    - Switch `assignments-writes` off in the flag file and try to create another assignment. What happens, and why is that more dangerous than an error?

    Put the two lines back and rebuild. Then add a sentence to the **Rules** in your `AGENTS.md` about checking a new provider's configuration in a trace before trusting it.

4. **Tests for every flag.** Write a small `TestFlags` helper in the test project that builds `InMemoryProvider`s for your three flags, starts each flag on, lets a test switch one off, and records the targeting key `allocation-check` was evaluated with (a `Flag<bool>`'s `contextEvaluator` receives the context). Use it in both your unit tests (a domain per test) and your component test app (replacing the keyed provider, as in Practice step 4). Then test:
    - with `assignment-notifications` off, an assignment is saved but nothing is published;
    - with `assignments-writes` off, create, update, and delete are refused, and the API returns 503;
    - with `assignments-writes` off, listing and the `employee.deleted` clean-up still work;
    - with `allocation-check` off, an employee can be booked over 100%;
    - the rollout uses `X-User-Id` as the targeting key when it's sent, and the employee ID when it isn't.
5. Stop flagd and run the whole test suite. Every test should pass. Start flagd again.
