# OpenFeature

Every feature flag vendor ships its own SDK, and code written against one vendor's SDK has to be rewritten to move to another. [OpenFeature](https://openfeature.dev/docs/reference/intro/) solves this the way [OpenTelemetry](3-application-development/3.3.4-opentelemetry.md) does for telemetry: it defines one vendor-neutral API for evaluating flags, with SDKs for many languages, and leaves the flag management to whichever system you plug in. It is a [CNCF incubating project](https://www.cncf.io/projects/openfeature/).

## The Pieces

| Piece | What it does |
| --- | --- |
| **API and client** | What your code calls: `client.get_boolean_value(...)`, `get_string_value(...)`, and so on. The same in every application, whatever system stores the flags. |
| **[Provider](https://openfeature.dev/docs/reference/concepts/provider/)** | The adapter between the API and a flag management system, such as flagd, a commercial vendor, or an in-memory provider for tests. Switching systems means switching providers, not rewriting flag checks. |
| **[Evaluation context](https://openfeature.dev/docs/reference/concepts/evaluation-context/)** | Facts about the request, set globally, per client, per request (the *transaction context*), or per call, and merged before each evaluation. |
| **[Hooks](https://openfeature.dev/docs/reference/concepts/hooks/)** | Code that runs before and after every evaluation, for cross-cutting concerns such as logging, validation, or telemetry. |

Each evaluation can also return its **details**, not just the value: the variant, an error code if it failed, and a **reason**. Reasons include `STATIC` (no targeting rules), `TARGETING_MATCH` (a rule chose the variant), `DEFAULT`, `DISABLED`, `CACHED`, and `ERROR`. Call `get_boolean_details(...)` instead of `get_boolean_value(...)` to see them.

## flagd

[flagd](https://flagd.dev/) is OpenFeature's own flag service. It reads flag definitions from files, HTTP endpoints, or Kubernetes resources, and evaluates them. The flagd provider can use it in two ways:

- **RPC** (the default): the application asks flagd for each evaluation over the network. Flags without targeting rules are cached in the application, and flagd tells it when they change.
- **In-process**: flagd sends the flag definitions to the application, and the provider evaluates them locally, with no network call per evaluation. Set `FLAGD_RESOLVER=in-process` to use it.

## Flags in Telemetry

When a request misbehaves, you need to know which flags it saw. OpenTelemetry's [semantic conventions for feature flags](https://opentelemetry.io/docs/specs/semconv/feature-flags/) define a `feature_flag.evaluation` event, with attributes such as `feature_flag.key`, `feature_flag.result.variant`, and `feature_flag.result.reason`. OpenFeature's OpenTelemetry hook adds that event to the current span after every evaluation, so each trace records the flag decisions made during its request.

## Testing Flagged Code

A flag doubles the paths through the code it guards, and a test suite that only ever sees one variant leaves the other untested. Test both, and test the default too. Your tests shouldn't depend on a running flag service, so set an **in-memory provider** that returns exactly the variants each test needs. The provider is global state, so reset it after each test, or one test's flags leak into the next.

## Exercise: Trace and Test Flagged Code

This exercise continues from the [Rollouts and Experiments exercise](3-application-development/3.4.2-rollouts-and-experiments.md#exercise-roll-out-a-change-to-a-percentage-of-users), with flagd running and `strict-names` at 50/50. For the first part, you also need the `grafana/otel-lgtm` stack from the [Observability exercises](3-application-development/3.3-observability.md#exercise-set-up-the-stack).

1. Install the OpenTelemetry hook with `pip install openfeature-hooks-opentelemetry`. In `app/flags.py`, before setting the provider, register it with `api.add_hooks([TracingHook()])`, imported from `openfeature.contrib.hook.opentelemetry`.
2. Restart the app under `opentelemetry-instrument`, with the environment variables from the Observability exercises. Send short-name requests as 20 different users, with the `post` function from the previous exercise.
3. In Grafana Explore, search Tempo with TraceQL for traces that recorded a flag evaluation, then open one that returned `400`. New traces can take a few seconds to appear.

    ```traceql
    {event:name = "feature_flag.evaluation"}
    ```

    - Find the `feature_flag.evaluation` events on the request span. Which flags were evaluated, and with which variant and reason?
    - Why is the reason different for `user-signups` and `strict-names`?
    - The trace has a second span, for a gRPC call. What is it, and how long did it take?
    - `feature_flag.context.id` holds the user ID from your request. What should you check before sending flag events like this from a production system?
4. Finish the rollout: set `strict-names`' `defaultVariant` to `"on"` and remove its `targeting` block. Send three requests, a second apart, and compare their traces. How do the gRPC span and the `strict-names` reason change after the first request, and why?
5. Now test both sides of the flag. Create `tests/test_flags.py` that sets an `InMemoryProvider` (from `openfeature.provider.in_memory_provider`) with the variants each test needs. For example, `InMemoryFlag("on", {"on": True, "off": False})` is a flag whose variant is `on`. Write tests for:
    - a one-character name, rejected when `strict-names` is on and accepted when it is off;
    - a create request when `user-signups` is off.
6. Add `tests/conftest.py` with an `autouse` fixture that calls `api.clear_providers()` after each test. Stop flagd, then run `pytest`. Every test should pass without flagd running.

### Deliverables

- Your hook registration, a screenshot of a trace showing the flag events, and your answers to the questions in step 3.
- Your tests and fixture, and the `pytest` output.
- Remove the fixture from step 6 and run the whole test suite, including the original tests in `tests/test_routes.py`. What can fail, and why does it depend on the order the tests run in?
- Discuss: your team uses flagd today and might move to a commercial flag vendor next year. What would have to change in this application, and what wouldn't?
