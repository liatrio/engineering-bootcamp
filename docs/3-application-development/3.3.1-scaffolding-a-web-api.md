# Scaffolding a Web API

A .NET Web API is three things: a project file, a `Program.cs` that wires services and the request pipeline, and a folder of controllers. The template gives you a working one in a single command. This page takes that template and turns it into a service that fits the Company app: it reads its configuration from the environment, tells the platform whether it's alive and ready, builds into a container image, and runs behind the proxy with everything else.

## Install the .NET SDK

The SDK includes the `dotnet` CLI, the compiler, and the runtime. You need **.NET 10**, the current long-term-support release. Pick one of two ways.

### Option 1: the dev container

Your team repository has a [dev container](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/.devcontainer/devcontainer.json) with .NET 10, Python and uv, Go, Node, and the Docker CLI. Open the repository in VS Code with the [Dev Containers extension](https://code.visualstudio.com/docs/devcontainers/containers) and choose **Reopen in Container**, or open it in GitHub Codespaces. Nothing else to install.

### Option 2: install it on your machine

- **macOS:** `brew install --cask dotnet-sdk`
- **Windows:** `winget install Microsoft.DotNet.SDK.10`, then open a new terminal so `dotnet` is on your `PATH`.
- **Linux:** follow [Install .NET on Linux](https://learn.microsoft.com/dotnet/core/install/linux) for your distribution, or use the [install script](https://learn.microsoft.com/dotnet/core/install/linux-scripted-manual#scripted-install) with `--channel 10.0`.

For an editor, [VS Code](https://code.visualstudio.com/) with the [C# Dev Kit](https://marketplace.visualstudio.com/items?itemName=ms-dotnettools.csdevkit) extension gives you IntelliSense, debugging, and a test runner. Rider and Visual Studio work too.

Check the install:

```bash
dotnet --version
```

It prints a version starting with `10.`. If the command isn't found, open a new terminal and try again. SDKs install side by side, so .NET 10 won't break projects that use an older version; `dotnet --list-sdks` shows everything installed.

## What the Template Gives You

`dotnet new webapi --use-controllers` creates a project with controller classes and attribute routing, the style employees-service uses (the alternative, minimal APIs, maps lambdas in `Program.cs` instead).

| File | What it is |
| --- | --- |
| `<Project>.csproj` | The project file: target framework, build settings, and NuGet packages |
| `Program.cs` | The entry point: registers services, builds the app, sets up the request pipeline |
| `Controllers/WeatherForecastController.cs`, `WeatherForecast.cs` | A sample endpoint you'll delete |
| `appsettings.json`, `appsettings.Development.json` | Logging settings. In the Company app, nothing else goes here. |
| `Properties/launchSettings.json` | Ports and environment variables for `dotnet run` on your machine. Never used in a container. |
| `<Project>.http` | Example requests you can send from your editor |

### Registration, then the pipeline

`Program.cs` has two halves, split by `builder.Build()`:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();      // registration: what exists
builder.Services.AddOpenApi();

var app = builder.Build();
app.MapOpenApi();                       // pipeline: what happens to each request
app.MapControllers();
app.Run();
```

Everything above `Build()` registers a capability in the dependency injection container ([3.3.3](3-application-development/3.3.3-dependency-injection-and-solid.md) covers it in depth). Everything below decides, in order, what happens to an incoming request. employees-service's [`Program.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Program.cs) has the same shape with more lines, each under a comment saying which foundation concern it belongs to.

## Configuration from the Environment

The same container image runs on your laptop, in CI, and in production. Only its environment changes. So the Company app's rule, from [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md#conventions-for-every-backend-service), is that **configuration comes from environment variables only**: no URLs, ports, or credentials in code or in `appsettings.json`.

ASP.NET Core already reads environment variables into its configuration. Two habits make that safe to use:

- **The options pattern.** Bind every setting into one typed class, and inject `IOptions<ServiceOptions>` wherever a setting is needed. Nobody calls `Configuration["SOME_KEY"]` with a string they might misspell. `[ConfigurationKeyName]` maps the SPEC's `SCREAMING_CASE` names onto C# property names.
- **Fail fast.** `ValidateDataAnnotations()` checks the attributes on the class, and `ValidateOnStart()` does it when the app starts, not when the first request happens to need the value. A missing variable stops the deploy with a message naming it, instead of a 500 an hour later.

```csharp
[Required(ErrorMessage = "EMPLOYEES_URL must be set, for example http://localhost:5101.")]
[Url]
[ConfigurationKeyName("EMPLOYEES_URL")]
public string EmployeesUrl { get; init; } = "";
```

The database connection string is the one exception: it uses the standard `ConnectionStrings__Default` key, because EF Core tooling understands it. The double underscore is how an environment variable spells the `:` in a nested configuration key.

## Liveness and Readiness

Docker Compose, and later Kubernetes, ask a running container two different questions:

| Endpoint | Question | Checks | On failure the platform |
| --- | --- | --- | --- |
| `GET /healthz` | Is the process alive? | Nothing. If it can answer, it's alive. | Restarts the container |
| `GET /readyz` | Can it do its job right now? | The dependencies it owns: its database and RabbitMQ | Stops sending it traffic, but leaves it running |

Keep liveness dumb. If `/healthz` checked the database, a database outage would make the platform restart every replica in a loop, which fixes nothing. A failing readiness check is the right signal: "don't send me requests until the database is back".

ASP.NET Core's health checks do both with one mechanism. Each check gets a tag, and each endpoint runs the checks whose tags match. employees-service's [`HealthEndpoints.cs`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Health/HealthEndpoints.cs) maps `/healthz` to no checks and `/readyz` to every check tagged `ready`.

> [!NOTE]
> Readiness covers what the service **owns**. assignments-service will call employees-service and projects-service, but they are deliberately left out of its `/readyz`. If they were in, one of them going down would mark assignments unready, and the platform would stop sending it requests that don't need either of them, like listing assignments.

## The Container Image

Every backend service ships as a multi-stage `Dockerfile`: a build stage with the full SDK, and a small runtime stage with only the ASP.NET Core runtime and the published app, running as a non-root user. You'll write your own in [Chapter 4.4](4-virtual-machines-containers/4.4-containers.md). For now you copy employees-service's [`Dockerfile`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/Dockerfile), change the project name, and say so at the top:

```dockerfile
# Copied from employees-service; you'll write your own in Chapter 4.4.
# Only the project name changed.
```

The image has no `HEALTHCHECK`: compose defines its own checks, and so will Kubernetes.

### Practice: see fail-fast configuration and readiness at work

With the app running (`docker compose up -d`):

1. Ask employees-service both questions:

    ```bash
    curl -s localhost:5101/healthz
    curl -s localhost:5101/readyz
    ```

    The first prints `{"status":"ok"}`. The second prints `{"status":"ok","checks":{"postgres":"healthy","rabbitmq":"healthy"}}`.

2. Stop RabbitMQ and ask again:

    ```bash
    docker compose stop rabbitmq
    curl -si localhost:5101/readyz
    curl -s localhost:5101/healthz
    ```

    `/readyz` now answers `503 Service Unavailable` with `"rabbitmq":"unhealthy"`, while `/healthz` still says `ok`. The process is fine; one of its dependencies isn't. Notice that the response names the failing check but not the error message, because probes are unauthenticated and error messages can leak internals.

3. Start RabbitMQ again with `docker compose start rabbitmq`. Within a few seconds `/readyz` is back to 200, without restarting employees-service.
4. Start a one-off copy of employees-service with `RABBITMQ_URL` set to an empty value:

    ```bash
    docker compose run --rm --no-deps -e RABBITMQ_URL= employees-service
    ```

    Before it serves anything, it logs `OptionsValidationException` with the message `RABBITMQ_URL must be set, for example amqp://guest:guest@localhost:5672/.` Press `Ctrl+C` to get your prompt back.

5. Write down: what would have happened instead if the options weren't validated at startup? When would you have found out, and what would the error have looked like?

### Apply: scaffold assignments-service

One person does this on a branch, `feat/assignments-scaffold`, and everyone else reviews the pull request and runs it locally. `assignments-service/` already exists from M1 and holds your `openapi.yaml` sketch; the project goes next to it.

1. Generate the project and a solution file, and copy the repository-level files from employees-service:

    ```bash
    cd assignments-service
    dotnet new webapi --use-controllers -n AssignmentsService -o src/AssignmentsService
    dotnet new sln -n AssignmentsService
    dotnet sln add src/AssignmentsService
    cp ../employees-service/global.json ../employees-service/.gitignore ../employees-service/.dockerignore .
    ```

    `dotnet new sln` creates `AssignmentsService.slnx`, the newer XML solution format. `global.json` pins the SDK version and opts the tests you'll write in 3.4 into the new test runner.

2. Delete the sample: `src/AssignmentsService/WeatherForecast.cs` and the whole `src/AssignmentsService/Controllers/` folder. Create `Features/Assignments/` and `Infrastructure/` folders instead, matching employees-service.
3. In `AssignmentsService.csproj`, copy employees-service's two extra build settings into the `<PropertyGroup>`:

    ```xml
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <InvariantGlobalization>true</InvariantGlobalization>
    ```

4. **Configuration.** Create `Infrastructure/Configuration/ServiceOptions.cs`. Start from employees-service's copy, keep `RabbitMqUrl` and `AuthToken`, drop the seed and provider-state settings (assignments has neither), and add required `EmployeesUrl` and `ProjectsUrl` properties like the example above. Change the namespace to `AssignmentsService.Infrastructure.Configuration`.
5. **Health.** Copy `Infrastructure/Health/HealthEndpoints.cs` from employees-service and change its namespace. Leave `RabbitMqHealthCheck.cs` behind for now; there's no RabbitMQ connection yet.
6. **Program.cs.** Replace the template's contents with the foundation so far:
    - the `UseSetting(WebHostDefaults.HttpPortsKey, ...)` line that listens on `PORT`;
    - the `AddOptions<ServiceOptions>()` registration with `ValidateDataAnnotations()` and `ValidateOnStart()`;
    - `AddControllers()`, `AddOpenApi()`, and `AddHealthChecks()` with no checks yet;
    - in the pipeline: `MapOpenApi()` (always, not only in Development), `MapHealthEndpoints()`, and `MapControllers()`.

    Leave out the template's `UseHttpsRedirection()` and `UseAuthorization()`. Inside compose, services talk plain HTTP and the proxy is the only way in; TLS belongs at the edge, which Chapter 8 covers.

7. **A first endpoint.** So the web app has something to call, create `Features/Assignments/AssignmentsController.cs` with one temporary action. 3.3.2 replaces it.

    ```csharp
    [ApiController]
    [Route("api/assignments")]
    public sealed class AssignmentsController : ControllerBase
    {
        // Temporary: 3.3.2 replaces this with the real endpoints.
        [HttpGet]
        public IActionResult List() => Ok(Array.Empty<object>());
    }
    ```

8. **Local runs.** Replace `Properties/launchSettings.json` with a single `http` profile like employees-service's: no `applicationUrl`, and an `environmentVariables` block with `ASPNETCORE_ENVIRONMENT`, `PORT` set to `5103`, and the localhost versions of `ConnectionStrings__Default`, `RABBITMQ_URL`, `EMPLOYEES_URL` (`http://localhost:5101`), and `PROJECTS_URL` (`http://localhost:5102`).

    > [!IMPORTANT]
    > Remove `applicationUrl`. When it's set, `dotnet run` passes it to the app as the listen URL, which overrides `PORT`, so your service would ignore the variable every other environment relies on.

9. Run it from `assignments-service/`:

    ```bash
    dotnet run --project src/AssignmentsService
    ```

    In a second terminal, `curl -s localhost:5103/healthz` prints `{"status":"ok"}`, and `curl -s localhost:5103/api/assignments` prints `[]`. Stop it with `Ctrl+C`, then delete the `EMPLOYEES_URL` line from the launch profile and run again: it refuses to start and names the variable. Put the line back.

10. **The image.** Copy `../employees-service/Dockerfile` into `assignments-service/`, replace every `EmployeesService` with `AssignmentsService`, and add the two-line header comment shown above.
11. **Compose.** In the repository's `compose.yaml`, add `assignments-service` to `frontend-proxy`'s `depends_on` list, and add this service block after `projects-service`. It's long, but every line matters:

    ```yaml
      assignments-service:
        build: ./assignments-service
        ports: ["5103:8080"]
        environment:
          <<: *otel
          OTEL_SERVICE_NAME: assignments-service
          ConnectionStrings__Default: Host=postgres;Database=assignments;Username=postgres;Password=postgres
          RABBITMQ_URL: amqp://guest:guest@rabbitmq:5672/
          EMPLOYEES_URL: http://employees-service:8080
          PROJECTS_URL: http://projects-service:8000
          FLAGD_HOST: flagd
          SEED_DATA: "false"
          AUTH_TOKEN: ${AUTH_TOKEN:-}
        depends_on:
          postgres: { condition: service_healthy }
          rabbitmq: { condition: service_healthy }
    ```

    Inside the compose network, services reach each other by service name on their *container* port (`employees-service:8080`), not the host port you use from your laptop (`localhost:5101`). The `assignments` database already exists: `infra/postgres/init.sql` created it in 3.2.

12. Build and start it, then call it through the proxy:

    ```bash
    docker compose up --build -d assignments-service
    curl -si localhost:8080/api/assignments
    ```

    The answer is `200 OK` with `[]`. Until now that same request returned a 502 from the proxy.

13. Open `http://localhost:8080` and go to **Assignments**. The "isn't running yet" message is gone, replaced by *No assignments yet*. The web app was always ready; your service just arrived.
14. Commit, push, and open the pull request. Reviewers check out the branch, run steps 12 and 13, and compare `Program.cs` line by line with employees-service: is anything there that the reviewer can't explain?
