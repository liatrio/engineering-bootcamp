# Code Review

Automated tools are helpful in ensuring code quality, but these tools can only get you so far. When you're developing in a team, one of the biggest assets you have to ensure the quality of the code entering your codebase is each other.

Whenever you're attempting to add code to a codebase, chances are you'll need to have a peer review your code. Oftentimes a code review will be required to merge a pull request into your main branch. Receiving feedback on your code can feel intimidating, especially if a group or team doesn't have any agreed upon guidelines for code reviews.

## General Etiquette

Code review guidelines and procedures will likely look different from organization to organization, but there are some general guidelines everyone should follow when engaging in code reviews, both from the perspective of the reviewer and the developer.

### Everyone

- **Be respectful in your comments.** There are humans on both sides of the screen.
- **Have good intentions.** The reviewer and developer should both be going into the process with the intention of ensuring and maintaining quality code in the codebase.

### Developer

- **Separate yourself from your work.** Remember that criticism of your code is not criticism of you.
- **Be open to feedback.** This might seem obvious, but when you're asking for a code review, be ready to take into account any feedback you get rather than just expecting a rubber stamp from the reviewer.

### Reviewer

- **Comment only on the code, not on the developer.** Again, keep your comments respectful and relevant. Avoid statements about the developer, and keep your statements about the code.
- **Consider adding positive feedback.** It can help build rapport and trust between you and the developer if you point out positive things you see in someone's code rather than just negative things.

## Before the Review

When you're developing code, it's good to keep in mind that someone will need to review it. Try to write your code in such a way that it can be understood by others.

Before making a pull request, consider if your code is ready to be merged into the codebase. Are there testing requirements for this repository, and does your code meet these? Is your code complete, or is it a work in progress? If you want input but your code isn't quite ready, consider making a [draft pull request](https://github.blog/2019-02-14-introducing-draft-pull-requests/).

If you've decided it's the right time to raise a pull request, it's worth taking a look at some things you can do before the review to make the review easier both for yourself and the reviewer. If it's not already integrated into the repository, you could run a linter on your code to catch small, easy to fix things like styling, or look into other automated tools that assist with code review.

When you're raising a pull request, you should leverage the description field not only to document what changes you're making, but also to help the reviewer understand why this pull request is being raised and what it's supposed to do. If this pull request addresses a ticket, you should reference that ticket to give additional context.

### Keep pull requests small

Review quality drops as size grows. A reviewer reads a 50-line change line by line; a 1,000-line change gets skimmed and approved. Google's [guide on small changes](https://google.github.io/eng-practices/review/developer/small-cls.html) gives the reasons: small changes are reviewed faster and more thoroughly, are less likely to introduce bugs, and are easier to roll back.

A pull request should do one thing. Split a feature by slice or by layer, the way your team split the Apply work in 3.3. Send a refactor separately from the behavior change it enables, so the reviewer can check each on its own terms.

### Use a pull request template

A file at `.github/pull_request_template.md` pre-fills the description of every new pull request. It's the cheapest way to make every author answer the same questions: what changed and why, how to check it, and whether the things reviewers always ask about (tests, API docs, contracts, migrations, secrets) are handled.

## Finding a Reviewer

Making a pull request doesn't necessarily guarantee someone will see it. Depending on the organization you're working in, there may be different ways of notifying potential reviewers, like through your typical communication platform (Slack, Microsoft Teams, etc) or by requesting reviews from specific users through GitHub.

When seeking out a reviewer, you should try to get a review from someone who is at least generally familiar with the project you're contributing to. That being said, you should still try to write understandable code and add a thorough description.

## Reviewing Code

When you're reviewing code, your goal is to help find any potential defects in the code and help the developer make their code be the best it can be. This can feel pretty intimidating if you haven't done it before, but there are some things you can do to try to give structure to your review.

- **Consider writing a checklist.** You could write a checklist of things you're looking for when you're  going into a code review. This list could include things like whether or not the code is secure, if it accomplishes the task it says it's meant to, etc.

- **Think about if now is the right time to do a review.** Sometimes you might not be in the right headspace to do a code review. Doing a code review while you're tired or frustrated could result in you missing bugs/errors in the code, or making less than polite comments.

- **Denote nitpicks.** If you have an opinion about the way a piece of code is written, feel free to share that opinion, but make sure you make it clear when you're presenting an alternative way to do something and when you're commenting on a blocking issue.

- **Label every comment.** [Conventional Comments](https://conventionalcomments.org/) puts a label at the start of each comment, so the author knows what you need from them: `issue (blocking):` must be fixed before merging, `suggestion:` is a better way that the author may decline, `question:` asks for an explanation, `nitpick:` is a matter of taste, and `praise:` is something done well.

- **Let the tools do their job.** CI, the linters, and SonarQube already check formatting, style, and coverage. Spend your attention on what they can't judge: whether the change does what the issue asked, whether the design fits the codebase, whether the tests would catch a regression, and whether the next person can understand it.

## Specific Guidelines

If you're working in a small team without dedicated code review guidelines, consider taking some time to formalize your group's approach. Some good questions to ask to guide what you want your process to look like could include:

- How should a developer seek out a reviewer?

- Are you going to integrate any automated tools to assist with the code review process?

- How should a reviewer denote blocking issues and nitpicks?

- Should reviewers put forth particular code suggestions?

- Whose responsibility is it to make changes to PRs that need small fixes?

If you're working in an organization that already has code review customs put into place, take some time to familiarize yourself with that particular process before reviewing code or asking for a code review.

## Exercise

### Example: M4's pull request template

Read M4's [`.github/pull_request_template.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/.github/pull_request_template.md). For each item on its checklist, name a mistake from 3.3 or 3.4 that the item would have caught, or that your team actually made. Which item would you add for your team?

### Practice: review a teammate's pull request

Pair up. Each of you reviews the other's open Practice pull request from [3.4.8](3-application-development/3.4.8-code-coverage.md) or [3.4.9](3-application-development/3.4.9-code-styling.md). If yours is merged already, pick any open pull request in the team repository instead: you can only approve or request changes on an open one.

1. Before you open the diff, read the description and the linked issue. Write down, in one sentence, what you expect the change to do.
2. Check out the branch (`gh pr checkout <number>`) and run the service's tests and linter yourself.
3. Review the diff on GitHub against this checklist:
    - Does the change do what the description says, and nothing else?
    - Would the new tests fail if the fix were reverted? Try it: revert one line and rerun.
    - Are names, comments, and error messages clear to someone who wasn't in the room?
    - Does it follow the conventions in the team's `AGENTS.md`?
    - Is anything missing: a README line, an `openapi.yaml` change, a migration?
4. Leave at least three comments, each with a [Conventional Comments](https://conventionalcomments.org/) label, and at least one `praise:`. Use GitHub's **suggestion** block (the ± button in the comment box) for at least one small change, so the author can apply it with one click.
5. Submit the review as **Approve** or **Request changes**, with a summary that says what the author must do before merging, if anything.
6. As the author, answer every comment: apply it, or reply with why not. Resolve each conversation once it's settled.

### Apply: code review rules for the team repository

1. **Template.** Add `.github/pull_request_template.md` with three sections: *What and why* (with `Closes #123`), *How to check it*, and a *Checklist* that fits your repository. Include the items from M4's template you agreed with in the Example, plus your own. Open it as a pull request, and let the template fill in its own description.
2. **Rules.** Add a **Code review** section to `AGENTS.md`:
    - CI must be green before review is requested;
    - nobody merges their own pull request without an approval;
    - comments use Conventional Comments labels, and only `issue (blocking)` blocks a merge;
    - the author resolves conversations, and the reviewer re-reviews after changes;
    - pull requests stay small: if one passes about 400 changed lines, say why in the description or split it.
3. **Ruleset.** In the `main` ruleset, also turn on **Dismiss stale pull request approvals when new commits are pushed** and **Require conversation resolution before merging**. Your required status checks from [3.4.10](3-application-development/3.4.10-test-automation.md) stay.
4. **Use it.** Every remaining 3.4 pull request, including the ones for 3.4.11 and 3.4.13, goes through this process.

> [!TIP]
> Compare with M4's [`pull_request_template.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/.github/pull_request_template.md) and the review rules in the *Rules* section of [`AGENTS.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/AGENTS.md).

## Deliverables

- A link to the review you gave in the Practice, and a link to the review you received, with every conversation resolved.
- A merged pull request with the template and the **Code review** section of `AGENTS.md`, and the updated ruleset.
- You find a line in a teammate's pull request that you would have written differently. Write a good and a bad comment for it, with labels.
- You find a likely bug. Write a good and a bad comment for it, with labels.
- Discuss with your team: which part of your review did CI, the linters, or SonarQube already cover? What did only a person catch?
