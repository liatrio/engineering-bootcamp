# Component Testing

A component test checks one component of a system, such as a service, a module, or a front-end widget, through its public interface, with everything outside the component replaced by [test doubles](3-application-development/3.4.3-test-doubles.md). Martin Fowler's [definition](https://martinfowler.com/bliki/ComponentTest.html) is a test that "limits the scope of the exercised software to a portion of the system under test."

Component tests sit between unit and integration tests:

- A **unit test** checks a single function or class.
- A **component test** checks many units working together inside one component, driven the way a real caller would drive it, but with no real external dependencies.
- An **integration test** checks a component against a real dependency, such as a database or another service.

For a web service, a component test sends real HTTP requests to the service running in the test process, and stubs out the databases, queues, and other services it talks to. Because it never leaves the process, it stays fast and deterministic, yet it exercises the routing, validation, business logic, and serialization together. Those are often where bugs hide: in how the units fit together rather than in any single one.

## What Makes a Good Component Test

- **Drive the public interface.** Call the component the way its clients do, such as an HTTP endpoint, a CLI command, or a module's exported functions, rather than reaching into internal classes. Then the tests survive refactoring.
- **Replace only what is outside the component.** Use in-memory fakes or stubs for databases and remote services, but let the component's own layers run for real.
- **Assert on observable behavior**, such as the response status and body, or the data handed to a dependency, rather than on which internal methods were called.
- **Isolate every test.** Each test should start from a known state. Shared state between tests makes the results depend on the order the tests run in.

Toby Clemson's [Testing Strategies in a Microservice Architecture](https://martinfowler.com/articles/microservice-testing/) shows where component tests fit alongside the other test types in a service-based system.

## Component Tests in ASP.NET Core

ASP.NET Core ships the tool for this: `WebApplicationFactory<Program>`, from the `Microsoft.AspNetCore.Mvc.Testing` package. It boots your real `Program` in the test process on an in-memory server, and `CreateClient()` gives you an `HttpClient` whose requests go through the whole pipeline (routing, model validation, middleware, controllers, and exception handling) without opening a port.

Override `ConfigureWebHost` to change the app for the test. `UseSetting` supplies configuration, and `ConfigureTestServices` runs after `Program`'s own registrations, so it can remove a registration and add a double in its place. That's how a component test swaps PostgreSQL for an in-memory store and RabbitMQ for a fake publisher while every other class stays real.

### Where test state lives in xUnit

xUnit creates a **new instance of the test class for every test**, so anything you create in the constructor or in a field initializer is fresh each time. Two things outlive a single test:

- **Fixtures.** A class that implements `IClassFixture<T>` gets one `T` shared by every test in the class. That saves setup time, and it shares whatever state `T` holds.
- **Static fields.** These are shared by every test in the assembly, for the whole run.

xUnit v3 doesn't run the tests in a class in the order you wrote them. It sorts them by a hash of each test's ID. A test that only passes because another test ran first may pass on your laptop and fail in CI.

### Practice: find and fix the shared-state leak in employees-service

SPEC's gap for 3.4.4 has two parts: the component tests share one in-memory store, so their results depend on test order, and nothing tests `DELETE` of an unknown ID. Work on a branch, `test/employees-component-isolation`.

1. Add two tests to `EmployeesApiTests`. They look harmless:

    ```csharp
    [Fact]
    public async Task A_created_employee_can_be_read_back()
    {
        var create = await _client.PostAsJsonAsync("/api/employees", NewEmployee("katherine@example.com"), Ct);
        Assert.Equal(HttpStatusCode.Created, create.StatusCode);

        var read = await _client.GetAsync(create.Headers.Location, Ct);
        Assert.Equal(HttpStatusCode.OK, read.StatusCode);
    }
    ```

    The second, `Research_has_one_employee_alan_turing`, gets `/api/employees?department=Research` and asserts that the list holds exactly one employee, named Alan Turing, as the seed data says.

2. Run each test on its own. Both pass:

    ```bash
    dotnet test --filter-method "*A_created_employee_can_be_read_back"
    dotnet test --filter-method "*Research_has_one_employee_alan_turing"
    ```

3. Run the whole class with the command from the Example. One of the two tests that create Katherine fails, with `Expected: Created` and `Actual: Conflict`. Run it again: the same test fails every time.
4. Work out why before you read on. Look at how `ComponentTestApp` holds the store, and at how `EmployeesApiTests` gets its `ComponentTestApp`.
5. **The cause.** `Store` is `public static readonly`, so every test in the run shares one store, and `IClassFixture<ComponentTestApp>` shares one app across the class as well. Whichever Katherine test runs second finds her already there. `Research_has_one_employee_alan_turing` is worse: it passes or fails depending on whether it runs before or after `Delete_returns_204_and_the_employee_is_gone` removes Alan. The order comes from a hash that includes where the test assembly sits on disk, so the result can differ between your machine, a teammate's, and CI. To see it, copy `employees-service` to another folder and run the class there.
6. **The fix.** Give every test its own app and its own freshly seeded store:
    - In `ComponentTestApp`, replace the static field with an instance property: `public InMemoryEmployeeStore Store { get; } = new(EmployeeSeed.Create());`. Add a `<remarks>` saying why it isn't static.
    - In `EmployeesApiTests`, remove `IClassFixture<ComponentTestApp>` and the primary constructor. Create the app in a field instead, and dispose of it after each test:

      ```csharp
      public sealed class EmployeesApiTests : IAsyncDisposable
      {
          private readonly ComponentTestApp _app = new();
          private readonly HttpClient _client;

          public EmployeesApiTests() => _client = _app.CreateClient();

          public ValueTask DisposeAsync() => _app.DisposeAsync();
      ```

    - Replace the remaining uses of `app` with `_app`, and change `using var securedApp` to `await using var securedApp`.

7. Run the class a few times, and from the copied folder. Every test passes, in any order. Booting the in-memory app costs a few milliseconds per test, which is a small price for tests you can trust.
8. **Close the other gap.** Add `Delete_of_an_unknown_id_returns_404_problem_details`: `DELETE` a new GUID, then assert a 404, the content type `application/problem+json`, and that `_app.Events.Published` is empty.
9. Run `dotnet test --filter-not-trait "Category=Integration"`, and open a pull request. In its description, explain the order dependency in two sentences.

### Apply: component-test the assignments endpoints

Your unit tests prove the rules. Component tests prove the HTTP layer around them: status codes, the Problem Details shape, JSON names and date formats, the `Location` header, and auth.

1. **The app.** Create `tests/AssignmentsService.Tests/ComponentTestApp.cs`, a `WebApplicationFactory<Program>` modeled on the fixed employees one:
    - `UseSetting` every required setting: the connection string, `RABBITMQ_URL`, `EMPLOYEES_URL`, and `PROJECTS_URL`. Nothing connects to them;
    - in `ConfigureTestServices`, remove the `DatabaseInitializer` and `EmployeeDeletedConsumer` hosted services, because there's no database to migrate and no queue to consume;
    - replace `IAssignmentStore`, `IEmployeesClient`, `IProjectsClient`, and `IEventPublisher` with your fakes from 3.4.3, and expose each as a property so tests can arrange and inspect them.
2. **The tests.** Create `Features/Assignments/AssignmentsApiTests.cs` with a fresh `ComponentTestApp` per test, as in the Practice step. Cover:
    - `POST` returns 201, a `Location` header ending in the new ID, and the assignment;
    - dates are plain `"2026-03-01"` strings in the JSON, and a missing `endDate` is `null`;
    - posting the same employee and project twice returns 409;
    - an unknown employee returns 400 with exactly one error key, `employeeId`;
    - with `Employees.IsDown = true`, `POST` returns 503 with a Problem Details body;
    - an invalid body returns 400 with camelCase field names in `errors`;
    - `GET /api/assignments?employeeId=` filters, and `GET` of an unknown ID returns 404;
    - `PUT` replaces the assignment, and `DELETE` returns 204 and then 404;
    - with `AUTH_TOKEN` set, a request without the bearer token gets 401, and one with it gets 200.
3. Don't repeat every rule here. The allocation and end-date edge cases are already proven by the unit tests. One component test per HTTP mapping is enough.
4. Run `dotnet test --filter-not-trait "Category=Integration"`, and open a pull request.
