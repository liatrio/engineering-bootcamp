# Rollouts and Experiments

A flag that is simply on or off releases a feature to everyone at once. The real power of flags comes from giving different users different answers, so you can release gradually and learn as you go.

## Evaluation Context

To decide per user, the flag system needs to know who's asking. The [evaluation context](https://openfeature.dev/docs/reference/concepts/evaluation-context/) carries that information with each evaluation:

- A **targeting key**, a stable identifier for the subject of the evaluation, usually a user ID.
- **Attributes**, other facts the rules can use, such as plan, country, or email domain.

Your application builds the context from what it knows about the request, often from the authenticated user. Only include what your rules need: the context may be sent to the flag service, and it can end up in your telemetry.

In the OpenFeature .NET SDK, you build a context and pass it to the evaluation:

```csharp
var context = EvaluationContext.Builder()
    .SetTargetingKey(userId)
    .Set("plan", "beta")
    .Build();
var on = await flags.GetBooleanValueAsync("allocation-check", false, context, cancellationToken: ct);
```

The Company app has no login in Chapter 3, so requests say who's making them with an optional `X-User-Id` header. It isn't authentication, just a stable key for rollouts. The k6 load script sends one with every request, as many different users.

## Targeting Rules

A targeting rule picks a variant from the context. flagd writes rules in [JsonLogic](https://flagd.dev/reference/flag-definitions/#targeting-rules). This rule gives `on` to beta users and falls back to the flag's default variant for everyone else:

```json
"targeting": {
  "if": [{ "==": [{ "var": "plan" }, "beta"] }, "on", null]
}
```

## Release Strategies

With context and rules, you can release in stages:

- **Dark launch:** deploy the code with the flag off for everyone. You can still turn it on for yourself to test it in production.
- **Internal users first:** turn it on for employees, then for beta customers. Hodgson calls this a "champagne brunch", for drinking your own champagne.
- **Percentage rollout:** turn it on for 1% of users, then 10%, 50%, and 100%, checking error rates and latency at each step. Hodgson calls a release to a random group a *canary release*.
- **Kill:** if the metrics get worse, turn the flag off. Every user is back on the old code in seconds.

A percentage rollout must be **sticky**: the same user must get the same answer on every request, or they would see the feature appear and disappear. flagd's [`fractional`](https://flagd.dev/reference/custom-operations/fractional-operation/) operation does this by hashing the flag key and the targeting key into a bucket. The same user always lands in the same bucket, so raising the percentage adds users without removing any:

```json
"targeting": {
  "fractional": [["on", 25], ["off", 75]]
}
```

The hash only sees the targeting key, so choosing that key is a design decision. Key on the user, and each *user* gets a consistent experience. Key on something else, such as the employee being assigned, and each *employee* gets consistent treatment whoever is making the change.

## Experiments

An **experiment**, or A/B test, uses the same mechanism to answer a question. Users are split into groups that each get a different variant, and you compare a metric between the groups: does the new assignment form lead to fewer abandoned assignments? To trust the answer:

- **Decide the metric and the stopping point before you start**, so you aren't tempted to stop when the numbers happen to look good.
- **Run long enough for a meaningful result**, but not so long that other changes to the system muddy it.
- **Record which variant each user got**, so you can join flag decisions to outcomes. [OpenFeature](3-application-development/3.6.3-openfeature.md) shows how flag decisions appear in your traces.

## Exercise

### Example: who's asking?

1. Read [`infra/k6/load.js`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/infra/k6/load.js). How many distinct `X-User-Id` values does it send over a run with five virtual users, and why does the comment say that matters for percentage rollouts?
2. flagd evaluates a context you send it, so you can try targeting without any application code. Add a `beta-preview` flag to the flag file with the beta rule from [Targeting Rules](#targeting-rules), then evaluate it for two users:

    ```bash
    flag() { curl -s -X POST localhost:8013/flagd.evaluation.v1.Service/ResolveBoolean \
      -H 'Content-Type: application/json' -d "{\"flagKey\":\"$1\",\"context\":$2}"; echo; }
    flag beta-preview '{"targetingKey":"ada","plan":"beta"}'
    flag beta-preview '{"targetingKey":"grace"}'
    ```

    What are the `reason` and `variant` for each, and why?

### Practice: a sticky percentage rollout

Use the `flag` function from the Example against a fractional flag.

1. Add a `practice-rollout` flag to the flag file: `on` and `off` variants, `defaultVariant` `"off"`, and the 25/75 `fractional` rule from [Release Strategies](#release-strategies).
2. Check stickiness: evaluate it for `user-1` five times. Does the answer ever change?
3. Count how many of 1,000 users get `on`, and save their IDs:

    ```bash
    for i in $(seq 1 1000); do
      flag practice-rollout "{\"targetingKey\":\"user-$i\"}" | grep -q '"variant":"on"' && echo user-$i
    done > at-25.txt
    wc -l < at-25.txt
    ```

    Why isn't it exactly 250?
4. Roll out further: change the split to 50/50, save, and repeat step 3 into `at-50.txt`. Check that nobody in the first group lost the feature:

    ```bash
    comm -23 <(sort at-25.txt) <(sort at-50.txt)
    ```

    It should print nothing.
5. Rename the flag to `practice-rollout-2`, keeping the 50/50 split, and repeat step 3. Compare the list with `at-50.txt`. Why would two flags at 50% not give the same 50% of users, and why is that usually what you want?
6. Delete `beta-preview` and both practice flags from the flag file.

### Apply: roll out the allocation rule

In 3.4.2 your team added a rule, test-first: an employee's overlapping assignments can't add up to more than 100%. Pretend it's new in production. It could reject assignments that work today, so roll it out gradually with an `allocation-check` flag, targeted per user.

1. **The context.** In `AssignmentsController`, read the optional `X-User-Id` header in `Create` and `Update` (`[FromHeader(Name = "X-User-Id")] string? userId`) and pass it to the service. Keep the header name in a constant.
2. **The check.** Add `AllocationCheck = "allocation-check"` to `AssignmentFlags`, with a default you can defend. In the method that enforces the 100% rule, build an evaluation context whose targeting key is the user ID, or, when there's no header, the employee ID. Return early, skipping the rule, when the flag is off.
3. Discuss as a team, and write the answer in a comment: why fall back to the employee ID rather than a random value or an empty key?
4. **The flag.** Add `allocation-check` to the flag file: `defaultVariant` `"off"`, with the 25/75 `fractional` rule. Rebuild.
5. **Watch it work.** Create an employee in the UI and assign them to one project at 100%. Then try to book them for another 10% as 200 different users. A user with the rule on gets a 409; a user with it off gets a 201, and the script deletes that assignment again so the next user starts from the same state:

    ```bash
    EMP=<the employee's id>
    check() {
      out=$(curl -s -o /dev/null -w '%{http_code} %header{location}' -X POST localhost:8080/api/assignments \
        -H 'Content-Type: application/json' -H "X-User-Id: $1" \
        -d "{\"employeeId\":\"$EMP\",\"projectId\":\"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb\",\"role\":\"Extra\",\"allocationPercent\":10,\"startDate\":\"2026-01-05\"}")
      if [ "${out%% *}" = 201 ]; then curl -s -X DELETE "localhost:8080/api/assignments/${out##*/}"; echo "$1 off"; else echo "$1 on"; fi
    }
    for i in $(seq 1 200); do check user-$i; done > rollout-25.txt
    grep -c ' on' rollout-25.txt
    ```

    Use a project the employee isn't already on. If they are, every request gets a 409 for the duplicate, not for the rule.

6. Compare with Practice: for the first 200 users, are the users with the rule on the same ones flagd put in `at-25.txt`? Explain why, or why not. (Hint: what goes into the hash?)
7. **Roll forward.** Raise the split to 50/50, rerun the loop into `rollout-50.txt`, and check with `comm` that no user lost the rule. Then send one request *without* `X-User-Id`, twice. Which targeting key was used, and is the answer the same both times?
8. Leave the flag at 50/50. You'll watch this rollout in your traces in [OpenFeature](3-application-development/3.6.3-openfeature.md).
