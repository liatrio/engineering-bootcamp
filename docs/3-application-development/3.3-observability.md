# Observability

Tests tell you whether your code works before you ship it. Observability tells you what it is actually doing once it's running: which requests are slow, which ones fail, and why. No test suite can predict every input, load pattern, or dependency failure that production will throw at your code. When something goes wrong at 2 a.m., the telemetry your application emits is how you find out what happened.

The OpenTelemetry [observability primer](https://opentelemetry.io/docs/concepts/observability-primer/) puts it this way: "Observability lets you understand a system from the outside by letting you ask questions about that system without knowing its inner workings." To make that possible, the application has to emit **telemetry**, which is data about what it is doing. Adding the code that emits telemetry is called **instrumentation**.

## Monitoring and Observability

**Monitoring** watches for problems you already know about: CPU above 90%, error rate above 1%, disk almost full. It answers questions you thought to ask in advance, usually with dashboards and alerts.

**Observability** goes further. A system is observable when you can answer *new* questions about its behavior, ones nobody anticipated, without shipping new code to answer them. Why are requests from one customer slow, but only on Tuesdays? Which code path produced this error? Observability needs richer telemetry than monitoring does, and it needs that telemetry to be connected, so you can move from a spike on a dashboard to the exact request that caused it.

## The Three Signals

Telemetry usually comes as three kinds of signal. Each subsection covers one in depth.

| Signal | What it is | Good for | Section |
| --- | --- | --- | --- |
| Logs | Timestamped records of discrete events | The details of what happened in one specific case | [Logging](3-application-development/3.3.1-logging.md) |
| Metrics | Numeric measurements aggregated over time | Trends, dashboards, and alerts: how much, how often, how fast | [Metrics](3-application-development/3.3.2-metrics.md) |
| Traces | The path of one request through the system, as a tree of timed operations | Where time is spent and where failures start, especially across services | [Tracing](3-application-development/3.3.3-tracing.md) |

The signals are most useful together. A metric shows that the error rate jumped. A trace from that period shows which operation failed. The logs attached to that trace explain why. [OpenTelemetry](3-application-development/3.3.4-opentelemetry.md) is the open standard most teams now use to produce all three in a consistent, connected way.

## What to Watch

Measuring everything is easy. Knowing what matters is harder. Three well-known starting points:

- **The four golden signals**, from the [Google SRE book](https://sre.google/sre-book/monitoring-distributed-systems/): latency, traffic, errors, and saturation. If you can measure only four things about a user-facing system, measure these.
- **The RED method**, created by Tom Wilkie for request-driven services: **R**ate (requests per second), **E**rrors (how many of those requests fail), and **D**uration (how long they take). See [The RED Method](https://grafana.com/blog/2018/08/02/the-red-method-how-to-instrument-your-services/).
- **The USE method**, from Brendan Gregg, for resources such as CPUs, disks, and queues: "For every resource, check utilization, saturation, and errors." See [The USE Method](https://www.brendangregg.com/usemethod.html).

RED describes your service from the outside, as its users experience it. USE describes the resources underneath it.

## Service Levels

Telemetry becomes actionable when you decide what "good" looks like:

- A **service level indicator (SLI)** is a measurement of user experience, such as the proportion of requests that succeed, or that complete in under 300 ms.
- A **service level objective (SLO)** is a target for an SLI over a period of time, such as 99.9% of requests succeeding over 30 days.
- The **error budget** is the gap between the SLO and perfection, here 0.1% of requests. While budget remains, the team can ship changes quickly. When it runs out, reliability work comes first.

The SRE book's [Service Level Objectives](https://sre.google/sre-book/service-level-objectives/) chapter and the SRE workbook's [Implementing SLOs](https://sre.google/workbook/implementing-slos/) explain how to choose them.

The SRE book also says monitoring should answer two questions: "what's broken, and why?" The "what" is a symptom users feel, such as slow pages or failed checkouts. The "why" is a cause, such as a full disk or a slow database. Alert on symptoms, so every page means users are affected, and use the rest of your telemetry to find the cause.

## Exercise: Set Up the Stack

The exercises in this section build on each other. In each one you add a signal to the same application, the [layered Flask app](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/layered-architecture/example2) from the testing exercises. You will send its telemetry to [`grafana/otel-lgtm`](https://github.com/grafana/docker-otel-lgtm), a single container that bundles an OpenTelemetry Collector with Loki (logs), Grafana, Tempo (traces), and Prometheus (metrics). It is "intended for development, demo, and testing environments", which is exactly what you need here.

1. Start the stack. Grafana listens on port 3000 and the collector on 4317 and 4318. If port 3000 is already in use, map Grafana to another port, such as `-p 3001:3000`.

    ```bash
    docker run --rm -d --name lgtm -p 3000:3000 -p 4317:4317 -p 4318:4318 grafana/otel-lgtm
    ```

2. Copy `examples/layered-architecture/example2` into a new directory, then install the app and OpenTelemetry's [zero-code instrumentation for Python](https://opentelemetry.io/docs/zero-code/python/):

    ```bash
    python3 -m venv .venv && source .venv/bin/activate
    pip install -r requirements.txt opentelemetry-distro opentelemetry-exporter-otlp
    opentelemetry-bootstrap -a install
    ```

    `opentelemetry-bootstrap` detects the libraries you use, such as Flask, and installs the matching instrumentation packages.

3. Configure OpenTelemetry with environment variables, and run the app under `opentelemetry-instrument`:

    ```bash
    export OTEL_SERVICE_NAME=user-api
    export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
    export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
    export OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED=true
    export OTEL_METRIC_EXPORT_INTERVAL=5000
    opentelemetry-instrument flask --app app run --port 5001 --no-reload
    ```

    `OTEL_METRIC_EXPORT_INTERVAL` sends metrics every 5 seconds instead of the default 60, so you see results quickly. `--no-reload` keeps the app in a single process under the instrumentation. Port 5001 avoids macOS's AirPlay Receiver, which uses 5000.

4. In another terminal, generate steady traffic for about five minutes, including requests that fail validation. Metrics such as request rates need traffic spread over time, not one burst. Rerun this loop whenever you need fresh data in later sections:

    ```bash
    for i in $(seq 1 300); do
      curl -s localhost:5001/users > /dev/null
      curl -s -X POST -H 'Content-Type: application/json' -d '{"name":"Ada"}' localhost:5001/users > /dev/null
      curl -s -X POST -H 'Content-Type: application/json' -d '{}' localhost:5001/users > /dev/null
      sleep 1
    done
    ```

5. Open Grafana at <http://localhost:3000> (log in with `admin` / `admin` if asked) and go to **Explore**. You haven't changed a line of application code, yet the instrumentation already produces all three signals. Pick each data source from the picker at the top of Explore, and answer the questions as you go.

6. **Traces.** Choose Tempo, switch the query editor to **TraceQL**, and search for the requests that failed validation:

    ```traceql
    {resource.service.name="user-api" && span.http.status_code=400}
    ```

    Open one of the results. The waterfall draws one bar per span. Click the span to see its attributes, which describe the request.
    - How many spans does the trace have, and how long did the request take?
    - Which attributes give the HTTP method, the route, and the response code?
    - Is the span marked as an error? The [HTTP semantic conventions](https://opentelemetry.io/docs/specs/semconv/http/http-spans/#status) leave a server span's status unset for a 4xx response: the client sent a bad request, and the server handled it correctly. Only a 5xx response marks a server span as an error.

7. **Metrics.** Choose Prometheus, switch the query editor to **Code**, and run `http_server_duration_milliseconds_count`. Each row in the results is a **series**: one combination of label values, with its own number.
    - How many series are there, and which labels tell them apart?
    - Compare each series' value with the number of requests the traffic loop has sent. What is the value counting? Run the query again a minute later: what happened to it?

8. **Logs.** Choose Loki and run `{service_name="user-api"}`. Each line is one request, written by Werkzeug, Flask's development server. Expand a line to see the attributes sent with it.
    - Find a line for a rejected request. Can you tell from the log why it was rejected?
    - Is there a `trace_id` among the attributes? Without one, how would you get from this line to the trace you opened in step 6?

    The gaps you found here are what the next sections fill: Logging adds the reason and the trace ID, and Tracing breaks the single span into the work inside the request.

Keep the stack and the app running for the next sections. When you are finished with the whole Observability section, stop the stack with `docker stop lgtm`.

### Deliverables

- Screenshots of a trace, a metric query, and the logs for `user-api` in Grafana.
- Your answers to the questions in steps 6–8.
- Which of the four golden signals can you already see, and which are missing?
- Discuss: what can't you tell about the application yet, from this zero-code telemetry alone?
