# Calling Other Services

An assignment is only valid if its employee and project exist, and only employees-service and projects-service know that. So before saving, assignments-service asks them over HTTP. This page covers how to make that call properly in .NET, and, more importantly, what to do when the answer is slow, wrong, or never comes. Every network call fails sometimes. The design question is what your service does then.

## Why Not Just `new HttpClient()`

The obvious code has two opposite bugs, depending on where you put it:

- **A new `HttpClient` per call** opens a new connection each time, and closed connections linger in the operating system for a while. Under load the machine runs out of sockets.
- **One static `HttpClient` forever** keeps its connections open forever, so it never notices when a service's DNS name starts pointing somewhere else, which is exactly what happens when containers are replaced.

`IHttpClientFactory` solves both: it pools and recycles the underlying handlers for you. The cleanest way to use it is a **typed client**: a small class that takes an `HttpClient` in its constructor and exposes methods named after what your service needs.

```csharp
public sealed class EmployeesClient(HttpClient http) : IEmployeesClient
{
    public Task<bool> ExistsAsync(Guid id, CancellationToken ct) =>
        http.ResourceExistsAsync($"/api/employees/{id}", "employees-service", ct);
}
```

`IEmployeesClient` has one method, `ExistsAsync`. assignments-service doesn't need names, titles, or departments, so its interface doesn't offer them (that's Interface Segregation from 3.3.3, applied to another service). It's also the seam tests will fake in 3.4.3 and contract-test in 3.4.6.

### Registration and the handler pipeline

`AddHttpClient<TInterface, TImplementation>` registers the typed client and lets you configure the `HttpClient` it receives. The base address comes from your options, so `EMPLOYEES_URL` decides where calls go:

```csharp
services.AddHttpClient<IEmployeesClient, EmployeesClient>((sp, http) =>
        http.BaseAddress = new Uri(sp.GetRequiredService<IOptions<ServiceOptions>>().Value.EmployeesUrl))
    .AddHttpMessageHandler<ForwardAuthTokenHandler>()
    .AddStandardResilienceHandler(ConfigureResilience);
```

Each `Add...Handler` call adds a `DelegatingHandler` to the client's outgoing pipeline. It works like ASP.NET Core middleware, but for requests you send: each handler can change the request, wait for the response, retry, or give up. `ForwardAuthTokenHandler` adds the `Authorization` header; the resilience handler wraps everything in timeouts and retries.

## Resilience: Timeouts, Retries, and Circuit Breakers

[3.2.4](3-application-development/3.2.4-service-communication.md#synchronous-requests) named the failure modes of synchronous calls. Here are the tools against them, all provided by `AddStandardResilienceHandler()` from the [Microsoft.Extensions.Http.Resilience](https://learn.microsoft.com/dotnet/core/resilience/http-resilience) package (built on Polly).

| Strategy | Protects against | How |
| --- | --- | --- |
| **Total timeout** | A request that takes forever, retries included | Gives up after a fixed budget for the whole call |
| **Retry** | A blip: one dropped connection, one 503 during a restart | Tries again, with exponential backoff and random jitter, but only for transient failures: network errors, 5xx, 408, and 429 |
| **Circuit breaker** | Hammering a service that's clearly down | After too many failures, fails calls immediately for a while, then lets one through to test the water |
| **Attempt timeout** | One slow attempt eating the whole budget | Cancels a single attempt so the retry gets a chance |

A retry never helps with a 404 or a 400: asking again for an employee that doesn't exist gives the same answer. That's why the handler only retries transient failures.

### Pick a budget for your caller

The defaults are generous: 30 seconds in total, 10 seconds per attempt, and 3 retries. The circuit breaker only opens once at least 100 calls in 30 seconds have run and 10% or more of them failed, then stays open for 5 seconds. Those defaults suit background work. A person waiting on a form should hear "try again" much sooner, so M2 tightens them:

```csharp
options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(5);
options.Retry.MaxRetryAttempts = 2;
options.Retry.Delay = TimeSpan.FromMilliseconds(200);
```

Every service in a chain needs a budget smaller than its caller's. If the web app gives up after 10 seconds, assignments must give up on projects well before that, or the user sees a generic error instead of your clear 503.

## Mapping Answers to Your Own Status Codes

The interesting part of the call isn't the success path. It's turning every possible outcome into something your caller can act on:

| employees-service answers | It means | assignments-service returns |
| --- | --- | --- |
| 200 | The employee exists | Carries on |
| 404 | The employee doesn't exist: the **caller's** mistake | **400**, with `errors.employeeId` |
| 5xx, after retries | employees-service is broken right now | **503**: we can't decide, so we say so |
| Timeout, refused connection, open circuit | employees-service can't be reached | **503** |

Two details matter:

- **Never pass a dependency's status straight through.** A 404 from employees-service doesn't mean the *assignment* wasn't found, so returning 404 would mislead the client. A 500 from employees-service isn't a bug in assignments, so it shouldn't be a 500 either.
- **Never guess.** If you can't tell whether the employee exists, don't save the assignment "just in case". Return 503 and let the client retry.

M2 puts this in one extension method, [`ResourceExistsAsync`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M2-assignments-mvp/assignments-service/src/AssignmentsService/Infrastructure/Clients/HttpClientExtensions.cs), shared by both clients. It returns `false` for a 404, and wraps any failure that means "unavailable" in a `DependencyUnavailableException`, which `GlobalExceptionHandler` maps to 503. It's careful about one case: a `TaskCanceledException` because *your* caller hung up isn't an outage, so it isn't turned into a 503.

The service collects both answers before failing, so a request with two bad IDs gets both errors at once, in the same `errors` shape as a validation failure:

```json
{ "status": 400, "title": "One or more validation errors occurred.",
  "errors": { "employeeId": ["Employee '…' does not exist."], "projectId": ["Project '…' does not exist."] } }
```

## Forwarding the Auth Token

When `AUTH_TOKEN` is set (Chapter 7.3 turns it on), every service requires `Authorization: Bearer <token>`, including the ones assignments calls. `ForwardAuthTokenHandler` adds the header to every outgoing request when the option is set, and does nothing otherwise. Because it's a handler, neither client has to remember.

## Dependencies and Readiness

As 3.3.1 noted, employees-service and projects-service stay out of assignments' `/readyz`. Think about what happens otherwise: projects-service goes down, assignments reports unready, the platform stops routing to it, and now listing and deleting assignments fail too, though neither needs projects. With them left out, only the requests that really need a dependency fail, with a clear 503, and everything else keeps working.

Those are the same three decisions your typed clients make.

### Practice: two ways to be down

A stopped service and a hung service fail very differently for their callers. Feel the difference before you code for it. With the app running:

1. Stop projects-service and call it directly:

    ```bash
    docker compose stop projects-service
    time curl -s -m 5 localhost:5102/api/projects
    ```

    It fails immediately: `Failed to connect`. Nobody is listening, so the operating system refuses the connection at once. This is the easy kind of failure.

2. Start it again, wait until `curl -s localhost:5102/readyz` answers, then **pause** it instead. A paused container keeps its port open but never answers, like a service stuck on a lock or out of threads:

    ```bash
    docker compose start projects-service
    docker compose pause projects-service
    time curl -s -m 5 localhost:5102/api/projects
    ```

    This time `curl` waits the full 5 seconds you allowed with `-m 5`, then gives up with `Operation timed out`. Without `-m`, it would wait much longer.

3. Run `docker compose unpause projects-service`.
4. Write down: which of the two is more dangerous for a caller with no timeout, and why? What happens to a service that keeps accepting requests while every one of them waits on a paused dependency?

### Apply: validate employee and project IDs

Split the steps: one person takes the clients and registration (1 to 4), another the error mapping (5 and 6), and a third the service changes (7).

1. **Package.** From `src/AssignmentsService/`:

    ```bash
    dotnet add package Microsoft.Extensions.Http.Resilience --version 10.11.0
    ```

2. **Exceptions.** In `Infrastructure/Errors/DomainExceptions.cs`, add two:
    - `RequestValidationException`, holding an `IDictionary<string, string[]> Errors`, for "the request is well formed but refers to something invalid";
    - `DependencyUnavailableException(string service, Exception? inner = null)`, with a `Service` property, for "a service we depend on didn't answer".
3. **The clients.** Under `Infrastructure/Clients/`, create `IEmployeesClient.cs` and `IProjectsClient.cs`, each with an interface (`ExistsAsync(Guid id, CancellationToken ct)`) and its typed-client implementation, as shown above. Create `HttpClientExtensions.cs` with `ResourceExistsAsync`: `GetAsync` the path; `false` for 404; `EnsureSuccessStatusCode()` otherwise; and catch `HttpRequestException`, Polly's `ExecutionRejectedException` (timeouts and an open circuit), and a `TaskCanceledException` when *your* token wasn't cancelled, wrapping each in `DependencyUnavailableException`.
4. **Registration.** Create `Infrastructure/Clients/ForwardAuthTokenHandler.cs`: a `DelegatingHandler` that takes `IOptions<ServiceOptions>` and sets `request.Headers.Authorization` when `AuthToken` is set. Then create `ClientRegistration.cs` with an `AddDependencyClients(this IServiceCollection services)` extension method that registers the handler with `AddTransient`, and both typed clients with their base address, the handler, and `AddStandardResilienceHandler` using the budget above. In `Program.cs`, one line:

    ```csharp
    // Other services: typed HttpClients with timeouts, retries, and a circuit breaker.
    builder.Services.AddDependencyClients();
    ```

5. **Error mapping.** In `GlobalExceptionHandler`, map `RequestValidationException` to a 400 `HttpValidationProblemDetails` built from its `Errors`, and `DependencyUnavailableException` to a 503 whose `detail` is the exception's message. Log the 503 case as a warning with the failing service's name: it isn't your bug, but an operator wants to see it.
6. Check the controller's `POST` and `PUT` actions both declare 503 with `[ProducesResponseType]`, from 3.3.2.
7. **The rule.** Add `IEmployeesClient employees` and `IProjectsClient projects` to `AssignmentService`'s constructor. Write a private `EnsureReferencesExistAsync(request, ct)` that asks both, collects an error per unknown ID, and throws `RequestValidationException` if there are any. Call it in `CreateAsync` and `UpdateAsync` before the duplicate check.
8. **Try every outcome.** Rebuild with `docker compose up --build -d assignments-service`, then:

    ```bash
    BAD='{"employeeId":"00000000-0000-4000-8000-000000000000","projectId":"00000000-0000-4000-8000-000000000001","role":"Tech Lead","allocationPercent":50,"startDate":"2026-02-01"}'
    curl -s -X POST localhost:5103/api/assignments -H 'Content-Type: application/json' -d "$BAD"
    ```

    The answer is a 400 with both `errors.employeeId` and `errors.projectId`. A request with Ada and Platform Modernization still succeeds (or returns 409 if that pair exists).

9. **Outages.** Repeat the Practice's two failures, this time behind assignments-service, using a valid body:
    - `docker compose stop projects-service`: `POST` returns 503 within about a second, after two quick retries. `GET /api/assignments` still works, and `/readyz` is still 200.
    - `docker compose start projects-service`, wait for it, then `docker compose pause projects-service`: `POST` returns 503 after about 5 seconds, your total budget. Time it with `time curl ...`.
    - Run `docker compose logs assignments-service` and find the warning naming `projects-service`. Then unpause it.
10. **In the UI.** Pause projects-service once more and create an assignment from the **Assignments** page. Read the message the web app shows. Is it good enough for a user? Unpause.
11. Refresh `openapi.yaml` (`curl -s localhost:5103/openapi/v1.yaml > assignments-service/openapi.yaml`), check the diff, and open the pull request.
