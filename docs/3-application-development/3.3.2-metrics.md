# Metrics

A metric is a number measured over time: requests per second, error count, response time, queue length. Where a log describes one event in detail, a metric summarizes thousands of events into a few numbers. That makes metrics cheap to store and fast to query, which is why they power dashboards and alerts.

## Kinds of Metrics

Most metrics systems, including [Prometheus](https://prometheus.io/docs/concepts/metric_types/) and [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/metrics/), offer the same basic kinds:

| Kind | What it records | Example |
| --- | --- | --- |
| Counter | A total that only goes up | Requests served, users created, errors |
| Gauge | A value that goes up and down, measured at a point in time | Memory in use, queue length, temperature |
| Histogram | The distribution of many measurements, in buckets | Request duration, response size |

OpenTelemetry also has an **UpDownCounter**, for totals that can decrease, such as active connections, and *asynchronous* counters, UpDownCounters, and gauges, which read a value on demand rather than having your code record every change.

You usually look at a counter's **rate** (how fast it grows) rather than its raw value, and at a histogram's **percentiles**. An average hides your slowest requests, but the 95th or 99th percentile (p95, p99) shows what your unhappiest users experience.

## Attributes and Cardinality

Metrics carry **attributes** (Prometheus calls them labels), such as the HTTP method, route, or status code, so you can break a metric down: errors *by route*, latency *by status code*. Every distinct combination of attribute values is stored as a separate time series. The [Prometheus naming guide](https://prometheus.io/docs/practices/naming/) warns:

> Do not use labels to store dimensions with high cardinality (many different label values), such as user IDs, email addresses, or other unbounded sets of values.

A `user_id` attribute on a request counter creates one time series per user, which can overwhelm your metrics backend. Put unbounded values in logs and traces instead, where each event is stored individually anyway.

## Naming

Consistent names make metrics discoverable. The Prometheus conventions are widely followed:

- Use base units: seconds, not milliseconds; bytes, not megabytes.
- Include the unit in the name, as in `http_request_duration_seconds`.
- Give counters a `_total` suffix, as in `http_requests_total`.

OpenTelemetry names use dots, such as `http.server.request.duration`, and record the unit separately. When OpenTelemetry metrics are stored in Prometheus, the dots become underscores, and counters gain `_total`.

## Exercise: Custom Metrics and a RED Dashboard

This exercise continues from the [Logging exercise](3-application-development/3.3.1-logging.md#exercise-structured-logs).

1. The zero-code instrumentation already records a request-duration histogram. In Grafana Explore, run these PromQL queries against Prometheus and work out what each one shows:

    ```promql
    sum by (http_status_code) (rate(http_server_duration_milliseconds_count[1m]))
    histogram_quantile(0.95, sum by (le) (rate(http_server_duration_milliseconds_bucket[5m])))
    ```

    These names follow an older OpenTelemetry HTTP convention. Newer instrumentation versions may emit `http_server_request_duration_seconds` instead, so check the metric browser for the name your version uses.
2. HTTP metrics can't tell you about the business. Add two counters to `app/services/user_service.py` using the [OpenTelemetry metrics API](https://opentelemetry.io/docs/languages/python/instrumentation/#metrics):
    - `users.created`, incremented each time a user is created;
    - `users.validation_failures`, incremented on each rejected request, with a `reason` attribute.

    Get a meter with `metrics.get_meter(__name__)` from `opentelemetry`, create each counter once at module level with `meter.create_counter(...)`, and call `.add(1, {...})` where the event happens.
3. Restart the app, rerun the traffic loop, and find your counters in Prometheus. What names did they end up with, and why?
4. Build a Grafana dashboard (**Dashboards → New dashboard**) with one panel for each part of RED:
    - **Rate:** requests per second, by status code.
    - **Errors:** the fraction of requests that fail validation, using either the `400` responses or your new counter.
    - **Duration:** p95 request duration.
5. Add a fourth panel for users created per minute.

### Deliverables

- Your metrics code and a screenshot of your dashboard.
- Explain why `rate()` is more useful than the raw value of a counter.
- Discuss: a teammate wants to add a `user_name` attribute to `users.created`. What do you tell them, and where should that information go instead?
