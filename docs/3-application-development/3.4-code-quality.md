# Code Quality

Before a team releases a change, it needs confidence that the change doesn't break anything, that other developers can understand and change it, and that it doesn't make the codebase more expensive to own. Pair programming and code review help, but they're slow and they miss unintended consequences. To release often, a team needs quality checks that are automated, repeatable, and visible to everyone.

At the end of 3.3 your team has a working `assignments-service` with no tests. This section works on the whole Company app: every page shows a technique in the starter services, has you close a small gap in one of them, then has your team apply it to `assignments-service`. It ends twice:

- **After 3.4.7, at M3:** the service is tested at every level, from unit tests to a browser journey.
- **After 3.4.13, at M4:** those tests, plus coverage, linting, a security and quality scan, and pre-commit hooks, run automatically on every pull request, and the team reviews every change before it merges.

## Test-Driven Development

Test-driven development (TDD) is a practice where you write a failing test *before* you write the code that makes it pass. Kent Beck popularized it in *Test-Driven Development: By Example* (2002). Instead of writing tests after a feature is finished, when they are easy to skip, TDD makes tests the way you build the feature.

### Red, Green, Refactor

TDD works in short cycles, often just a few minutes long. Martin Fowler's [summary](https://martinfowler.com/bliki/TestDrivenDevelopment.html) has three steps:

1. **Red:** write a test for the next small piece of behavior you want, run it, and watch it fail. Seeing it fail proves the test can fail, and that it fails for the reason you expect.
2. **Green:** write the simplest code that makes the test pass. Resist adding behavior that no test asks for yet.
3. **Refactor:** with the tests passing, clean up both the new code and the code around it: remove duplication, improve names, and simplify. The tests tell you immediately if a change breaks something.

Then repeat with the next piece of behavior. Fowler notes that the most common way to get TDD wrong is skipping the third step. Without refactoring, the code works but its design gets steadily worse.

### Canon TDD

In 2023 Kent Beck described the workflow he considers canonical, in [Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd). It adds a test list to the cycle:

1. Write a list of the test scenarios you want to cover.
2. Turn exactly one item on the list into a concrete, runnable test.
3. Change the code to make that test, and all previous tests, pass. Add new scenarios to the list as you discover them.
4. Optionally, refactor to improve the design.
5. Until the list is empty, go back to step 2.

The list keeps you focused on one behavior at a time while recording everything else you think of along the way. Beck warns against turning the whole list into tests up front: each test you make pass can change how you approach the next.

### Why Practice TDD

- **Every behavior has a test**, because no production code is written without a failing test asking for it.
- **Fast feedback.** You find out within minutes, not days, whether your code does what you intended.
- **Better design.** Code that is hard to test is usually too tightly coupled. Writing the test first pushes you toward small, focused units with clear inputs and outputs, the qualities covered in [Foundational Layers](3-application-development/3.2.1-foundational-layers.md) and [Dependency Injection and SOLID](3-application-development/3.3.3-dependency-injection-and-solid.md).
- **Safe refactoring.** A thorough, fast suite lets you change the structure of code with confidence.
- **Living documentation.** The tests describe what the code is supposed to do, in a form that fails when it stops being true.

### Common Pitfalls

- **Skipping the refactor step**, which leaves working but tangled code.
- **Taking steps that are too big.** If a test takes an hour to make pass, split it into smaller behaviors.
- **Testing implementation details.** Tests that assert *how* the code works, rather than *what* it does, break whenever you refactor. Test through the public interface.
- **Never seeing the test fail.** A test that passes the first time it runs may not be testing anything.

### When TDD Fits

TDD works best when you know what behavior you want, even if you don't yet know how to build it. When you are exploring an unfamiliar library or idea, a time-boxed [spike](1-ways-of-working/1.3.5-sizing.md#what-is-a-spike) without tests is often faster. Throw the spike away once you have learned what you need, then build the real implementation test-first.
