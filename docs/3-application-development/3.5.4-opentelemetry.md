# OpenTelemetry

Every exercise in this section has used [OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/) (often shortened to OTel) to produce logs, metrics, and traces. It is "a Cloud Native Computing Foundation (CNCF) project that is the result of a merger between two prior projects, OpenTracing and OpenCensus", and it has become the industry standard for producing telemetry.

OpenTelemetry standardizes how telemetry is *produced and transported*. It is "**not** an observability backend itself": storing, querying, and visualizing the data is left to tools such as Prometheus, Loki, Tempo, Jaeger, Grafana, or commercial vendors. Because every backend accepts the same format, you instrument your code once and can change backends without touching it. And because every language speaks the same protocol and propagates the same context, a .NET service, a Python service, a Go service, and a browser can all add spans to one trace.

## The Pieces

| Piece | What it does | In the Company app |
| --- | --- | --- |
| **API** | The interfaces your code calls to create spans, record metrics, and emit logs. It is safe to call from libraries: without an SDK configured, the calls do nothing. | .NET's own `ActivitySource` and `Meter`; `opentelemetry.metrics` in projects-service's custom counter |
| **SDK** | The implementation that processes telemetry, applies sampling, batches it, and hands it to exporters. Configured once, by the application. | `AddOpenTelemetry()` in .NET, `sdktrace.NewTracerProvider` in Go, `TracerProvider` in the browser |
| **Instrumentation libraries** | Ready-made instrumentation for popular frameworks and clients. **Zero-code instrumentation** installs and configures them without code changes. | ASP.NET Core, `HttpClient`, Npgsql, `otelhttp`, fetch; projects-service's `opentelemetry-instrument` |
| **Exporters** | Send telemetry out of the process, to the console, a backend, or a collector. | The OTLP exporter in every service |
| **OTLP** | The OpenTelemetry Protocol, the standard wire format for all three signals, over gRPC (port 4317) or HTTP (port 4318). | `http/protobuf` to `otel-lgtm:4318` |
| **Collector** | A standalone service that receives, processes, and exports telemetry. | Inside the `otel-lgtm` container |

## The Collector

Applications can export directly to a backend, but most production setups send telemetry to an [OpenTelemetry Collector](https://opentelemetry.io/docs/collector/) first. A collector [pipeline](https://opentelemetry.io/docs/collector/configuration/) has three stages:

- **Receivers** accept data, for example OTLP from your applications, or scraped Prometheus metrics.
- **Processors** transform it: batch it, add or remove attributes, drop noisy data, redact sensitive fields, or sample traces.
- **Exporters** send it to one or more backends.

This keeps applications simple. They only speak OTLP to a nearby collector, while decisions about routing, retries, filtering, and which vendor to use live in one place that operators can change without redeploying any applications. The `otel-lgtm` container runs a collector in front of Loki, Tempo, and Prometheus. Even the browser's spans go through it: the frontend-proxy forwards `/otlp/` to the collector, so the browser never needs to know where the backend is.

## Semantic Conventions

If one service names its attribute `http_status` and another `statusCode`, you can't query across them. OpenTelemetry's [semantic conventions](https://opentelemetry.io/docs/concepts/semantic-conventions/) define standard names for common operations and attributes, such as `http.request.method`, `http.response.status_code`, `messaging.destination.name`, `db.system.name`, and `service.name`. Instrumentation libraries follow them, and your own attributes should follow them wherever a convention exists.

Conventions do evolve, and libraries don't all move at the same speed. You met the result in [Metrics](3-application-development/3.5.2-metrics.md#one-measurement-two-names): .NET and Go record `http.server.request.duration` in seconds, while projects-service's Python instrumentation still records the older `http.server.duration` in milliseconds, with `http.status_code` instead of `http.response.status_code` on its spans too.

## Resources

A **resource** describes the entity producing telemetry: the service name and version, the deployment environment, the host, container, or Kubernetes pod. Resource attributes are attached to every span, metric, and log the process emits, which is what lets you filter "errors in version 1.4.2 in production". `OTEL_SERVICE_NAME` sets `service.name`, and `OTEL_RESOURCE_ATTRIBUTES` sets the others, as a comma-separated list such as `service.version=1.4.2,deployment.environment.name=production`.

In Prometheus, resource attributes become labels with dots turned into underscores. `service.name` also becomes the `job` label, which is why your queries have used `job="employees-service"`.

## Sampling

A busy service can produce millions of traces an hour, and storing them all is expensive. [Sampling](https://opentelemetry.io/docs/concepts/sampling/) keeps a representative subset:

- **Head sampling** decides when a trace starts, for example keeping a fixed 25% of traces. It's simple and cheap, but it decides before anyone knows whether the request will be slow or fail.
- **Tail sampling** decides after the trace is complete, by "considering all or most of the spans within the trace". That lets you keep every error and every slow request, plus a sample of the rest. It runs in a collector, because it needs to see whole traces.

Sampling applies to traces. Metrics are aggregated in the SDK before export, so they still count every request: you can sample traces aggressively while keeping accurate rates and percentiles.

### The decision travels with the trace

In a distributed system, every service must make the *same* decision for a trace, or you get fragments: a parent kept, its children dropped. So the **root** service decides, and it records the decision in the `sampled` flag of `traceparent`. Every service downstream should use a **parent-based** sampler, which just follows that flag. The standard samplers you can choose with `OTEL_TRACES_SAMPLER` include:

| Value | Root spans | Spans with a parent |
| --- | --- | --- |
| `parentbased_always_on` (the default) | Always kept | Follow the parent |
| `parentbased_traceidratio` | Kept with probability `OTEL_TRACES_SAMPLER_ARG` | Follow the parent |
| `traceidratio` | Kept with probability `OTEL_TRACES_SAMPLER_ARG` | Decided again, ignoring the parent |
| `always_off` | Never kept | Never kept |

This only works if the context actually reaches the next service. You'll see in the exercise what happens when it doesn't.

## Configuring OpenTelemetry

Most SDK settings can be configured with [environment variables](https://opentelemetry.io/docs/languages/sdk-configuration/general/), which keeps configuration out of your code and works the same way across languages, mostly. Each SDK supports its own subset, so check before you rely on one:

| Variable | .NET SDK (1.21) | Python zero-code | Go SDK | Browser |
| --- | --- | --- | --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `_PROTOCOL` | Yes | Yes | Yes | No: set in code |
| `OTEL_SERVICE_NAME` | Yes | Yes | Yes | No: set in code |
| `OTEL_RESOURCE_ATTRIBUTES` | Yes | Yes | Yes | No |
| `OTEL_METRIC_EXPORT_INTERVAL` | Yes | Yes | Yes | No metrics |
| `OTEL_TRACES_SAMPLER`, `_ARG` | Yes | Yes | Yes | No: always on |

The .NET and Go columns were checked against the running Company app; don't assume a variable works in an SDK until you've seen its effect in your telemetry. The browser is configured in [`telemetry.ts`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/web/src/lib/telemetry.ts), because a browser has no environment variables. Its default sampler keeps every trace it starts, which matters below. For everything else Python supports, see the [Python zero-code configuration](https://opentelemetry.io/docs/zero-code/python/configuration/).

### Practice: sample employees-service and watch the decision travel

You'll set head sampling on employees-service only, put the app under load, and compare what the traces say with what the metrics say.

1. Create `compose.override.yaml` next to `compose.yaml`. Docker Compose merges this file in automatically, and keeping your experiment there means it survives every `docker compose up`:

    ```yaml
    services:
      employees-service:
        environment:
          OTEL_TRACES_SAMPLER: parentbased_traceidratio
          OTEL_TRACES_SAMPLER_ARG: "0.25"
    ```

    Don't commit `compose.override.yaml`; you'll delete it at the end of this exercise.

2. Apply it and start the load:

    ```bash
    docker compose up -d employees-service
    docker compose --profile load up -d --force-recreate load
    ```

3. Tempo's metrics generator counts every span it *receives* as `traces_spanmetrics_calls_total`. The services count every request they *handle* in their own HTTP metrics. After two or three minutes, run this ratio in Prometheus:

    ```promql
    sum(rate(traces_spanmetrics_calls_total{service="employees-service", span_name="GET api/employees"}[2m]))
      / sum(rate(http_server_request_duration_seconds_count{job="employees-service", http_route="api/employees", http_request_method="GET"}[2m]))
    ```

    - What value do you get, and why isn't it exactly 0.25?
    - Did the HTTP metric itself drop? Check its rate on its own.

4. Now the same comparison for notifications-service, which only does work when employees-service publishes:

    ```promql
    sum(rate(traces_spanmetrics_calls_total{service="notifications-service", span_kind="SPAN_KIND_CONSUMER"}[2m]))
      / sum(rate(company_notifications_received_total[2m]))
    ```

    notifications-service uses the default sampler, `parentbased_always_on`, so it should follow employees-service and keep about a quarter. It doesn't: the ratio is close to 1.

5. Find out why. In Tempo's **Service Graph**, look at the edges into notifications-service. Then run:

    ```traceql
    {resource.service.name="notifications-service" && kind=consumer}
    ```

    and look at the **Service** column of the results: which service is the root of most of these traces? RabbitMQ.Client only writes `traceparent` into a message when its publish span is being recorded. For the 75% of requests employees-service didn't sample, the message carries no trace context at all (you can confirm it with **Get messages** on a queue of your own in the RabbitMQ UI), so notifications-service sees no parent, starts a new root, and keeps it. Over HTTP, the "not sampled" flag travels. Over RabbitMQ here, nothing travels.
6. Answer:
    - How many of notifications-service's traces are now useful for debugging an employee creation, and what does the rest cost?
    - Two ways to fix it: give notifications-service a ratio sampler too, or make the publisher always send the context. What does each one change about which traces you keep?
7. Delete `compose.override.yaml`, then run `docker compose up -d employees-service` so employees-service keeps every trace again.

### Apply: resources and a sampling decision for assignments-service

1. **Resource attributes.** Add `OTEL_RESOURCE_ATTRIBUTES: service.version=0.5.0,deployment.environment.name=local` to assignments-service's block in `compose.yaml` (use your own version number). Rebuild, create an assignment, and find the attributes:
    - on a span, under **Resource attributes**;
    - on `company_assignments_created_total` in Prometheus, where the dots become underscores;
    - on a log line in Loki.

    Then write a PromQL query for 5xx responses from assignments-service *in this version only*.

2. **Who decides?** Put the sampler from the Practice step on assignments-service instead, in a new `compose.override.yaml`, and run `docker compose up -d assignments-service`. Then:
    - create five assignments in the UI, and find their traces with `{resource.service.name="web" && span.http.request.method="POST"}`. How many did you keep, and why?
    - send 40 requests with `curl` that call both dependencies (an unknown project ID is fine: assignments still asks employees-service and projects-service). How many assignments-service traces are kept? How many employees-service and projects-service server spans for those requests? Check with TraceQL.
    - Explain the two results using the sampler table in [The decision travels with the trace](#the-decision-travels-with-the-trace). Which service was the root each time?
3. Delete `compose.override.yaml` again. As a team, decide what sampling assignments-service should use in production, given what you saw. Record the decision and the reason as a row in the **Foundation decisions** table of your `AGENTS.md`.
