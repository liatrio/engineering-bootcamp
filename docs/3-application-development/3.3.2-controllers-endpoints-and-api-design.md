# Controllers, Endpoints, and API Design

An API is a promise to everyone who calls it. The web app, other services, and later a Terraform provider (Chapter 7.3) will all depend on the URLs, status codes, and JSON shapes your service returns. This page covers how to design those so callers can guess them, and how ASP.NET Core controllers implement them without mixing HTTP concerns into your business rules.

## Resources and URLs

REST APIs are organized around **resources**: the nouns of your domain. Each resource has a collection URL and an item URL, and the HTTP method says what to do with it.

| Request | Means |
| --- | --- |
| `GET /api/assignments` | List assignments |
| `GET /api/assignments?employeeId=...` | List assignments, filtered |
| `GET /api/assignments/{id}` | Get one |
| `POST /api/assignments` | Create one; the server picks the ID |
| `PUT /api/assignments/{id}` | Replace every writable field of one |
| `DELETE /api/assignments/{id}` | Delete one |

A few conventions keep APIs predictable:

- **Plural nouns, no verbs.** `POST /api/assignments`, not `POST /api/createAssignment`. The method is the verb.
- **Filters are query parameters on the collection.** `?projectId=` narrows a list. It never changes what a single item is.
- **IDs in the path identify one resource.** If a filter can match many, it's a query parameter; if it names exactly one, it's in the path.
- **The same shape everywhere.** `GET` by ID, the `POST` response, and the `PUT` response all return the same JSON for an assignment.

### Safe and idempotent methods

| Method | Safe (changes nothing) | Idempotent (repeating it has the same effect as doing it once) |
| --- | --- | --- |
| `GET` | Yes | Yes |
| `PUT` | No | Yes: replacing with the same body twice leaves the same result |
| `DELETE` | No | Yes: the second call finds nothing to delete (and returns 404), but the state is the same |
| `POST` | No | No: two calls create two resources |

Idempotency matters for retries. A client, a proxy, or the resilience handler you'll add in [3.3.5](3-application-development/3.3.5-calling-other-services.md) can safely retry a `GET` or a `PUT` after a timeout. Retrying a `POST` might create a duplicate, which is one reason assignments-service has a unique rule for employee and project pairs.

## Status Codes

Status codes are how a caller decides what to do next without parsing your error text. Every Company app service uses the same ones, from [`SPEC.md`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/SPEC.md#conventions-for-every-backend-service):

| Code | When | What the caller does |
| --- | --- | --- |
| 200 OK | A read or update succeeded | Uses the body |
| 201 Created | `POST` created a resource; `Location` says where | Uses the body, or follows `Location` |
| 204 No Content | `DELETE` succeeded | Nothing |
| 400 Bad Request | The request is invalid: a missing field, a value out of range, an ID that doesn't exist | Fixes the request; shows `errors` next to the fields |
| 401 Unauthorized | `AUTH_TOKEN` is set and the request has no valid token | Authenticates |
| 404 Not Found | The ID in the path doesn't exist | Stops; retrying won't help |
| 409 Conflict | The request is valid but clashes with current state, such as a duplicate | Tells the user; retrying the same request gives the same answer |
| 500 Internal Server Error | A bug | Reports it; the body never contains a stack trace |
| 503 Service Unavailable | A dependency is down | Retries later |

The line between 400 and 409 is worth getting right: 400 means "this request could never succeed as written", 409 means "it could, but not right now, given what already exists".

## Controllers in ASP.NET Core

A controller is a class whose public methods (actions) handle requests. Attributes do the routing and binding:

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeesController(IEmployeeService employees) : ControllerBase
{
    [HttpGet("{id:guid}")]
    public Task<EmployeeResponse> Get(Guid id, CancellationToken ct) => employees.GetAsync(id, ct);
}
```

- **`[Route]`** gives the controller's base path. Write it out instead of using `[controller]`, so renaming a class can't change your public URL.
- **`[HttpGet("{id:guid}")]`** adds a path segment with a route constraint. A request for `/api/employees/not-a-guid` doesn't match, so the caller gets a 404 without the action running.
- **Binding.** Simple parameters come from the route or the query string (`[FromQuery] string? department`). A complex parameter, like `EmployeeRequest`, comes from the JSON body.
- **`CancellationToken`** is cancelled when the client disconnects, so database queries and HTTP calls further down can stop early.
- **`[ApiController]`** turns on the behaviors a JSON API wants. The most important: it validates the bound body **before the action runs**, and returns a 400 Problem Details if anything fails.

### Keep controllers thin

A controller translates HTTP into a method call and back. That's all. employees-service's [`EmployeesController`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Features/Employees/EmployeesController.cs) has no `if` statements, no `try`/`catch`, and no database code:

- **Rules** live in the service. A duplicate email is `EmployeeService`'s decision.
- **Errors** are exceptions. The service throws `NotFoundException` or `ConflictException`, and [`GlobalExceptionHandler`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/starter/employees-service/src/EmployeesService/Infrastructure/Errors/GlobalExceptionHandler.cs), registered once in `Program.cs`, decides the status code. Nobody else maps exceptions to HTTP.
- **Success** is the return value. Returning an `EmployeeResponse` means 200 with that body; returning `NoContent()` means 204.

The payoff is that every error in the service has the same shape, and you can change a rule without touching HTTP code, or change HTTP code without touching a rule.

## Validation and DTOs

The JSON a client sends and the JSON you return are **DTOs** (data transfer objects): classes that exist only to describe the wire format. They're separate from the entity you store, for three reasons:

- **The request isn't the entity.** A client sends a name and an email; the server generates the ID and timestamps. If the request type were the entity, a client could set its own `createdAt`.
- **The wire format is a contract.** You can rename a column without breaking every client, because the response DTO stays the same.
- **Validation lives on the request.** Data annotations describe the shape a valid request must have:

```csharp
public sealed class AssignmentRequest
{
    [Required]
    public Guid? EmployeeId { get; init; }

    [Required, Range(1, 100)]
    public int? AllocationPercent { get; init; }
}
```

Notice the `?` on value types. A non-nullable `Guid` that's missing from the JSON silently becomes `Guid.Empty`, and a missing `int` becomes `0`, so `[Required]` would never fire. Making them nullable lets a missing field fail validation, and after validation the service can safely use `.Value`.

Data annotations check the **shape** of one request. Rules that need other data, such as "no other employee has this email" or "this project exists", belong in the service, because only the service can look.

employees-service registers `SystemTextJsonValidationMetadataProvider` in `Program.cs` so the keys of the `errors` map use the JSON names (`allocationPercent`), not the C# names (`AllocationPercent`). That's what lets the web app show each message next to the right field.

## Problem Details

Every error body is an RFC 9457 Problem Details document, as you saw in [3.2.4](3-application-development/3.2.4-service-communication.md#problem-details-the-error-contract). Three lines in `Program.cs` produce it for every error path:

```csharp
builder.Services.AddProblemDetails();                         // the format
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();  // exceptions → status codes
app.UseExceptionHandler();                                    // first in the pipeline
```

`app.UseStatusCodePages()` adds a Problem Details body to empty error responses too, such as a 404 for an unknown route or a 405 for a wrong method.

## 201 Created and Location

A successful `POST` returns 201 with the new resource in the body and a `Location` header pointing at it. `CreatedAtAction` builds both:

```csharp
var created = await employees.CreateAsync(request, ct);
return CreatedAtAction(nameof(Get), new { id = created.Id }, created);
```

It uses the `Get` action's route to build the URL, so the header can't drift from the real route.

## OpenAPI

ASP.NET Core generates an OpenAPI document from your controllers (`AddOpenApi()` and `MapOpenApi()`). It sees routes, parameters, and return types by itself. What it can't see is which **errors** an action returns, because those come from exceptions. `[ProducesResponseType]` attributes fill that in:

```csharp
[ProducesResponseType<EmployeeResponse>(StatusCodes.Status201Created, "application/json")]
[ProducesResponseType<HttpValidationProblemDetails>(StatusCodes.Status400BadRequest, "application/problem+json")]
[ProducesResponseType<ProblemDetails>(StatusCodes.Status409Conflict, "application/problem+json")]
```

Each service serves its document live at `/openapi/v1.json` (and `/openapi/v1.yaml`) and commits a saved copy as `openapi.yaml`, so API changes show up in pull request diffs.

    def list(self, status: str | None = None) -> Sequence[Project]:
