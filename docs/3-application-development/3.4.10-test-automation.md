# Automated Testing

All the tests, linters, and gates from the last pages buy nothing if they don't run. Running them by hand works until the day someone is in a hurry. **Continuous integration (CI)** runs them on every push and every pull request, on a clean machine, the same way every time.

Running CI on every change does two things:

- It keeps detectably broken code out of `main`, so `main` is always safe to branch from and to deploy.
- It reports a failure minutes after the change, while the author still remembers why they made it.

## GitHub Actions

[GitHub Actions](https://docs.github.com/actions) runs **workflows**: YAML files in `.github/workflows/`. The vocabulary:

- **Triggers** (`on:`) say when a workflow runs: `pull_request`, `push` to a branch, a schedule, or a manual run.
- A workflow has one or more **jobs**. Each job runs on a fresh virtual machine (a **runner**), in parallel with the others unless it `needs:` another job.
- A job is a list of **steps**. A step either runs a shell command (`run:`) or uses a published **action** (`uses:`), such as `actions/checkout` to clone the repository or `actions/setup-dotnet` to install the SDK.

Every job reports a **status check** on the pull request. A **branch rule** that marks a check as *required* turns it into a merge gate: the **Merge** button stays disabled until that check passes.

### CI for a repository with several services

The Company app keeps five services in one repository. Running every suite on every change wastes time: a pull request that only touches `web/` shouldn't wait for the Python and .NET suites. Two techniques keep it fast without losing safety:

- **Path filters.** A first job works out which folders changed, and each service's job runs only if its folder (or something it depends on) changed. A skipped job counts as passing for a required check, so branch rules still work.
- **An end-to-end job that always runs.** A change in one service can break a journey that crosses several. The E2E job starts the whole app with `docker compose` and runs the Playwright suite on every pull request, whatever changed.

### Keep workflows safe

A workflow runs code from the internet with access to your repository. Three habits limit the damage if something goes wrong:

- **Pin actions to a commit SHA**, with the version in a comment: `uses: actions/checkout@3d3c42e... # v7.0.1`. A tag such as `v7` can be moved to point at different code; a SHA can't.
- **Grant the least permissions:** `permissions: contents: read` at the top, and more only on the job that needs it.
- **Keep secrets in repository secrets**, never in the YAML, and read them only in the steps that need them.

> [!TIP]
> [act](https://github.com/nektos/act) runs a workflow on your machine in Docker, which can save a few push-and-wait cycles while you write one.

## Exercise

### Example: the bootcamp's own Company app workflow

The bootcamp repository tests the Company app with [`.github/workflows/company-app.yml`](https://github.com/liatrio/engineering-bootcamp/tree/master/.github/workflows/company-app.yml). Read it and answer:

1. What are its triggers, and what does its `paths:` filter do?
2. What does the `matrix` produce? How many jobs run for one pull request?
3. Each matrix job copies the starter and a milestone on top of it before testing. Why does the bootcamp check every milestone that way, rather than testing the starter alone?
4. Which steps install toolchains, and which run tests? Find the command for each service: are they the same ones each service's README tells you to run locally?

It's one job per milestone, testing every service in sequence. That suits a reference repository that changes rarely. Your team repository changes many times a day, so its CI is organized per service instead.

### Practice: watch a failing test block a merge

Start with a workflow that has one job, see it pass, then break a test and watch the branch rule stop the merge.

1. Branch: `git switch -c ci/first-workflow`.
2. Create `.github/workflows/ci.yml` with the name `CI`, these triggers, and read-only permissions:

    ```yaml
    on:
      pull_request:
      push:
        branches: [main]
    permissions:
      contents: read
    ```

3. Add one job, `projects`, copied from the `projects` job of M4's [`ci.yml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/.github/workflows/ci.yml), without its `needs:` and `if:` lines: check out, install uv, `uv sync --locked`, `uv run ruff check .`, `uv run pytest`.
4. Push and open a pull request. On its **Checks** tab, watch `projects` run and pass. The runner has Docker, so the Testcontainers tests run too.
5. Merge it, then make the check required. In the `main` ruleset you created in 3.2 (**Settings → Rules → Rulesets**), turn on **Require status checks to pass**, add `projects`, and save.
6. On a new branch, break a test on purpose. For example, change the expected names in `test_list_returns_projects_sorted_by_name` in `tests/unit/test_project_service.py`. Push and open a pull request.
7. Watch `projects` fail. Read the log until you find the failing assertion. On the pull request, the **Merge** button is disabled, with a message that a required check failed.
8. Push a fix to the same branch. The check reruns, passes, and the button unlocks. Close the pull request without merging.

### Apply: CI for the whole Company app

Grow the workflow into one job per service plus end to end. Split the jobs among the team, and have one person own the `changes` job and the ruleset.

1. **Concurrency.** Add a `concurrency:` block keyed on `github.ref` with `cancel-in-progress: true`, so a new push cancels the run it replaces.
2. **The `changes` job.** Use [`dorny/paths-filter`](https://github.com/dorny/paths-filter) to output `true` or `false` for `employees`, `assignments`, `projects`, `notifications`, and `web`. Each filter lists its service's folder and `.github/workflows/ci.yml`. Providers also rerun when a pact file they verify changes: employees on `assignments-service/pacts/**`; projects on `assignments-service/pacts/**` and `web/pacts/**`. This job needs `pull-requests: read`.
3. **One job per service.** Each has `needs: changes`, an `if:` on its output, a `timeout-minutes`, and `defaults.run.working-directory` set to its folder:
    - **employees:** set up .NET from `employees-service/global.json`, then `dotnet test`.
    - **assignments:** set up .NET, then `dotnet format --verify-no-changes`, `dotnet build`, and `dotnet test --no-build` with the coverage gate from 3.4.8. Upload `TestResults/` as an artifact with `if: always()`. Finish with `git diff --exit-code -- pacts/`: if the tests rewrote a pact file that wasn't committed, the contract changed and the providers haven't seen it.
    - **projects:** the job from the Practice.
    - **notifications:** set up Go from `go.mod`, fail if `gofmt -l .` lists anything, then `go vet ./...`, `go test -race ./...`, and the integration tests with `-tags integration`.
    - **web:** set up Node 24 with the npm cache, then `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`.
4. **The `e2e` job.** No `needs`, no `if`. Set up Node, run `docker compose up --build -d`, and wait until every service's `/readyz` and the web app answer. Then, in `web/`, install Playwright's Chromium with `npx playwright install --with-deps chromium` and run `npm run test:e2e`. On failure, upload `web/playwright-report/` and print `docker compose logs`. Always finish with `docker compose down -v`.
5. **Pin every action** to a commit SHA with a version comment. Copy the SHAs from M4's file, or look them up on each action's releases page.
6. **Open the pull request** and check the run: every job runs, because the workflow file itself changed. Then open a small pull request that touches only `web/` and confirm that only `changes`, `web`, and `e2e` do any work.
7. **Require the checks.** In the ruleset, require `employees`, `assignments`, `projects`, `notifications`, `web`, and `e2e`.
8. **Badge.** Add the workflow's status badge to the top of the repository's `README.md` (**Actions → CI → ⋯ → Create status badge**).

> [!TIP]
> Compare with M4's [`.github/workflows/ci.yml`](https://github.com/liatrio/engineering-bootcamp/tree/master/examples/company-app/milestones/M4-quality-automation/.github/workflows/ci.yml) once yours is green. Note how each job's comments say *why* a step is there.

## Deliverables

- The Practice pull request that was blocked, with a screenshot of the disabled **Merge** button, and the fix that unblocked it.
- A merged `.github/workflows/ci.yml` with the `changes` job, five service jobs, and the `e2e` job, all required by the `main` ruleset.
- A link to a run where path filtering skipped the jobs for unchanged services.
- Discuss with your team: the E2E job takes the longest and runs on every pull request. What would you lose by path-filtering it too? What would make you change your mind?
