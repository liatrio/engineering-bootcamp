# Test Doubles

When writing unit tests, it is important to isolate the code you are testing from any external dependencies that could result in false positives or negatives, so that the test only checks the logic of the code under test.

Imagine you are writing a function `isBirthdayThisWeek(userId)` that checks whether a user's birthday falls in the current week. It has to fetch the user's birth date from a database. Your test would depend on the database being up and running, and on the data in it matching the test's assumptions. On top of that, the function depends on today's date, which changes every day. So how could you ever write a reliable test for it? Enter **test doubles**.

## What a Test Double Is

A test double is an object that stands in for a real dependency during a test, the way a stunt double stands in for an actor. It lets you test your code without the systems it normally talks to, which can be slow, unreliable, or hard to set up, and it makes their answers predictable.

A double needs a **seam**: a place where the code receives its dependency instead of creating it. [Dependency injection](3-application-development/3.3.3-dependency-injection-and-solid.md) gives you those seams. A class that takes an `IEventPublisher` and a `TimeProvider` in its constructor can be handed doubles by a test. A class that calls `new RabbitMqEventPublisher()` and `DateTime.UtcNow` can't.

## Kinds of Test Doubles

People often call every double a "mock", but Gerard Meszaros's *xUnit Test Patterns* names five kinds, and Martin Fowler's [Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html) popularized the terms:

| Kind | What it does | Example |
| --- | --- | --- |
| **Dummy** | Is passed in but never used; it just fills a parameter | A `null` logger the code path never touches |
| **Stub** | Returns canned answers to the calls the test makes | A clients class whose `ExistsAsync` always returns `true` |
| **Spy** | A stub that also records how it was called, so the test can check afterwards | A publisher that keeps a list of every event it was asked to send |
| **Mock** | Is set up with expectations in advance, and fails the test if the calls don't match | A mocking-library object told "expect `PublishAsync("employee.created", ...)` exactly once" |
| **Fake** | A working, simplified implementation | An in-memory dictionary in place of a database table |

### State or interaction?

The difference that matters most is *what the test checks*:

- **State verification** checks the outcome: what the method returned, and what the fake store holds afterwards. Fakes and stubs support this style.
- **Interaction verification** checks which calls the code made, with which arguments. Mocks and spies support this style.

State-based tests survive refactoring better, because they don't care *how* the code reaches the result. Interaction checks are the right tool when the call *is* the behavior: "an event is published" is an outcome only a spy or a mock can observe.

The Company app's tests use hand-written fakes and spies rather than a mocking library such as Moq or NSubstitute. They take a few minutes to write, read like ordinary code, and are reused by every test that needs them. Mocking libraries are useful when an interface is large and a test needs only one call from it.

### Keep doubles honest

A double only behaves the way you wrote it. If the fake store accepts two employees with the same email but the real database rejects them, every test that uses the fake can pass while production fails. Two habits help:

- **Copy the real rules that matter** into the fake, such as unique keys, ordering, and copies in and out, and say so in a comment.
- **Test the real thing too.** [Integration tests](3-application-development/3.4.5-integration-testing.md) run against the real database, and [contract tests](3-application-development/3.4.6-contract-testing.md) check that another service still answers the way your fake of it does.

### Time is a dependency

`DateTime.UtcNow` returns a different value on every call, so a test can only assert that a timestamp is "somewhere around now". .NET's `TimeProvider` is the seam for the clock, and `FakeTimeProvider` from the `Microsoft.Extensions.TimeProvider.Testing` package is its fake: it starts at a time you choose, and only moves when the test calls `Advance`. Python code gets the same effect by taking a `clock` function, as projects-service does.

### Practice: give employees-service a fake clock

In 3.3.3 you gave `EmployeeService` an injected `TimeProvider`, and passed `TimeProvider.System` in the unit tests. SPEC's gap for 3.4.3 is what's left: those tests still can't control time. Work on a branch, `test/employees-fake-clock`, in `employees-service/`.

1. Read `Create_sets_created_and_updated_timestamps_to_now` and `Update_keeps_created_at_and_moves_updated_at_forward` in `EmployeeServiceTests.cs`. The first only checks the timestamp is between two readings of the real clock. The second only checks it moved forward. Neither knows the actual value.
2. Prove the weakness. In `src/EmployeesService/Features/Employees/EmployeeService.cs`, change `UpdateAsync` to set `employee.UpdatedAt = DateTime.UtcNow;`, which is exactly the slip the injected clock exists to prevent. Run the unit tests:

    ```bash
    dotnet test --filter-class "*EmployeeServiceTests"
    ```

    They all pass. Leave the bug in for now.

3. Add the package that contains `FakeTimeProvider`:

    ```bash
    dotnet add tests/EmployeesService.Tests package Microsoft.Extensions.TimeProvider.Testing --version 10.11.0
    ```

4. In `EmployeeServiceTests`, add `using Microsoft.Extensions.Time.Testing;`, then a fixed instant and a fake clock, and pass the clock to the service instead of `TimeProvider.System`:

    ```csharp
    private static readonly DateTimeOffset Now = new(2026, 3, 1, 9, 0, 0, TimeSpan.Zero);
    private readonly FakeTimeProvider _clock = new(Now);

    public EmployeeServiceTests() => _service = new EmployeeService(_store, _events, _clock);
    ```

5. Rewrite the create test to assert that `CreatedAt` and `UpdatedAt` both equal `Now.UtcDateTime` exactly.
6. Rewrite the update test: call `_clock.Advance(TimeSpan.FromMinutes(5))` before the update, then assert that `UpdatedAt` equals `Now.UtcDateTime.AddMinutes(5)`, and that `CreatedAt` didn't change.
7. Run the unit tests again. The update test now fails, and the message shows the real time where it expected 09:05 on 1 March 2026. Put `time.GetUtcNow().UtcDateTime` back, and run the fast suite:

    ```bash
    dotnet test --filter-not-trait "Category=Integration"
    ```

8. Update the class comment on `EmployeeServiceTests` to mention the fake clock, and open a pull request.

### Apply: fake the Employees and Projects clients

In 3.4.2 you stubbed both clients to say "yes, that exists" to everything. That was enough for the allocation rule, but it can't test the rules about the other services: an unknown employee is a 400, and a service that can't answer is a 503 with nothing saved. Replace the stubs with fakes.

1. **One fake for both clients.** Both interfaces have the same single method, so write an abstract `FakeDirectory` in `Fakes/FakeDirectoryClients.cs`, with two small subclasses: `FakeEmployeesClient : FakeDirectory, IEmployeesClient`, and the same for projects. The base class:
    - takes the service name and a set of known IDs (Ada and Grace for employees, the three seed projects for projects);
    - has an `Add(Guid id)` method for tests that need more IDs;
    - has an `IsDown` property. When it's `true`, `ExistsAsync` throws `DependencyUnavailableException`, just as the real client does when the service doesn't answer:

      ```csharp
      public Task<bool> ExistsAsync(Guid id, CancellationToken ct) =>
          IsDown
              ? throw new DependencyUnavailableException(service)
              : Task.FromResult(_known.Contains(id));
      ```

2. **A fake clock.** Add `Microsoft.Extensions.TimeProvider.Testing` to the test project, add a fixed `Now` to `TestData`, and give `ServiceTestContext` a `FakeTimeProvider Clock` in place of `TimeProvider.System`. Swap the stubs for the fakes there too, and delete the stubs.
3. **Run the rules tests.** They should all still pass, because the seed IDs they use are known to the fakes.
4. **Write `Features/Assignments/AssignmentServiceTests.cs`**, deriving from `ServiceTestContext`, with one test per behavior:
    - create saves the assignment, with `CreatedAt` and `UpdatedAt` equal to `TestData.Now`;
    - create publishes `assignment.created` with the assignment it returned;
    - an unknown employee throws `RequestValidationException` with exactly the key `employeeId`, and an unknown employee *and* project reports both keys;
    - when `Employees.IsDown` is `true`, create throws `DependencyUnavailableException`, the store is still empty, and nothing was published. Give `InMemoryAssignmentStore` a `Count` property so the test can check;
    - creating the same employee and project twice is a conflict;
    - update replaces the fields and moves `UpdatedAt` by exactly the time you `Advance` the clock;
    - update and delete of an unknown ID throw `NotFoundException`;
    - `RemoveForEmployeeAsync` deletes only that employee's assignments;
    - list filters by employee and by project.
5. For the outage test, break the code to see it fail: in `CreateAsync`, move the lines that build and save the assignment above `EnsureReferencesExistAsync`. The test fails on `Store.Count`, because the assignment was saved even though the check then failed. Put the lines back.
6. Run `dotnet test`, and open a pull request.
