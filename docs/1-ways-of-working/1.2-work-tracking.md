# Work Tracking

Every delivery team needs a shared place to record, prioritize, and report on its work. Teams use many different tools for this — Jira, GitHub Projects, Azure Boards, Linear, Trello, and others — but the practices behind them are the same. Learn the practices and you can pick up any tool quickly.

Tracking work in one visible place creates transparency into everything a delivery team does, resulting in:

- A single source of truth for all work done by a team
- No hidden or untracked work
- High alignment between team members on the work in progress
- Ownership of all the work by the team
- Leaders can see what is happening without interrupting team members

?> You will get hands-on with one of these tools, GitHub Projects, in [2.2.3 - Projects](2-version-control/2.2.3-projects.md).

## Core Concepts

Tools name things differently. Jira calls a unit of work an *issue*, Azure Boards calls it a *work item*, and GitHub calls it an *issue* that can be added to a *project*. This bootcamp uses the generic term **ticket**.

- **Backlog.** A prioritized list of tickets to be reviewed, refined, and readied before the team commits to them.
- **Board.** A single pane of glass for the work currently in progress, usually laid out as columns (see [Kanban](1-ways-of-working/1.1.2-kanban.md)).
- **Ticket history.** Each ticket collects comments, status changes, and links to related commits, pull requests, and builds, so anyone can see how the work progressed.

![An example board with two tickets, one planned, and one in progress](img/jira-board.webp ':size=2248x660 :class=img-shadow-center')

The board above (from Jira) shows a common set of stages a ticket moves through:

- To Do
- In Progress
- To Demo (Review)
- Done

Your team may use different column names, but the idea is the same: the board reflects reality. As you move a ticket from stage to stage, comment on what changed and notify teammates when it affects them. Keeping your tickets up to date is what makes the board trustworthy.

## Ticket Hierarchy

Most tools support many ticket types out of the box, and most can be customized. A lean DevOps team usually focuses on three levels:

| Ticket | Purpose | Duration |
| --- | --- | --- |
| **Epic** | Large body of work, feature-focused or higher, that spans multiple sprints | 1-4 iterations |
| **Story** | Small, valuable slice of work, driven by the Product Owner | ~1 day |
| **Subtask** | Small piece of work (often created in-sprint) that lives under a story | <1 day |

![A large initiative being broken down into epics, which are then broken down to stories, which are then broken down to subtasks](img/ticket-format.svg ':size=2495x1254 :class=img-center')

## Recommended Fields

Field names vary by tool, but these are worth filling in. ✓ means the field is recommended for that ticket type.

| Field | Epic | Story | Subtask | Purpose |
| --- | :-: | :-: | :-: | --- |
| **Title / Summary** | ✓ | ✓ | ✓ | Short, high-level description of the work |
| **Description** | ✓ | ✓ | ✓ | Detailed context, including acceptance criteria |
| **Assignee** | ✓ | ✓ | ✓ | Person initially accountable for completion |
| **Labels / Tags** | ✓ | ✓ | | Team, component, or other categorization |
| **Project / Area** | ✓ | | | Which project the work belongs to (one team can work on several) |
| **Estimate** | | ✓ | | Relative size, e.g. story points: 1, 2, 3, 5, 8, 13, 21 (see [Sizing](1-ways-of-working/1.1.6-sizing.md)) |
| **Iteration / Sprint** | | ✓ | ✓ | The sprint the work is planned for |
| **Blocked flag** | | ✓ | ✓ | Whether the work is currently blocked by something else |
| **Linked tickets** | | ✓ | ✓ | Work that must happen before, alongside, or after this ticket |
| **Release / Milestone** | ✓ | ✓ | ✓ | The version or release the work is planned for |
| **Attachments** | ✓ | ✓ | ✓ | Files, diagrams, or documents relevant to the work |

## Creating Effective Tickets

![grammar image](img/grammar.webp ':size=300x341')

### Styling

- Structure tickets to maximize readability
- Use syntax, grammar, capitalization, and punctuation to your advantage
- Make things as simple and direct as possible
- Use your tool's formatting features (headings, checklists, callouts) — for example, a callout for warnings such as version dependencies
- Mention teammates (`@name`) when you need their attention
- Use screenshots effectively, with meaningful captions — not "Screen Shot 2019-02-25 at 2.07.34 PM"

### Content

- Make sure that each ticket has [Acceptance Criteria](1-ways-of-working/1.1.4-stories.md)
- Make sure the work meets the team's [Definition of Done](1-ways-of-working/1.1.5-scoping-and-refinement.md#definition-of-done); record any story-specific "done" criteria as acceptance criteria
- Keep the description updated with any relevant links
- Write solutions so they are easily repeatable by anyone
- Reference tickets in commits and pull requests so the tool links them automatically. The format depends on the tool:
  - Jira-style keys: `THEIA-107 update /theia directory path for easier buildability`
  - GitHub issues: `Update /theia directory path (#107)`, or `Fixes #107` in a pull request to close the issue on merge
