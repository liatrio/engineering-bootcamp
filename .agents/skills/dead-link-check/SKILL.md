# Dead Link Check

## The core problem this skill solves

A naive link check treats "curl didn't return 200" as "dead link." That's wrong often enough to make the naive approach actively harmful: it "fixes" links that were never broken, and it can miss the actual signal (a systematic migration) hiding among the noise. The whole value of this skill is one judgment call, applied consistently:

**A non-200 result is a lead, not a verdict. Find out *why* before you act.**

## Procedure

1. **Run the script.** From the repo root: `node .agents/skills/dead-link-check/scripts/check-links.js docs`. For a long run you may need to resume, add `--results /tmp/links-<checkout-folder-name>.jsonl` with the repo folder's name written out literally (worktrees have their own, so parallel runs never share a file); never put a shell variable such as `$TMPDIR` in the path, because the expansion gets the command denied under restrictive permission modes. Run it as one plain command: no `;`, `&&`, pipes or `$(…)` around it, because compound lines are denied under restrictive permission modes. Read long output with the Read tool on a saved file or rerun with `--json`, not by piping to `head`. It needs `node_modules` (`npm install`); if it exits with "missing dependency", install and rerun. It extracts external URLs from the markdown AST (links, images, reference definitions, bare `http(s)://` URLs in prose, and `href`/`src` in raw HTML with HTML entities decoded, so URLs with parentheses survive; front-matter and `docs/README.md` are skipped), checks each with `curl` under a browser user agent, and prints a TSV (`url status redirects final_url class files:lines`) plus a grouped summary. Use `--json` for machine-readable output. Prefer the script over a hand-rolled grep, because grep truncates URLs that contain parentheses and picks up markup fragments. If the script is missing or exits non-zero, say so and fall back to `grep -rohE 'https?://[^)"'"'"'[:space:]>]+' docs --include='*.md' --exclude='README.md' | sort -u` plus `curl -s -o /dev/null -w "%{http_code} %{num_redirects} %{url_effective}\n" -A "<browser UA>" -L --max-time 10 "$URL"` per URL, and check any URL with parentheses by hand.
   - **Scope:** a single chapter when asked (`docs/N-*/`, or a file path). `examples/` only if asked (`--examples`). `localhost` and IP-literal URLs in loopback, private or link-local ranges are skipped because they only resolve while a demo is running (and to avoid probing internal hosts); pass `--include-local` to check them. Redirects are followed by the script, at most 10 hops, and a redirect from a public URL into one of those ranges is not requested and is reported as `blocked-redirect` (needs-browser-check). Internal links follow the cross-link rule in AGENTS.md (relative paths, not `#/` hashes).
   - **Resume:** the `--results` file records every URL checked; rerun the same command after an interruption and recorded URLs are skipped. Rows that ended in a timeout, connection error or possible TLS interception are re-checked on resume; definitive results (200, 404, DNS failure and so on) are skipped. Delete the file to recheck from scratch.
2. **Read the classes as leads.** The script pre-sorts into `likely-dead` (404/410, DNS failure, cert for a different host), `needs-browser-check` (403/503, timeouts, unverifiable-certificate errors (curl exit 35/60, possibly a TLS-intercepting proxy), too many redirects, other 4xx/5xx), `redirect` (grouped by old host to new host, with a `migration-pattern` flag when one old host redirects across 3+ files) and `ok`. These are pre-classifications only; the next step decides what each one actually means.
3. **Diagnose every non-200 before deciding it's dead:**
   - `403`/`503` from academic/API/publisher sites (ACM, DOI, university, OpenAI, Google AI docs, etc.) is usually an anti-bot challenge a real browser would pass — not proof of death. Cross-check with the harness's web-fetch or browser tool when available. Otherwise, inspect the response with `curl -v` and ask the user to verify the URL in a browser before concluding either way.
   - A block page from a network filter or TLS-intercepting proxy is the *network's* verdict, not the site's. Get the real answer with `curl -v` and read the actual TLS/HTTP handshake.
   - `404`, DNS failure (`Could not resolve host`), or a TLS cert issued for a *different* domain than requested — these are real. Confirm with `curl -v`, then treat as genuinely dead.
   - A `3xx` that redirects to a sane new URL isn't dead at all — but if the *same* redirect shows up across many files, that's a migration in progress. Flag it, then `grep -rn '<old-host>' docs examples` to count every remaining instance outside the files you were given, and offer to fix all of them now, before the old domain's redirect gets retired.
4. **Report before fixing.** Group findings: fine / likely-false-positive-not-fixed / genuinely-dead / migration-pattern. Never silently "fix" something that was only a bot-blocking false positive. This holds even when the request says "fix whatever is broken": that grants permission to fix, not knowledge of what the right replacement is. Present the groups and the proposed replacements first, and edit only after the user confirms. Skip the confirmation only when the user named the exact replacement.
5. **Replace carefully, if asked to fix.** Prefer the vendor's current page > a Wayback Machine snapshot > an independently-verified alternative mirror (e.g. confirm a DOI via the Crossref API, don't just pattern-match on title). Verify the replacement resolves before writing it.
6. **A verified replacement can still fail for this user specifically.** If the user reports a fix you already verified is blocked on their end (their IT blocks `web.archive.org`, a TLD, etc.), don't just re-confirm it works from your side — get a different replacement that isn't on the blocked host, and independently verify *that* one's identity too.
