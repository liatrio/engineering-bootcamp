# AGENTS.md

Canonical agent instructions for Liatrio's Engineering Bootcamp — a Docsify-based static documentation site teaching engineering fundamentals with a DevOps focus. Read this file first for anything not obvious from the code itself.

## Domain Glossary

| Term | What it means in this repo |
| --- | --- |
| Chapter | Top-level `docs/<chapter>/` directory, where `<chapter>` is `N-<topic>` (1–11). One per major topic (fundamentals, virtualization, CI/CD, etc.). |
| Section | Sub-page inside a chapter: `docs/<chapter>/<section>.md`, where `<section>` is `N.X-<topic>`. Numbering appears in the filename. |
| Exercise | Hands-on unit inside a section, described in that section's YAML front-matter. |
| Front-matter | YAML block at top of a section file listing `category`, `estReadingMinutes`, `exercises[]`, `technologies[]`. Drives learning-metric visualizations. |
| Master record | Consolidated front-matter data in `docs/README.md`. Auto-generated by the pre-commit hook — never hand-edit. |
| Sidebar | `docs/_sidebar.md`. Authoritative navigation, and the list of sections the front-matter hook reads. A section missing from it is invisible and left out of the stats. |
| Quiz | Interactive quizdown component. Source lives in `src/quizzes/chapter-N/N.X/`, embedded via a `<div class="quizdown">` wrapper. |

## Repository Layout

- `docs/` — All learner-facing content, organized by chapter. See `docs/_sidebar.md` for the authoritative section list.
- `docs/<chapter>/img/` — Images for that chapter's sections. The folder is unnumbered, so it moves with the chapter.
- `docs/README.md` — Auto-generated master record. Regenerate with `npm run refresh-front-matter`; do not hand-edit the front-matter block.
- `docs/_sidebar.md` — Navigation. Link every new section here; a sidebar entry pointing at a missing file makes the front-matter hook fail.
- `src/` — Docsify plugins, quiz sources, webpack entry points.
- `examples/` — Runnable code referenced from exercises (Go modules, docker-compose files, etc.).
- `img/` — Site-wide assets shared across chapters (goal icons, favicon). Section-specific images go in the chapter's `img/` folder.
- `.husky/pre-commit` — Regenerates the master record (`front-matter-condenser.js update`), then runs `npm run lint`, the same checks as CI.
- `.husky/front-matter-condenser.js` — Reconciles section front-matter into `docs/README.md`.
- `.husky/check-docsify-links.js` — Link and image checker behind `npm run lint:links`.
- `.github/workflows/` — CI: `markdown-linter.yml` (markdownlint, links, spelling) and `test-front-matter.yml` (`compare-front-matter`) on PRs; `static.yml` builds and deploys the site to GitHub Pages on push to `master`.
- `STYLE.md` — Contributor style guide (front-matter template, HTML-in-markdown rules, multi-column grids).

## Commands

Copy these verbatim; do not paraphrase.

- `npm install` — install dependencies (also sets up the Husky git hooks).
- `npm start` — build dev bundle + serve Docsify on `http://localhost:3000`.
- `npm run serve:docsify` — serve only, no rebuild.
- `npm run build:dev` / `npm run build:prod` — webpack builds.
- `npm run lint` — runs `lint:markdown`, `lint:links` and `lint:spelling`. CI runs the same three scripts.
- `npm run lint:markdown` — markdownlint-cli2 over all `.md` (see `package.json` for excluded directories).
- `npm run lint:links` — check that every internal link, `#anchor`, and image in `docs/` resolves the way Docsify serves it, and that every file in an `img/` folder is used. Delete an image when you remove its last reference.
- `npm run lint:spelling` — cspell over all `.md`. Add legitimate new words to `.cspell.json`.
- `npm run refresh-front-matter` — regenerate `docs/README.md` from current section front-matter.
- `npm run compare-front-matter` — read-only comparison; used by CI.

Docker:

- `docker build . -t engineering-bootcamp`
- `docker run -d -p 3000:3000 --name engineering-bootcamp engineering-bootcamp`
- `docker compose up -d` / `docker compose down` (v2 syntax — see decision table below).

There is no unit-test suite for the docs themselves. Go modules under `examples/` (e.g. `examples/terraform-provider/devops-api/`, `examples/data-patterns/`) do have `go test`; run it when touching those modules.

## Front-matter System

Every section that is linked from `docs/_sidebar.md` must carry a YAML front-matter block matching the template in `STYLE.md`. The pre-commit hook walks the sidebar, reads each section's front-matter, and rewrites `docs/README.md`. When the master record changes, the hook stops the commit on purpose: inspect the `docs/README.md` diff, stage it, and commit again.

When adding a new exercise, reuse existing values for `category` and `technologies` from `docs/README.md` — the visualizations aggregate by exact string match, so novel casing or near-synonyms fragment the data.

## Commit & Branch Conventions

- Conventional Commits, lowercase type. Examples from history: `docs: …`, `chore: …`, `chore(deps): …`, `fix: …`, `feat: …`.
- Reference GitHub issues in the subject where applicable: `docs: update docker-compose v1 syntax to docker compose v2 (#468)`.
- Branches follow `<type>/<slug>`: `docs/update-docker-compose-syntax`, `chore/agents-md-adoption`, `fix/broken-cross-links`.
- One PR per parent task / issue. Rebase on `master` before opening; never merge `master` into a feature branch.

## Content Guidelines

- One `#` page title per section file; `##` for sections and `###` for subsections.
- Images use Markdown with Docsify attributes and a page-relative path: `![alt](img/<descriptive_image_name>.svg ':size=600px :class=img-center')` for the chapter's own images, `../../img/<descriptive_image_name>.svg` for site-wide assets. Light/dark variants pair `:class=light-mode-*` and `:class=dark-mode-*`.
- Blank line required between adjacent HTML and Markdown blocks (Docsify parser requirement — see `STYLE.md`).
- Multi-column layouts use `<div class="grid2|grid3|grid4">` with `<div class="col">` children.
- Quiz embed: place source at `src/quizzes/chapter-N/N.X/<slug>.js`, then embed with:

  ```html
  <div class="quizdown">
    <div id="chapter-N/N.X/<slug>.js"></div>
  </div>
  ```

  The `id` is the path relative to `src/quizzes/`. Do not inline `<script>` tags or `import` statements. Quiz images resolve from the site root, not the page, so write the full path to the chapter folder: `![](docs/<chapter>/img/<descriptive_image_name>.png)`.

## Decision Tables

When multiple valid patterns exist, pick per this table.

| Situation | Use | Do not use | Why |
| --- | --- | --- | --- |
| New Docker Compose invocation in prose or code block | `docker compose <verb>` (v2, space) | `docker-compose <verb>` (v1, hyphen) | v1 unsupported since 2023. Filenames (`docker-compose.yaml`) stay hyphenated. |
| Adding a category or technology to front-matter | Reuse an existing string from `docs/README.md` | Introduce a new synonym / different casing | Visualizations aggregate by exact match; fragmentation kills the charts. |
| Referencing an image | The chapter's `img/` folder, page-relative (`img/<descriptive_image_name>.png`); root `img/` only for images several chapters use (`../../img/<descriptive_image_name>.png`) | Root path (`/img/<descriptive_image_name>.png`), another chapter's folder (`../<chapter>/img/`), or a numbered folder (`img4/`) | Docsify resolves image paths from the page's folder, so `/img/<descriptive_image_name>.png` becomes `/docs/<chapter>/img/<descriptive_image_name>.png` and 404s. An unnumbered folder moves with its chapter, so renumbering needs no image edits. |
| Citing a report, PDF, or other document | Link to the publisher's public URL | Committing the file and linking it (`[report](img/report.pdf)`) | Docsify routes any link to a local file as a page, so it 404s. Local files are only embedded as images. `npm run lint:links` rejects these links. |
| Cross-linking a section | Path from the `docs/` root (`<chapter>/<section>.md`, `<chapter>/<section>.md#<heading>`), even within the same chapter | Page-relative path (`<section>.md`, `../<chapter>/<section>.md`) or Docsify hash (`#/<chapter>/<section>`) | Docsify resolves links from `basePath` (`/docs/`), not the current page, so page-relative links 404 on the site while looking fine on disk. |
| Linking to `examples/` or other repo files outside `docs/` | Full GitHub URL (`https://github.com/liatrio/engineering-bootcamp/tree/master/examples/...`) | Root path (`/examples/...`) | Docsify only serves `docs/`, so repo paths 404 on the site. |
| Adding a tip, note, or warning callout | GitHub-style alert: `> [!TIP]` (or `NOTE`, `IMPORTANT`, `WARNING`, `CAUTION`) on its own line, text on following `> ` lines. Types are defined in `STYLE.md`. | Docsify v4 shorthand `?>` / `!>` | Docsify v5 deprecated the shorthand and plans to remove it; alerts also render on GitHub. `npm run lint:markdown` rejects the shorthand (`.markdownlint/no-legacy-callouts.cjs`). |
| Documenting a new tool or command in an exercise | Add to that section's `technologies:` list | Freeform prose only | Feeds the tech word-cloud. |
| Referencing another repo doc from an agent | Plain path with "read when needed" | `@path` auto-import | Auto-imports expand at every session start; only this file uses the stub pattern. |

## Do / Don't

- Do run `npm run lint` before pushing. It runs the same markdownlint, link, and spelling checks as CI.
- Do add every new section to `docs/_sidebar.md` in the same commit that creates the file, so it shows up in navigation and the stats.
- Do let the pre-commit hook regenerate `docs/README.md`. Don't hand-edit the master-record front-matter block.
- Do reuse existing category/technology strings. Don't invent variants ("Kubernetes" vs "K8s" fragments the data).
- Do preview changes with `npm start` and click through affected pages. Don't assume markdown-only edits render correctly — Docsify has parser quirks around HTML.
- Do put screenshots and diagrams in the chapter's `img/` folder, next to the pages that use them.
- Do keep code fences small (≤10 lines) — link to files under `examples/` for anything longer.
- Do write commit subjects that name the artifact and the reason. Don't ship subjects like "update" or "fixes".

## Destructive-Action Guardrails

- Never push directly to `master`. All changes land via PR from a feature branch.
- Never rewrite history on `master` (`push --force`, `reset --hard`, filter-branch). Feature-branch force-push is fine before review.
- Never bypass the Husky pre-commit hook (`git commit --no-verify`) to work around front-matter validation. Fix the front-matter or run `npm run refresh-front-matter` and commit the regenerated master record.
- Never hand-edit `docs/README.md`'s front-matter block; it is machine-generated.
- Never delete a chapter or renumber sidebar entries without also fixing every cross-link; `npm run lint:links` lists the ones that broke.
- Before deleting `examples/` code, confirm it is not referenced from any `docs/**/*.md` file.

## Keeping This File Current

Update this file whenever a command name, directory structure, or convention changes — an out-of-date AGENTS.md is worse than a short one. Aim for ~150 lines; the hard ceiling is 300. If a section grows past ~30 lines, consider moving detail to a dedicated doc under `docs/` and leaving a "read when …" pointer here.
