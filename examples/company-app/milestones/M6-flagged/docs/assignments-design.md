# Assignments service design

**Status:** agreed in 3.2; rules 1–3 built in 3.3, rules 4–5 test-first in 3.4. **Owner:** the team.

An assignment says that an employee works on a project, in a role, for a share
of their time, from a start date to an optional end date. It is the only part
of the Company app that relates the other two, so it is the only service that
has to talk to both.

## Context

```text
             web (via frontend-proxy)
                       │ HTTP
                       ▼
             assignments-service ──── PostgreSQL: assignments database
              │       │       ▲
   GET /api/  │       │ GET   │ employee.deleted
   employees/ │       │ /api/ │
   {id}       ▼       ▼ projects/{id}
   employees-service  projects-service
                       │
              assignment.created ──► RabbitMQ company.events ──► notifications-service
```

- **Owns:** the `assignments` database. Nothing else reads it.
- **Calls:** employees-service and projects-service, only to check that an ID
  exists. It does not copy their data.
- **Publishes:** `assignment.created`.
- **Consumes:** `employee.deleted`.

`Infrastructure/Clients/` with typed `HttpClient`s for the two services.

## Data

| Field | Type | Rules |
| --- | --- | --- |
| `id` | uuid | Generated by the service (v4) |
| `employeeId` | uuid | Required; must exist in employees-service |
| `projectId` | uuid | Required; must exist in projects-service |
| `role` | string | Required, 1–100 characters |
| `allocationPercent` | integer | Required, 1–100 |
| `startDate` | date (`YYYY-MM-DD`) | Required |
| `endDate` | date or null | Optional; null means open-ended |
| `createdAt`, `updatedAt` | UTC datetime | Set by the service |

Table `Assignments`: primary key `Id`; **unique index (`EmployeeId`,
`ProjectId`)** so the database refuses a duplicate even if two requests race;
index on `ProjectId` for the `?projectId=` filter (the unique index already
serves `?employeeId=`).

## Endpoints

| Method and path | Success | Errors |
| --- | --- | --- |
| `GET /api/assignments?employeeId=&projectId=` | 200, list (both filters optional) | |
| `GET /api/assignments/{id}` | 200 | 404 |
| `POST /api/assignments` | 201 + `Location` | 400 (invalid body, unknown employee or project), 409 (duplicate), 503 (a dependency is down) |
| `PUT /api/assignments/{id}` | 200, replaces every writable field | 400, 404, 409, 503 |
| `DELETE /api/assignments/{id}` | 204 | 404 |
| `GET /healthz`, `GET /readyz` | 200 | `/readyz` 503 when PostgreSQL or RabbitMQ is down |

All errors are Problem Details. The detailed sketch is
`assignments-service/openapi.yaml`.

## Rules

1. **Both IDs must exist.** `GET /api/employees/{id}` and
   `GET /api/projects/{id}`: 200 means it exists, 404 means 400 for our caller
   with `errors.employeeId` / `errors.projectId`.
2. **No duplicates.** The same employee on the same project again is 409.
3. **Fail honestly.** Anything else from a dependency (timeout, connection
   refused, 5xx after retries) is 503. We never save an assignment we could not
   check.

Added test-first in 3.4 (not in the first version):

4. An employee's total `allocationPercent` across assignments whose date
   ranges overlap must stay at or below 100, otherwise 409.
5. `endDate`, when set, must be after `startDate`, otherwise 400 with
   `errors.endDate`.

## Calling other services

- Typed clients (`IEmployeesClient`, `IProjectsClient`) registered with
  `AddHttpClient`, base URLs from `EMPLOYEES_URL` and `PROJECTS_URL`.
- `Microsoft.Extensions.Http.Resilience`'s standard handler: short timeouts,
  a few retries with backoff for transient failures, and a circuit breaker so
  a dead dependency fails fast instead of piling up requests.
- When `AUTH_TOKEN` is set, the clients send it too, since every service
  shares it.
- `/readyz` does **not** check employees or projects. If it did, one service
  being down would mark every caller unready and the outage would spread.
  Reads (`GET /api/assignments`) keep working while a dependency is down.

## Events

Envelope as in the spec: `eventId`, `type`, `occurredAt`, `source`
(`assignments-service`), `data`. Persistent JSON on the `company.events` topic
exchange, routing key = type.

| Direction | Type | `data` | What we do |
| --- | --- | --- | --- |
| Publish | `assignment.created` | the full assignment | After the insert commits |
| Consume | `employee.deleted` | `{ "id": "uuid" }` | Delete every assignment for that employee. Durable queue `assignments.employee-deleted`, bound with key `employee.deleted`. Ack after the delete; deleting nothing is fine (idempotent). |

Publishing after commit means a crash between the two loses the event. We
accept that for now; the transactional outbox is the fix (3.3.6).

## Feature flags (3.6)

| Flag | Kind | Code default | Effect |
| --- | --- | --- | --- |
| `assignment-notifications` | Release | off | Gates publishing `assignment.created` |
| `assignments-writes` | Kill switch | on | Off makes POST, PUT, DELETE return 503 |
| `allocation-check` | Percentage rollout | off | Rule 4, for a share of callers; targeting key `X-User-Id`, else the employee ID |

## Configuration

`PORT`, `ConnectionStrings__Default`, `RABBITMQ_URL`, `EMPLOYEES_URL`,
`PROJECTS_URL`, `AUTH_TOKEN`, and later `FLAGD_HOST` / `FLAGD_PORT` and the
`OTEL_*` variables. No seed data: assignments start empty.

## Open questions

- Should deleting a project remove its assignments? projects-service publishes
  no events yet, so not now.
- Should `PUT` allow moving an assignment to another employee or project? Yes:
  it replaces every field, so both IDs are checked again.
